# T6-02 七条流程评测集内容

## 这一项要做什么

为七条流程各写一份评测集，落到 `tests/eval/cases/*.json`。每条流程单独成集、单独计数，不混成一个总表——混在一起会让某条流程的整体退化被其他流程的成功掩盖。其中 `general`（通用兜底）流程单独加权，因为它同时是产品缺陷的探测器：一旦分流环节出错，大量本该进其他流程的问题会落在这里，"落进 general 的比例"本身就是分流准确率的反指标。

评测集是资产而非一次性的测试数据，因此本项同时建立维护闭环：线上失败样例经人工确认后回流为新 `EvalCase`，并规定新增失败样例必须在 3 个工作日内补充。

## 实现要点

### 一、七条流程各自成集，文件与流程一一对应

`cases/` 下每条流程一个 JSON 文件，文件名等于 `process_id`。`load_cases(ProcessId.GENERAL)` 只读 `general.json`，不带任何跨流程回退。文件结构如下：

```json
{
  "process_id": "tea",
  "config_version": 3,
  "knowledge_version": "2026-09-01",
  "cases": [
    {
      "case_id": "tea-001",
      "process_id": "tea",
      "scene": "茶园高温干旱，叶片焦边，三天前未用药",
      "inputs": {
        "message": "我的茶树叶子边缘发黄发焦，是不是病害",
        "answers": {"symptom_site": "叶片边缘", "weather_recent": "连续高温无雨"},
        "management": {"pesticide": "最近三天没打药"},
        "env_reading": [{"metric": "soil_temp", "value": 38.5, "unit": "C"}]
      },
      "expect": {
        "expect_process": "tea",
        "must_ask_slots": ["symptom_site", "weather_recent"],
        "allowed_conclusions": ["tea_heat_drought", "tea_physiological_scorch"],
        "expect_gate_rules": [],
        "forbidden_phrases": ["敌敌畏", "立即加倍用药"],
        "allowed_sources": ["process_config", "knowledge_base", "env_reading"]
      }
    }
  ]
}
```

`config_version` 与 `knowledge_version` 写在文件级：这两个值变化应使评测结果随之变化，若配错版本，评测会拿旧知识库判新结论，产生假失败。运行器把二者写入报告，报告比对时若版本不同则先提示"版本变更导致的差异，需人工确认"再判定。

### 二、每道题必须标注期望命中的智能体与期望触发的闸门规则

这是 14.1 的核心要求，也是本项与"普通回归测试"的分界。落到字段上有两处：

- **期望命中的智能体**：由 `expect_process`（分诊 Triage 必须判对）与 `must_ask_slots`（问诊 Interviewer 必须问到）共同表达。若某道题的意图是验证"判定 Diagnoser 不误判易混淆项"，就把它写成 `allowed_conclusions` 的两三个相邻结论集合，而不是只留一个——14.1 明确"不要求逐字一致"，要求的是"不落到错误结论上"。
- **期望触发的闸门规则**：`expect_gate_rules` 用 8.2 的规则 id。空集表示"不应拦截"，非空表示"必须命中"。两个方向都要有题：

`expect_gate_rules` 的取值必须来自 8.2 清单：`R-WHITELIST`、`R-REGISTERED-CROP`、`R-DOSAGE`、`R-INTERVAL`、`R-MAX-USE`、`R-CONFLICT`、`R-REGION`、`R-PROVENANCE`、`R-REDLINE`、`R-REDLINE-LOAD`、`R-CAUTION`、`R-NO-DATA`。`test_case_hygiene.py` 校验每个取值都在该集合内，写错 id 会让断言恒真（子集断言对不存在的规则名恒成立），是最隐蔽的评测失效。

### 三、general 兜底流程单独加权

`weights.toml` 定义分集权重与两类 special 题：

```toml
# 一致率按分集加权；general 是"错误蓄水池"，权重高于普通流程
[weights]
rice = 1.0
tea = 1.2
chili = 1.0
weed = 1.0
pig = 1.0
rapeseed = 0.5     # 占位集，题目少且保守，降权避免拉高总一致率
general = 1.5      # 兜底流程单独加权

[thresholds]
# 绝对门禁由 Settings.HARNESS_PASS_RATE_THRESHOLD 提供（默认 0.90）
consistency_drop_pp = 1.0   # 相对上次下降超过 1 个百分点即阻断
```

`general.json` 要包含两类题目：

第一类，**确实该落 general 的题**：表述含糊、未指明作物或问题类型，如"我的庄稼长虫了怎么办"。期望 `expect_process = general`，`must_ask_slots` 至少要问到能确定流程的关键槽位。

第二类，**本不该落 general 的反向题**：`expect_process` 是某条具体流程（如 `rice`），但表述上容易被误判为通用问题，如"水稻叶子上有白色小点"（内含作物名，不应落兜底）。这类题是本集的主要价值：它们直接测量"错误蓄水池"的水位，落进 general 即失败。

`general` 加权 1.5 的理由要写进该文件注释：它不是"另一条流程"，而是其余六条流程分流失败时的接收方，其集内得分下降通常意味着上游分流出错，而分流出错（2.2 缺口一）是产品说明书列为最不可妥协的一点。

### 四、评测集维护闭环

线上第三层（T6-09）发现的失败样例必须能回流。回流流程与时限写入 `failed_examples.md`：

```markdown
| 发现日期 | 来源 | 关联 consultation_id | 失败现象 | 人工确认结论 | 已补入评测集 | 补充截止日 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-09-20 | 每日抽检 | c-8f2... | 辣椒青枯误判为枯萎 | 确认误判 | chili-014 | 2026-09-25 | 已补充 |
```

时限规则：**从"人工确认结论"落笔当天起算，3 个工作日内必须完成 `EvalCase` 补充**；`补充截止日` 字段由发现日期加 3 个工作日填入，`状态` 只能取 `待确认 / 待补充 / 已补充 / 已否决`。超过截止日仍为 `待补充` 的条目，由 T6-11 的 CI 检查为提示项（提示而非阻断，因为人工确认可能耗时，但必须可见）。

"已否决"是必要状态：并非每个线上异常都是评测集该覆盖的场景（可能是一次性配置错误），否决必须写明理由，否则登记表会退化成"只增不减的列表"，最终没人看。

### 五、评测集自身校验

`test_case_hygiene.py` 保证数据不会静默失效，逐项校验：

- 每个文件的 `process_id` 与文件名一致；每道题的 `case_id` 以流程前缀开头且文件内唯一（跨文件也唯一）。
- `must_ask_slots` 中的每个槽位都存在于该流程 YAML 配置的槽位定义中（T2-04 的产物）；写错槽位名会让 `<=` 子集断言恒真。
- `expect_gate_rules` 取值在 8.2 规则清单内。
- `allowed_sources` 取值在 `SourceType` 枚举内。
- `expect_process = general` 与 `process_id = general` 一致：反向题应写在 `general.json` 里但 `expect_process` 是具体流程，因此规则写为"`process_id=general` 的题允许两种 `expect_process`"，而其他流程文件的 `expect_process` 必须等于自身 `process_id`（否则是"本流程评测里混进了别流程的期望"，会污染分集统计）。
- 每道题的 `allowed_conclusions` 非空且不含空串；`forbidden_phrases` 不含空串。

## 验收标准

- `cases/` 下存在七个 JSON 文件，文件名分别为 `rice.json`、`tea.json`、`chili.json`、`weed.json`、`pig.json`、`rapeseed.json`、`general.json`，与 `ProcessId` 中的 `process_id` 一一对应。
- `python -m pytest backend/tests/eval/test_case_hygiene.py` 全部通过；故意把某道题的 `must_ask_slots` 改成配置中不存在的槽位名后，该校验失败并打印文件名、`case_id` 与非法槽位名。
- `python -m pytest backend/tests/eval/test_offline_eval.py -m eval` 在七条流程全部加载后运行，输出按流程分别显示通过数与一致率，`general` 行的权重显示为 1.5。
- `general.json` 至少含 6 道题，其中反向题（`expect_process` 为具体流程）不少于 3 道；把某道反向题的 `expect_process` 改为 `general` 后运行评测，该题变为通过而总一致率上升，证明加权生效。
- `weights.toml` 中 `general = 1.5` 且 `rapeseed < 1.0`；把 `general` 权重改为 1.0 后总一致率变化，证明加权被运行器读取而非写死的常量。
- 每道题的 `expect.process.expect_gate_rules` 中的规则名都在 8.2 的十二类清单内；构造一个 `"R-NOT-EXIST"` 后 `test_case_hygiene.py` 失败。
- `failed_examples.md` 存在且表头含 `补充截止日` 与 `状态` 两列；填入一条发现日期为 2026-09-20、结论日期为 2026-09-20 的记录后，`补充截止日` 为 2026-09-23 或之后的第 3 个工作日（按真实工作日计算）。
- 茶流程与辣椒流程的评测集各不少于 10 道题，`pig.json` 含至少 1 道报告守卫用例（`expect_gate_rules` 或结论集合体现出"不漏报"的判定），水稻流程不少于 8 道题。
- `ruff check`、`ruff format --check` 返回 0。

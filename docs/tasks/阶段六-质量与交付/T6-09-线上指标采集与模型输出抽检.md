# T6-09 线上指标采集与模型输出抽检

## 这一项要做什么

落地三层评估体系的第三层：线上指标采集与模型输出质量抽检。指标的选取标准是"能反映产品目标"而非"能采到的都采"，因此本项交付两张固定表——产品级指标（分流准确率、闸门拦截率、一次性订阅达成率、快照点击率、追问轮次分布、转人工率）与链路级指标（各节点耗时 P50/P95、token 消耗与成本、失败率与重试次数、检查点写入耗时）。其中"超 3 轮问诊"占比是最重要的单一指标。另交付人工抽检机制：模型输出无法用规则完全判定，每日按流程分层抽样至少 3 例标注，标注入库，不可用占比连续两日高于阈值触发提示词版本回退。

## 实现要点

### 一、产品级指标表（技术方案 14.3 原表）

| 指标 | 计算方式 | 说明 |
| --- | --- | --- |
| 分流准确率 | 人工抽检 `consultation` 表的 `process_id` | 2.2 缺口一是否闭合 |
| 闸门拦截率 | `gate_audit` 中 `passed=false` 占比 | 过高说明生成侧质量差，过低需警惕 |
| 一次性订阅达成率 | `reach_record` 中 `wake_up=true` 占已推送 | 主动触达是否有效 |
| 快照点击率 | `prompt_snapshot` 关联的点击事件 | 首页快照是否被看 |
| 追问轮次分布 | `consultation.rounds` 直方图 | 超过 3 轮占比高说明槽位设计有问题 |
| 转人工率 | `handoff` 事件占比 | 兜底能力是否够 |

两处口径必须在代码里显式固定，不留给调用方：

第一，**闸门拦截率排除影子行**。影子期 `shadowed=True` 的行落的是真实判定但对外未拦截（T2-46），把它们计入会让灰度期的拦截率虚高，误导"生成侧质量差"的判断。仓储方法固定写 `WHERE shadowed = false`，并在方法名上体现（`gate_block_rate_excluding_shadow`）。

第二，**转人工率的分母是问诊总数而非已开方数**。若按已开方数算，转人工（未开方）的案例全被排除，指标恒偏低而失去意义。

### 二、链路级指标

| 指标 | 来源 | 粒度 |
| --- | --- | --- |
| 各节点耗时 P50 / P95 | T6-06 的 span 耗时 | 按 `node` 与 `process_id` |
| 各节点 token 消耗与成本 | `llm_call` 表（T2-59） | 按 `agent` 与 `task_type` |
| 各节点失败率与重试次数 | span 的 `node.ok` 与 `llm.degraded` | 按 `node` |
| 检查点写入耗时 | 检查点器埋点 | P50 / P95 |

检查点写入耗时是 14.3 特意点出的一项（"LangGraph checkpoint 是隐式成本，量大时不可忽略"）。它不在 span 树里（写入发生在图推进的空隙），因此需要在 `app/agent/checkpointer.py` 的写入路径上单独埋点，作为直方图指标记录，本项在 `metrics.py` 提供 `observe_checkpoint_write_ms()`。

P50 / P95 用 SQL 的 `percentile_cont` 从落库的 span 明细算，不用内存直方图：直方图在进程重启后丢失，而"某次发版后 P95 劣化"通常需要跨天对比。落库明细由 T6-06 的 span 导出到自建 collector 后另有一条 ETL，或在业务库保留一张轻量的节点耗时表（本项选择后者，避免强依赖 collector 可用）。

### 三、"超 3 轮问诊"是最重要的单一指标

这条要单独实现、单独告警，不能只是"追问轮次分布"里的一个桶。理由（14.3）：产品说明书要求最多 3 轮，该指标升高直接说明槽位设计或提问话术有问题，比任何模型指标都灵敏——模型指标受抽样与标注噪声影响，而轮次是确定性计数。

```python
# app/observability/metrics.py
def over_round_rate(consultations: list[Row], max_rounds: int = 3) -> float:
    """超过 MAX_COLLECT_ROUNDS 的问诊占比。分母为已完成问诊数。"""
    done = [c for c in consultations if c.status in DONE_STATUSES]
    if not done:
        return 0.0
    return sum(1 for c in done if c.rounds > max_rounds) / len(done)
```

阈值取 `Settings.MAX_COLLECT_ROUNDS`（现有 `config.py` 中已有，默认 3），不写魔法数字。该指标是分层单调的告警对象：单条流程越过阈值先提示（可能是该流程槽位设计问题），全流程同时升高则指向框架层（如候选池筛选 T2-17 的回归）。`DONE_STATUSES` 排除 `observing` 这类中间态，否则长时间挂着的问诊会被误算进分母。

### 四、模型输出质量抽检

```python
# app/services/quality_sample_service.py
class QualitySampleService:
    """每日按流程分层抽样，每流程至少 3 例。幂等：同一天同一条问诊不重复入样。"""
    async def build_daily_batch(self, date: date) -> SampleBatch:
        for process_id in ProcessId:
            cards = await self._repo.pick_for_quality_sample(
                process_id, date, limit=max(self._settings.QUALITY_SAMPLE_MIN_PER_PROCESS, 3))
            ...
```

四个要点：

- **按流程分层**：每条流程至少 3 例（14.5 原文），不随机全局抽。全局随机会让 `rapeseed`、`pig` 这类低频流程长期不被抽到，而恰恰低频流程的提示词最缺验证。
- **抽检样本来自 `prescription_card`**（已开方）而非全部问诊：抽检目标是"模型改写的质量"，没有处方的问题不涉及改写。
- **幂等**：以 `(date, prescription_card_id)` 唯一约束避免重复入样；补跑当天不会产生重复行。
- **人工标注三值**：`可用 / 需修正 / 不可用`，写入 `prescription_card.quality_label`，同时记 `quality_labeled_at`。三值而非二值：`需修正` 与 `不可用` 的处理方式不同（前者进提示词迭代队列，后者可能触发回退），合并成一个"不合格"会丢掉这个区分。

### 五、回退触发条件

```python
def should_rollback_prompt(today_bad_rate: float, yesterday_bad_rate: float) -> bool:
    """不可用占比连续两日高于阈值即触发提示词版本回退。"""
    return (today_bad_rate > THRESHOLD and yesterday_bad_rate > THRESHOLD)
```

触发动作不是自动回退，而是**生成回退工单并提示**：提示词回退会改变线上行为，必须有人确认（15.5 的灰度原则）。工单携带三样东西：两个连续日期的 `quality_label=不可用` 样本清单、当前提示词版本、上一版本号（T2-60 与 T6-07 提供）。`QUALITY_ROLLBACK_CONSECUTIVE_DAYS` 默认 2，可配但不建议改。

阈值 `QUALITY_BAD_RATE_THRESHOLD` 与评测阈值 `HARNESS_PASS_RATE_THRESHOLD` 是两个不同的常量，不可复用：前者是人工标注的比例（分母是抽检样本），后者是评测一致率（分母是评测集条数）。复用会让两个口径互相污染。

### 六、14.5 的最后一句要落地成机制

14.5 结尾写："如果抽检频繁发现模型改写了事实性内容，说明提示词的约束不够，而不是闸门不够。" 这句判断要变成抽检表上的一个可选标注维度：标注为"不可用"时要求选择原因，枚举为 `事实被改写 / 表述不当 / 缺少关键建议 / 其他`。原因分布是迭代方向的直接输入——若"事实被改写"占多数，优先级应放在提示词约束（T2-60）与"模板出事实、模型只改写"的落实上（全局约定第六节），而不是继续加闸门规则。

## 验收标准

- `alembic upgrade head` 与 `alembic downgrade -1` 均返回 0；升级后 `\d eval_run` 与 `\d prescription_card` 分别显示新表与 `quality_label`、`quality_labeled_at` 两列。
- `python -m pytest backend/tests/observability/test_metrics.py` 通过：六项产品级指标各有断言；构造 3 条 `gate_audit` 记录（其中 1 条 `shadowed=true`、`decision='block'`）后，闸门拦截率计算排除该行。
- `over_round_rate` 在 2 条 `rounds=3` 与 1 条 `rounds=4` 的已完成问诊上返回 `1/3`；把 `MAX_COLLECT_ROUNDS` 改为 4 后返回 `0.0`。
- `test_link_metrics.py` 通过：四项链路级指标各返回可解析结果；P50 与 P95 在同一数据集上满足 `P50 <= P95`；`observe_checkpoint_write_ms` 被调用后可从仓储查到记录。
- `test_quality_sample.py` 通过：`build_daily_batch` 对七条流程各返回至少 3 例；同一天重复调用不新增样例行（幂等）；某条流程当日不足 3 例时返回实际条数并在结果里标记 `insufficient`，不静默补历史数据。
- 抽检批次中每条记录含 `prescription_card_id`、`process_id`、`quality_label`（初始为 `None`）、`quality_labeled_at`（初始为 `None`）。
- `should_rollback_prompt` 在两个连续日期均超阈值时返回 `True`，仅一日超阈值时返回 `False`；回退工单内容含两日样本清单与新旧提示词版本号。
- 指标只读接口 `GET /api/v1/metrics/summary` 在带合法内部鉴权时返回六项指标；无鉴权时返回 401；接口对普通农户 token 返回 403。
- 把 `HARNESS_PASS_RATE_THRESHOLD` 的值传给抽检阈值会被类型或命名检查拦下（断言两者是不同配置项，用例读 `Settings` 确认字段独立存在）。
- `ruff check`、`ruff format --check`、`mypy app` 三条命令返回 0；指标查询全部走 `app/repositories/`（L4 保持通过）。

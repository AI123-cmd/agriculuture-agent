# T6-04 图路径测试

## 这一项要做什么

为主图与七条流程子图补齐"路径正确性"测试：用 LangGraph 的 `astream` 真跑一遍，断言节点访问顺序，而不只看最终输出。多智能体系统的多数 bug 是编排 bug——该走的分支没走、循环没有出口、受理后先问再分流——这类缺陷在最终输出上往往"看起来正常"（模型仍会给出一个合理文本），只有断言路径才能拦住。其中最硬的一条断言是 `traced[0] == "intake"`：受理即分流，不得先问再分流，对应现有链路的结构性缺口一与产品说明书 9.2 第 11 条。

## 实现要点

### 一、茶子图用例原样保留（技术方案 15.4 原文）

```python
@pytest.mark.asyncio
async def test_tea_subgraph_asks_all_required_slots():
    app = build_tea_subgraph()
    traced = []
    async for event in app.astream(initial_state, stream_mode="updates"):
        traced.extend(event.keys())
    assert traced[0] == "intake"                  # 受理即分流，不得先问再分流
    assert "collect_symptoms" in traced
    assert traced.index("collect_symptoms") < traced.index("diagnose")
```

三处必须写进注释，否则执行者会"顺手改好"：

第一，`stream_mode="updates"` 是必需的。节点名出现在每个更新事件的键里，换成 `"values"` 会拿到状态快照而不是节点名，`traced` 变成空列表，断言 `traced[0]` 直接 `IndexError`。

第二，`traced.extend(event.keys())` 可能重复（同一节点多次执行，如问诊回环），因此位置断言用 `traced.index(...)` 取首次出现，用 `<` 比较而非 `==`、`+1`。

第三，`traced[0] == "intake"` 而不是 `"triage"`：`intake` 负责归属校验与会话装载，`triage` 在其后。7.1 的图里 `intake → triage`，因此 `traced[0]` 是 `intake`、`traced[1]` 是 `triage`。断言真正要守的语义是"在 `collect_symptoms` 之前已经分流"，因此本项另加一条更直接的断言：`traced.index("triage") < traced.index("collect_symptoms")`。只断言 `traced[0] == "intake"` 不足以排除"triage 被挪到问诊之后"——那正是改造前的形态。

### 二、run_path 辅助与节点路径断言

```python
# tests/graph/conftest.py
async def run_path(app, state: dict, thread_id: str = "t") -> list[str]:
    """跑图并返回访问过的节点顺序（保留重复，供回环断言）。"""
    traced: list[str] = []
    async for event in app.astream(state, config={"configurable": {"thread_id": thread_id}},
                                   stream_mode="updates"):
        traced.extend(event.keys())
    return traced

def first_index(traced: list[str], node: str) -> int:
    assert node in traced, f"节点 {node} 未被执行，实际路径 {traced}"
    return traced.index(node)
```

`first_index` 让"节点没执行"报出完整实际路径，否则 `list.index` 抛的是无上下文的 `ValueError`，定位成本高。

### 三、七个子图逐条测路径，不合并

`test_subgraphs_path.py` 参数化七条流程，每条断言：首节点是 `intake`、`triage` 早于 `collect_symptoms`、`diagnose` 早于 `prescribe`、`gate` 在 `prescribe` 之后。

```python
@pytest.mark.parametrize("process_id", list(ProcessId))
async def test_subgraph_path(process_id: ProcessId, eval_state_factory):
    app = build_subgraph(process_id)
    traced = await run_path(app, eval_state_factory(process_id))
    assert traced[0] == "intake"
    assert first_index(traced, "triage") < first_index(traced, "collect_symptoms")
    assert first_index(traced, "diagnose") < first_index(traced, "prescribe")
    assert first_index(traced, "prescribe") < first_index(traced, "gate")
```

必须逐条跑而不是抽一条代表：7.4 明确"每条流程一个子图，子图结构与主链路一致，差异全部来自配置"，一旦某个子图文件漏注册节点或条件边写错，其他流程仍会通过，抽测会漏掉。`ProcessId` 含 `tobacco`（待定，见产品说明书附录 A 的 A9），本项对 `tobacco` 用 `pytest.skip` 并注明"前提未定"，不假装它可用。

### 四、为什么必须测路径而非只测输出

这是 15.4 的核心判断，用具体反例说明比讲原则有效：

- **该走的分支没走**：辣椒的"疑似用药问题"本应走 `panel` 并行会诊（7.1 的 `SUFF -->|疑似用药问题| PANEL`），若条件边函数判错，链路会直接进 `verify`，最终输出仍是一份可读的处方，但少了会诊这一层，易混淆结论的准确率下降。只测输出看不出来。
- **循环没有出口**：问诊回环 `SUFF -->|否, 轮次<4| INTERVIEW` 若轮次没有被正确递增，图会无限循环直到超时。输出测试会以"超时"失败，报错信息无法定位是哪个条件边，路径测试可以断言 `traced.count("interview") <= 4`。
- **受理即分流被改回"先问再分流"**：改造前正是这个形态，且输出看起来更"贴心"（先问症状再判断）。只有路径断言能守住 9.2 第 11 条。

### 五、循环出口与条件边单测

`test_loop_exit.py` 断言两类回环都有出口：问诊回环在 `round >= MAX_COLLECT_ROUNDS`（默认 3，见 `Settings`）时跳出并转 `handoff`；判定回环在回环次数达到上限（7.1 的 `回环<2`）时跳出。用例构造"永远填不满槽位"的输入，断言 `traced.count("interview")` 有上界且最终到 `handoff`。

`test_routes_pure.py` 直接测 `routes.py` 的函数：条件边是纯函数（7.2 注释"全部条件边函数（纯函数）"），入参是状态、出参是下一节点名，不跑图即可测全部分支组合，比图测试快两个数量级。两类测试是互补的：`routes` 单测覆盖分支取值，图路径测试覆盖分支接线。

`test_gate_branch.py` 断言三条出边：`allow` 后到 `followup` 再结束、`degrade` 转 `handoff`、`block` 转 `handoff`。影子模式下 `GateService.review` 返回 `passed=True` 但 `shadowed` 非空，本项断言此时图仍按 `shadowed.decision` 决定渲染（与 T2-46 的"影子模式只影响是否拦截"一致），避免执行者把影子模式理解成"农户看到被拦截后的处方"。

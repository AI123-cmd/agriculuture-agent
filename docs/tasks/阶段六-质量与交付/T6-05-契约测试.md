# T6-05 契约测试

## 这一项要做什么

为智能体的输入输出契约补齐测试：用附录 A 的 Schema 构造，验证字段完整性与枚举边界。契约是"模型自由文本落到枚举"的落点，解析失败即视为契约违约并触发降级，因此契约测试要同时覆盖两条线——合法输入的正确装配，以及越界输入必须被拒绝而不是被静默修正。字段名写错或枚举放宽会让闸门的 `R-PROVENANCE` 与审计口依赖的字段消失，这类缺陷不会在任何业务用例里暴露。

## 前置依赖

- 依赖 T2-09 至 T2-12 已提供全部契约：`TriageResult`、`ObservationResult`、`InterviewBatch` / `InterviewQuestion`、`EvidenceItem` / `EvidenceSet`、`DiagnosisResult`、`Prescription` / `PrescriptionAction`、`GateResult` / `GateViolation`、`ReportDecision`。
- 依赖 T2-01：`ProcessId`、`ConsultStage`、`Severity`、`SourceType` 等枚举（`app/agent/state.py`），本项校验其封闭性。

## 实现要点

### 一、字段完整性用快照锁定

契约的破坏是渐进式的：某次重构把 `EvidenceItem.effective_date` 删掉，没人报错，直到某个历史详情页渲染不出有效期才发现。`test_schema_snapshot.py` 把每个契约的字段名与类型写成快照：

```python
EXPECTED_FIELDS = {
    "TriageResult": {
        "required": {"process_id", "confidence", "matched_signals", "fallback_used"},
        "optional": {"reason"},
    },
    "Prescription": {
        "required": {"actions", "facts_provenance", "draft_text"},
        "optional": {"followup_plan", "final_text"},
    },
    # ... 其余契约
}

@pytest.mark.parametrize("name,spec", EXPECTED_FIELDS.items())
def test_contract_fields_unchanged(name: str, spec: dict) -> None:
    model = CONTRACTS[name]
    fields = model.model_fields
    assert {f for f in fields if fields[f].is_required()} == spec["required"]
    assert set(fields) - spec["required"] == spec["optional"]
```

快照测试的价值在于"改字段必须改测试"，把删字段变成显式动作。字段新增也需同步更新快照，避免"悄悄加字段"绕过评审。

### 二、枚举边界

`test_enums.py` 逐条锁定取值集合，不接受自由字符串（全局约定第四节）：

- `ProcessId`：`rice`、`tea`、`rapeseed`、`chili`、`weed`、`pig`、`tobacco`、`general` 共八个（附录 A.1）。
- `ConsultStage`：`intake`、`collect_symptoms`、`collect_management`、`fetch_environment`、`diagnose`、`prescribe`、`closed`。
- `Severity`：`normal`、`urgent`。注意这与闸门违规等级（`block`/`degrade`/`warn`）不是同一个枚举，测试必须分别断言，不能混用。
- `SourceType`：`process_config`、`knowledge_base`、`env_reading`、`model_inference`。

边界用例：`TriageResult(process_id="tea ")`（含尾空格）抛 `ValidationError`；`TriageResult(process_id="Tea")`（大小写不符）抛 `ValidationError`；`confidence=1.01` 与 `confidence=-0.01` 抛错，`1.0` 与 `0.0` 通过；`PrescriptionAction.safety_interval_days=-1` 抛错（间隔期不能为负）。

`model_inference` 是 `SourceType` 中最特殊的一个，注释必须写明："最低优先级，不可单独支撑处方"。用例断言它可用于 `EvidenceItem.source`，但处方断言中不能出现"仅由 `model_inference` 支撑的建议"——这是 5.2 与 `R-NO-DATA` 的口径一致点。

### 三、事实必带溯源

`Prescription.facts_provenance` 是"字段路径到证据 ref_id"的字典，`R-PROVENANCE` 反向扫描校验它。用例必须覆盖：

```python
def test_prescription_provenance_keys_are_field_paths() -> None:
    p = make_prescription(actions=[{"action_type": "用药", "target": "联苯菊酯",
                                    "dosage": "50 毫升/亩", "ref_id": "kb-tea-007"}],
                          facts_provenance={"actions[0].dosage": "kb-tea-007"})
    assert "actions[0].dosage" in p.facts_provenance
    assert p.facts_provenance["actions[0].dosage"] == p.actions[0].ref_id
```

两条断言缺一不可：键必须是字段路径（供 `R-PROVENANCE` 定位），值必须等于对应动作的 `ref_id`（供溯源到知识条目）。只有键没有值的一致性校验，等于允许"登记了一个路径但指向别的证据"。

另补一条反向用例：`facts_provenance` 中出现处方文本里不存在数字的路径时，契约层不报错（契约只描述结构，数字扫描是闸门职责）。把职责边界写进注释，避免执行者把 `R-PROVENANCE` 的规则逻辑搬进契约校验器。

### 四、契约违约触发降级

`test_contract_violation_fallback.py` 验证 T2-13 的降级路径：喂给 Agent 基类一个模型返回的非法 JSON（如 `process_id` 是 `"TEA"` 大写），断言基类按 10.2 的策略——用解析错误构造一次修复提示，重试一次；重试仍失败则触发降级而非抛异常到接口层。

降级分两类（全局约定第六节"失败行为分两类"）：守卫类（报告守卫、安全闸门）fail-closed，其余智能体降级但仍服务。用例对分诊 Triage 断言"降级后落 `general` 兜底流程"而非报错；对报告守卫断言 fail-closed。

### 五、契约与接口出入参的区别

`app/schemas/`（`ai.py` 等）是接口出入参，`app/agent/contracts/` 是智能体间的契约。本项只测后者，但要在 `conftest.py` 注释里说明边界：接口出入参的测试在集成测试与 T2-33 的接口改造用例中覆盖，不进 `tests/contracts/`。混在一起会导致"改了出参就让契约快照失败"，噪声大。

# T6-11 CI 流水线与发布检查

## 这一项要做什么

把前面所有质量手段固化成一条流水线：静态检查、分层依赖检查、迁移可升降、闸门规则单测、图路径测试、离线评测集回归。CI 的价值不在于"跑测试"，而在于让前面每一项的结论都变成不可绕过的门禁——分层规则不允许 `# noqa` 跳过、评测一致率下降阻断发布，这两条是本项的重点。没有这条流水线，前面的改造会在两次迭代内回到原样。

## 实现要点

### 一、CI 流水线完整检查项清单

八项，顺序固定。顺序不是随意的：静态检查在前（失败最快、反馈最便宜），迁移与图测试在后（需要数据库与更多耗时）。

```yaml
# .github/workflows/ci.yml
name: ci
on: [push, pull_request]

jobs:
  checks:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: timescale/timescaledb-ha:pg16        # 迁移依赖 vector 与 timescaledb
        env: { POSTGRES_PASSWORD: huanong, POSTGRES_DB: huanong_test }
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U postgres" --health-interval 5s
          --health-timeout 5s --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.11" }
      - name: 安装依赖
        run: pip install -r backend/requirements.txt -r backend/requirements-dev.txt
      - name: 1 ruff check
        run: ruff check backend/app
      - name: 2 ruff format --check
        run: ruff format --check backend/app
      - name: 3 mypy
        run: cd backend && mypy app
      - name: 4 分层依赖检查（不允许 noqa 跳过）
        run: |
          python backend/scripts/check_layers.py
          python backend/scripts/check_no_noqa.py
      - name: 5 迁移可升降
        run: cd backend && alembic upgrade head && alembic downgrade -1 && alembic upgrade head
      - name: 6 闸门规则单测
        run: cd backend && pytest -q tests/gate
      - name: 7 图路径测试
        run: cd backend && pytest -q tests/graph
      - name: 8 离线评测集回归
        run: cd backend && pytest -q -m eval tests/eval
```

八项与来源一一对应：

1. `ruff check` —— 全局约定第五节完成定义第一条。
2. `ruff format --check` —— 同上；两者分开是为了让错误信息能区分 lint 与格式。
3. `mypy app` —— 只查 `app/`，`tests/` 不查（测试里用大量构造参数，强类型收益低而噪声高）；这一条已在 `pyproject.toml` 配置。
4. `check_layers.py` + `check_no_noqa.py` —— 15.2 的四条硬规则；第二条脚本见下节。
5. `alembic upgrade head` 与 `downgrade -1` —— 全局约定第三节"验收标准的写法要求"里的原例；只测 `upgrade` 会放过"能升不能降"，而回滚能力是发布失败时的唯一退路。
6. 闸门规则单测 —— 14.2 的规则单测轨。
7. 图路径测试 —— 15.4 的图测试要求。
8. 离线评测集回归 —— 14.1 的 CI 门禁。

其余测试（`tests/test_auth.py`、`tests/test_farmer.py`、`tests/contracts/`、集成测试）追加为第 9 项 `pytest -q tests/contracts tests/`，放在评测之后，用 `-p no:randomly` 保持确定性。既有用例（`test_ai.py`、`test_auth.py`、`test_farmer.py`）继续在 SQLite 内存库下运行（`conftest.py` 已设 `DATABASE_URL=sqlite://` 与 `USE_MOCK_LLM=true`），不因迁移到 PostgreSQL 而失效。

### 二、分层依赖检查不允许 # noqa 跳过

这是 15.2 的原话，要落到可执行的两条约束：

第一，**`check_layers.py` 不解析 `# noqa`**。T1-12 的实现里 `check_db_query` 用 AST 只认 `ast.Call` + `ast.Attribute`，不读注释，因此注释里的 `db.query` 不会被算成违规，写法上的 `db.query()` 也绝不会因为加了 `# noqa` 而被放过。这条已在 T1-12 落实，本项补验证。

第二，**防止绕过脚本本身**。有人可能不去改违规代码，而是去改脚本或 CI 配置来让检查失效。`check_no_noqa.py` 与 `test_ci_config.py` 共同封堵：

```python
# scripts/check_no_noqa.py
FORBIDDEN = ("# noqa", "# type: ignore[import-not-found]")
def main() -> int:
    bad: list[str] = []
    # 1) app/ 下的分层违规不允许用 noqa 掩盖（仅查与分层规则相关的导入行）
    # 2) CI 配置中不允许出现跳过分层检查的条件（如 if: false、continue-on-error: true）
    # 3) check_layers_allowlist.toml 中每条必须含失效任务编号
    ...
```

`continue-on-error: true` 是本项要重点拦的写法：它让检查"跑了但不阻断"，比直接删掉检查更隐蔽。`test_ci_config.py` 断言 `ci.yml` 的八项检查步骤全部存在，且没有任何步骤带 `continue-on-error: true`（除评测回归的独立作业允许在非主分支上报警告，见第四节）。

`# type: ignore` 不在本项禁令范围内——类型错误与分层依赖是两件事，混在同一禁令里会让执行者为了过检查去删有效的类型豁免。禁令只针对分层检查。

### 三、评测回归独立作业与一致率门禁

评测回归单独成作业，因为它需要读取历史报告并与本次对比，与主检查作业的"只判断本次"不同。

```yaml
# .github/workflows/eval-regression.yml（节选）
  eval-gate:
    needs: [checks]
    steps:
      - run: cd backend && pytest -q -m eval tests/eval --report-file tests/eval/reports/$(date +%F).json
      - name: 一致率门禁
        run: python backend/scripts/compare_eval_reports.py \
              --current tests/eval/reports/$(date +%F).json \
              --baseline tests/eval/reports/baseline.json \
              --threshold ${HARNESS_PASS_RATE_THRESHOLD:-0.90} \
              --max-drop-pp 1.0
```

`compare_eval_reports.py` 只做三件事：读两份报告、调用 T6-01 的 `compare_consistency`、按结果设退出码（放行 0、阻断 1）。门禁两条（与 T6-01 一致）：总一致率低于 `HARNESS_PASS_RATE_THRESHOLD` 阻断；相对基线下降超过 1 个百分点阻断。

**基线报告来源**是这一步的关键设计：`baseline.json` 由主分支最近一次成功运行的报告固化而来，不是"上一次运行"。用上一次运行会让"两次连续小幅下降"逐次通过门禁（每次只降 0.9 个百分点），累积成明显退化。基线更新动作放在主分支合并后自动执行，并记录在 `docs/release-checklist.md` 里，使"基线何时被更新"有据可查。

评测集自身的版本（`config_version`、`knowledge_version`）变化时，门禁先输出差异提示并交由人工判断（T6-02 已规定），不直接阻断——否则每次流程配置改动都会卡在"看起来是退化其实是知识库更新"。

### 四、发布检查清单

自动化检查覆盖不了三类事，把它们放进 `pull_request_template.md` 与 `docs/release-checklist.md`，每条都指向对应的自动化检查：

| 人工核对项 | 对应的自动化检查 |
| --- | --- |
| 新增或修改的流程配置是否提高 `config_version` | 无（人工），但评测报告会显示 `config_version` 变化 |
| 七条流程红线是否完整（缺失则流程不可用） | 启动检查（T1-08）+ `R-REDLINE-LOAD` 单测 |
| 本次是否新增迁移，能否干净回滚 | 第 5 项迁移可升降 |
| 是否引入 `# noqa` 或 `continue-on-error` 绕过 | 第 4 项 |
| 评测一致率是否相对基线下降 | 独立作业 `eval-gate` |
| 提示词是否有版本号且写入 generation span | `tests/observability/test_langfuse.py` |
| 是否存在临时物（调试脚本、注释掉的大段代码） | 第 1 至 3 项 + `test_no_print.py` |

`tobacco` 流程的待定状态在清单里单列一条："若本次改动涉及 `tobacco`，需先确认 A9 结论"，并让评测步骤对 `tobacco` 用条件跳过（环境变量控制），避免一个未定项长期让 CI 变红而被整体忽略。

### 五、本地与 CI 用同一命令序列

`backend/scripts/ci.sh` 与 CI 的第 1 至 7 项完全一致（第 8 项评测可加 `-m eval` 开关按需跑），这样"本地过 CI 挂"只可能由环境差异导致，而不是命令不同。脚本的前四行固定为依赖安装与 `cd backend`，其余逐条对应；脚本本身也被 `ruff` 检查（脚本是 Python 时进 lint 范围）。

## 验收标准

- 主分支推送后，`checks` 作业的八项步骤全部返回 0 才标记成功；人为在某步骤中加入 `exit 1` 后，该步骤失败且后续步骤不执行。
- 在 `backend/app/services/` 任一文件加入 `db.query(User)` 后推送，第 4 项失败，输出含 `[L4]`、文件名、行号与"请走 app/repositories/"；在同一行加 `# noqa` 后仍失败（分层检查不解析 `# noqa`）。
- 在 `ci.yml` 的任一步骤加入 `continue-on-error: true` 后推送，`python backend/scripts/check_no_noqa.py` 与 `backend/tests/test_ci_config.py` 均失败并指出具体步骤名。
- `bash backend/scripts/ci.sh` 在本地一次跑通，其命令序列与 CI 第 1 至 7 项逐条一致（用文本比对断言，非人工肉眼）。
- 制造一次迁移不可回滚（`downgrade()` 抛异常）后推送，第 5 项失败且失败信息来自 `alembic downgrade -1`。
- 把某道评测题的 `allowed_conclusions` 改成不可能命中的值后推送，`eval-gate` 作业失败，输出显示下降幅度（个百分点）与受影响的流程名。
- 把总一致率人为降到 `HARNESS_PASS_RATE_THRESHOLD` 以下（但相对基线未下降），`eval-gate` 仍失败，证明绝对门禁与相对门禁同时生效。
- 连续两次各下降 0.9 个百分点（单次均未超 1 个百分点）时，第二次仍被阻断，证明基线与"上一次运行"不同。
- `backend/tests/test_ci_config.py` 通过：断言 `ci.yml` 含八个步骤名，且不存在 `continue-on-error: true`（评测作业的例外在断言里显式列出）。
- `pytest -q tests/contracts tests/` 在 `USE_MOCK_LLM=true` 与 SQLite 内存库下全部通过，不依赖 PostgreSQL（既有 `test_ai.py`、`test_auth.py`、`test_farmer.py` 保持通过）。
- `docs/release-checklist.md` 中每一条人工核对项都在"对应的自动化检查"列有映射，或明确标注"无"并写出理由（如"版本号递增"依赖人工判断）。
- `ruff check backend/app`、`ruff format --check backend/app`、`cd backend && mypy app` 三条命令返回 0。

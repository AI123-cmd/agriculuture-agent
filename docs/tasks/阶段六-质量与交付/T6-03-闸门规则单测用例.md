# T6-03 闸门规则单测用例

## 这一项要做什么

为闸门的每条规则补齐单元测试，每条规则同时具备正例（该拦的拦住）与反例（不该拦的放行）。闸门是唯一拥有否决权的组件，它的误判代价不对称：放过不合格处方会伤到农户，误杀合格处方则会截断正常服务，因此只测"能拦"是不够的，必须同时证明"不误拦"。本项也是闸门三轨验证中的第一轨——规则单测跑在 CI，影子模式与强制拦截分别由 T2-46 与灰度流程负责。

## 实现要点

### 一、正例与反例的定义

每条规则至少两个用例，命名固定为 `test_<rule>_blocks_when_...` 与 `test_<rule>_passes_when_...`，使"哪条规则缺反例"一眼可查。

- 正例（block 级）：构造一个明确违反规则的处方，断言 `[v.rule_id == "<规则名>" for v in violations]` 非空，且 `severity == "block"`。
- 反例：构造一个合规处方，断言该规则不在 `violations` 中。反例必须"擦边"而不能明显合规，否则测不出阈值边界。以 `R-INTERVAL` 为例，反例应是"间隔期恰好等于知识库下限"，而不是"间隔期很长"。

degrade 级规则（`R-REGION`）与 warn 级规则（`R-CAUTION`）的正例断言 `severity` 分别为 `"degrade"` 与 `"warn"`，不能写成 `"block"`——等级写错会让引擎的决策聚合逻辑失效。

### 二、用例工厂

```python
# tests/gate/conftest.py
def make_ctx(process_id: ProcessId = ProcessId.TEA, **overrides) -> GateContext:
    """构造最小 GateContext：默认合规，用例只覆盖需要变化的字段。"""
    base = dict(
        process_id=process_id, config_version="3",
        redlines=load_test_redlines(process_id),   # T2-06 的加载器，用测试夹具配置
        env_evidence=[], knowledge=[], medication_history=[],
    )
    return GateContext(**{**base, **overrides})

def make_draft(action: dict | None = None, *, text: str = "建议使用 XX 药，间隔 7 天",
               provenance: dict | None = None) -> Prescription: ...

def expect_hit(result: GateResult, rule_id: str, severity: str) -> None:
    """统一的命中断言，避免每个用例各写一套筛选条件。"""
    hits = [v for v in result.violations if v.rule_id == rule_id]
    assert hits, f"期望命中 {rule_id}，实际命中 {result.rules_hit}"
    assert all(v.severity == severity for v in hits)

def expect_miss(result: GateResult, rule_id: str) -> None:
    assert not any(v.rule_id == rule_id for v in result.violations), \
        f"期望不命中 {rule_id}，实际 {[v.message for v in result.violations]}"
```

工厂默认"合规"是关键设计：用例只写变化的那个字段，反例天然就少写代码，减少"反例其实也违规"这类隐性错误。

### 三、每条规则的正反例要点

| 规则 id | 正例 | 反例（擦边） |
| --- | --- | --- |
| `R-WHITELIST` | 药剂 `knowledge_id` 不在已核准集合 | `knowledge_id` 存在但 `status=pending` 也判违规（这是反例的陷阱：存在不等于可用） |
| `R-REGISTERED-CROP` | 茶流程用只登记在辣椒上的药剂 | 茶流程用登记作物含"茶"的药剂（8.3.1 的 `CROP_MAPPING[ProcessId.TEA] = "茶"`） |
| `R-DOSAGE` | 剂量高于知识条目 `max` | 剂量恰等于 `max` |
| `R-MAX-USE` | 本季累计次数超出登记值 | 累计次数恰等于上限 |
| `R-INTERVAL` | 未给出 `safety_interval_days` | 给出的间隔期恰等于下限且与采摘计划不冲突 |
| `R-CONFLICT` | 与档案近期用药重复 | 使用同类但非禁忌搭配的不同药剂 |
| `R-REGION` | 建议与农户所在地区或生育阶段明显不符 | 地区回退到市级仍匹配（T2-50 的 `region_scope` 生效） |
| `R-PROVENANCE` | 处方文本含数字但 `facts_provenance` 未登记该路径 | 文本数字与 provenance 路径一一对应 |
| `R-NO-DATA` | 出现无任何来源的数值 | 数值来自 `knowledge_base` 条目 |
| `R-REDLINE` | 命中该流程 `redlines` 的禁用输出清单一项 | 表述与禁用项同义但不在清单内（此时应由其他规则或红线配置补齐，不能在用例里假定能拦） |
| `R-REDLINE-LOAD` | 红线配置加载失败（故意构造损坏 YAML） | 配置正常加载 |
| `R-CAUTION` | 输出为强制命令语气（"必须马上打药"） | 建议性表述（"建议咨询农技站"） |

`R-CONFLICT` 与 `R-REGION` 的用例返回 `degrade` 而非 `block` 的规则必须用对应 severity 断言。`R-REDLINE` 的反例这一行刻意留了一个已知边界：同义改写不会被规则拦住，这是设计事实（规则是关键词/清单纯函数），必须写进注释，否则执行者会误以为实现有缺陷而去放宽匹配，进而引入误杀。

### 四、闸门的三轨验证

单测只是三轨之一，本项要在 `test_coverage_matrix.py` 的文档字符串里把三轨固定下来，并在 CI 输出里显式提示当前处于哪一轨：

```python
TRACKS = {
    "rule_unit": "T6-03 本项：CI 期。每条规则正例/反例，验证规则本身写对了",
    "shadow":    "T2-46 影子模式：灰度期。GATE_MODE=shadow，只记不拦，人工抽查误杀率",
    "enforce":   "全量期。误杀率达标后切 GATE_MODE=enforce，生产启动检查拒绝 shadow",
}
```

三轨之间是递进关系而非并列：单测证明"规则在构造输入上正确"，影子模式证明"规则在真实流量上不会大面积误杀"，强制拦截是全量开启后的稳定态（14.2）。单测全绿不构成开启强制拦截的依据——`test_coverage_matrix.py` 因此不校验 `GATE_MODE` 的值，只校验覆盖度，避免把"测试通过"误读为"可以切强制"。

### 五、规则注册完整性

`test_rule_registry.py` 断言引擎注册的规则 id 集合与 8.2 清单**完全相等**（不是包含）：

```python
EXPECTED_RULE_IDS = {
    "R-WHITELIST", "R-REGISTERED-CROP", "R-DOSAGE", "R-INTERVAL", "R-MAX-USE",
    "R-CONFLICT", "R-REGION", "R-PROVENANCE", "R-REDLINE", "R-REDLINE-LOAD",
    "R-CAUTION", "R-NO-DATA",
}

def test_engine_registers_exactly_expected_rules(engine: GateEngine) -> None:
    assert set(engine.registered_rule_ids()) == EXPECTED_RULE_IDS
```

用相等而不是包含：注册了清单外的规则意味着有规则在无人知晓的情况下参与判定，"拦了但不该拦"将无从归因。

`R-REDLINE-LOAD` 值得单独一提：它的语义是"红线配置必须成功加载"，因此它的反例是"配置正常"，正例是"配置损坏"。这条规则是全局约定第六节"红线缺失的流程必须处于不可用状态"的落地，用例必须证明损坏配置会 block，否则流程会在无红线状态下对外服务（17.2 风险表列出的合规风险）。

# T3-11 订阅授权接口与额度模型

## 这一项要做什么

实现订阅授权与推送额度的管理：`SubscriptionQuota` 模型、`GET /api/v1/subscription/quota`、`POST /api/v1/subscription/grant` 两个接口，以及四条硬规则——授权一次消费一次、无额度不得调用推送接口、失败不得静默丢弃、长期无额度不反复索要。额度模型的定位由产品说明书 4.6.2 功能点 3 决定：长期订阅消息对农业类小程序默认不可开通，因此**不把"建立长期推送关系"作为设计前提，而是把每一次触达当作一次需要争取的机会**。本项把这个产品判断变成一套可核算的额度账本，T3-12 的推送链路从它这里取授权、扣额度、写失败记录。

## 前置依赖

- T3-01 的 `subscription_quota` 表与 `reach_record` 表（含 `reject_streak`、`fail_reason` 字段）。
- T1-02 的异步数据库引擎（额度扣减必须用行级原子更新）；T1-16 提供发额度相关的事件通道（任务表编号为 T1-16，若该编号在阶段一实际未落地则由 `subscription.consumed` 事件直接驱动）。

## 实现要点

### 一、SubscriptionQuota 模型

```python
class SubscriptionQuota(BaseModel):
    user_id: str
    granted_total: int          # 累计获得授权次数
    consumed_total: int         # 累计已消费次数
    remaining: int              # 剩余可用额度
    last_grant_at: datetime | None
    last_consume_at: datetime | None
```

`remaining` 是冗余字段而非每次现算 `granted_total - consumed_total`，原因在 T3-01 已说明：额度校验在推送上高频发生且必须原子扣减。扣减用行级条件更新实现：

```python
async def try_consume(db: AsyncSession, user_id: str) -> bool:
    """原子扣减：返回是否成功。失败即额度不足，调用方不得发送。"""
    result = await db.execute(
        update(SubscriptionQuota)
        .where(SubscriptionQuota.user_id == user_id, SubscriptionQuota.remaining > 0)
        .values(remaining=SubscriptionQuota.remaining - 1,
                consumed_total=SubscriptionQuota.consumed_total + 1,
                last_consume_at=func.now())
        .returning(SubscriptionQuota.remaining))
    return result.first() is not None
```

`WHERE remaining > 0` 使扣减具备条件性，`UPDATE ... RETURNING` 使判断与扣减在一条语句内完成。若拆成"先查再扣"，并发推送会双花同一份额度：两个请求都读到 `remaining=1`，都判定为可发，最终发出两条而额度只扣了一次，第二天农户会发现"没授权却收到推送"。用一条带条件的 UPDATE 后，第二个请求的条件不成立、返回空结果，从而被拒绝。这个实现与 T3-12 的推送链路构成"先扣额度再发送"的顺序，扣减失败即不发送，因此不存在"发送了但没扣额度"的情形；反向的"扣了额度但发送失败"存在，处理方式是失败时把额度退还（见实现要点三）。

### 二、四条硬规则

| 规则 | 实现 |
| --- | --- |
| 授权一次、消费一次 | 每次发送成功即 `consumed_total += 1`，额度不足则拒绝发送 |
| 无额度不得调用推送接口 | 发送前强制校验 `remaining > 0`，否则直接记录 `reach_failed` |
| 失败不得静默丢弃 | 未授权/额度耗尽/接口失败三类分别记录原因 |
| 长期无额度不反复索要 | 连续 N 天无额度则授权入口降级为弱提示，仅保留小程序内提示位 |

**第一条与第二条的分工**：第一条是账本规则（消耗与授权一一对应），第二条是调用门槛（没额度就不调用微信接口）。门槛必须在调用微信接口之前，而不是之后：微信的一次性订阅消息接口在不满足条件时也会返回错误，但那次调用已经被计入微信侧的频率限制，且失败原因无法区分是"没授权"还是"接口异常"。因此后端先判额度、再调接口，把"没额度"拦截在自己的系统里并记 `quota_exhausted`，微信侧只处理真正需要它的请求。

**第三条的落地**：每次触达尝试无论成败都写 `reach_record`，`fail_reason` 四类在 T3-14 细化。这里要强调的是不允许"try 捕获异常后静默 return"的写法——推送失败必须落库，因为产品说明书 4.6.2 明确要求"记录为触达失败并计入送达率指标，据此发现触达断点"。

**第四条用 `reject_streak` 实现**：

```python
WEAKEN_AFTER_DAYS = 3          # 连续 N 天无额度则降级索要


def should_weaken_prompt(quota: SubscriptionQuota, today: date) -> bool:
    """长期无额度时授权入口降级为弱提示，避免反复索要。"""
    if quota.remaining > 0:
        return False
    if quota.reject_streak >= WEAKEN_AFTER_DAYS:
        return True
    return quota.last_grant_at is None and _days_since_first_seen(quota) >= WEAKEN_AFTER_DAYS
```

**连续 N 天无额度则授权入口降级为弱提示**。弱提示的含义是：不再在"更新提示成功后"的黄金位置弹出授权请求卡（8.7 的交互示意），只在提示列表底部保留一行不打扰的说明，如"想收到提醒可以去设置里开"。`WEAKEN_AFTER_DAYS` 取 3 是因为农户的授权意愿与具体场景强相关（刚生成处方卡时意愿最强），连续三天都不授权说明当前不是合适的时机，继续在同位置索要会变成骚扰。降级不是永久放弃：农户下次生成处方卡或登记回访时（8.7 定义的三个高频意愿时点）仍会在那些位置请求授权，因为那是新场景而非重复索要。

`reject_streak` 的记录方式：农户点"以后再说"时 `record_reject` 加一，授权成功时清零，连续三天无额度且无新增授权也计入。只记拒绝次数不够，因为农户更常见的行为是不点任何按钮（既不授权也不明确拒绝），这种沉默也需要被计入以免系统误以为"有机会可争取"。

### 三、授权的记录与退还

`POST /api/v1/subscription/grant` 接收前端回传的授权结果，`granted=true` 时把 `granted_total` 与 `remaining` 各加一、`reject_streak` 清零；`granted=false` 时只做 `record_reject` 并返回当前额度。接口返回最新额度视图，使前端不需要再发一次查询。

授权时机的选择不在本项实现，而是由 T3-12 或前端在三个时点调用：生成今日提示后、生成处方卡后、登记回访后（8.7 与 4.6.2 功能点 3 明确"在动作完成的瞬间请求：生成今日提示后、生成处方卡后、登记回访后"）。本项只保证额度账本正确，不决定何时请求。

**扣减后退还的场景**：T3-12 在扣减成功后调用微信接口，若接口返回失败（非额度问题，如网络异常），需要把额度退还，否则农户的授权机会被无声消耗。退还用与扣减对称的一条 SQL（`remaining + 1`、`consumed_total - 1`）并在 `reach_record.fail_reason="api_error"` 中记录。这是"授权一次消费一次"的准确含义——消费的是**成功送达**，不是**尝试发送**。这与 T3-12 的顺序设计相关，本项提供 `refund` 方法供其调用。

### 四、接口与查询

`GET /api/v1/subscription/quota` 返回 `{remaining: N, grantedTotal, consumedTotal, weakened: bool}`，供 11.6 序列图中的小程序在生成快照后查询额度以决定是否显示授权请求。`weakened` 字段让前端知道应显示强索要还是弱提示，判定逻辑集中在后端，避免前端各自实现导致策略不一致。

两个接口都走 T1-06 的归属校验，`user_id` 从令牌取，不接受请求体传入——额度是每户的资产，允许客户端指定 `user_id` 会造成额度篡改。

## 验收标准

- `pytest tests/services/test_quota_service.py` 全部通过，含：`grant` 后 `granted_total` 与 `remaining` 各加一、`reject_streak` 归零；`try_consume` 在 `remaining > 0` 时返回 `True` 且 `remaining` 减一、在 `remaining == 0` 时返回 `False` 且各计数不变。
- 并发扣减：`remaining=1` 时并发调用 10 次 `try_consume`，断言恰好 1 次返回 `True`、9 次返回 `False`，最终 `consumed_total == 1`。
- 降级索要：`remaining=0` 且 `reject_streak=3` 时断言 `should_weaken_prompt is True`；`remaining=1` 时断言为 `False`；`reject_streak=2` 时断言为 `False`。
- 退还：连续执行 `try_consume` 成功后调用 `refund`，断言 `remaining` 与 `consumed_total` 回到调用前的值；断言退还在 `remaining == 0` 时不会把 `remaining` 变成负数。
- 接口：`POST /subscription/grant` 带 `granted=false` 后 `GET /subscription/quota` 返回的 `remaining` 不变且 `reject_streak` 加一；用另一用户令牌查询断言读不到该用户额度（返回自己的或 403）。
- 断言额度接口不接受请求体传 `user_id`：`QuotaView.model_fields` 不含 `user_id`，`GrantRequest.model_fields` 不含 `user_id`。
- `ruff check`、`ruff format --check`、`mypy app` 三条命令均返回 0。

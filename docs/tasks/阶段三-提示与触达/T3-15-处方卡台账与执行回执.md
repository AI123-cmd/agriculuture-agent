# T3-15 处方卡台账与执行回执

## 这一项要做什么

实现两件事：把处方卡存入农事台账（`POST /api/v1/ai/prescription/{id}/ledger`），以及提示条目的执行勾选回执（`POST /api/v1/broadcast/items/{id}/execute`，可取消）。两件事共用一个目标——**沉淀农户自己的农事记录**：处方卡是"AI 建议我做什么"，执行回执是"我实际做了什么"，两者合起来构成产品说明书 4.5.2 功能点 2 所说的"这一季我做过什么"的完整视图。其中执行勾选承载的 `executed` 字段是北极星指标"执行率"的数据来源，也是产品后续优化唯一的真实反馈；未勾选的条目同样是重要信号，连续多条未被勾选说明提示内容与农户实际需求不匹配，需要复盘规则与文案，而不是加大推送力度。

## 实现要点

### 一、处方卡入台账

```python
async def save_prescription_to_ledger(db: AsyncSession, user_id: str, card_id: str) -> LedgerEntry:
    """处方卡存入农事台账：幂等，重复点击返回既有条目。"""
    card = await prescription_repo.get(db, user_id, card_id)      # 归属校验在 repository 内
    if card is None:
        raise NotFoundError("处方卡不存在")
    existing = await ledger_repo.get_by_source(db, user_id, source_type="prescription",
                                               source_id=card_id)
    if existing is not None:
        return existing                                          # 幂等：不重复入账
    entry = LedgerEntry(
        id=new_id("lg"), user_id=user_id, entry_date=card.created_at.date(),
        process_id=card.process_id, source_type="prescription", source_id=card_id,
        title=card.diagnosis_summary, actions=_actions_of(card),
        safety_interval_days=card.safety_interval_days,
        facts_provenance=card.facts_provenance, followup_needed=_has_followup(card))
    await ledger_repo.save(db, entry)
    await prescription_repo.mark_ledger_saved(db, user_id, card_id)   # 回写 ledger_saved
    return entry
```

入台账必须幂等。农户会重复点击"存入台账"（尤其当他没看到明确反馈时），若每次都新增一条，台账里会出现同一份处方的多条重复记录。幂等键是 `(user_id, source_type, source_id)`，`source_id` 对处方卡就是 `card.id`。`ledger_saved` 字段回写后，前端可据此把按钮改为"已存入台账"状态，减少重复点击。

**台账条目的字段从处方卡复制而非引用**：药剂名、剂量、安全间隔期这些事实性内容在入台账时做一次快照。理由是知识条目会随版本迭代而 `deprecated`（12.7 说明"保留历史引用需要允许引用已废弃条目"），若台账只存 `knowledge_id`，未来回看时会因条目废弃而显示不出当时的药剂名。台账的价值在于沉淀历史，因此必须自包含。

**无生育期流程的呈现方式**：产品说明书 4.5.2 功能点 2 指出"杂草防治与通用农业流程无生育期节点，改为按防除/处置时间线呈现"。实现为 `LedgerEntry.process_id` 落在 `NO_CALENDAR_PROCESSES`（T3-03 的常量）内时 `entry_date` 就是唯一的时间轴，不挂生育期节点；`list_ledger` 对这两条流程按 `entry_date` 倒序返回纯时间线。这条复用 T3-03 定义的同一份常量，不另建一份，避免两处口径漂移。

### 二、执行勾选回执

```python
async def set_item_executed(db: AsyncSession, user_id: str, item_id: str,
                            executed: bool) -> PromptItem:
    """勾选或取消勾选：executed 是北极星指标的数据来源。"""
    item = await snapshot_repo.get_item_for_user(db, user_id, item_id)   # 归属校验
    if item is None:
        raise NotFoundError("提示条目不存在")
    if item.suppressed:
        raise InvalidStateError("被抑制的条目不接受执行勾选")            # 它没展示给农户
    item.executed = executed
    item.executed_at = datetime.now(TZ) if executed else None             # 取消时清空时间戳
    await snapshot_repo.save_item(db, item)
    return item
```

接口一次点击完成，勾选后立即给出肯定反馈（产品说明书 4.3.3 功能点 4 要求"勾选动作必须极简（一次点击），且勾选后立即给出肯定反馈"）。`POST /broadcast/items/{id}/execute` 接受 `{"executed": true}` 或 `{"executed": false}` 表达勾选与取消（13.1 注明"可勾选已执行（可取消）"）。

**取消时清空 `executed_at`** 而不是保留旧时间戳。若保留，执行率统计（按 `executed_at` 落入的时段）会把一条已取消的记录算成"当时执行了"，导致指标虚高。清空后 `executed=False` 且 `executed_at IS NULL`，两者始终一一对应，统计条件只需 `WHERE executed = true`。

**被抑制条目拒绝勾选**：`suppressed=True` 的条目从未展示给农户，农户不可能勾选它。若允许，会出现"农户勾选了不存在的提示"这一无法解释的数据。虽然正常情况下前端拿不到被抑制条目的 id，但接口必须自行拦截，不能依赖前端。

### 三、北极星指标的数据来源

执行率的计算口径：

```python
async def execution_rate(db: AsyncSession, since: date, process_id: str | None = None) -> dict:
    """执行率：按流程分别统计，混在一起会掩盖单条流程的退化。"""
    shown = await snapshot_repo.count_items(db, since, process_id, suppressed=False)
    executed = await snapshot_repo.count_items(db, since, process_id,
                                               suppressed=False, executed=True)
    return {"shown": shown, "executed": executed,
            "rate": executed / shown if shown else 0.0}
```

产品说明书 6.3 第三层明确"上述指标需按流程分别统计"，因此 `execution_rate` 的 `process_id` 参数不是可选的便利参数，而是必须提供的统计维度——不传时按流程分组返回字典，而不是返回一个总数。`suppressed=False` 是必须的过滤条件：被抑制条目从未展示，计入分母会让执行率被人为压低，而它反映的是"系统主动隐藏了多少"，属于另一个指标（T3-06 的复盘用途）。

执行率之外，**未勾选同样是信号**。产品说明书 4.3.3 功能点 4 明确"连续多条提示未被勾选，说明提示内容与农户实际需求不匹配，需要复盘规则与文案，而不是加大推送力度"。实现为同时产出 `ignored_streak`（某农户连续未被勾选的条目数），供 T6-09 的指标采集，使"连续多条未勾选"成为一个可观测的触发条件而不是一句原则。

### 四、归属校验与数据隔离

两条接口都必须走归属校验，这直接对应产品说明书 4.5.2 功能点 4 与 9.2 第 1 条验收项。台账与提示条目是农户的私有农事记录，任何遍历或猜测标识访问他人数据的行为都必须被拒。实现上所有查询经 T1-05 的 `OwnedRepository`，`user_id` 从令牌取，不接受请求体传入。

现有 `mark_done` 的问题正是"用 `item_id` 加 `user_id` 两个条件查询"——这一写法本身是对的，但它是手工拼的，一旦有人复制这段代码到新接口时漏掉 `user_id` 条件，就越权了。改为走 repository 后，归属条件是基类强制的，漏写会直接抛异常（T1-05 的设计：无 `user_id` 参数则抛 `OwnershipError`），而不是静默返回他人的数据。

### 五、与旧实现的替换关系

现有 `POST /broadcast/mark-done` 与 `BroadcastLog.done` 整体废弃：`done` 是 `SmallInteger` 的 0/1，无法表达取消后的时间戳清理、无法关联到 `prompt_item`、也没有"被抑制条目不接受勾选"的约束。旧的 `BroadcastTodayResponse` 出参（`id / time / title / content / done / type`）由 T3-10 的 `SnapshotView` 取代。为兼容旧前端，可在过渡期保留一个转发路由，但必须在 T4 阶段的适老化改造前删除，避免新旧两套并行长期存在。

## 验收标准

- `pytest tests/services/test_ledger_service.py` 全部通过，含：同一处方卡连续调用 `save_prescription_to_ledger` 两次，断言台账表只有 1 条记录且返回同一 `entry_id`；断言处方卡的 `ledger_saved` 被置为 `True`。
- 台账自包含：断言 `LedgerEntry` 中存有药剂名与 `safety_interval_days` 的副本；把对应知识条目置为 `deprecated` 后，断言台账读取仍能显示药剂名（`grep -c "knowledge_item" app/services/ledger_service.py` 的读取路径不参与台账展示）。
- 勾选与取消：`executed=True` 后断言 `executed_at` 非空；再次调用 `executed=False` 断言 `executed=False` 且 `executed_at is None`；断言被抑制条目的勾选请求抛 `InvalidStateError`。
- 执行率：构造 10 条已展示条目其中 4 条勾选、另有 5 条被抑制，断言 `execution_rate` 的 `shown` 为 10、`rate` 为 0.4；不传 `process_id` 时断言返回按流程分组的字典。
- 归属：用另一用户的令牌调用两条接口，断言均返回 404 或 403 且不修改目标数据；`grep -n "db.query" backend/app/services/ledger_service.py backend/app/api/v1/ledger.py` 无输出。
- 接口路径：断言 `POST /api/v1/ai/prescription/{id}/ledger` 与 `POST /api/v1/broadcast/items/{id}/execute` 均在路由表中，且 `POST /api/v1/broadcast/mark-done` 已移除或标记为待删除。
- `grep -rn "BroadcastLog" backend/app/` 无输出（旧表与旧字段引用清空）；`ruff check`、`ruff format --check`、`mypy app` 三条命令均返回 0。

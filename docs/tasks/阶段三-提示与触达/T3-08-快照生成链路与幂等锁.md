# T3-08 快照生成链路与幂等锁

## 这一项要做什么

串起完整的快照生成链路：三类输入采集 → 规则层匹配 → 合并排序截断 → 文案生成 → 文案安全校验 → 写入快照，并用 Redis 分布式锁加幂等键保证"同日同农户同地块"只生成一份有效快照。同日重复点击不重新生成全部内容，而是检查是否有新信号，有则合并、无则返回原快照并提示"今日提示已是最新"；同日第三次点击起显示"今日已更新 N 次，明天会有新内容"。现有实现 `broadcast_service.get_today` 的问题正是产品说明书 9.2 第 6 条列出的缺陷（"提示生成不幂等、无去重合并、无条数上限"）：它只判断当日是否已有 `broadcast_log` 记录，一旦有就直接返回，既没有幂等键也没有并发保护，并发请求会双双生成。

## 实现要点

### 一、generate_snapshot 与幂等锁

```python
async def generate_snapshot(db: Session, user_id: str, plot_id: str | None) -> Snapshot:
    """生成提示快照：幂等 + 当日有效。"""
    today = date.today()
    key = f"snapshot:{user_id}:{plot_id or 'default'}:{today.isoformat()}"

    # Redis 分布式锁 + 幂等键
    async with redis_lock(key, timeout=30):
        existing = await snapshot_repo.get_today(db, user_id, plot_id, today)
        if existing and not existing.invalidated:
            # 同日重复点击：合并去重后返回增强版，而非重新生成
            return existing
        snapshot = await _build_snapshot(db, user_id, plot_id, today)
        await snapshot_repo.save(db, snapshot)
        return snapshot
```

幂等键的粒度是"农户 + 地块 + 自然日"，与 T3-01 的唯一约束一致。`plot_id or 'default'` 处理杂草流程不绑定地块的情形（12.2），使杂草流程也有一把锁而不是无锁。锁超时 30 秒，与快照生成的预期耗时匹配：三类输入采集要查环境、农事历、问诊三路数据，加上一次可选的模型改写（超时 8 秒），30 秒留了足够余量又不至于让卡死的锁长期占位。

`redis_lock` 的实现要点有三个。其一，锁值必须是随机 token，释放时用 Lua 脚本比对 token 后才删除，否则"A 的锁超时后 B 拿到，A 执行完却删掉了 B 的锁"会造成互斥失效。其二，获取锁失败时不是直接报错，而是短暂等待后重试一两次，因为并发点击同一农户的「更新提示」是可预期的（农户连点两下），直接报错会让农户看到失败提示。其三，Redis 不可用时 `redis_lock` 必须降级为"仅依赖数据库唯一约束"而不是整体失败——唯一的强一致保障来自 T3-01 的唯一约束，Redis 锁只是减少无效工作，这个层次关系要写进代码注释，避免后人以为锁是必需的。

`existing and not existing.invalidated` 这个条件里的 `invalidated` 是给"档案变更后需要重算"留的口子：农户在当日新增了经营条目，旧快照的内容可能已经不对，此时把旧快照标 `invalidated` 后再次点击就会真正重新生成。

### 二、同日重复点击的处理

- 第一次点击：正常生成。
- 同日再次点击：**不重新生成全部内容**，而是检查三类输入是否出现新信号（如新到期的回访），若有则合并；若无则返回原快照并提示"今日提示已是最新"。
- 频次提示：**同日第三次点击起，按钮下方显示"今日已更新 N 次，明天会有新内容"。**

```python
def build_update_notice(click_count: int, merged_new: bool) -> str | None:
    """频次提示文案：第三次起提示今日已更新次数。"""
    if click_count < 3:
        return None
    return f"今日已更新 {click_count} 次，明天会有新内容"
```

"检查是否出现新信号"具体实现为：重新跑一遍三类输入采集与规则匹配，得到的条目集合与快照中已有条目按 `rule_id` 做差集；差集为空则返回原快照，非空则把新条目按 T3-06 的排序插入并重新执行截断，`revision` 自增后落库。**注意这里必须重新跑规则而只做差集合并，不能整份替换**，因为整份替换会让已被农户勾选 `executed` 的条目丢失勾选状态——农户上午勾了"已灌溉"，下午点开更新提示发现勾还在还好，勾没了会让他怀疑自己的操作没生效。

`click_count` 不落库在快照上，而是每次点击在 Redis 里对该农户当日的计数加一（键 `snapshot_clicks:{user_id}:{date}`，过期设为次日凌晨）。理由是这个计数只服务于提示文案，不影响任何业务判定，落库会增加写入且需要清理；同时 Redis 计数丢失后最坏后果只是提示文案不显示，不影响幂等。

### 三、完整链路与安全校验

```python
async def _build_snapshot(db: Session, user_id: str, plot_id: str | None, today: date) -> Snapshot:
    """三类输入 → 规则匹配 → 合并截断 → 文案 → 安全校验 → 落库对象。"""
    facts = await collect_env_facts(user_id, plot_id)
    calendar_tasks = await collect_calendar_tasks(profile, today)
    consult_signals = await collect_consult_signals(user_id)
    hits = RuleEngine().match_all(RuleContext(facts=facts, calendar=calendar_tasks,
                                             signals=consult_signals, profile=profile))
    kept_hits = merge_and_rank(hits)                   # T3-06：合并去重 + 排序
    kept, dropped = apply_limit(kept_hits)             # T3-06：条数控制，被截断项标 suppressed
    for item in kept:
        item.text = await build_text(item)             # 模板出事实 + 模型改写
    kept = await gate_check(kept)                      # 文案安全校验，不过关即丢弃该条
    return Snapshot(user_id=user_id, plot_id=plot_id, snapshot_date=today,
                    generated_at=datetime.now(UTC), env_source=facts.source,
                    revision=1, items=kept + dropped)
```

安全校验放在文案生成之后、落库之前，因为校验对象是最终文案里的数字，而数字在模型改写阶段才可能被引入或改错。校验复用闸门规则的三条：`R-PROVENANCE`（文案中的每个数字是否在 `facts_provenance` 中有登记）、`R-NO-DATA`（是否出现无来源的数值）、`R-REDLINE`（是否命中当前流程的禁用输出清单）。校验不通过的条目**丢弃并记录，不落库到展示位**，同时写一条 `gate_audit` 供复盘——这里的处理与处方不同（处方是降级为转人工，提示是整条丢弃），因为提示条目是离散的，丢弃一条不影响其他条，而处方是整体交付物。

`GATE` 节点在 11.1 的流程图中还包含"静默时段"检查，但那是触达链路的约束（T3-13），不是快照生成的约束：农户主动查看不受时段限制（11.9 明确"农户主动查看不受限，仅约束主动推送"）。因此生成阶段只做文案安全，不判断当前是否静默时段。

### 四、接口与事件

`POST /api/v1/broadcast/snapshot` 返回快照加 `updateCompleted=true`（13.1 与 11.6 的序列图），`GET /api/v1/broadcast/snapshot` 返回当日快照（不存在时返回空状态而不自动生成，避免 GET 产生写副作用）。两个接口都走 T1-06 的归属校验。

`snapshot.requested` 事件（6.6）在本项作为发件箱消费者接入：小程序点击「更新提示」走同步路径直接生成（农户在等结果），事件用于异步场景（定时任务预生成）。同步路径不经过发件箱，这条区分与 T1-13 的说明一致。

## 验收标准

- `pytest tests/broadcast/test_snapshot_idempotency.py` 全部通过，含：并发发起 10 次 `generate_snapshot`（`asyncio.gather`），断言 `prompt_snapshot` 表中当日该农户该地块的记录数为 1；断言所有调用返回同一 `snapshot_id`。
- 同日重复点击：第一次调用后记录条目数，第二次调用（无新信号）断言返回原 `snapshot_id`、`revision` 仍为 1、条目数与勾选状态不变；构造一条新到期的回访任务后再次调用，断言 `revision` 为 2 且新条目已合并、原有已勾选条目的 `executed` 仍为 `True`。
- 频次提示：连续调用 3 次，断言第 3 次返回的 `updateNotice` 非空且含"今日已更新"与数字 3；调用 2 次时断言 `updateNotice is None`。
- 唯一约束兜底：绕过 Redis（`redis_lock` 用 no-op 替换）并发调用 10 次，断言数据库抛唯一约束冲突且被捕获重试后最终仍只有 1 条记录。

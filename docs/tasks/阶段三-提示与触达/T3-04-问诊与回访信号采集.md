# T3-04 问诊与回访信号采集

## 这一项要做什么

实现第三类输入"问诊与回访信号"的采集：处于观察期且未到回访时点的问诊、以及到期未回访的处方卡，两类都转为首页提示条目。这是"让首页记得住农户"的关键通路，也是让首页提示与问诊产生连贯感的唯一通道——没有这一路，首页只是一个静态阈值看板，农户问过的问题在关掉对话页后就消失了。本项与 T3-09（回访调度服务）是一对：T3-09 负责按流程算出"何时该回访"并写 `followup_task`，本项负责把"到期的那些"变成首页上的 `followup` 类条目。

## 前置依赖

- T3-01 的 `PromptItem.source_kind` 取值口径（`followup`）与 `rule_id` 字段。
- T3-09 的 `followup_task` 表与 `list_due` 查询能力（本项只读，不写回访任务）；T2-11 处方契约的 `FollowupPlan` / `FollowupTask`（`due_offset_days`、`kind`、`ask`、`content_rule`）。
- T2-19 与 T2-21 产出的 `prescription_card`（含 `followup_plan` 与 `safety_interval_days`）与 T2-33 落库的 `consultation`（`status` 取 `observing` / `resolved` / `followup` / `escalated` / `blocked`）。
- 外部环境：`consultation`、`prescription_card`、`followup_task` 三表由 T1-04 迁移建好；数据访问须走 T1-05 的 `OwnedRepository`（守 L4）。

## 实现要点

### 一、两个来源与 collect_consult_signals

```python
async def collect_consult_signals(user_id: str) -> list[RuleResult]:
    """问诊信号：未解决提问 + 到期回访。"""
    signals = []
    # 1. 处于观察期的问诊（有结论但未闭环且未到回访时点）
    observing = await consult_repo.list_observing(user_id)
    for c in observing:
        if c.needs_followup_check(today):
            signals.append(build_followup_prompt(c))
    # 2. 到期未回访的处方卡
    due = await followup_repo.list_due(user_id, today)
    for f in due:
        signals.append(build_followup_rule(f))
    return signals
```

两个来源解决的痛点不同。第一个来源（观察期问诊）回答的是"你前两天问的叶片斑点，现在情况如何"——它针对的是**没有处方、只有观察建议**的问诊，这类问诊在 `status="observing"` 状态下停留数天后如果没有这一路，就会被农户遗忘，形成"问了但没结论也没后续"的断点。第二个来源（到期回访）针对的是**有处方卡**的问诊，它携带明确的动作与效果询问，是本项与 T3-09 的接口。

`c.needs_followup_check(today)` 是判定"该问了"的方法，实现为"`status == observing` 且上次交互距今天数 ≥ 该流程观察期阈值 且未到 T3-09 登记的回访时点"。最后一个条件避免与第二个来源重复：如果该问诊已有处方卡且已登记回访任务，则由第二个来源负责，第一个来源必须让位。这个互斥判定是为了防止农户在同一天看到"你的叶片斑点怎么样了"两次，一次来自观察期提示、一次来自回访提示，内容几乎一样会削弱信任。

### 二、两类条目的内容规则不同

```python
def build_followup_prompt(c: Consultation) -> RuleResult:
    """观察期问诊：询问现状，不询问"效果"（尚无处方，无效果可问）。"""
    return RuleResult(
        source_kind="followup", severity="reminder",
        callout=c.object_label,               # 如"水稻田"
        fact=f"你 {c.days_ago()} 天前问的{c.topic_summary}",
        impact="当时建议先观察两天，现在可以再看看情况",
        action="看看现在和之前比有没有变化",
        rule_id=f"followup.observing.{c.process_id}",
    )


def build_followup_rule(f: FollowupTask) -> RuleResult:
    """到期回访：按处方卡的 followup_plan 取询问语与内容规则。"""
    return RuleResult(
        source_kind="followup", severity=_severity_of(f),
        callout=f.object_label,
        fact=f.ask,                            # 来自 FollowupTask.ask
        impact="上次给的做法是否起作用，是判断要不要调整的依据",
        action="回填一下效果",
        rule_id=f.content_rule or "followup.effect_check",
    )
```

两类的 `severity` 默认不同：观察期问诊是 `reminder`（最轻，因为它是软性跟进），到期回访默认 `notice`，其中 `kind="preserve_scene"` 的药害固定现场提示可到 `urgent`（见 T3-09 对杂草药害分支的说明，错过表现期就失去鉴别依据）。`severity` 的判定写在 `_severity_of` 里按 `kind` 映射，不写在流程配置的文案里，因为这是分类逻辑而非文案。

**观察期问诊不得询问"效果"**：这类问诊没有处方卡，也就没有"效果"可问。若模板统一写成"上次建议的做法效果如何"，农户会觉得系统记错了——他上次拿到的只是一句"再观察看看"。因此 `build_followup_prompt` 用 `c.topic_summary`（当时问的主题）而不是"上次的建议"，用"看看有没有变化"而不是"效果如何"。

### 三、幂等与去重

本路输入的条目必须先查同日快照是否已存在同 `rule_id` 的条目，存在则跳过。原因有两个：一是回访任务在 `due_at` 当天会持续被 `list_due` 命中，直到农户回填结果，如果每次「更新提示」都新增一条，同日重复点击会让快照条目数不断增长；二是 `followup_task` 的状态在农户回填前一直是 `pending`，不存在"已被消费"的自然标记。去重的判据是 `(user_id, snapshot_date, rule_id)`，`rule_id` 对回访类条目取 `followup.effect_check:{task_id}` 形态以保证逐任务唯一。

去重放在本项而不是 T3-08 的幂等锁里，因为幂等锁解决的是"整份快照是否重新生成"，本项解决的是"同一信号是否重复成条"。两者层次不同：锁保证同日只生成一份快照，去重保证一份快照内同一回访不出现两次。

### 四、复核 product 的三种回答价值

产品说明书 4.2.3 功能点 7 指出农户对回访的三种回答各有用途：形成闭环、反馈"没效果"时重新进入问诊、为知识库正确性提供真实反馈。本项只负责把回访"送达农户"，回答的处理在 `POST /api/v1/followup/{id}/result` 与 T2-33 的图驱动接口。但本项产出的条目必须携带 `followup_task_id`（存入 `PromptItem.facts_provenance` 的 `task_id` 键），使农户在首页点"回填"时前端能直接定位到对应任务，不必再查一遍"这条提示对应哪次问诊"。

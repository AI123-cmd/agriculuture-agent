# T3-05 规则层匹配引擎（零模型可用）

## 这一项要做什么

把三类输入变成结构化的提示条目：规则层匹配负责"哪些输入命中哪条规则、命中后条目长什么样"，全部是纯代码逻辑，不调用大模型。核心约束是**必须能在零模型模式下工作**——产品说明书 6.3 兜底三要求"规则层能力（阈值提示、农事历提示）继续提供，界面提示智能问答暂时不可用"，并明确"不允许整体页面不可用"。本项是实现这条要求的地方：模型网关整体不可用时，首页提示必须照常生成、照常展示、照常可勾选，损失的只是文案的口语化程度。现有实现 `app/broadcast/rules/` 的规则只在 `generator.py` 里以"命中即直出 `RuleResult`"的方式工作，且兜底分支会调 `BroadcastSkill` 找模型，本项重建引擎并把模型调用彻底移出规则层。

## 实现要点

### 一、RuleResult 与 PromptItem 字段对齐

规则层的输出结构必须与 T3-01 的 `prompt_item` 列一一对应，否则 T3-08 落库时要做一轮字段翻译，翻译层会随字段增删而漏改。

```python
@dataclass(frozen=True)
class RuleResult:
    source_kind: str                 # env_risk / calendar / followup
    severity: str                    # urgent / notice / reminder
    callout: str                     # 呼告（对象）
    fact: str                        # 事实
    impact: str                      # 影响
    action: str                      # 行动
    rule_id: str
    facts_provenance: dict[str, str]
    timeliness_score: float = 0.0    # 供 T3-06 排序
    relevance_score: float = 0.0     # 供 T3-06 排序
```

`frozen=True` 让规则结果不可变。规则层的每条结果都要经过合并、去重、排序、截断四道处理，可变对象在过程中被就地修改会让"这条为什么被抑制"难以复现。排序用的两个分数字段留在规则结果里而不单列一张表，因为它们只在生成快照的这一次调用内有意义，不需要持久化——落库的是 `priority_score` 这一合成值。

### 二、零模型模式

```python
class RuleEngine:
    """规则层匹配引擎：纯确定性，任何路径都不调用模型。"""

    def __init__(self, rules: list[BaseRule] | None = None) -> None:
        self.rules = rules if rules is not None else load_rules()

    def match_all(self, ctx: RuleContext) -> list[RuleResult]:
        """三类输入 → 全部命中条目。此函数在零模型模式下行为完全一致。"""
        results: list[RuleResult] = []
        for rule in self.rules:
            if not rule.applies_to(ctx.process_id):
                continue
            if rule.requires_env and ctx.env.source == "none":
                continue                       # 11.2：环境不可用时该路条目在生成阶段拦截
            for item in rule.evaluate(ctx):
                results.append(item)
        return results
```

零模型模式的实现方式是**结构性**的而不是开关式的：`RuleEngine` 的构造签名里没有任何 gateway 或 llm 参数，`match_all` 的函数体内不存在 `await`，因此"规则层调了模型"这件事在不改函数签名的前提下不可能发生。用 `isfile` 式开关（如 `ENABLE_MODEL = False`）来保证零模型是不够的——开关会被人打开，而结构性缺失不会。

`requires_env` 是规则类属性，标为 `True` 的规则在 `EnvFacts.source == "none"` 时被整体跳过。这样 T3-02 的拦截点落在引擎侧与规则侧两处：引擎跳过整条规则，规则内部也不必再逐字段判空。两处都做的原因是规则可以被单独调用（测试、影子模式），单测直接调 `rule.evaluate(ctx)` 时引擎的拦截不生效，规则内部仍需判空。

### 三、按流程筛选不用 if 分支

```python
class BaseRule(ABC):
    process_ids: frozenset[ProcessId] | None = None   # None 表示全流程适用
    requires_env: bool = False
    source_kind: str = "env_risk"

    def applies_to(self, process_id: ProcessId) -> bool:
        return self.process_ids is None or process_id in self.process_ids
```

`applies_to` 取代 `if ctx.process_id == ProcessId.RICE` 这类分支。全局约定第六节要求"新增一条流程的改动量应控制为一份 YAML + 一个约 15 行的子图文件 + 路由表注册一行"，规则层若遍地是流程判断，新增流程就要改每一处。规则若只为某条流程存在（如水稻的抗药性暂停提示），在类上声明 `process_ids={ProcessId.RICE}` 即可，不改引擎。

阈值也要从全局配置迁到流程配置：现有六个 `BROADCAST_` 配置是全局标量，水稻的高温阈值与茶的高温阈值本应不同（茶树 35℃ 即为热害胁迫，水稻更耐受）。因此 `RuleEngine` 的阈值来源改为 `load_process_config(process_id).timing_rules` 里的阈值定义，`app/core/config.py` 的 `BROADCAST_` 六项作为兜底默认值保留（流程配置未定义该指标阈值时使用），并在配置说明里标注"逐步迁移至流程配置"。

### 四、删除 AI 兜底生成整份简报

现有 `generator.py` 的兜底逻辑是"所有规则都没命中时，用通用农业模型生成一份今日农事简报"，`skill.py` 的实现还引用了即将删除的 `app/ai_router/registry.py`。这一段必须删除，理由有三：

其一，它违反"模板出事实、模型只改写"。整份简报的事实（环境概况、风险点、农事操作）全部由模型生成，没有任何模板约束，也没有 `facts_provenance`，与红线四"不出现无数据支撑的数字"直接冲突。

其二，它使零模型模式失效。模型不可用时这段兜底会抛异常，而它在"规则未命中"这个最常见的情形下被调用（农户档案不完整时几乎所有规则都不命中），恰好是最需要零模型可用的场景。

其三，规则未命中不等于无话可说。规则未命中时的正确行为是"生成零条提示"，前端展示空状态引导农户补全档案或提问，而不是让模型编一份泛泛的农事简报给农户看。产品说明书 4.3.3 功能点 3 的原则是"宁可少而准，不要多而虚"，一条被执行的提示价值远高于五条被划过的提示。

### 五、条目字段的必填校验

```python
def validate_item(item: RuleResult) -> RuleResult:
    """落库前的完整性校验：五段式缺一段即视为规则实现错误。"""
    for field in ("callout", "fact", "impact", "action"):
        if not getattr(item, field) or not getattr(item, field).strip():
            raise RuleImplementationError(f"{item.rule_id} 缺少 {field}")
    return item
```

五段式（呼告、级别、事实、影响、行动）是产品说明书 4.3.3 功能点 2 规定的标准结构，`severity` 另有枚举约束。校验在引擎出口处统一做，而不是让每条规则各自保证——规则会被不断新增，靠约定维持字段完整性的成本远高于一个集中校验点。校验失败抛异常而不是跳过该条目：缺字段是规则实现错误，静默跳过会让这类错误长期存在而不被发现。

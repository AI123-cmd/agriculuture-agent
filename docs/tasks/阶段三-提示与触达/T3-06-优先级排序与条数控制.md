# T3-06 优先级排序与条数控制

## 这一项要做什么

对规则层产出的条目做合并去重、按"紧急程度 → 时效性 → 相关度"排序、并按条数上限截断。规则是：普通提示每日不超过 3 条、紧急提示不受限、`urgent` 的判定需双条件命中以避免贬值、被抑制条目保留可追溯。现有实现没有任何排序与截断，`generator.py` 把规则命中按注册顺序直接拼成列表，实测页面会一次展示七到八条，与产品说明书 4.3.3 功能点 3"宁可少而准"直接冲突。本项全部是纯函数，便于单测，也便于产品复盘时复现"当时为什么展示的是这三条"。

## 实现要点

### 一、排序键

```python
SEVERITY_WEIGHT: dict[str, int] = {"urgent": 3, "notice": 2, "reminder": 1}


def priority_key(item: RuleResult) -> tuple:
    """排序键：紧急程度 → 时效性 → 与当前关注点相关度。"""
    return (
        -SEVERITY_WEIGHT[item.severity],           # urgent > notice > reminder
        -item.timeliness_score,                    # 越紧迫越高
        -item.relevance_score,                     # 与近期提问/回访的相关度
    )
```

三个维度按产品说明书 4.3.3 功能点 3 的定义顺序排列，用元组而不是加权求和。加权求和的三个系数无法在没有真实数据前定标，且一旦定标就解释了"为什么这条排在前面"这个问题——元组比较的顺序本身就是答案，复查时可以直接说"因为它更紧急"。三个维度都取负号是因为排序要降序（`sorted` 默认升序），而 Python 元组比较逐项进行，因此紧急程度的权重天然高于时效性，时效性天然高于相关度，不会出现"相关度极高但只是提醒"的条目压过"紧急但相关度低"的条目。

`priority_score` 落库时是三个维度的合成值（如 `SEVERITY_WEIGHT * 100 + timeliness * 10 + relevance`，保留三位小数），落库后排序依据变为可查的数字，供产品复盘。合成公式与 `priority_key` 必须保持单调一致，实现方式是用同一个 `priority_key` 生成分数，避免两套排序逻辑漂移。

### 二、合并去重

```python
def merge_and_rank(items: list[RuleResult]) -> list[RuleResult]:
    """合并去重后按优先级降序排列。"""
    by_rule: dict[str, RuleResult] = {}
    for item in sorted(items, key=priority_key):
        by_rule.setdefault(item.rule_id, item)     # 同 rule_id 保留优先级最高的一条
    return sorted(by_rule.values(), key=priority_key)
```

去重的粒度是 `rule_id`。三类输入可能出现同一件事的重复条目：环境层"土壤墒情不足"与农事历层"该灌水了"可能同时命中同一块地；回访层的同一处方卡也可能既有观察期提示又有到期回访（虽然 T3-04 已做互斥，但边界情形仍需本层兜底）。去重保留优先级最高的一条而非第一条，因为输入采集的顺序不确定，保留第一条会让结果随采集顺序变化。

先 `sorted` 再 `setdefault` 是关键：如果直接遍历原列表 `setdefault`，保留的就是"先出现的那条"，与优先级无关。这里的 `sorted` 提升了复杂度到 `O(n log n)`，但条目数量在个位数，无实际影响。

### 三、条数控制

| 规则 | 实现 |
| --- | --- |
| 普通提示 ≤ 3 条 | 截断后仅展示 top-3，其余标记 `suppressed=True` 保留 |
| 紧急提示不受限 | `severity=urgent` 不参与截断 |
| 紧急判定严格 | `urgent` 的判定条件写在规则配置中且需双条件命中，避免贬值 |
| 被抑制条目可追溯 | `suppressed` 记录在快照中，供产品复盘"哪些内容长期被压制" |

```python
NORMAL_LIMIT = 3


def apply_limit(items: list[RuleResult]) -> list[RuleResult]:
    """普通提示限 3 条，紧急不受限；被截断条目保留并标 suppressed。"""
    ordered = sorted(items, key=priority_key)
    urgent = [i for i in ordered if i.severity == "urgent"]
    normal = [i for i in ordered if i.severity != "urgent"]
    kept = urgent + normal[:NORMAL_LIMIT]
    dropped = [(i, True) for i in normal[NORMAL_LIMIT:]]
    return kept, dropped                                # 两者都落库
```

**紧急条目不参与 3 条限额**，因为它代表"要出事了"的级别，与"今天可以做点什么"的普通提示不是同一类信息。灾害性天气预警被"今天已经有三条了"挤掉，是产品不能接受的失败。但这带来一个风险：如果 `urgent` 判定宽松，页面会长期显示五六条紧急提示，3 条上限名存实亡且紧急标签贬值。因此下一小节的严格化是本节的前提，两者必须同时成立。

被截断的条目必须返回并落库，不能只在内存里丢弃。产品说明书 4.3.3 功能点 4 指出"连续多条提示未被勾选，说明提示内容与农户实际需求不匹配，需要复盘规则与文案"——复盘"哪些内容长期被压制"（11.3）需要历史数据，只在内存丢弃就无从统计。落库的 `suppressed=True` 条目不出现在接口返回的展示列表中。

### 四、urgent 双条件命中

**以水稻为例，`urgent` 要求同时满足"阈值严重偏离（非临界）"与"当前处于敏感生育期"。单条件只给 `notice`。**

```python
def is_urgent(rule_id: str, facts: EnvFacts, process_config: ProcessConfig) -> bool:
    """双条件判定：严重偏离 且 处于敏感生育期。缺一条即降为 notice。"""
    spec = process_config.urgency_specs.get(rule_id)
    if spec is None:
        return False                                    # 未配置的规则永不为 urgent
    severe = _deviation_ratio(facts, spec) >= spec.severe_ratio
    sensitive = _stage_in(facts, process_config, spec.sensitive_stages)
    return severe and sensitive
```

两条条件的分工是：第一条排除"刚刚越过阈值"的临界情况，第二条排除"当前阶段其实无所谓"的情况。以水稻高温为例，`BROADCAST_TEMP_HIGH` 是 35℃，若气温 35.2℃ 就报紧急，整个夏季首页会天天有紧急提示；"严重偏离"要求偏离幅度达到 `severe_ratio`（如超过阈值 15%，即 40.25℃ 以上）才算第一条命中。第二条 `sensitive_stages` 列出该流程的敏感生育期（水稻为抽穗扬花期、灌浆期），因为同样 40℃ 在分蘖期与抽穗扬花期造成的损失量级完全不同。两条都命中的情形是"40℃ 以上的高温恰逢抽穗扬花期"，这才是真正需要当天紧急处置的组合。

`urgency_specs` 放在流程配置里而非代码里，理由是这些数值需要农技人员按流程校准，且水稻与茶的阈值、敏感期名单各不相同。配置缺失时 `is_urgent` 返回 `False`——**未配置即为不紧急**，这是 fail-safe 方向：宁可漏报紧急（降为 notice 仍会展示），不可误报紧急（会绕过条数上限并让标签贬值）。

需要说明的是，`is_urgent` 的判定发生在规则层产出条目时（T3-05 的 `severity` 字段），本项只做校验与截断。放在本项的理由是这样可以让"紧急判定是否过松"成为一个单纯的测试对象：给一组 `facts` 与配置，断言 `severity` 的取值，不必构造完整的快照生成链路。

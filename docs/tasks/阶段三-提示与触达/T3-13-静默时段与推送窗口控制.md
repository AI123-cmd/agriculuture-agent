# T3-13 静默时段与推送窗口控制

## 这一项要做什么

实现主动推送的时段判断：22:00 至次日 06:00 为静默时段，不产生新的主动提醒；最佳触达窗口为早晨 6:30 至 7:30 与傍晚 18:00 至 19:00。农户主动查看不受时段限制，本项只约束主动推送。这里有一处与常规判断相反的取舍必须明确落地：**刻意允许晚间推送**——调研显示超过 40% 的线上农技服务发生在晚 8 点至早 8 点之间，晚间 20:00 至 22:00 是登录高峰，因此必须避开的是静默时段而不是晚间。若按"工作时间推送更礼貌"的常规判断把窗口收在白天，目标用户恰恰在工作时间之外才是可触达的，主动触达通道等于形同虚设。

## 前置依赖

- T3-12 的推送链路（本项的 `is_sendable` 是其第二道门槛，返回 `False` 时由 T3-12 记 `fail_reason="quiet_hours"`）。
- T3-01 的 `reach_record.fail_reason` 取值口径（`quiet_hours` 为本项产出）。
- T1-08 的时区配置（时段判断必须按农户所在时区而非服务器时区；本项目目标用户在中国，统一使用 `Asia/Shanghai`）。
- 外部环境：无（纯函数）。现有改造起点：无（全新，`app/broadcast/` 下无时段相关模块）。

## 实现要点

### 一、常量与 is_sendable

```python
QUIET_HOURS = (22, 6)          # 22:00 ~ 06:00 不产生新的主动提醒
BEST_WINDOWS = [(6, 30, 7, 30), (18, 0, 19, 0)]   # 最佳触达窗口


def is_sendable(now: datetime) -> bool:
    """触达时段判断：农户主动查看不受限，仅约束主动推送。"""
    if QUIET_HOURS[0] <= now.hour or now.hour < QUIET_HOURS[1]:
        return False
    return any(start_h <= now.hour < end_h for start_h, _, end_h, _ in BEST_WINDOWS)
```

`QUIET_HOURS = (22, 6)` 是一个跨零点的区间，判断条件 `now.hour >= 22 or now.hour < 6` 用 `or` 连接两段，不能写成 `22 <= now.hour < 6`（后者恒为假）。这个细节在全天任意小时都应被测试覆盖，尤其是 22 点整与 6 点整两个边界：22:00 属于静默（`>= 22` 命中），06:00 不属于静默（`< 6` 不成立）。

`BEST_WINDOWS` 每项是 `(起始时, 起始分, 结束时, 结束分)` 四元组，判断时只比较小时（`start_h <= now.hour < end_h`），因此 6:30 至 7:30 窗口在实现上覆盖 6:00 至 7:59。这是技术方案 11.9 原样给出的代码，本项不改。这个"粗略到小时"的判断是刻意的：精确到分钟会让"到期日早晨 6:30 至 7:30"这些边界在定时任务的调度抖动下出现大量"刚好错过窗口"的情况，而农户对早晨还是傍晚收到的感知远没有那么敏感。窗口的分钟信息保留在常量里，供 `next_window` 计算下一次窗口的准确时刻。

### 二、刻意允许晚间推送的理由

`BEST_WINDOWS` 中 18:00 至 19:00 是傍晚窗口，且晚间 19:00 至 22:00 虽然不在"最佳窗口"内，但也不在静默时段内——这意味着系统在 19:00 至 22:00 之间同样可以推送。这看起来与"最佳窗口"的说法矛盾，需要说清四层关系：

第一，静默时段只有 22:00 至 06:00，其余 16 小时都属于"可以推送"的时段。`BEST_WINDOWS` 是"优先选择"的窗口，不是"只允许"的窗口。定时任务优先在最佳窗口内扫描并发送，若因额度、接口重试等原因未能在窗口内完成，可以在窗口外的允许时段继续推送，不必等到次日。

第二，**刻意允许晚间推送的依据是产品说明书 4.6.2 的调研数据**：超过 40% 的线上农技服务发生在晚 8 点至早 8 点之间，晚间 20:00 至 22:00 是登录高峰。如果按常规把晚间排除在推送时段外，等于主动放弃了一天中用户活跃度最高的两小时。产品说明书明确把这条列为"注意到这里刻意允许晚间推送"并指出"这与白天工作时间推送更礼貌的常规判断相反"。

第三，**要避开的是静默时段而不是晚间**。22:00 之后农户开始休息，此时推送的服务通知可能震动手机、打断睡眠，且农户次日醒来时消息已被其他通知淹没。因此静默时段是硬约束（不产生新的主动提醒），而 19:00 至 22:00 是可用时段。

第四，清晨窗口 6:30 至 7:30 对应产品说明书 4.6.2 提到的"清晨有'起床第一件事看农情'的习惯性行为"。这与 T3-09 的回访时点设计呼应：到期回访的推送首选清晨窗口，让农户在一天开始时看到"上次做的事该检查效果了"。

### 三、静默时段与生成时机的关系

产品说明书 4.6.2 有一句关键限定："本模块只负责送达，不改变提示的生成时机。" 因此本项只作用于 T3-12 的推送链路，**不作用于 T3-08 的快照生成**。农户在 23:00 打开小程序点击「更新提示」，快照必须正常生成并展示——11.9 的注释明确"农户主动查看不受限，仅约束主动推送"。若把时段判断误加到生成链路上，夜间农户会看到"当前不可更新"，而夜间查看农情恰恰是 40% 那个数据所描述的高频场景。

22:00 至 06:00 之间产生的到期回访条目，其处理路径是：快照照常生成（农户主动看时能看到）、主动推送被延迟到次日 6:30 的窗口。这与 T3-12 的 `quiet_hours` 记录配合，使"被延迟"可统计。

### 四、next_window 与调度

```python
def next_window(now: datetime) -> datetime:
    """返回下一个可发送窗口的开始时刻，供延迟任务重新排队。"""
    for start_h, start_m, _, _ in BEST_WINDOWS:
        candidate = now.replace(hour=start_h, minute=start_m, second=0, microsecond=0)
        if candidate > now:
            return candidate
    tomorrow = (now + timedelta(days=1)).replace(hour=BEST_WINDOWS[0][0],
                                                 minute=BEST_WINDOWS[0][1],
                                                 second=0, microsecond=0)
    return tomorrow
```

`next_window` 供 T3-12 的延迟逻辑使用：处于静默时段的条目不被丢弃，而是记 `quiet_hours` 后重新排队到下一个窗口。ARQ 的定时任务用 `cron` 在窗口开始时触发密集扫描（如 6:30 至 7:30 之间每 5 分钟一次），窗口外只需低频扫描一次以处理重试，避免全天高频占用。

时区处理：`is_sendable` 接收的 `now` 必须已经是 `Asia/Shanghai` 时区的 aware datetime。若传入 naive datetime，`now.hour` 的取值依赖于运行环境，在容器中通常为 UTC，会导致静默时段的判断整体偏移 8 小时（实际是 14:00 至 22:00 静默）。因此 `is_sendable` 内部第一件事是断言 `now.tzinfo is not None` 并转换为配置时区，不合规直接抛错而不是默默按本地时区算。

### 五、与农户主动查看的边界

静默时段是全链路唯一区分"主动推送"与"农户主动查看"的地方，边界必须写清，否则会被误用为全局时段限制：

| 行为 | 是否受静默时段约束 | 理由 |
| --- | --- | --- |
| 主动推送（一次性订阅消息） | 是 | 服务通知会震动手机、打断休息 |
| 首页快照生成（点「更新提示」） | 否 | 农户主动查看不受限，11.9 明确 |
| 打开小程序查看已有提示 | 否 | 同上 |
| 勾选已执行 | 否 | 农户主动操作 |
| 回访任务的按时点登记 | 否 | 登记不是送达，延迟由推送侧承担 |

判定为静默时段的到期回访，其处理是"快照里照常出现、推送延迟到下一个窗口"，而不是"不生成这条回访"——这条区分是产品说明书 4.5.2 功能点 3 所说的双通道触达（首页加主动推送）能够成立的前提。若静默时段连带阻断回访的生成，夜间产生的到期任务会整条丢失，农户第二天既收不到推送也看不到首页提示。

`is_sendable` 因此只在 T3-12 的推送判定处被调用一次，不在任何生成、排序、展示路径中调用。这一条由验收标准里的 `grep` 检查固定，避免后续有人把它当作"全局时段开关"加在别处。

## 验收标准

- `pytest tests/broadcast/test_window.py` 全部通过，含边界用例：22:00 时 `is_sendable is False`、21:59 时 `False`（不在任何最佳窗口内）、06:00 时 `False`（不在窗口内但已出静默）、06:30 时 `True`、07:29 时 `True`、07:30 时 `False`、18:00 时 `True`、17:59 时 `False`、23:59 时 `False`。
- 晚间允许：断言 20:00 与 19:30 时 `is_sendable is False`（不在最佳窗口内），但 `QUIET_HOURS` 判断对这两点返回"非静默"，即它们属于"可用但非最佳"；断言 21:59 不被判为静默、22:00 被判为静默。
- 跨日：断言 00:30、03:00、05:59 均为 `False`（静默时段）；断言 06:30 为 `True`（跨日后的第一个窗口）。
- 时区：传入 naive datetime 时断言 `is_sendable` 抛错；传入 `UTC` 的 22:00（对应北京时间次日 06:00）断言其按 `Asia/Shanghai` 换算后判断正确。
- `next_window`：从 23:00 出发断言返回次日 06:30；从 07:00 出发断言返回当日 18:00；从 19:00 出发断言返回次日 06:30。
- 与生成链路隔离：断言 `generate_snapshot` 的调用链中不出现 `is_sendable`（`grep -rn "is_sendable" backend/app/broadcast/snapshot.py` 无输出），即夜间农户主动更新不受限。
- `ruff check`、`ruff format --check`、`mypy app` 三条命令均返回 0。

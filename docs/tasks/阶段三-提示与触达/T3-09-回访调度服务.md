# T3-09 回访调度服务

## 这一项要做什么

按流程取值为每一次处方卡登记回访任务，并在到期时触发首页提示与主动推送。七条流程的回访时点各不相同：水稻按生育期窗口、茶按安全间隔期结束加下一轮采摘、辣椒药后固定取中位 5 天、杂草药后 7 天与 15 天两次回访、养猪按法定时限链、通用按处方卡的 `followup_plan`。其中有一条特殊分支必须单独实现：**杂草流程药害纠纷的首次回访时点设为 T+0（立即），内容是现场固定动作清单而非效果询问**，因为药害鉴定要求保留典型性状，错过表现期将无法鉴别起因。现有实现没有任何回访表与调度逻辑，本项从零建立，同时为 T3-04 提供 `list_due` 的数据来源。

## 实现要点

### 一、七条流程的回访时点取值

| 流程 | 回访时点 | 实现方式 |
| --- | --- | --- |
| 水稻 | 生育期窗口（两次施药之间） | 由 `timing_rules` 推算，需农事历支持 |
| 茶 | 安全间隔期结束 + 下一轮采摘计划 | 由处方卡 `safety_interval_days` 与 `next_pick_date` 计算 |
| 辣椒 | 药后 3~7 天 | 固定间隔，取中位 5 天 |
| 杂草 | 药后 7~15 天（含后茬观察） | 两次回访：7 天查药效，15 天查后茬 |
| 养猪 | 处置时限与检疫节点 | 按法定时限链 |
| 通用 | 观察建议指定时点 | 由处方卡 `followup_plan` 给出 |

四条流程的取值方式不同，但都从流程配置取，不在代码里写死天数。水稻的"生育期窗口"最复杂：它不是一个固定天数，而是"下一次施药的窗口开始前"。实现为从农事历取当前生育期的下一个节点日期，`due_at` 设为该节点日期减一天（在动作到来前提醒）。这也是为什么水稻需要农事历支持——农事历不可用时水稻回访回落到通用策略（按药后 7 天）。

辣椒取中位 5 天而不是区间端点，是为了让农户有一个明确的可期待时点，而不是"3 到 7 天之间某天"。区间端点会造成两个问题：前端无法显示"还有几天回访"、同一批农户的回访会分散在五天内增加推送管理的复杂度。中位值牺牲了对个别情况的适配，换来可预期性。

茶的 `safety_interval_days + next_pick_date` 是取两者中较晚的那个：安全间隔期未过当然不能采摘，但如果下一轮采摘计划本来就晚于安全间隔期结束，回访应跟着采摘计划走，因为那时农户才有"要不要采"的实际决策。这两个日期都在处方卡上有值，因此茶流程的回访不依赖农事历。

### 二、杂草药害分支的 T+0 立即回访

```python
def build_followup_plan(process_id: ProcessId, prescription: Prescription,
                        branch: str | None) -> FollowupPlan:
    """回访计划：按流程取值，药害分支立即触发。"""
    if branch == "herbicide_damage":
        return FollowupPlan(tasks=[
            FollowupTask(due_offset_days=0, kind="preserve_scene",
                         content_rule="weed.damage_evidence_checklist"),
        ])
    policy = load_process_config(process_id).followup_policy
    return FollowupPlan(tasks=policy.build_tasks(prescription))
```

产品说明书 4.2.3 功能点 7 指出"杂草防治流程还有一类特殊回访：药害纠纷的**保护现场**提示，因为药害鉴定要求保留典型性状，错过表现期将无法鉴别起因"。因此这个分支的 `due_offset_days=0`、`kind="preserve_scene"`、`content_rule="weed.damage_evidence_checklist"`。

**这是现场固定动作清单而不是效果询问**。普通回访是"上次建议的做法效果如何"，药害分支是"现在就去做这几件事"：不要拔除病株、不要翻耕、拍照记录受害分布与边界、留存所用除草剂包装与购买凭证、记录施药日期与用量。二者在语义上完全不同——前者是数据采集，后者是证据固定，且后者必须在数小时内完成。因此 `kind` 用 `preserve_scene` 而不是 `effect_check`，文案层（T3-07）据此取不同的模板，T3-04 据此把 `severity` 判为 `urgent`。

`branch == "herbicide_damage"` 的判断来自 T2-14 分诊与 T2-19 判定给出的分支标识，它优先于流程配置的 `followup_policy`。药害分支下不再叠加常规回访：农户已经进入纠纷处理路径，此时再给他"7 天后看看药效如何"会造成"你既让我保护现场又让我观察效果"的矛盾。

### 三、养猪流程的法定时限链

养猪的回访不是"效果检查"而是"义务节点"，时点来自法定时限链（如隔离观察期、检疫申报节点、疑似疫病报告后的跟进）。实现为从 `pig.yaml` 的 `followup_policy.triggers` 读取，每条触发条件带 `after_action` 与 `after_days`，`kind` 取值包含 `risk_check`（法定时限节点）与 `quarantine`（隔离期节点）。这些时点的具体天数属农技与法规内容，需人工确认（全局约定第八节），执行者按给定数据录入。

`kind="quarantine"` 的任务在其文案里必须明确"这是法定义务提示"而非"建议"，且不得提供任何兽药用法用量替代方案（产品说明书 6.4 流程红线）。这类约束由 T3-07 的模板与闸门的 `R-REDLINE` 双重把关，本项只负责按时点登记任务。

### 四、登记与到期扫描

```python
async def register_from_prescription(db: AsyncSession, card: PrescriptionCard) -> list[FollowupTask]:
    """处方落库后登记回访任务；本函数是 prescription.created 的消费者。"""
    plan = card.followup_plan                     # 已由 T2-21 产出并随处方落库
    tasks = []
    for t in plan.tasks:
        tasks.append(FollowupTask(
            id=new_id("fu"), user_id=card.user_id, consultation_id=card.consultation_id,
            prescription_card_id=card.id, kind=t.kind,
            due_at=_resolve_due_at(t, card), status="pending"))
    return await followup_repo.bulk_save(db, tasks)
```

`due_at` 用绝对时间戳存，而 `FollowupTask` 契约里是 `due_offset_days`。原因是扫描到期任务是按时间范围查询（`due_at <= now`），相对天数无法直接查询；转换在登记时一次完成，之后的扫描不需要再算基准日。`_resolve_due_at` 对 `window_based=True` 的任务还要叠加农事历窗口计算（水稻），对 `safety_interval_days` 类任务叠加处方卡上的日期（茶）。

首次回访立即执行的任务（`due_offset_days=0`）在登记后必须**立即触发一次 `followup.due` 事件**，不能等次日定时扫描。药害分支的 T+0 提醒若延迟数小时到下一个扫描周期，现场可能已被农户处理掉（拔除、翻耕），提示的价值归零。这条要在代码里显式处理：登记循环结束时检查是否有 `due_at <= now` 的任务，有则直接投递事件。

`followup.due` 事件的消费者有两个（T3-08 快照服务把它变成首页提示条目，T3-12 触达服务尝试推送），两者互不阻塞：推送失败不影响首页提示，这是产品说明书 6.3 兜底五的要求，也是事件驱动在本场景的价值。

# T3-12 一次性订阅消息发送链路

## 这一项要做什么

打通一次性订阅消息的发送链路：定时任务扫描到期快照条目 → 检查额度与静默时段 → 扣减额度 → 调用微信接口发送 → 记录送达结果。本项的核心是一条顺序约束：**推送内容必须来自已落库的快照条目**，实现方式是 `reach_record.prompt_item_id` 外键指向 `prompt_item.id`，从数据层保证；推送服务不接受"直接传入文案"的调用方式，只能通过 `prompt_item_id` 取内容。这条约束落实产品说明书 4.3.3 功能点 7 与 8.7 的要求——"保证收到消息打开小程序看到的是同一条内容，不会出现对不上的情况"。

## 实现要点

### 一、顺序约束的实现

**推送内容必须来自已落库的快照。** 实现上通过数据约束保证：`reach_record.snapshot_item_id` 是外键，指向 `prompt_item` 表。推送服务不接受"直接传入文案"的调用方式，只能通过 `snapshot_item_id` 取内容。

```python
async def notify_item(db: AsyncSession, prompt_item_id: str) -> ReachRecord:
    """推送一条提示条目：内容只能来自 prompt_item，不接受直接传文案。"""
    item = await snapshot_repo.get_item(prompt_item_id)   # 唯一的取内容路径
    if item is None:
        raise NotFoundError(f"提示条目不存在: {prompt_item_id}")
    ...
```

函数签名里刻意没有 `text` 参数，这是约束的第一层。第二层是外键：`reach_record.prompt_item_id` 是 `nullable=False` 的外键，任何"凭空构造一条推送记录"的尝试都会在写入时失败。两层叠加后，"推送与首页显示不一致"这个故障在结构上不可能发生——推送的内容是从农户能在首页看到的那一行数据里读出来的同一份字节。

这与技术方案 6.6 的"触达必须与生成解耦"配合：`followup.due` 与 `snapshot.requested` 事件在快照落库的同一事务内写入发件箱，消费者读到事件时快照必定已提交，因此推送不会读到半个快照。顺序上不可能违反，而非靠代码约定遵守。

**为什么不用"代码约定 + 抽查"**：推送与展示用的是同一份内容这件事，一旦被某次重构打破，表现是农户收到"该灌水了"而首页显示"注意防冻"，这种不一致会直接摧毁信任，但代码审查很难发现——两边的文案各自都对，只是不是同一条。外键把这个不变量交给数据库强制，任何违规都在写入时暴露。

### 二、完整链路与顺序

```python
async def deliver_due_items(db: AsyncSession, limit: int = 200) -> dict[str, int]:
    """扫描待推送条目并逐条尝试送达，返回各结果的计数。"""
    stats = {"delivered": 0, "skipped": 0, "failed": 0}
    now = datetime.now(TZ)
    candidates = await reach_repo.list_unpushed_due(db, now, limit)
    for item in candidates:
        if not is_sendable(now):
            await _record(db, item, status="failed", fail_reason="quiet_hours")
            stats["skipped"] += 1
            continue                                   # 静默时段：记录后跳过，可重试
        if not await quota_service.try_consume(db, item.user_id):
            await _record(db, item, status="failed", fail_reason="quota_exhausted")
            stats["failed"] += 1
            continue                                   # 无额度：不调用推送接口
        try:
            await _send_via_wechat(db, item)
            await _record(db, item, status="delivered")
            await emit(db, event_type="subscription.consumed", ...)
            stats["delivered"] += 1
        except WechatApiError as exc:
            await quota_service.refund(db, item.user_id)      # 退还授权机会
            await _record(db, item, status="failed", fail_reason="api_error", note=str(exc))
            await emit(db, event_type="reach.failed", ...)
            stats["failed"] += 1
    return stats
```

四道门槛的顺序是刻意的：**先判时段、再判额度、再扣额度、最后调接口**。时段判断在前是因为它最便宜且最常见（一天中有 8 小时处于静默时段），能过滤掉大量条目；额度判断在前是因为它决定是否调用外部接口，拦截在自己的系统里成本最低；扣额度在调用之前是因为"发送成功才消费"的准确落地方式是"先占用、失败再退还"，若反过来（先发送再扣额度）会出现发送成功但扣额度失败的情形，透支无法追回。

`quota_exhausted` 与 `no_grant` 两类失败的区别在 T3-14 说明：前者是有过授权但用完了，后者是从未授权。本项在 `try_consume` 返回 `False` 时需再查一次 `granted_total == 0` 以区分这两类，因为农户看到的界面说明不同（"授权已用完，本次提醒只在首页保留" vs "授权一下，明天提醒你"）。

### 三、静默时段只延迟不失败

`fail_reason="quiet_hours"` 的记录语义是"因时段被延迟"，不是真实失败。这一类的处理与前三类不同：不退还额度（额度未被消费，因为还没到调用接口那一步）、不触发 `reach.failed` 指标事件、条目保持"待推送"状态在下一个窗口重试。T3-13 会给出 `is_sendable` 的实现与窗口定义，本项只负责在判断为不可发送时记录并跳过。

**为什么单独记一类而不静默跳过**：如果静默时段的条目被静默跳过，运维会看到"送达率 100%"的假象，而实际上有相当比例的消息被延迟到次日，农户的感知是"有时收到有时收不到"。记录 `quiet_hours` 使"被延迟"可被统计，从而回答"有多少消息因为时段约束没能及时送达"这个问题。

### 四、失败不得影响已有功能

产品说明书 6.3 兜底五明确"推送失败不能影响任何已有功能——提示照常生成、照常在本地下展示、执行回执照常记录，只是没有被主动送达"。实现上有三条保障：其一，`deliver_due_items` 的整个循环包在"逐条 try"内，单条失败不影响后续条目；其二，本项不修改任何 `prompt_item` 的状态（不因为推送失败就把提示标为不可见）；其三，本项在 worker 中独立运行，其异常不会冒泡到 API 进程。

`deliver_due_items` 返回统计而不抛异常。定时任务的失败吞掉真实错误是常见反模式，因此所有异常都在逐条级别被捕获并落到 `reach_record`，函数自身只需处理数据库连接失败这类全局性错误。

### 五、微信接口调用

`send_subscribe_message` 处理三类事项：`access_token` 缓存（有效期 7200 秒，缓存在 Redis，避免每次推送都换取）、错误码解析（`40003` 无效 openid、`43101` 用户拒绝接收、`45011` 频率限制等分别映射到具体异常）、以及"用户拒绝接收"的特殊处理。第三项要注意：`43101` 表示农户在授权后又关闭了订阅，此时不能退还额度当作接口错误，而应把该农户的 `remaining` 归零并记 `no_grant`，因为系统持有的授权已经失效，继续尝试只会反复失败。

## 验收标准

- `pytest tests/broadcast/test_notifier.py` 全部通过，含：构造一条已落库的 `prompt_item`，断言 `notify_item` 产出的 `reach_record.prompt_item_id` 等于该条目 id 且 `status="delivered"`。
- 顺序约束：`inspect.signature(notify_item)` 不含 `text` 参数；构造一条 `prompt_item_id` 不存在于 `prompt_item` 表的 `reach_record` 插入，断言抛 `ForeignKeyViolation`。
- 门槛顺序：`remaining=0` 时断言不调用微信接口（mock 断言零次调用）且 `reach_record.fail_reason="quota_exhausted"`；处于静默时段时断言不调用微信接口、`fail_reason="quiet_hours"`、额度未变、无 `reach.failed` 事件。
- 失败退还：让微信接口抛 `WechatApiError`，断言 `remaining` 恢复到调用前的值、`fail_reason="api_error"`、产出 `reach.failed` 事件。
- 失败隔离：让第 2 条推送抛异常，断言第 1、3 条仍正常送达，`deliver_due_items` 返回的 `failed` 计数为 1；断言函数本身不抛异常。
- 用户拒绝：mock 微信返回 `43101`，断言该用户 `remaining` 归零且 `fail_reason` 为 `no_grant`。
- `grep -n "content=\|text=" backend/app/broadcast/notifier.py` 不含向微信接口传入"来自函数参数"的文案（文案只能取自 `item`）；`ruff check`、`ruff format --check`、`mypy app` 三条命令均返回 0。

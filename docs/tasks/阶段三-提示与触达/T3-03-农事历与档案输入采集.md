# T3-03 农事历与档案输入采集

## 这一项要做什么

实现第二类输入"档案与农事历"的采集：依据农户档案中的流程类型、起始时间、地区推算当前生育阶段，再据此检索农事历节点生成管理类提示。两条流程不参与此路——杂草防治没有生育期概念，通用农业流程无法确定生育期模型，两者只保留环境风险类与回访类提示。现有实现 `app/broadcast/calendar.py` 把农事历写在代码里的字典（`_CALENDAR`，只覆盖水稻、小麦、玉米三种作物），既无法表达七条流程，也违反"流程配置是唯一事实来源"。本项把农事历来源迁移到知识库与流程配置，代码只保留筛选逻辑。

## 前置依赖

- T3-01 的 `PromptItem.source_kind` 取值口径（`calendar`），本项产出的条目必须标为该值。
- T2-04 的七份流程 YAML：`calendar_source` 字段（水稻 `rice.growth_stage`、茶 `tea.picking_round`、辣椒 `chili.growth_stage`、油菜 `rapeseed.growth_stage`，杂草与养猪与通用为 `null`）与 `timing_rules` 字段（时机判据与提示文案）。
- T2-03 的 `load_process_config`；T2-49 的知识库混合检索与 T2-50 的地区回退匹配（农事历条目从知识库取，不写死在代码里）；T2-01 的 `ProcessId` 枚举。
- 外部环境：知识库已导入一期五条流程的农时节点条目。现有改造起点：`app/broadcast/calendar.py`、`app/broadcast/generator.py`（其 `phase_tasks` 调用点）、`app/tools/profile.py`。

## 实现要点

### 一、两条流程不参与农事历

```python
NO_CALENDAR_PROCESSES = {ProcessId.WEED, ProcessId.GENERAL}


async def collect_calendar_tasks(profile: FarmerProfile, today: date) -> list[RuleResult]:
    """农事历节点提示：杂草防治与通用农业不生成此类提示。"""
    tasks = []
    for entry in profile.entries:
        if entry.process_id in NO_CALENDAR_PROCESSES:
            continue  # 产品说明书 4.3.2：无生育期概念，不生成农时节点类提示
        stage = resolve_stage(entry, today)      # 由流程类型+起始时间+地区推算
        tasks += query_calendar(entry.process_id, stage, profile.region, today)
    return tasks
```

排除用 `continue` 而不是在循环外过滤：一个农户可能同时有多条经营条目（如既有水稻田又有茶园），其中杂草类问诊不绑定条目（12.2 指出杂草不进 `farm_entry` 的主作物位），但通用农业条目可能存在于档案中，必须在逐条目循环内排除，否则一条通用条目会把整户的农事历提示都带偏。`NO_CALENDAR_PROCESSES` 定义在模块顶层而非函数内，因为它是可被测试直接引用的常量，也是产品说明书 4.3.2 那句话的代码形式——写在函数里会让"哪两条流程不参与"变得不可 grep。

### 二、阶段推算的三类来源

`resolve_stage(entry, today)` 的输入来自流程配置的 `calendar_source`，取值有三种形态：

| `calendar_source` 形态 | 流程 | 推算方式 |
| --- | --- | --- |
| `rice.growth_stage` | 水稻、辣椒、油菜 | 由 `entry.start_date` 与品种的生育期天数区间推算当前阶段 |
| `tea.picking_round` | 茶 | 按采摘轮次而非生育期，由上次采摘日与采摘间隔推算当前轮次 |
| `null` | 杂草、养猪、通用 | 不推算（前者被 `NO_CALENDAR_PROCESSES` 排除，养猪与通用由本函数返回 `None`） |

这里需要一条硬约束：**`resolve_stage` 返回 `None` 时 `query_calendar` 必须直接返回空列表**，不允许退化成"用当前月份猜一个阶段"。生育期是靠不住的输入，用月份反推会在气候异常年份产出明显错误的农时提示，例如暖冬年份水稻实际处于分蘖期而按月份推算出"抽穗期施穗肥"，这类错误比没有提示危害更大。

养殖流程（养猪）没有生育期但有法定时限链，其农时节点由回访链路（T3-09）承担，不在本项范围。这个分界要写进代码注释，避免后续有人为了"养猪也应该有历"而在本项里加分支。

### 三、地区回退与命中级标注

`query_calendar` 走 T2-49 的混合检索与 T2-50 的地区回退匹配，命中顺序为县级 → 市级 → 省级 → 全国通用。每次回退都要在结果里记下实际命中的级别（全局约定第六节），供界面标注"当前按 XX 市通用农时提示"。这个级别同时写入 `PromptItem.facts_provenance`，来源标识形如 `knowledge:K-2013:hit_level:city`，使"这条提示是按哪一级给的"可被追溯。

农事历知识库缺失时的行为由产品说明书 4.2.4 规定：回退通用知识并标注不确定。实现为 `query_calendar` 在县级到省级全部未命中时返回带 `uncertain=True` 标记的通用条目，而不是返回空——但通用农业流程本身不查农事历，因此这个回退只对其他六条流程生效。两种情况必须区分：通用农业流程（`NO_CALENDAR_PROCESSES` 内）返回空列表、其他流程查不到具体条目返回标注不确定的通用条目。

### 四、timing_rules 的接入

流程配置的 `timing_rules` 给出季节或天气触发条件与提示文案（如茶的 `tea_pick_window` 在春茶采摘期触发、`tea_rain_alert` 在连续降雨时触发）。本项把它们一并纳入农事历输入：按 `id` 生成 `rule_id`，按 `prompt` 生成 `fact`，文案模板从流程配置取而非代码拼接。这样新增一条时令提示的改动量是"在 YAML 里加一行"，不触碰本项代码。

`timing_rules` 里引用天气条件的条目（如 `when: {weather: continuous_rain}`）要与 T3-02 联动：当 `EnvFacts.source == "none"` 时，任何 `when` 里含天气或环境条件的 `timing_rule` 都必须被跳过，理由与 11.2 一致——天气数据不可用时不用推测值生成。判定方式是检查 `timing_rule.when` 的键是否落在环境指标集合内，而不是逐条硬编码条件名。

### 五、档案读取与数据访问约束

本项的输入是 `FarmerProfile` 与它的经营条目列表，读取路径必须走 T1-05 的 `OwnedRepository`，`user_id` 由调用方（T3-08）传入且不可为空。`collect_calendar_tasks` 的签名里带 `profile` 对象而不是 `db`，这是刻意的：本项是纯筛选逻辑，把数据库访问前移到调用方，使本项可以直接用构造的 `FarmerProfile` 做单测，不需要起数据库。这条与全局约定 L2 / L4 的方向一致——领域逻辑不耦合 ORM。

需要区分三种"档案不完整"的表现，它们在界面上引导不同：

| 表现 | 判据 | 处理 |
| --- | --- | --- |
| 无经营条目 | `profile.entries` 为空 | 返回空列表，引导农户去补档案 |
| 有条目但缺 `start_date` | 条目存在但起始时间缺失 | 该条目不产出农事历提示，追问补时间 |
| 有条目但缺地区 | 县级到省级均无法匹配 | 回退全国通用条目并标注不确定 |

三种情况的共同点是都**不阻断流程**：农事历类提示产出为空时，环境风险类与回访类提示照常生成（T3-08 的链路不会因为某一路输入为空而失败）。这与产品说明书 4.2.4 表格中"农事历知识库缺失时回退通用知识，标注不确定；通用农业流程不查农事历"的口径一致——档案完整度只影响提示质量，不影响提示能否生成。

### 六、多经营条目的处理

一个农户可能同时有多条经营条目（多块地、多种作物），本项的输出是**所有条目产出的农事历提示的并集**，每条提示携带所属条目的标识（写入 `PromptItem.facts_provenance` 的 `farm_entry_id` 键与 `callout` 字段的对象名）。这样做的原因有两个：其一，首页提示是"今天该做什么"的汇总视图，农户不希望在首页再选一次"看哪块地"，那是问诊入口的事；其二，条数控制的截断（T3-06）需要在全体条目上统一进行，若按条目分别截断，三块地各展示三条会得到九条提示，直接破坏每日上限。

多条目也带来了"callout 必须带对象名"的硬要求。单块地的农户看到"土壤墒情不足"能理解，多块地的农户不能——他需要看到"东边水田：土壤墒情不足"。因此农事历产出条目的 `callout` 一律取条目的显示名而非流程名，这条约束由 T3-05 的 `validate_item` 兜底检查非空，但取值是否正确只有本项能保证。

# T3-14 触达记录与失败原因分类

## 这一项要做什么

建立 `reach_record` 触达记录表与失败原因的四类区分：`no_grant`（从未授权）、`quota_exhausted`（授权已用完）、`api_error`（接口失败）、`quiet_hours`（因时段被延迟）。前三类直接对应产品说明书 9.4 的"区分未授权、额度耗尽、推送失败三类情况，用于发现触达断点"，第四类是本项新增的，用途是**区分"因时段被延迟"（可重试）与真实失败**——若不区分，"静默时段被跳过的消息"会与"接口报错的消息"混在同一个失败计数里，导致送达率指标失真，运维会去查一个根本不存在的接口故障。本项同时产出触达率与送达率的统计口径，供 T6-09 的线上指标采集。

## 实现要点

### 一、reach_record 表与四类 fail_reason

```python
class ReachRecord(Base, OwnedMixin):
    __tablename__ = "reach_record"
    id = mapped_column(String(36), primary_key=True)
    user_id = mapped_column(String(36), nullable=False, index=True)
    prompt_item_id = mapped_column(String(36), ForeignKey("prompt_item.id"), nullable=False)
    channel = mapped_column(String(20))                   # subscribe_once / in_app
    status = mapped_column(String(20))                    # delivered / failed
    fail_reason = mapped_column(String(30))               # no_grant / quota_exhausted / api_error / quiet_hours
    attempted_at = mapped_column(DateTime(timezone=True), nullable=False)
    delivered_at = mapped_column(DateTime(timezone=True))
```

`prompt_item_id` 外键的强制意义：产品说明书 4.3.3 功能点 7 要求推送内容必须是快照里已存在的条目。用外键从数据层保证这一点，比在代码里约定更可靠。

`channel` 用 `subscribe_once` / `in_app` 两值，第二值用于记录"仅在小程序内提示位展示"的条目（额度耗尽时的降级路径，4.3.3 功能点 7 要求标记为"仅在首页保留"）。把 `in_app` 也记一条的理由是农户侧看到的行为与"推送成功"不同但都属于"这条提示被送达过"，分开记使"主动触达通道的实际覆盖"可被准确统计，而不是把仅本地展示也算进送达率。

四类的语义与判据：

| `fail_reason` | 含义 | 判据 | 可否重试 | 是否退还额度 |
| --- | --- | --- | --- | --- |
| `no_grant` | 从未授权 | `granted_total == 0` 或微信返回 `43101` | 否（需农户重新授权） | 不涉及 |
| `quota_exhausted` | 授权已用完 | `try_consume` 返回 `False` 且 `granted_total > 0` | 否（需新授权） | 不涉及 |
| `api_error` | 接口失败 | 微信接口抛异常或返回非授权类错误码 | 是（下次扫描重试） | 是 |
| `quiet_hours` | 因时段被延迟 | `is_sendable(now) is False` | 是（下个窗口重试） | 是（未消费） |

`no_grant` 与 `quota_exhausted` 必须区分，因为农户看到的界面说明不同（T3-12 已说明）：前者是"授权一下，明天提醒你"（还有争取空间），后者是"授权已用完，本次提醒只在首页保留"（需要新的授权动作）。把两者混为一类会导致要么对着已用尽额度的农户反复索要授权，要么对从未授权的农户显示"已用完"这个不准确的说明。

### 二、classify_fail 与记录

```python
def classify_fail(*, sendable: bool, consumed: bool, granted_total: int,
                  exc: Exception | None) -> str | None:
    """失败分类：按判据优先级返回四类之一，成功返回 None。"""
    if not sendable:
        return "quiet_hours"                      # 最早判定，优先级最高
    if not consumed:
        return "no_grant" if granted_total == 0 else "quota_exhausted"
    if exc is not None:
        return "api_error"
    return None
```

```python
async def record_attempt(db: AsyncSession, *, user_id: str, prompt_item_id: str,
                         channel: str, fail_reason: str | None,
                         note: str | None = None) -> ReachRecord:
    """记录一次触达尝试：成功与失败都必须落库，不允许静默丢弃。"""
    now = datetime.now(TZ)
    record = ReachRecord(
        id=new_id("rr"), user_id=user_id, prompt_item_id=prompt_item_id,
        channel=channel, status="failed" if fail_reason else "delivered",
        fail_reason=fail_reason, attempted_at=now,
        delivered_at=None if fail_reason else now)
    await reach_repo.save(db, record)
    return record
```

`notify_item` 与 `deliver_due_items` 的每条路径都必须以"记录"收尾，包括成功。这是"失败不得静默丢弃"（11.7 第三条）的落地方式：不允许出现 `except: pass` 或"失败时只打日志不落库"的写法。`note` 字段（本项在 12.5 基础上按需补充于 `reach_record` 的可选列或写入 `fail_reason` 之外的附加 JSON）保留微信返回的错误码原文，供排查。

`status` 与 `fail_reason` 的组合关系由一条约束固定：`status="delivered"` 时 `fail_reason` 必为 `NULL`，`status="failed"` 时 `fail_reason` 必非空。这条用模型校验器实现，避免出现"失败了但没写原因"的记录——那种记录在统计时无法归入任何一类，等于静默丢弃。

### 三、统计口径

```python
async def reach_metrics(db: AsyncSession, since: date) -> dict[str, float]:
    """触达指标：送达率、失败构成、静默延迟占比。"""
    delivered = await reach_repo.count_by_status(db, "delivered", since)
    failed = await reach_repo.count_by_fail_reason(db, since)
    total = delivered + sum(failed.values())
    return {
        "delivered_rate": delivered / total if total else 0.0,
        "no_grant_rate": failed.get("no_grant", 0) / total if total else 0.0,
        "quota_exhausted_rate": failed.get("quota_exhausted", 0) / total if total else 0.0,
        "api_error_rate": failed.get("api_error", 0) / total if total else 0.0,
        "quiet_hours_rate": failed.get("quiet_hours", 0) / total if total else 0.0,
    }
```

**`quiet_hours` 单独统计且不计入"系统故障"类指标**，这是本项相对 9.4 的三类划分增加第四类的全部理由。若把静默延迟混入失败率：其一，失败率会比真实值高出一大截（因为一天有 8 小时处于静默，晚间产生的到期回访都会被计入）；其二，值班人员会被引去排查接口，而实际上接口没有任何问题；其三，告警阈值无法设定——一个健康的系统在静默时段的失败率天然就是高的。

技术方案 14.3 定义的"一次性订阅达成率 = `reach_record` 中已推送的唤醒占比"在此实现为 `delivered_rate`，但要注意它的分母。若分母包含 `quiet_hours` 记录，达成率会被静默时段的延迟拉低，指标失去意义。因此 `delivered_rate` 的分母用"已尝试且未被时段延迟"的条目数（即 `total - quiet_hours`），静默延迟单列为 `quiet_hours_rate`。这条口径要写进代码注释与 T6-09 的指标定义，避免两处算法不一致。

### 四、与兜底五的关系

产品说明书 6.3 兜底五要求"推送失败不能影响任何已有功能"。本项作为记录方，需额外保证一件事：**记录写入自身的失败不能影响推送链路**。实现为 `record_attempt` 的调用包在推送主逻辑的外层 try 中——即便数据库写入失败（连接抖动），推送流程也应正常结束并返回统计，最坏后果是这一条触达记录丢失，而不会让整批推送中断。这与"不允许静默丢弃业务失败"不矛盾：前者是"记录写入失败"这个运维问题，后者是"推送失败未被记录"这个业务问题，优先级不同。

同时本项明确：`reach_record` 不参与任何农户可见的判定。额度状态由 `subscription_quota` 决定（T3-11），提示条目是否展示由 `prompt_item` 决定（T3-08）。触达记录是纯观测数据，这保证推送链路出问题时，首页提示与执行回执完全不受影响。

## 验收标准

- `pytest tests/broadcast/test_reach_log.py` 全部通过，含：`classify_fail(sendable=False, ...)` 返回 `"quiet_hours"`；`classify_fail(sendable=True, consumed=False, granted_total=0)` 返回 `"no_grant"`；`granted_total=2` 时返回 `"quota_exhausted"`；`consumed=True` 且带异常返回 `"api_error"`；全部成功时返回 `None`。
- 记录完整性：断言 `status="delivered"` 的记录 `fail_reason is None` 且 `delivered_at` 非空；构造 `status="failed"` 但 `fail_reason=None` 的记录，断言模型校验抛错；断言 `record_attempt` 在成功与四类失败下均产生一条记录。
- 不可静默丢弃：让推送主流程抛非预期异常，断言该条目仍有 `reach_record`（`fail_reason="api_error"`）而非无记录。
- 指标口径：构造 6 条 `delivered`、2 条 `no_grant`、1 条 `quota_exhausted`、1 条 `api_error`、4 条 `quiet_hours`，断言 `delivered_rate` 的分母为 10（不含 `quiet_hours`）且值为 0.6、`quiet_hours_rate` 为 0.4（分母为 14）。
- 记录失败不影响推送：让 `reach_repo.save` 抛异常，断言 `deliver_due_items` 仍返回正常统计且不抛异常。

# T2-17 追问候选池筛选器

## 这一项要做什么

在 `app/agent/agents/candidate_pool.py` 中实现追问候选池的筛选器，把流程必问清单经过三步筛选压到最多六个候选方向，交给问诊智能体生成问题文本。它是"跳过已知项"与"不漏必问项"两个要求的实现者，也是"凡是能被规则判定的，不交给模型"这条原则最典型的落地。

这是一个**纯代码模块，模型不参与**。筛选的每一步都是集合运算与排序，输入是流程配置与黑板状态，输出是一份确定性的候选列表。同一个状态无论调用多少次都得到同一个候选池，这是路由与问诊可重放的前提。

## 前置依赖

- 依赖 T2-03：必须已提供 `get_process_config` 与流程配置加载
- 依赖 T2-08：必须已提供 `ConsultationState`、`SlotValue`、`slot_summary`
- 依赖 T2-02：必须已提供 `SlotSpec`（含 `source_hint`、`ask_order`、`required`、`options`）
- 依赖 T2-15：必须已提供 `ObservationResult`，环境读数与观察事实用于第二步的剔除
- 本项不依赖模型网关，也不依赖数据库，可完全脱离外部环境单测

## 实现要点

### 返回结构

```python
class CandidateSlot(BaseModel):
    """候选池中的一项。含排序分与入选理由，便于线上排查。"""
    model_config = ConfigDict(extra="forbid", frozen=True)

    slot_key: str
    display_label: str
    group: str
    required: bool
    options: list[str] | None = None
    relevant_score: int = 0
    reason: Literal["must_ask", "offline_enhance", "relevant_followup"] = "must_ask"


class CandidatePool(BaseModel):
    """筛选结果。keys 是给问诊智能体校验用的白名单。"""
    model_config = ConfigDict(extra="forbid", frozen=True)

    process_id: ProcessId
    candidates: tuple[CandidateSlot, ...]
    excluded: dict[str, str] = {}       # slot_key → 剔除原因，供排查
    top_k: int = 6

    @property
    def keys(self) -> set[str]:
        return {c.slot_key for c in self.candidates}
```

`excluded` 记录每个被剔除的槽位及其原因，是排查"为什么没问某个应该问的槽位"的主要依据。没有它，筛选器一旦有 bug，表现只是"某类问题很少被问"，很难定位。`keys` 属性供 T2-16 的问诊智能体做输出校验，二者共用同一结构避免口径不一致。

### 三步筛选的入口

```python
def select_candidate_slots(config: ProcessConfig, state: ConsultationState, *,
                           observations: ObservationResult | None = None,
                           top_k: int = 6) -> CandidatePool:
    """三步筛选：剔除已填、剔除可自动读、按相关性排序取 top-k。"""
    excluded: dict[str, str] = {}
    step1 = _drop_filled(config, state, excluded)
    step2 = _drop_auto_readable(step1, state, observations, excluded)
    step3 = _rank_by_relevance(step2, state, config)
    return CandidatePool(process_id=config.process_id,
                         candidates=tuple(step3[:top_k]), excluded=excluded, top_k=top_k)
```

三步严格串行，顺序不能调换：先做集合减法（去掉不需要的），再做排序（决定剩下哪个优先）。若先排序再剔除，排序时还得为会被剔除的项计算相关性，属于无效计算。

### 第一步：剔除已 filled 槽位

```python
def _drop_filled(config: ProcessConfig, state: ConsultationState,
                 excluded: dict[str, str]) -> list[SlotSpec]:
    """剔除 status 为 filled 或 unknown 的槽位。"""
    out: list[SlotSpec] = []
    slots = state.get("slots") or {}
    for spec in config.required_slots:
        slot = slots.get(spec.key)
        if slot is None or slot.status == "missing":
            out.append(spec)
        elif slot.status == "filled":
            excluded[spec.key] = "已确认"
        else:
            excluded[spec.key] = "农户已表示不清楚"
    return out
```

`filled` 与 `unknown` 都要剔除。`unknown` 必须剔除是"不反复逼问"的直接实现：农户答不出就是合法答案，系统据此降低确定性表述，而不是换个措辞再问一遍。非必问槽位在第一步也参与筛选，只是排序时权重低。

### 第二步：剔除可由档案或环境直接读取的项

```python
AUTO_SOURCES = {"profile", "sensor", "weather"}


def _drop_auto_readable(specs: list[SlotSpec], state: ConsultationState,
                        observations: ObservationResult | None,
                        excluded: dict[str, str]) -> list[SlotSpec]:
    """剔除可由档案/环境直接读取的项，以及超限的槽位。"""
    auto_filled = _collect_auto_facts(state, observations)
    ask_counters = state.get("_ask_counters") or {}
    max_rounds = state.get("_max_slot_rounds", 6)

    out: list[SlotSpec] = []
    for spec in specs:
        if any(src in AUTO_SOURCES for src in spec.source_hint) and spec.key in auto_filled:
            excluded[spec.key] = "档案或环境已有"
            continue
        if ask_counters.get(spec.key, 0) > max_rounds:
            excluded[spec.key] = "追问次数超限，转 unknown"
            continue
        out.append(spec)
    return out
```

`_collect_auto_facts` 汇总当前确实可得的槽位键：档案里 `slot_values` 非空的值、环境读数中 `quality == "ok"` 的 `metric`、以及 `observed_facts` 中非空的键。

剔除条件是"该槽位的 `source_hint` 含自动来源"**且**"该来源确实已有值"。两个条件都满足才剔除：若只看 `source_hint` 就剔除（例如档案里配了 `profile` 但农户其实没填），这个槽位永远不会被问到，形成信息盲区。技术方案 5.3.3 的原文表述是"剔除可由档案/环境直接读取的项（如档案已有播种时间则不问）"，"已有"是这个条件的核心。

追问超限的剔除本质属于"不该再问"，与状态过滤同类，放在第二步比单开第四步更自然。

### 第三步：按流程必问清单与关键词相关性排序

```python
def _rank_by_relevance(specs: list[SlotSpec], state: ConsultationState,
                       config: ProcessConfig) -> list[CandidateSlot]:
    """相关性排序：必问清单优先，易混淆项相关优先，其余按 ask_order。"""
    confusable_terms = _confusable_terms(config)
    symptom_terms = _symptom_terms(state)
    offline_keys = _offline_keys(config, state)

    scored: list[tuple[int, int, CandidateSlot]] = []
    for spec in specs:
        score, reason = 0, "relevant_followup"
        if spec.required:
            score, reason = score + 100, "must_ask"
        if spec.key in offline_keys:
            score, reason = score + 40, "offline_enhance"
        score += 20 * _term_hits(spec, confusable_terms)
        score += 10 * _term_hits(spec, symptom_terms)
        if spec.group == "病虫情":
            score += 5
        scored.append((score, -spec.ask_order, CandidateSlot(
            slot_key=spec.key, display_label=spec.display_label, group=spec.group.value,
            required=spec.required, options=spec.options, relevant_score=score, reason=reason)))

    scored.sort(key=lambda t: (t[0], t[1]), reverse=True)
    return [item[2] for item in scored]
```

排序是**多级权重加分**而不是单一关键词匹配，权重含义如下：

| 加分项 | 分值 | 理由 |
| --- | --- | --- |
| 必问槽位 | 100 | 必问清单是流程的底线，必须排在前列 |
| 无传感器增强追问 | 40 | 缺少环境数据时这些问题的信息增量最大 |
| 命中易混淆项候选词 | 20 每命中 | 易混淆项是误判最直接来源，鉴别点优先 |
| 命中农户已述症状词 | 10 每命中 | 与当前描述相关的问题更可能有答案 |
| 病虫情分组 | 5 | 农户提问以病虫情为主，轻微加权 |

排序键为 `(score, -ask_order)`，即分数相同则 `ask_order` 小者优先；取负值是因为 `sort` 升序而 `ask_order` 越小越应先问。**排序必须稳定**：同分同 `ask_order` 的项其相对顺序由构造顺序决定，而构造顺序来自 `config.required_slots` 的列表顺序，因此同一配置与状态得到完全确定的候选池，这是可重放的要求。

### 相关性匹配的取词

`_confusable_terms(config)` 从易混淆项提取候选名与决定性特征中的分词结果；`_symptom_terms(state)` 从已填槽位的值里抽取分词结果；`_term_hits(spec, terms)` 统计槽位的 `label`、`display_label` 与 `options` 拼成的文本中命中的词数。三者都是纯字符串包含判断，不做语义相似度计算，因为语义相似度需要模型或向量，与本模块"模型不参与"的定位冲突。分词用 jieba 并过滤单字与停用词，分词器已随 jieba 引入（用于知识库检索兜底），这里复用。

### 六的上限与配置边界

`top_k` 默认 6，与技术方案 5.3.3 与 9.4 的 `top_k=6` 一致。上限的理由在技术方案 10.4 的上下文裁剪：候选方向过多会让提示词膨胀，且模型在有大量选择时遵循度下降，容易挑中最不相关的两个。若三步筛选后剩余项少于两个（接近收敛时只剩一个未问项），照常返回剩余项，不补齐也不报错。

筛选器**只读**流程配置与状态，不修改任何东西，对 `_ask_counters` 等处以下划线前缀的临时键也是只读的（写入方在 T2-16）。这样筛选器可以反复调用而不产生副作用，便于在测试中直接断言输出。

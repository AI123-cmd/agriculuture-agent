# T2-55 模型网关统一入口

## 这一项要做什么

在 `app/llm/gateway.py` 中实现模型网关的统一入口 `gateway.chat(task_type, messages, schema)`，把方案 10.1 列出的六项职责收在一个类里：统一入口、任务路由、结构化输出、超时熔断、计量与审计、内容审计。现有实现（`app/ai_router/base.py`）直接用 `httpx` 调单一端点，四个问题一次性在这里解决：无法按任务类型选模型、无统一超时与熔断、无 token 计量、无调用审计。

网关是通用组件，它不得导入任何业务模块（`agent`/`gate``/`services`/`broadcast`），这是全局约定 L3 硬规则。

## 实现要点

### 六项职责与入口签名

```python
class ModelGateway:
    """模型调用统一入口。六项职责：入口、路由、结构化输出、超时熔断、计量审计、内容审计。"""

    def __init__(self, router: ModelRouter, providers: dict[str, ModelProvider],
                 circuit: CircuitBreaker, meter: TokenMeter, auditor: CallAuditor) -> None:
        self._router = router
        self._providers = providers
        self._circuit = circuit
        self._meter = meter
        self._auditor = auditor

    async def chat(self, task_type: TaskType, messages: list[dict],
                   schema: type[BaseModel] | None = None) -> ModelResponse:
        """所有模型调用的唯一入口。"""
        ...
```

| 职责 | 在本项的实现 | 说明 |
| --- | --- | --- |
| 统一入口 | `chat(task_type, messages, schema)` | 业务侧只调这一个方法 |
| 任务路由 | 调 `router.resolve(task_type, budget)` | 得到候选模型与供应商链 |
| 结构化输出 | 把 `schema` 传给适配器，并按三层保障处理解析 | 解析与重试逻辑在 T2-56 |
| 超时熔断 | 调用前查熔断状态，调用时施超时 | 策略在 T2-58 |
| 计量与审计 | 调用后写 `llm_call` 记录 | 落库在 T2-59 |
| 内容审计 | 记录输入输出的哈希，不留原文 | 保护隐私 |

`chat` 的返回类型是 `ModelResponse`，其中 `parsed` 字段承载结构化结果（`schema` 非空时）。业务侧（智能体基类）拿到 `parsed` 为 `None` 即视为契约违约，触发降级。网关不抛"解析失败"，而是把解析结果与错误放进 `ModelResponse.error`，让调用方决策——因为不同智能体的降级出口不同。

### 六项职责的分工边界

```python
    async def chat(self, task_type, messages, schema=None) -> ModelResponse:
        decision = self._router.resolve(task_type)
        messages = trim_messages(messages, decision.max_history_rounds)
        self._auditor.record_digest(task_type, messages)          # 只记哈希
        last_error: str | None = None
        for candidate in decision.chain:
            if not self._circuit.allow(candidate.provider):
                last_error = f"{candidate.provider} 熔断中"
                continue
            response = await self._invoke(candidate, messages, schema)
            if response.error is None:
                await self._meter.record(task_type, response, candidate, is_fallback=(candidate is not decision.chain[0]))
                return response
            last_error = response.error
            self._circuit.record_failure(candidate.provider)
        raise AllProvidersFailedError(task_type.value, last_error)
```

网关按 `router.resolve` 给出的候选链依次尝试，每个候选有自己的供应商与模型名。熔断中的供应商被跳过（不浪费一次调用），失败的候选记一次熔断失败并继续下一个。全部失败才抛 `AllProvidersFailedError`，由调用方（智能体基类）决定降级出口。

计量只在成功或最后一次失败时记录，避免为每次失败的尝试都写一条计量记录——失败的调用没有可信的 token 数。但失败次数要计入熔断器，这是熔断器判断"该供应商是否连续失败"的依据。

### 上下文裁剪

```python
def trim_messages(messages: list[dict], max_rounds: int = 6) -> list[dict]:
    """只保留最近 N 轮对话，更早的压缩为已确认信息摘要。"""
    system = [m for m in messages if m.get("role") == "system"]
    rest = [m for m in messages if m.get("role") != "system"]
    if len(rest) <= max_rounds:
        return messages
    head = rest[: len(rest) - max_rounds]
    tail = rest[len(rest) - max_rounds:]
    summary = {"role": "system", "content": _summarize(head)}
    return [*system, summary, *tail]
```

方案 10.4 明确"只保留最近 N 轮对话（建议 6 轮），更早的压缩为已确认信息摘要"。这在技术上既控 token，也避免长上下文导致的指令遵循退化——对"每轮只问两个问题"这类硬约束，长上下文会显著降低遵循度。裁剪放在网关而不是各智能体，保证所有调用一致受控，也避免某个智能体忘记裁剪。

system 消息不参与裁剪，且摘要作为新的 system 消息插在 system 之后、tail 之前。摘要内容由纯函数 `_summarize` 生成（拼接早期消息的角色与截断内容），不用模型——裁剪本身不应触发又一次模型调用。

### 内容审计只记哈希

```python
class CallAuditor:
    """内容审计：记录输入输出的哈希，用于事后追溯，不留原文。"""

    def record_digest(self, task_type: TaskType, messages: list[dict]) -> str:
        payload = json.dumps(messages, ensure_ascii=False, sort_keys=True)
        digest = hashlib.sha256(payload.encode("utf-8")).hexdigest()
        return digest

    def record_output_digest(self, digest: str, content: str | None) -> None:
        out = hashlib.sha256((content or "").encode("utf-8")).hexdigest()
        ...
```

方案 10.1 明确"记录输入输出的哈希，用于事后追溯（不留原文，保护隐私）"。农事问诊内容含农户地块、位置、作物状况，属于敏感数据。哈希让系统能回答"两次调用是否相同输入""某次输出与某条审计记录是否对应"，但无法从审计表还原原文。这是隐私保护与可追溯性的平衡点。

原始 `messages` 只在本次调用内存在，不落库；落库的是哈希与元数据（task_type、model、token 数、耗时）。

### Mock 模式

```python
class MockProvider:
    """USE_MOCK_LLM=true 时的供应商。返回预设结构化响应，不发真实请求。"""

    name = "mock"

    async def chat(self, model, messages, response_schema=None, timeout=30.0) -> ModelResponse:
        parsed = _default_for_schema(response_schema) if response_schema else None
        return ModelResponse(content=json.dumps(parsed, ensure_ascii=False) if parsed else "（模拟响应）",
            parsed=parsed, model=model, provider=self.name, prompt_tokens=0, completion_tokens=0,
            latency_ms=0, is_fallback=False, error=None)
```

Mock 模式在自动化测试中是默认路径，与全局约定"所有不测模型的测试都应在 mock 模式下跑"一致。`MockProvider` 按 `schema` 生成一个满足契约的最小合法对象，让智能体的契约校验与下游逻辑能在不依赖外部服务的前提下被完整测试。

### 与现有 ai_router 的关系

现有 `CropModel.chat(message, context) -> str` 的接口形态（按作物选一个类、返回纯文本）在本项被彻底替换：网关按任务类型选模型、返回带 `parsed` 的结构化响应。`app/ai_router/` 的删除在 T2-61 执行，本项只提供新入口，不删旧代码，保证删除时新旧可对照。

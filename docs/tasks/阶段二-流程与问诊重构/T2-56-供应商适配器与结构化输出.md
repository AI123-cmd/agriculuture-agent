# T2-56 供应商适配器与结构化输出

## 这一项要做什么

在 `app/llm/providers/` 下实现供应商适配层：定义 `ModelProvider` 协议与 `ModelResponse` 模型，为每个供应商写一个适配器（OpenAI 兼容、私有化部署、Mock 三类），并把方案 10.2 的结构化输出三层保障落到代码上。它是网关与实际模型服务之间的唯一接口面，让"换供应商"变成新增一个适配器而不是改业务代码。

三层保障的核心是：解析失败要触发降级，绝不用正则硬抽。农业场景下错误的字段值比没有字段值更危险——一个编造的剂量数字会被农户照着用。

## 实现要点

### ModelProvider 协议与 ModelResponse

按方案 10.2 原样定义：

```python
class ModelProvider(Protocol):
    """模型供应商适配接口。"""
    name: str

    async def chat(
        self,
        model: str,
        messages: list[dict],
        response_schema: type[BaseModel] | None = None,
        timeout: float = 30.0,
    ) -> ModelResponse: ...


class ModelResponse(BaseModel):
    content: str | None
    parsed: BaseModel | None
    model: str
    provider: str
    prompt_tokens: int
    completion_tokens: int
    latency_ms: int
    is_fallback: bool = False
    error: str | None = None
```

九个字段各有用途：`content` 是原始文本（无结构化需求时使用，也用于审计哈希），`parsed` 是解析后的契约对象（智能体直接消费），`model` 与 `provider` 进计量表用于成本归属，`prompt_tokens` 与 `completion_tokens` 是成本与预算的输入，`latency_ms` 进链路指标，`is_fallback` 标记这是否降级链上的备选（用于统计各供应商可用率），`error` 承载失败原因（`parsed` 与 `content` 均为空时非空）。

`is_fallback` 由网关在调用前设置（是否为链上首个候选），不由适配器判定：适配器不知道自己在链上的位置。

### 三类适配器

```python
class OpenAICompatProvider:
    """OpenAI 兼容端点：优先用原生结构化输出（response_format=json_schema）。"""
    name = "openai_compat"

    def __init__(self, base_url: str, api_key: str) -> None: ...

    async def chat(self, model, messages, response_schema=None, timeout=30.0) -> ModelResponse:
        payload = self._build_payload(model, messages, response_schema)
        started = time.perf_counter()
        try:
            async with httpx.AsyncClient(timeout=timeout) as client:
                resp = await client.post(f"{self._base_url}/chat/completions", json=payload, headers=self._headers())
                resp.raise_for_status()
                data = resp.json()
        except httpx.TimeoutException:
            return self._error_response(model, "timeout", started)
        except httpx.HTTPStatusError as exc:
            return self._error_response(model, f"http_{exc.response.status_code}", started)
        return self._parse_response(model, data, response_schema, started)
```

`_build_payload` 在 `response_schema` 非空时注入原生结构化输出参数（`response_format={"type": "json_schema", ...}`），这是三层保障的第一层。原生能力由供应商保证输出是合法 JSON 且符合 Schema，能省掉解析失败与重试的整条路径。

```python
class PrivateModelProvider:
    """私有化部署模型：通常不支持原生结构化输出，走提示词约束路径。"""
    name = "private"

    def _build_payload(self, model, messages, response_schema=None) -> dict:
        msgs = messages
        if response_schema is not None:
            msgs = [*messages, {"role": "system", "content": _schema_instruction(response_schema)}]
        return {"model": model, "messages": msgs, "temperature": 0.0, "stream": False}
```

私有化模型（如本地部署的 Qwen 级模型）多数不支持 `response_format` 的 json_schema 模式，因此退到第二层：把 Schema 说明追加到 messages，再解析输出。`temperature=0.0` 是结构化输出场景的固定设置，降低输出格式的随机性。

```python
class MockProvider:
    """Mock 适配器：按 schema 生成满足契约的最小对象。"""
    name = "mock"
```

`MockProvider` 对 `response_schema` 用 `_default_for_schema` 生成合法对象：对必填字段填默认值，对 `Literal` 取第一个值，对 `list` 给空列表。它不是"随便返回一段文本"，而是"保证满足契约"，这样智能体的下游逻辑能在 mock 模式下被完整测试。

### 结构化输出的三层保障

```python
async def chat_with_structured(self, provider: ModelProvider, model: str, messages: list[dict],
                               schema: type[BaseModel], timeout: float) -> tuple[ModelResponse, str | None]:
    """三层保障的结构化调用。返回响应与采用的层标记。"""
    # 第一层：原生结构化输出（由适配器内部按能力决定是否启用）
    response = await provider.chat(model, messages, schema, timeout)
    if response.parsed is not None:
        return response, "native"
    # 第二层：提示词约束 + 解析失败构造修复提示重试一次
    repaired = await self._retry_with_repair(provider, model, messages, schema, response, timeout)
    if repaired.parsed is not None:
        return repaired, "repair"
    # 第三层：交由该智能体的降级路径
    return repaired, "degrade"
```

三层对应方案 10.2 的三步：优先原生结构化输出；退化到"提示词约束 + 解析"，解析失败用 `pydantic` 的错误信息构造一次修复提示重试一次；仍失败走该智能体的降级路径。

```python
    def _build_repair_messages(self, messages: list[dict], error: str) -> list[dict]:
        """把 pydantic 的错误信息反馈给模型，让它自己修。"""
        return [*messages,
            {"role": "assistant", "content": "（上一次输出未通过校验）"},
            {"role": "user", "content": f"你的上一次输出不符合下面的要求：{error}\n请仅输出符合 JSON Schema 的修正结果，不要附加解释。"}]
```

修复提示携带 `pydantic` 的原始校验错误（如"字段 dosage_min 期望 number 得到 string"），让模型知道具体错在哪。只重试一次：第二次仍失败说明该模型对这个 Schema 的遵循能力不足，继续重试只是浪费 token 与延迟。

第三层的"降级"不在本模块实现，而是返回 `parsed is None` 的响应，由网关返回给智能体基类，由基类按各智能体的降级出口处理（问诊降级为模板问题、判定降级为不确定）。本模块只负责把状态表达清楚。

### 为什么不做解析失败就用正则硬抽

方案 10.2 的原文是："农业场景下错误的字段值比没有字段值更危险。契约违约应当触发降级，而不是让不完整的数据流入下游。"

具体到农业场景：处方里的 `dosage_max`、`safety_interval_days` 是直接影响农户用药安全的数字。若模型返回的 JSON 格式错，正则硬抽可能抽到一个在错误上下文里的数字（比如把"共 2 条建议"里的 2 抽成安全间隔期 2 天）。这个数字比"没有字段值"更危险——没有值时系统降级为"建议咨询农技站"，有错误值时农户会照着打药。

因此本模块的全部补救手段都是"让模型重出"（修复提示），而不是"从文本里猜"。重出失败就走降级，绝不构造一个"看起来像"的值。这条原则由测试断言保证：注入一段格式错误但含数字的输出，断言解析结果为 `None` 而不是抽出了那个数字。

### 错误分类与熔断的衔接

适配器把 HTTP 错误分类为可重试与不可重试：

| 错误 | 分类 | 熔断计数 |
| --- | --- | --- |
| 超时 | 可重试，计入失败 | 是 |
| 429 限流 | 可重试，计入失败 | 是 |
| 5xx 服务端错误 | 可重试，计入失败 | 是 |
| 400 参数错误 | 不可重试，不计入熔断 | 否 |
| 401 鉴权失败 | 不可重试，不计入熔断 | 否（配置问题，重试无意义） |
| 解析失败 | 不算供应商失败，不计入熔断 | 否 |

解析失败不计入熔断是因为它不是供应商可用性问题，而是输出质量或 Schema 问题；把它计入熔断会让一个能正常返回内容的供应商被误熔断。这条区分让熔断器的语义保持为"这个供应商是否可用"。

- 断言各适配器均以 `httpx` 发起请求且被 `respx` 拦截时行为正确，且 `USE_MOCK_LLM=true` 时不构造真实适配器

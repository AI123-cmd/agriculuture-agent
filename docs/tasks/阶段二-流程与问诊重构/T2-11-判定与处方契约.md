# T2-11 判定与处方契约

## 这一项要做什么

在 `app/agent/contracts/diagnosis.py` 与 `app/agent/contracts/prescription.py` 中定义判定智能体与处方智能体的输出契约 `DiagnosisResult`、`Prescription`、`PrescriptionAction`、`PesticideItem`、`FollowupPlan`。这两个契约是安全链路的中心：`DiagnosisResult` 决定确定性与排除项，`Prescription` 携带全部数值与溯源，闸门按 `facts_provenance` 做反向扫描。

契约要落实三件事：把握程度用枚举而不是百分比分数，排除项必填且非空，每一个数字都必须在 `facts_provenance` 中登记。第三条是"模板出事实、模型只改写"从原则变成自动检查的关键。

## 前置依赖

- 依赖 T2-10：必须已提供 `EvidenceSet` 与 `EvidenceItem`，处方的证据引用要与之对齐
- 依赖 T2-08：必须已提供 `ConsultationState` 与槽位读取函数
- 依赖 T2-01：必须已提供 `ConfidenceLevel`
- 依赖 T2-02：必须已提供 `ConfusablePair`、`FollowupPolicy`，判定排除项与回访计划由配置驱动
- 外部条件：药剂名、剂量区间、安全间隔期为农技内容，需人工确认（见全局约定第八节）
- 与 T2-41 的关系：本项定义 `facts_provenance` 结构，反向扫描规则在 T2-41 实现

## 实现要点

### DiagnosisResult

```python
class DiagnosisResult(BaseModel):
    """判定输出。技术方案 5.3.4 原样定义。"""
    model_config = ConfigDict(extra="forbid")

    conclusion: str
    confidence_level: Literal["likely", "preliminary", "uncertain"]
    basis: list[str]
    uncertainty_source: list[str]
    excluded: list[str]
    terminology_profile: str
    needs_more_info: list[str]
    out_of_scope: bool
    boundary_reason: str | None = None

    @model_validator(mode="after")
    def _basis_not_blank(self) -> "DiagnosisResult":
        if not self.basis or not all(b.strip() for b in self.basis):
            raise ValueError("basis 必填且逐条非空")
        return self

    @model_validator(mode="after")
    def _boundary_reason_required(self) -> "DiagnosisResult":
        if self.out_of_scope and not self.boundary_reason:
            raise ValueError("out_of_scope=True 时必须给出 boundary_reason")
        return self

    @model_validator(mode="after")
    def _uncertain_needs_more_info(self) -> "DiagnosisResult":
        if self.confidence_level == "uncertain" and not self.needs_more_info and not self.uncertainty_source:
            raise ValueError("confidence_level=uncertain 时必须给出不确定性来源或需补信息")
        return self
```

第三条校验器是"不强行择一"的落地。技术方案 6.4 指出当把握不足时，正确做法是给出观察 + 复查的动作。若结论是"不确定"却既不说明不确定在哪，也不说需要补什么，农户拿到的就是一句模糊的话，因此契约层面不允许这种输出。

`excluded` 必填且非空这一条不能写成静态约束，因为它只对有易混淆项的流程成立。实现方式是：**契约允许空列表，但由判定智能体在调用前从流程配置读取 `confusable_items`，若 `must_exclude` 为 True 则在校验后做一次业务检查**。这个检查放在 T2-19 的智能体里而不是契约里，因为契约不知道当前流程。

`confidence_level` 用 `Literal` 三值，不含任何数值字段。技术方案 5.3.4 明确"内部可以保留置信度分数用于路由判断，但不得进入展示文案"。因此置信度分数是**节点返回的 state 字段**（供 T2-24 的路由函数读取），不是契约字段。二者分开是保证分数不泄漏到展示层的结构性手段。

```python
CONFIDENCE_DISPLAY: dict[str, str] = {
    "likely": "很可能是",
    "preliminary": "初步判断",
    "uncertain": "不确定",
}
```

映射表放在契约模块里，展示层只允许读这张表，不允许自行拼装。

### PesticideItem

```python
class PesticideItem(BaseModel):
    """药剂条目。只能由代码从知识库检索结果填充，模型无权写入。"""
    model_config = ConfigDict(extra="forbid")

    knowledge_id: str
    name: str
    dosage_min: float | None = None
    dosage_max: float | None = None
    dosage_unit: str | None = None
    safety_interval_days: int | None = None
    max_uses_per_season: int | None = None
    registered_crops: list[str] = []
    forbidden_combinations: list[str] = []
    source_note: str | None = None
```

`knowledge_id` 是必填的第一字段，因为闸门 `R-WHITELIST` 要求每一项的 `knowledge_id` 必须存在于已核准知识库且 `status = approved`。没有 `knowledge_id` 就无从校验，因此这一项不能为空也不能是模型生成的编造值。

`dosage_min` 与 `dosage_max` 允许为 `None`，但一旦有值就必须与 `evidence` 中的知识条目一致。这个一致性校验由 T2-21 的处方智能体在填充时保证（填充即照抄，模型无法介入），闸门的 `R-DOSAGE` 做二次校验。

### PrescriptionAction

```python
class PrescriptionAction(BaseModel):
    """一条处置动作。"""
    model_config = ConfigDict(extra="forbid")

    order: int
    action: str
    timing: str
    method: str
    cautions: list[str]
    stop_conditions: list[str]

    @model_validator(mode="after")
    def _stop_conditions_present(self) -> "PrescriptionAction":
        if not self.stop_conditions:
            raise ValueError("每条动作必须给出停止或求助条件")
        return self
```

`stop_conditions` 强制非空。技术方案与产品说明书反复强调"当把握不足时给出观察 + 复查"，而行动建议若无停止条件，农户会一路执行到出现明显损失。强制写停止条件是让"何时该停"成为每条动作的固有部分。

### Prescription

```python
class Prescription(BaseModel):
    """处方契约。技术方案 5.3.5 原样定义。"""
    model_config = ConfigDict(extra="forbid")

    diagnosis_summary: str
    actions: list[PrescriptionAction]
    safety_interval_days: int | None
    max_uses_per_season: int | None
    pesticide_items: list[PesticideItem]
    soil_level_actions: list[str]
    followup_plan: FollowupPlan
    facts_provenance: dict[str, str]
    requires_tech_station: bool
    detail_terms: dict[str, str]

    @model_validator(mode="after")
    def _provenance_covers_numbers(self) -> "Prescription":
        missing = [k for k in self.numeric_paths() if k not in self.facts_provenance]
        if missing:
            raise ValueError(f"数值字段缺少溯源: {missing}")
        return self

    @model_validator(mode="after")
    def _pesticide_items_need_provenance(self) -> "Prescription":
        if self.pesticide_items and not self.safety_interval_days:
            return self                            # 由闸门 R-INTERVAL 拦截，契约不阻断
        return self

    def numeric_paths(self) -> list[str]:
        """列出本处方中所有需要溯源的数值字段路径。"""
        paths: list[str] = []
        if self.safety_interval_days is not None:
            paths.append("safety_interval_days")
        if self.max_uses_per_season is not None:
            paths.append("max_uses_per_season")
        for i, item in enumerate(self.pesticide_items):
            for field in ("dosage_min", "dosage_max", "safety_interval_days", "max_uses_per_season"):
                if getattr(item, field) is not None:
                    paths.append(f"pesticide_items[{i}].{field}")
        return paths
```

`_provenance_covers_numbers` 是"事实必带溯源"的契约层执行点。它在对象构造完成时即检查 `facts_provenance` 是否覆盖了所有数值路径，不完整就抛错。这样模型产出的处方若漏登记来源，在解析阶段就会被拦住。

`facts_provenance` 的结构按技术方案 5.3.5 原样：

```python
facts_provenance = {
    "safety_interval_days": "knowledge:K-1023",
    "pesticide_items[0].dosage_min": "knowledge:K-1023:field:dose",
}
```

键是字段路径，值是来源标识。来源标识有两种形态：`knowledge:<id>` 指整个知识条目，`knowledge:<id>:field:<name>` 指条目的某个字段。后者用于需要精确到字段的场景（剂量来自条目的 `dosage_min`，而非整条）。

`_pesticide_items_need_provenance` 选择不阻断：技术方案 8.2 把"涉及用药但未给出安全间隔期"归为 `R-INTERVAL` 规则，违规等级 `block`，处置是闸门拦截并降级为转人工引导。若契约层直接抛错，处方节点会重试并可能反复失败，而此时正确的行为是让闸门给出 `degrade` 输出。因此契约层只保证结构完整，语义违规交给闸门——这与"闸门是唯一拥有否决权的组件"一致。

### FollowupPlan 与 FollowupTask

```python
class FollowupTask(BaseModel):
    model_config = ConfigDict(extra="forbid")

    due_offset_days: int                    # 相对当天的天数，0 表示立即
    kind: Literal["effect_check", "risk_check", "preserve_scene", "observe"]
    content_rule: str | None = None         # 内容规则 id，供文案层取模板
    ask: str | None = None                  # 面向农户的询问语
    window_based: bool = False


class FollowupPlan(BaseModel):
    model_config = ConfigDict(extra="forbid")

    tasks: list[FollowupTask]
    note: str | None = None

    @model_validator(mode="after")
    def _ordered(self) -> "FollowupPlan":
        self.tasks.sort(key=lambda t: t.due_offset_days)
        return self
```

`due_offset_days` 而非绝对日期，原因是处方可能在任意时刻生成，而回访时点总是相对动作。杂草流程的药害分支用 `due_offset_days=0` 与 `kind="preserve_scene"` 表达"立即固定现场"，`content_rule` 指向 `weed.damage_evidence_checklist`。

`_ordered` 保证任务按时间升序。回访服务的调度不需要自己排序，也不必担心处方层给出乱序而导致同一天多次触达。

### detail_terms 与展示层

```python
detail_terms: dict[str, str] = {}    # 术语 → 口语化改写对照
```

`detail_terms` 是处方契约里唯一允许进入展示层的术语映射。它与流程配置的 `colloquial_map` 有交集但不相同：`colloquial_map` 是流程级的固定对照，`detail_terms` 是本次处方中出现的术语的具体改写（如把本次判定名"青枯病"改写成"从土里传染的细菌病"）。展示层渲染时先应用 `detail_terms`，未命中的再应用 `colloquial_map`。

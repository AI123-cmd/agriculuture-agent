# T2-53 知识库内容建设油菜与通用兜底

## 这一项要做什么

在 `app/knowledge/seeds/` 下建立油菜流程与通用农业兜底两条线的知识条目：油菜先建非药剂类条目（专属病虫害谱、菌核病防治窗口、后茬关系、安全间隔期参考资料但不放行药剂推荐），通用农业只建通用农事知识、无专属阈值、无药剂条目。这两条线的共同特点是"能力弱于一期五条流程"，因此它们的设计重点不是内容量，而是"在知识不足时不越界"。

油菜流程按产品说明书 5.4 与方案 9.5 的红线处理：补齐专项调研前不得输出药剂推荐类内容。因此本项产出的油菜药剂类条目即使存在，也必须置为 `draft` 或 `suspended`，且流程配置侧要设 `disabled` 检索开关加 `RAPE-01` 红线双保险。

## 实现要点

### 油菜流程：建非药剂类，药剂类压制

```json
{"knowledge_id": "K-RAPE-0101", "process_id": "rapeseed", "kind": "disease", "title": "菌核病防治窗口", "content": "油菜花期是菌核病防治关键窗口，以花期降水与田间湿度为主要判据。", "regions": [{"region_code": "000000", "region_level": "national"}], "status": "draft", "source_ref": "专项调研（待补齐）；产品说明书 5.4"}
```

油菜条目的建设范围：

| 类别 | kind | 是否放行 | 说明 |
| --- | --- | --- | --- |
| 专属病虫害谱 | disease / pest | 是（approved 后可检索） | 菌核病、霜霉病、蚜虫、跳甲等 |
| 菌核病防治窗口 | cultivation | 是 | 以花期与湿度为判据，不含药剂 |
| 后茬关系 | cultivation | 是 | 前茬与后茬安排、轮作建议 |
| 安全间隔期参考 | pesticide | 否（draft） | 仅作参考录入，不为检索放行 |
| 登记药剂 | pesticide | 否（draft） | 待调研确认，暂不 `approved` |

关键约束是"没有 `status=approved` 的 `kind=pesticide` 条目"。这条约束有三重保障：本项保证数据文件里油菜药剂条目全部为 `draft`；T2-18 的 `kind_filter_for` 在油菜流程排除 `pesticide`；`RAPE-01` 红线拦截输出。三重保障并存是为了防止调研补齐过程中有误操作把油菜药剂条目误置 `approved`，单靠配置层的开关不够稳。

油菜的非药剂条目允许 `approved`，因为它们支撑"给出观察与农事建议"这部分能力，符合"在补齐之前不输出药剂推荐"而非"油菜流程完全不可用"。

### 通用农业兜底：只建通用知识

```json
{"knowledge_id": "K-GEN-0001", "process_id": "general", "kind": "cultivation", "title": "施肥通用原则", "content": "施肥应测土配方，避免单一过量偏施氮肥；追肥结合墒情与作物长势。", "regions": [{"region_code": "000000", "region_level": "national"}], "status": "approved", "source_ref": "现有资料"}
```

通用条目的建设范围与排除项：

| 类别 | kind | 是否建 | 说明 |
| --- | --- | --- | --- |
| 通用农事知识 | cultivation | 是 | 施肥、灌溉、通风、田间巡查通则 |
| 通用病害常识 | disease | 是（无专属阈值与判据） | 高温高湿与病害关系的通识 |
| 专属量化阈值 | threshold | 否 | 通用流程无专属阈值（方案 9.2、9.5） |
| 药剂条目 | pesticide | 否 | 通用流程无药剂条目（方案 9.5） |

通用流程的能力边界比油菜更窄：油菜有专属病虫害谱（只是暂不放行药剂），通用连专属阈值都没有。因此通用条目只表达"放之四海而皆可用"的农事原则，不做任何剂量、阈值、判据类的具体数字。

不建 `threshold` 与 `pesticide` 这两类，不是为了少写几条，而是避免下游误用。若通用流程库里存在阈值条目，判定智能体可能检索到并给出具体阈值数字（如"病叶率超过 5% 就打药"），而这个数字没有对应作物的登记依据，正是"无数据支撑的数字"红线要拦的情形。从数据源头不放这类条目，比在闸门拦更根本。

### 通用条目的地区挂载

通用条目一律挂全国（`region_code="000000"`，`region_level="national"`）。它们是任意流程的回退兜底：当某流程在该地区无条目时，检索可召回通用条目。T2-49 的过滤条件把 `process_id` 展开为 `[当前流程, general]`，正是为了让通用条目能作为兜底进入候选。因此通用条目必须挂全国，不能挂到具体地区，否则在未挂载的地区就失去兜底作用。

### 占位标记与调研补齐路径

油菜条目全部带 `source_ref` 提及"待补齐"或产品说明书条款，`status=draft`。数据文件里用 `# TODO(待确认)` 注释（jsonl 每行是独立 JSON，注释不能写在行内，因此占位说明放在 `README.md` 与 `source_ref` 字段中）。调研完成后按同一份模型补条目，走 T2-54 的核准流转改为 `approved`。

新增油菜药剂类条目的动作与新增其它流程条目一致：写一行 jsonl 加跑索引构建。不需要改任何代码，这与"新增内容不改编排逻辑"的约定一致。

### 与流程配置的对应检查

构建时要校验：`general` 流程的条目 `kind` 只允许 `{disease, pest, cultivation}`，出现 `threshold` 或 `pesticide` 时构建报错。这条校验防止通用流程库里混入不该有的类型。油菜流程的校验是：`status=approved` 且 `kind=pesticide` 的组合不允许出现。

这两条校验放在构建器的流程级校验里（本项实现），而不只是写在文档里，让"数据文件的约束"变成"构建时会被拦住的事实"。

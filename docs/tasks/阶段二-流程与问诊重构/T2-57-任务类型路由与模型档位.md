# T2-57 任务类型路由与模型档位

## 这一项要做什么

在 `app/llm/router.py` 中实现任务类型到模型档位的路由：按 `TaskType` 选择"用哪个模型档位、走哪条供应商链、上限多少 token、上下文留几轮"。它把方案 4.4 的模型分层策略从一张表变成可执行的决策，让"分诊用小模型、问诊与判定用主模型、安全闸门不用大模型"这类判断有唯一的落点。

路由是纯函数式的映射，不参与调用、不持有状态。同一次问诊内同一个 `TaskType` 必须解析出相同的档位，保证可复现。

## 前置依赖

- 依赖 T2-55：必须已提供 `ModelGateway`，路由是其持有的依赖
- 依赖 T2-02：必须已提供 `ProcessConfig`，部分档位需读流程配置（如启用并行会诊的流程）

- 外部环境：各档位对应的模型名、供应商、端点经环境变量配置

## 实现要点

### 档位定义

```python
class ModelTier(str, Enum):
    SMALL = "small"          # 小模型：分类、抽取、改写
    MEDIUM = "medium"        # 中等模型：检索改写、相关性判定
    PRIMARY = "primary"      # 主模型：问诊、判定
    VISION = "vision"        # 垂类图像加多模态：现场采集

@dataclass(frozen=True, slots=True)
class TierSpec:
    """一个档位的配置：模型名、供应商链、token 上限、上下文轮数。"""
    tier: ModelTier
    model: str
    provider_chain: tuple[str, ...]     # 供应商名，按优先级排列
    max_tokens: int
    max_history_rounds: int
```

档位是"能力等级"的抽象，具体模型名由环境配置填充。开发环境可以用轻量模型占位，生产环境换成正式模型，业务代码不动。这一点对成本控制很重要：小模型档位在预发环境可用更便宜的模型跑通链路。

### 任务类型到档位的映射

按方案 4.4 的表格逐项落实：

| 环节 | TaskType | 档位 | 选型考量 |
| --- | --- | --- | --- |
| 分诊 Triage | `TRIAGE` | SMALL | 分类加槽位抽取，输出枚举，可被规则校验 |
| 现场采集 | `OBSERVE` | VISION | 图像候选加事实归纳，候选域按流程限定 |
| 问诊 Interviewer | `INTERVIEW` | PRIMARY | 生成追问、解释为什么问，直接影响体验 |
| 证据核查 | `RETRIEVE` | MEDIUM | 检索改写加相关性判定，重排序质量决定证据质量 |
| 判定 Diagnoser | `DIAGNOSE` | PRIMARY | 鉴别推理与易混淆项排除，准确性核心 |
| 处方 Prescriber | `PRESCRIBE` | SMALL | 话术改写，不得新增事实，能力需求低 |
| 并行会诊 Panel | `PANEL` | PRIMARY | 多视角鉴别推理 |
| 快照文案 | `SNAPSHOT_WRITER` | SMALL | 模板转述，同处方 |
| 报告守卫 | `REPORT_GUARD` | SMALL | 规则优先，模型只做兜底归纳 |
| 安全闸门 | 无 TaskType | 不使用大模型 | 确定性规则实现 |

```python
DEFAULT_TIER_MAP: dict[TaskType, ModelTier] = {
    TaskType.TRIAGE: ModelTier.SMALL,
    TaskType.OBSERVE: ModelTier.VISION,
    TaskType.INTERVIEW: ModelTier.PRIMARY,
    TaskType.RETRIEVE: ModelTier.MEDIUM,
    TaskType.DIAGNOSE: ModelTier.PRIMARY,
    TaskType.PRESCRIBE: ModelTier.SMALL,
    TaskType.PANEL: ModelTier.PRIMARY,
    TaskType.SNAPSHOT_WRITER: ModelTier.SMALL,
    TaskType.REPORT_GUARD: ModelTier.SMALL,
}
```

安全闸门不在这个映射里——`TaskType` 里没有闸门项。方案 4.4 明确"安全闸门不使用大模型，确定性实现"。若有人试图给闸门加一个 `TaskType` 走模型，会因为映射里没有对应项而在装配期报错。这是"闸门不依赖大模型"从架构层面的保证。

### RoutingDecision 与候选链

```python
@dataclass(frozen=True, slots=True)
class RoutingDecision:
    task_type: TaskType
    tier: ModelTier
    chain: tuple[ModelCandidate, ...]     # 候选链：主供应商 A 到 B 到私有化
    max_tokens: int
    max_history_rounds: int

@dataclass(frozen=True, slots=True)
class ModelCandidate:
    provider: str
    model: str
    tier: ModelTier
    is_degraded: bool = False             # 私有化降档候选标记

class ModelRouter:
    """任务类型路由。纯映射，不持状态。"""

    def resolve(self, task_type: TaskType, *, budget_remaining: int | None = None) -> RoutingDecision:
        tier = DEFAULT_TIER_MAP[task_type]
        if budget_remaining is not None and budget_remaining < MIN_BUDGET_FOR_PRIMARY:
            tier = _downgrade(tier)
        spec = self._specs[tier]
        chain = tuple(ModelCandidate(provider=p, model=spec.model, tier=tier,
                       is_degraded=(i == len(spec.provider_chain) - 1))
                      for i, p in enumerate(spec.provider_chain))
        return RoutingDecision(task_type, tier, chain, spec.max_tokens, spec.max_history_rounds)
```

候选链由 `TierSpec.provider_chain` 展开：第一个是主供应商 A，第二个是同档备选 B，最后一个是私有化降档模型。链的最后一项 `is_degraded=True`，让网关与计量能标记"这次经过了降档"。方案 10.3 的降级链从这里获得候选顺序，具体熔断与切换逻辑在 T2-58。

`resolve` 是纯函数：同一 `task_type` 与同一预算状态返回相同结果，不读时间、不读随机数。这让"某次问诊为什么用了那个模型"可以事后复算。

### 预算降档

```python
def _downgrade(tier: ModelTier) -> ModelTier:
    """预算不足时降一档。PRIMARY 降为 MEDIUM，MEDIUM 降为 SMALL，SMALL 不变。"""
    return {ModelTier.PRIMARY: ModelTier.MEDIUM,
            ModelTier.MEDIUM: ModelTier.SMALL,
            ModelTier.VISION: ModelTier.MEDIUM}.get(tier, tier)
```

方案 10.4 的"单次预算：`max_tokens_per_consult` 超限即降档"。降档只在预算确实不足时发生，且降档后仍走同一条候选链，只是模型能力下降。降档不等同于降级：降档是"用次强模型继续做完"，降级是"放弃模型能力用规则兜底"。二者区别要在指标上分开统计，否则无法区分"预算控得好"与"服务其实挂了"。

`MIN_BUDGET_FOR_PRIMARY` 是一个阈值，低于它才降档；阈值取多少取决于主模型单次典型消耗。这个值由配置提供，不硬编码。

### 并行会诊与流程差异

`PANEL` 的档位为 PRIMARY，但只有启用并行会诊的三条流程（茶、辣椒、杂草）会走到这个 `TaskType`。路由本身不读流程配置——是否走 `PANEL` 由图的条件边决定，路由只负责"若走 PANEL 就用哪个档位"。这个分工让路由保持纯映射。

若某流程需要覆盖默认档位（如茶流程的安全间隔期计算需要更强推理），实现方式是 `RouterOverrides`：在 `resolve` 中先查流程级覆盖表，无覆盖再用默认表。覆盖表由配置提供，默认空。一期不启用覆盖，先把默认表跑通。

### 与成本控制的配合

路由同时输出 `max_tokens` 与 `max_history_rounds`，让网关的上下文裁剪与单次生成上限有统一来源。小模型档位的 `max_history_rounds` 更小（如 4），因为小模型的指令遵循对上下文长度更敏感；主模型可以给到 6。这两个值随档位走而不是全局固定，是"按环节配资源"的体现。

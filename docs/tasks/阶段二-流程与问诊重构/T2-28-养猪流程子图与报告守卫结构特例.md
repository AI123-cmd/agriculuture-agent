# T2-28 养猪流程子图与报告守卫结构特例

## 这一项要做什么

处理七条流程中唯一的结构差异：养猪流程以"不漏报"为最高目标，因此报告守卫 `report_guard` 必须插在 `observe` **之前**，且其输出优先级高于子图内部所有节点。方案 7.4 明确这条差异"用条件边实现而非修改通用节点"。同时落实方案 5.3.7 的旁路要求：守卫在 `observe` 与 `interview` 之后各挂一次检查，命中即 `stop_consultation = True` 并跳转 `handoff`，已收集的问诊内容保留但不继续追问。方案还纠正了一个认知盲区：不是只有群死群伤才需报告，单个识别信号命中即触发。

## 前置依赖

- T2-27 一期五条流程子图：提供猪流程标准骨架与注册表。
- T2-22 报告守卫 ReportGuard：提供 `ReportGuard.run(state) -> ReportDecision` 与 `build_report_guard_node(config)`。
- T2-12 门禁与报告守卫契约：`ReportDecision` 字段名（`triggered`、`matched_signals`、`trigger_source`、`mandatory_actions`、`contacts`、`stop_consultation`）。
- T2-24 条件边函数 routes：复用 `route_after_subgraph_guard` 与 `ROUTE_AFTER_SUBGRAPH_GUARD`（入口守卫与兜底守卫共用，按 `stage` 区分去向），本项不新增路由函数。
- T2-23 转人工上下文包生成器：守卫命中后 `handoff` 节点使用的联系入口与朗读文案。
- T2-04 流程配置 YAML：`pig.yaml` 中的识别信号清单与法定时限链。
- 外部环境：`USE_MOCK_LLM=true` 可离线；守卫为规则实现，不依赖模型。

## 实现要点

### 结构特例的三条硬性要求

| 要求 | 说明 | 落地方式 |
| --- | --- | --- |
| 守卫在 `observe` 之前 | 不能先看现场再判断是否应报告，先报告再决定后续 | 子图入口边指向 `report_guard`，而不是 `observe` |
| 守卫输出优先级最高 | 守卫命中即中止问诊，子图内部任何产出不得覆盖 | `stop_consultation=True` 时跳过 `observe`/`interview`/`judge`/`prescribe`，直接出 `handoff` |
| 用条件边实现，不改通用节点 | 其余六条流程不承担养猪的语义 | 差异只写在 `pig.py` 与猪专属路由函数里，`factories.py` 与其余节点零改动 |

### 养猪子图完整结构

```python
"""养猪流程子图：报告守卫前置，输出优先级最高（方案 7.4 唯一结构特例）。"""
from langgraph.graph import END, START, StateGraph

from app.agent.agents.report_guard import build_report_guard_node
from app.agent.graph.factories import (get_config, make_interview_node, make_judge_node,
                                       make_observe_node, make_prescribe_node, make_verify_node)
from app.agent.graph.routes import (ROUTE_AFTER_INTERVIEW, ROUTE_AFTER_JUDGE,
                                    ROUTE_AFTER_SUBGRAPH_GUARD,
                                    route_after_interview, route_after_judge, route_after_subgraph_guard)
from app.agent.state import ConsultationState, ProcessId


def build_pig_subgraph():
    """养猪子图：入口守卫 → observe → 兜底守卫 → interview → verify → judge → prescribe。"""
    config = get_config(ProcessId.PIG)
    graph = StateGraph(ConsultationState)

    guard = build_report_guard_node(config)     # 纯规则，不调模型，fail-closed

    graph.add_node("report_guard_entry", guard)   # 入口守卫：先于 observe
    graph.add_node("observe", make_observe_node(config))
    graph.add_node("report_guard", guard)         # 兜底守卫：observe 之后
    graph.add_node("interview", make_interview_node(config))
    graph.add_node("verify", make_verify_node(config))
    graph.add_node("judge", make_judge_node(config))
    graph.add_node("prescribe", make_prescribe_node(config))

    # 入口守卫：命中即出子图（handoff 键在 ROUTE_AFTER_SUBGRAPH_GUARD 里映射 __end__）
    graph.add_edge(START, "report_guard_entry")
    graph.add_conditional_edges(
        "report_guard_entry", route_after_subgraph_guard, ROUTE_AFTER_SUBGRAPH_GUARD,
    )

    # observe 之后再做一次兜底检查（方案 5.3.7：observe 与 interview 之后各挂一次）
    graph.add_edge("observe", "report_guard")
    graph.add_conditional_edges("report_guard", route_after_subgraph_guard, ROUTE_AFTER_SUBGRAPH_GUARD)

    graph.add_conditional_edges("interview", route_after_interview, ROUTE_AFTER_INTERVIEW)
    graph.add_edge("verify", "judge")
    graph.add_conditional_edges("judge", route_after_judge, ROUTE_AFTER_JUDGE)
    graph.add_edge("prescribe", END)
    return graph
```

注意 `graph.add_edge(START, "report_guard_entry")`：子图的入口被守卫占据，`observe` 只可能在入口守卫放行后执行。方案 7.1 主图里 `ROUTE -->|pig| RG1` 的入口守卫即此节点，它实例化在子图内部（子图的边不能指向父图节点）。

### 守卫路由复用既有函数

本项不新增路由函数。`route_after_subgraph_guard` 按 `stage` 区分两个挂载点：`stage in (INTAKE, TRIAGE)` 时是入口守卫，放行返回 `observe`；`stage == OBSERVE` 时是兜底守卫，放行返回 `interview`；命中信号或红线未加载都返回 `handoff`，在 `ROUTE_AFTER_SUBGRAPH_GUARD` 里映射到子图出口 `__end__`，由主图 `route_after_subgraph` 判定后去 `handoff` 节点。守卫命中时 `stop_consultation=True`，`route_after_subgraph` 据此转人工，`prescribe` 不执行。

复用的好处是七条流程共用一份守卫路由逻辑，养猪的结构差异只体现在"多一个入口守卫节点 + 两条边"，不产生猪专属的路由分支，也就没有新的未覆盖情形。`ROUTE_AFTER_SUBGRAPH_GUARD` 的键集合 `{observe, interview, handoff}` 在两个挂载点上都成立。

### 输出优先级的具体含义

`report_guard` 命中时写出的 `mandatory_actions`（立即隔离、消毒、报告）与 `contacts`（本地联系入口）必须出现在最终 `reply`，且**不得**被后续任何节点改写或截断。实现上有两层保障：

第一层，守卫命中即 `handoff`，`prescribe` 根本不执行，因此不存在"报告提示与处方文案混排"的可能。

第二层，`handoff` 节点读 state 上的 `report_decision`，用固定模板渲染，模型无权改写这段文本。守卫契约中的 `mandatory_actions` 顺序即展示顺序，隔离与消毒在前、报告对象在后。

### 单个识别信号即触发

`trigger_source = "signal"` 的判定门槛极低：只要 `matched_signals` 非空即置 `triggered = True`，不要求数量、不要求同时命中群组信号或群体死亡。这是产品说明书 5.7 明确要求纠正的认知盲区。实现上 `ReportGuard` 的判定是"任一信号命中即真"的析取，而非多数表决；本项只需确保路由函数不额外加"信号数量阈值"判断——门槛一律以 `ReportDecision.triggered` 为准。

### 内容保留但不继续追问

守卫命中后，`slots` 与 `messages` 原样保留在检查点里，`stage` 置 `ConsultStage.HANDOFF`。农户后续若在同一 `session_id` 继续提问，`handoff` 节点会看到已有 `report_decision`，重放法定义务提示，不会退回 `interview`。这一行为由 `route_after_subgraph_guard` 的 `handoff` 分支保证：只要 `report_decision` 已存在且 `stop_consultation`，无论 `stage` 是什么都出子图，主图 `route_after_subgraph` 再判定转人工。

### 这不是兜底而是正常分支

产品说明书 6.3 的界定要在文案与契约上体现：`ReportDecision` 不是异常对象，`handoff` 不是错误路径。主图 `handoff → END` 与 `followup → END` 是并列的正常出口。前端拿到的是 200 响应里带 `handoff` 字段，而不是错误码（见 T2-33）。守卫**不做**疫情的最终认定，只输出法定义务提示与报告对象。

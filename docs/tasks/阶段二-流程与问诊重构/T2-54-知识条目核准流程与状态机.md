# T2-54 知识条目核准流程与状态机

## 这一项要做什么

在 `app/services/knowledge_review.py` 与 `app/models/knowledge_review.py` 中实现知识条目的核准流程与状态机：条目必须经人工审核才能从 `draft` 变为 `approved`，`suspended` 的每次变更必须留下操作记录与理由，状态迁移必须合法（不允许从 `draft` 直接跳到 `suspended` 之类的越级）。它在技术上落实方案 9.2 的 `status` 四值语义，在流程上落实"L3 处置知识是红线的基础，其条目必须经过核准流程"。

这张表的每一个 `approved` 条目都是闸门规则的比对基准，因此"谁在什么时候把哪条改成了什么状态、理由是什么"必须可查。

## 实现要点

### 状态机的合法迁移

```python
class KnowledgeAction(str, Enum):
    SUBMIT = "submit"           # draft -> pending（提交待审）
    APPROVE = "approve"         # pending -> approved
    REJECT = "reject"           # pending -> draft（打回，带理由）
    SUSPEND = "suspend"         # approved -> suspended（带理由）
    RESUME = "resume"           # suspended -> approved
    DEPRECATE = "deprecate"     # approved/suspended -> deprecated

ALLOWED_TRANSITIONS: dict[KnowledgeStatus, dict[KnowledgeAction, KnowledgeStatus]] = {
    KnowledgeStatus.DRAFT: {KnowledgeAction.APPROVE: KnowledgeStatus.APPROVED,
                            KnowledgeAction.SUBMIT: KnowledgeStatus.DRAFT, },
    KnowledgeStatus.APPROVED: {KnowledgeAction.SUSPEND: KnowledgeStatus.SUSPENDED,
                               KnowledgeAction.DEPRECATE: KnowledgeStatus.DEPRECATED, },
    KnowledgeStatus.SUSPENDED: {KnowledgeAction.RESUME: KnowledgeStatus.APPROVED,
                                KnowledgeAction.DEPRECATE: KnowledgeStatus.DEPRECATED, },
    KnowledgeStatus.DEPRECATED: {},
}
```

`DEPRECATED` 是终态，没有任何出边：条目废弃是永久的，若要恢复它应新建条目而不是改回。这条约束由空字典表达，且需要测试断言。

不设 `pending` 独立状态（用 `draft` 承载"待审"），是为了与方案 9.2 的四值保持完全一致。方案只给了四值，若在这里加第五个状态，检索侧与闸门侧的所有 `status` 判断都要跟着改。审核队列可以用 `KnowledgeReviewLog` 查"最近提交待审的条目"来表达，不占用主表的状态位。

### 核准必须人工

```python
class KnowledgeReviewService:
    """知识条目状态机与核准流程。所有变更留痕。"""
    def __init__(self, session: AsyncSession) -> None:
        self._session = session
        self._repo = KnowledgeRepository(session)
        self._log_repo = KnowledgeReviewLogRepository(session)
    async def apply(self, *, knowledge_id: str, action: KnowledgeAction,
                    operator_id: str, reason: str | None = None) -> KnowledgeItem:
        """执行一次状态迁移。非法迁移与缺理由均抛异常。"""
        item = await self._repo.get_by_id(knowledge_id)
        if item is None:
            raise KnowledgeNotFound(knowledge_id)
        current = KnowledgeStatus(item.status)
        target = ALLOWED_TRANSITIONS[current].get(action)
        if target is None:
            raise IllegalTransition(f"{current.value} 不允许动作 {action.value}")
        self._require_reason(action, reason)
        await self._write_log(item, current, target, action, operator_id, reason)
        await self._repo.update_status(knowledge_id, target, reason)
        return await self._repo.get_by_id(knowledge_id)
    def _require_reason(self, action: KnowledgeAction, reason: str | None) -> None:
        """暂停、打回、废弃必须给出理由；核准与恢复可不填。"""
        if action in {KnowledgeAction.SUSPEND, KnowledgeAction.REJECT, KnowledgeAction.DEPRECATE}:
            if not reason or not reason.strip():
                raise ReasonRequired(f"动作 {action.value} 必须给出理由")
```

`draft -> approved` 不允许由自动流程触发：`apply` 的 `action=APPROVE` 需要 `operator_id` 非空且指向一个真实后台账号。索引构建器写入条目时只能用 `status=draft` 或数据文件里预先声明的状态，不能调用 `apply` 自行核准。这条边界保证"未经人工审核的条目不会进入检索"。一期可用运营账号人工操作，后台管理界面留待后续，但接口与留痕在本项就位。

`suspended` 的 `reason` 必填，且会同时写入主表的 `status_reason`（供检索侧排查）与变更记录（供追溯全历史）。两个位置都写是刻意的：主表的 `status_reason` 是当前状态的说明，变更记录是完整时间线；只留其一都会在某个查询场景下缺失信息。

### 变更记录表

```python
class KnowledgeReviewLog(Base):
    """知识条目状态变更记录。只追加，不修改，不删除。"""
    __tablename__ = "knowledge_review_log"

    id = mapped_column(String(36), primary_key=True)
    knowledge_id = mapped_column(String(36), nullable=False, index=True)
    from_status = mapped_column(String(20), nullable=False)
    to_status = mapped_column(String(20), nullable=False)
    action = mapped_column(String(20), nullable=False)
    reason = mapped_column(Text, nullable=True)
    operator_id = mapped_column(String(36), nullable=False, index=True)
    consulted_ref = mapped_column(String(36), nullable=True)   # 关联的问诊，若因某次问诊触发
    created_at = mapped_column(DateTime(timezone=True), nullable=False, server_default=func.now(), index=True)

    __table_args__ = (Index("ix_review_log_kid_created", "knowledge_id", "created_at"),)
```

`consulted_ref` 用于"因某次问诊触发的暂停"这类场景：某农户问诊后发现该药在其地区失效，触发把条目标 `suspended`，此时记录关联的问诊 id，日后复审能查到触发来源。它是可空的，因为多数变更来自通报名单而非单次问诊。

变更记录只追加。数据库层面用无 `updated_at` 与无更新接口表达"不可变"，与审计表的处理一致。若某次操作填错，正确做法是追加一条纠正记录（把状态改回），而不是修改历史记录。

### 与索引构建的衔接

索引构建器（T2-48）在写入条目时遇到已存在的条目，只更新内容字段，**不改状态**。状态只能经 `KnowledgeReviewService.apply` 变更。这条边界防止"重新构建索引把人工核准的裁决覆盖掉"——这是很隐蔽的一类事故：内容建设阶段反复跑构建，若构建会重置状态，则所有已核准条目会退回 `draft`，检索立即空掉。

若条目数据文件里的 `status` 与数据库里的不一致（如文件里写 `approved` 而库中是 `draft`），构建器以数据库为准并记一条 warn 日志，提示"文件里的状态声明被忽略，请通过核准流程变更"。这样数据文件的状态字段只在首次插入时生效。

### 恢复与地区差异

`resume` 把 `suspended` 改回 `approved`。若某药剂只在部分地区暂停，恢复也按地区：用两条地区不同的条目表达（见 T2-52），恢复动作只作用于对应 `knowledge_id`。因此状态机的操作粒度是单条 `knowledge_id`，不做按药剂名批量操作，避免"批量恢复"误伤其他地区的暂停状态。

### 权限与审计

核准接口需要后台权限，与农户侧接口分离。接口层校验 `operator_id` 来自后台账号，农户令牌无法调用。每次变更除写 `knowledge_review_log` 外，还要上报一条指标（各动作的日频次），供"暂停名单最近是否异常频繁变动"这类监控。

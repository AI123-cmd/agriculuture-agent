# T2-09 分诊与现场观察契约

## 这一项要做什么

在 `app/agent/contracts/triage.py` 与 `app/agent/contracts/observation.py` 中定义分诊智能体与现场采集智能体的输出契约 `TriageResult` 与 `ObservationResult`。前者决定流程归属与对象确认，后者把环境读数与图片识别归纳为带来源的现场事实。

这两个契约处在链路最前端，它们的字段必须支持两个硬要求：分诊不得生成任何问题（唯一产出是流程标识与缺口列表），现场采集的数据不可用必须被显式标记而不是静默返回空值。这两点都由契约结构保证，而不是靠提示词约束。

## 前置依赖

- 依赖 T2-08：必须已提供 `ConsultationState` 与 `SlotValue`，本项契约中的槽位缺口要能与之互操作
- 依赖 T2-01：必须已提供 `ProcessId`
- 依赖 T2-02：必须已提供 `SlotSpec`，缺口列表的取值须来自流程配置的槽位 key
- 外部环境：图片识别与传感器读数来源由 T5 提供，本项只定义契约，不实现采集

## 实现要点

### TriageResult

```python
class TriageResult(BaseModel):
    """分诊输出。技术方案 5.3.2 原样定义，字段语义如下。"""
    model_config = ConfigDict(extra="forbid")

    process_id: ProcessId
    object_confirmed: bool
    object_label: str
    slot_gaps: list[str]
    profile_ready: bool
    fallback_reason: str | None = None
    handoff_to_report: bool = False

    @model_validator(mode="after")
    def _fallback_requires_reason(self) -> "TriageResult":
        if self.process_id is ProcessId.GENERAL and not self.fallback_reason:
            raise ValueError("降级到 general 必须给出 fallback_reason")
        return self

    @model_validator(mode="after")
    def _pig_handoff_consistency(self) -> "TriageResult":
        if self.handoff_to_report and self.process_id is not ProcessId.PIG:
            raise ValueError("handoff_to_report 仅养猪流程可置为 True")
        return self
```

第一条校验器实现技术方案 5.3.2 的隐含要求：降级到 `general` 不是"没匹配上就默认"，而是一个需要说明理由的决策。有了 `fallback_reason`，线上指标里"哪些表述容易分流失败"就有据可查，而不只是看到一个模糊的 general 占比。

第二条校验器防止其他流程误用 `handoff_to_report`。这个字段的语义很窄：养猪流程以"不漏报"为最高目标，在 `observe` 之前就插入报告守卫。若杂草流程也能置它为 True，主图会在无关场景跳过现场采集。

`object_label` 是展示用字符串，如"水稻·3亩"、"2号栏舍·120头"。它是**有格式约定的字符串**而非结构化字段，因为它的唯一用途是回显给农户确认，结构化反而增加无用的解析负担。

### 对象确认

```python
class ObjectConfirmRequest(BaseModel):
    """对象待确认时插入的一次交互。"""
    model_config = ConfigDict(extra="forbid")

    asked_process_id: ProcessId          # 分诊初步判定的流程
    profile_process_id: ProcessId | None  # 档案中记录的流程
    candidate_labels: list[str]           # 供农户选择的对象名
    question_text: str                    # 面向农户的确认问句
    matched_alias: str | None = None      # 命中的同义词，便于复盘
```

对象确认的判定方式在技术方案 5.3.2 中写明：档案流程与农户表述中的作物词做实体匹配，基于流程配置里的同义词表（`object_aliases`）。不匹配时 `object_confirmed = False`，主图转入确认分支，确认后更新 `process_id` 并锁定。

`ObjectConfirmRequest` 因此要携带 `profile_process_id` 与 `matched_alias` 两个诊断信息：前者用于生成"您档案里登记的是水稻，这次问的是茶吗"这类问句，后者用于线上统计"哪些别名容易漏配"。二者都不进入面向农户的最终文案，只作为提示词与统计的输入。

匹配函数放在契约模块而不是分诊智能体里，因为它是纯函数，可独立测试：

```python
def match_object_alias(text: str, configs: dict[ProcessId, ProcessConfig]) -> ProcessId | None:
    """按各流程 object_aliases 做最长别名优先匹配。命中多个流程时取最长者。"""
    hits: list[tuple[int, ProcessId]] = []
    for pid, config in configs.items():
        for alias in config.object_aliases:
            if alias and alias in text:
                hits.append((len(alias), pid))
    if not hits:
        return None
    hits.sort(reverse=True)
    return hits[0][1]
```

"最长别名优先"是为了处理别名互相包含的情形：茶树流程的别名含"茶"，若农户说的是"茶小绿叶蝉"（害虫名而非作物名），按最短匹配会命中茶流程，按最长匹配若存在更长的别名也能正确路由。命中长度相同时返回流程枚举顺序靠前者，保证同一输入永远得到同一结果——这是路由可确定性重放的要求。

### ObservationResult

```python
class EnvReading(BaseModel):
    """一条环境读数。numeric 字段必须带来源。"""
    model_config = ConfigDict(extra="forbid")

    metric: Literal["air_temp", "air_humidity", "soil_temp", "soil_moisture", "light", "rainfall"]
    value: float | None
    unit: str
    source: Literal["sensor", "weather", "manual"]
    quality: Literal["ok", "stale", "suspect", "missing"] = "ok"
    observed_at: datetime | None = None
    device_sn: str | None = None


class ImageCandidate(BaseModel):
    """一条图片识别候选，候选域由流程限定。"""
    model_config = ConfigDict(extra="forbid")

    label: str
    score: float
    part: str | None = None              # 叶片/茎/根/果实


class ObservationResult(BaseModel):
    """现场采集输出。数据不可用必须显式标记。"""
    model_config = ConfigDict(extra="forbid")

    readings: list[EnvReading] = []
    image_candidates: list[ImageCandidate] = []
    data_available: bool
    unavailable_reason: str | None = None
    env_source: Literal["sensor", "weather", "manual", "none", "sensor_stale"]
    observed_facts: dict[str, str] = {}
    note: str | None = None              # 面向农户的环境说明

    @model_validator(mode="after")
    def _unavailable_requires_reason(self) -> "ObservationResult":
        if not self.data_available and not self.unavailable_reason:
            raise ValueError("data_available=False 时必须给出 unavailable_reason")
        return self

    @model_validator(mode="after")
    def _env_note_required(self) -> "ObservationResult":
        if self.env_source in ("none", "sensor_stale") and not self.note:
            raise ValueError("env_source 为 none 或 sensor_stale 时必须提供 note")
        return self
```

第二条校验器直接落实产品说明书 4.2.3 功能点 6：界面必须明确标注当前没有环境数据、以下判断基于农户描述。把这个要求做成契约必填字段，而不是靠接口层记得加，是唯一可靠的实现方式。

`EnvReading` 中的 `value: float | None` 配 `quality` 字段，把"读到了但数据可疑"与"根本没读到"分开：前者 `value` 有值且 `quality="suspect"`，后者 `value=None` 且 `quality="missing"`。这与 `SlotValue` 区分 `unknown` 与 `missing` 是同一个设计原则。

`observed_facts` 是 `dict[str, str]`，键为事实名（如 `rain_last_3d`），值为口语化描述。它进入 `ConsultationState.observations`，供问诊与判定的提示词注入。

### 现场采集的失败行为与分诊的区别

现场采集失败（传感器无数据、图片识别不可用）**不阻断问诊**：`data_available=False` 但流程继续，界面标注环境说明，判定智能体据此降低确定性表述。分诊失败**回退通用流程**：`process_id=general` 且 `fallback_reason` 非空。

这个差异要写进两个契约类的 docstring，避免执行者把两者的失败策略写成同一套。

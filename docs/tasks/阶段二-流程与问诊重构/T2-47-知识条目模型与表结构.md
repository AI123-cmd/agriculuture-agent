# T2-47 知识条目模型与表结构

## 这一项要做什么

在 `app/models/knowledge.py` 中建立知识库的持久化结构，把技术方案 9.2 的四层知识落到 `knowledge_item` 与 `knowledge_region` 两张表上，字段清单以 9.2 的表格为准逐项实现。这张表是整条安全链路的比对基准：闸门的 `R-WHITELIST` 判断药剂是否在已核准清单内，`R-REGISTERED-CROP` 判断登记作物，`R-DOSAGE` 判断剂量区间，`R-INTERVAL` 判断安全间隔期，全部都要回查这张表。没有它，闸门的所有药剂类规则都无从判定。 表结构要能从字段层面表达"抗药性暂停名单"这类动态变更，而不是靠删条目实现，因为历史问诊记录需要能追溯当时为什么没推荐某味药。

## 实现要点

### 知识条目主表

```python
class KnowledgeItem(Base):
    """知识条目。四层知识共用一张表，以 kind 区分。"""
    __tablename__ = "knowledge_item"

    knowledge_id = mapped_column(String(36), primary_key=True)     # 如 K-1023
    process_id = mapped_column(String(20), nullable=False, index=True)
    kind = mapped_column(String(20), nullable=False, index=True)   # disease/pest/pesticide/cultivation/threshold
    title = mapped_column(String(120), nullable=False)
    content = mapped_column(Text, nullable=False)                  # 正文，用于检索与改写

    # ---- 药剂类字段（kind=pesticide 时有值）----
    pesticide_name = mapped_column(String(80), nullable=True, index=True)
    registered_crops = mapped_column(JSONB, nullable=False, default=list)
    dosage_min = mapped_column(Numeric(12, 4), nullable=True)
    dosage_max = mapped_column(Numeric(12, 4), nullable=True)
    dosage_unit = mapped_column(String(16), nullable=True)         # 克/亩、毫升/亩、倍液
    safety_interval_days = mapped_column(Integer, nullable=True)
    max_uses_per_season = mapped_column(Integer, nullable=True)
    forbidden_combinations = mapped_column(JSONB, nullable=False, default=list)

    # ---- 适用范围与生效期 ----
    region_scope = mapped_column(String(12), nullable=True, index=True)  # 行政区编码前缀，NULL 表示全国
    effective_date = mapped_column(Date, nullable=True)
    expire_date = mapped_column(Date, nullable=True)

    # ---- 状态与来源 ----
    status = mapped_column(String(20), nullable=False, default="draft", index=True)
    status_reason = mapped_column(Text, nullable=True)             # suspended 的理由必填
    source_ref = mapped_column(Text, nullable=True)                # 权威来源引用

    # ---- 检索 ----
    embedding = mapped_column(Vector(1024), nullable=True)         # pgvector 列

    created_at = mapped_column(DateTime(timezone=True), nullable=False, server_default=func.now())
    updated_at = mapped_column(DateTime(timezone=True), nullable=False, server_default=func.now(), onupdate=func.now())

    __table_args__ = (
        CheckConstraint("kind != 'pesticide' OR dosage_min IS NULL OR dosage_max IS NULL OR dosage_min <= dosage_max",
                        name="ck_knowledge_dosage_range"),
        CheckConstraint("status != 'suspended' OR status_reason IS NOT NULL",
                        name="ck_knowledge_suspended_reason"),
        Index("ix_knowledge_process_status_kind", "process_id", "status", "kind"),
        Index("ix_knowledge_region_scope", "region_scope", postgresql_using="btree"),
    )
```

`knowledge_id` 用可读的业务主键（形如 `K-1023`）而不是 UUID。原因是它会被写入处方的 `facts_provenance`（形如 `knowledge:K-1023:field:dosage_min`），会出现在闸门拦截消息里，也会被审计表引用；一串 UUID 在这些位置既不便人工核对也不便排查。这与全局约定"主键统一 `String(36)`"不冲突：约定针对的是业务表主键必须可归属与可索引，本表用业务编码同样满足，且编码长度远小于 36。

`pesticide_name` 单独成列并建索引而不放进 `content`，是因为 `R-WHITELIST` 与 `R-CONFLICT` 需要按药剂名精确查。从正文里做模糊匹配会把"含某药名"的无关条目也召回，判定层无法区分。

### status 四值语义

```python
class KnowledgeStatus(str, Enum):
    DRAFT = "draft"            # 待核准，不参与检索
    APPROVED = "approved"      # 已核准，唯一可被检索使用的状态
    SUSPENDED = "suspended"    # 临时停用，检索强制排除，如抗药性暂停名单
    DEPRECATED = "deprecated"  # 已废弃，保留用于历史处方追溯，不参与新检索
```

四个取值的语义边界必须在实现里写死，不允许模糊：

| 取值 | 是否可被检索 | 语义 | 典型变更来源 |
| --- | --- | --- | --- |
| `approved` | 是 | 已核准，当前有效 | 人工核准通过 |
| `suspended` | 否（强制排除） | 临时停用，随时可能恢复 | 抗药性暂停名单、临时禁限用 |
| `deprecated` | 否（新检索排除） | 永久废弃，仅留档 | 标准更新、条目被新条目取代 |
| `draft` | 否 | 尚未核准 | 新建条目、修订中的条目 |

`suspended` 与 `deprecated` 在检索侧都是排除，但对历史追溯的含义不同：`suspended` 条目将来可能恢复 `approved`，`deprecated` 条目不会。因此 `status_reason` 在 `suspended` 时强制非空（由 `ck_knowledge_suspended_reason` 约束保证），在 `deprecated` 时可空。

### 为什么抗药性暂停用药建模为 suspended 而不是删除

抗药性暂停名单的实时性要求条目可以随时进出名单（某地稻飞虱对某药产生抗性即暂停，抗性消退或新配方上市后恢复）。若用"删除条目"实现，会同时丢掉两样东西：

第一，历史问诊无法追溯。农户三个月前问稻飞虱，当时该药被暂停所以没推荐，若条目已删除，历史详情页就说不清"当时为什么没给这味药"，客服复盘也查不到。保留条目并标记 `suspended`，加上 `status_reason` 与变更记录，能回答"什么时候因为什么被暂停"。

第二，恢复名单要重新录入全部字段。删除后恢复等于新建条目，剂量区间、登记作物、安全间隔期都要重新核一遍，而暂停往往只是短期措施。保留条目只需把 `status` 改回 `approved`。

因此检索侧的处理是：`_build_filters` 只放行 `status = "approved"`，`suspended` 与 `deprecated` 在候选集层面被排除，而不是在条目层面不存在。闸门的 `R-WHITELIST` 同样以 `approved` 为准，命中 `suspended` 条目即判定为未登记并拦截。

### 地区适用范围表

```python
class KnowledgeRegion(Base):
    """地区适用范围：一条知识条目可覆盖多个行政区，支持分级回退匹配。"""
    __tablename__ = "knowledge_region"

    id = mapped_column(String(36), primary_key=True)
    knowledge_id = mapped_column(String(36), nullable=False, index=True)
    region_code = mapped_column(String(12), nullable=False, index=True)  # 行政区编码
    region_level = mapped_column(String(10), nullable=False)             # county/city/province/national
    created_at = mapped_column(DateTime(timezone=True), nullable=False, server_default=func.now())

    __table_args__ = (UniqueConstraint("knowledge_id", "region_code", name="uq_knowledge_region"),
                      Index("ix_knowledge_region_code_level", "region_code", "region_level"), )
```

独立的地区表用于表达"一条水稻稻瘟病条目适用于全省但只在三个县有专门剂量"。`region_scope` 列保存条目的主适用范围前缀，用于快速过滤；`knowledge_region` 保存精确到县的多地挂载，用于 T2-50 的逐级回退匹配。两者并存：过滤走 `region_scope` 的 SQL 条件，回退判定走 `knowledge_region` 的精确查表。`region_level` 决定该条目在回退链的哪一级被命中，与 `EvidenceItem.region_scope` 的标注直接对应。

### 与知识库的关联不做数据库外键

技术方案 12.7 明确"与知识库表的关联建议不加数据库级外键"，原因是知识条目会随版本迭代而 `deprecated`，历史处方卡需要允许"引用已废弃条目"用于追溯。若加外键并在条目废弃时级联，历史处方卡会失去它引用的条目。因此 `prescription_card.pesticide_items` 里保存的 `knowledge_id` 是应用层校验的快照，不设外键。本项的表结构要为此留出空间：条目不允许物理删除，只允许改 `status`。

### 迁移要点

迁移中建立 `vector` 扩展的依赖检查（若 T1-03 未建则在本迁移开头 `CREATE EXTENSION IF NOT EXISTS vector`），然后建表、建两个校验约束、建普通索引，最后建向量索引：

```sql
CREATE INDEX ix_knowledge_embedding_hnsw ON knowledge_item
    USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

HNSW 索引单独建而不放进 `__table_args__`，因为它依赖数据规模与 pgvector 版本，且需要与普通索引分开调参。`downgrade` 中按"先 drop 索引、再 drop 表、最后不动扩展"的顺序回退，扩展由 T1-03 负责生命周期，本迁移不 drop。

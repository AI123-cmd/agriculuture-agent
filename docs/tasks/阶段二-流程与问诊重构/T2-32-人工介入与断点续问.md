# T2-32 人工介入与断点续问

## 这一项要做什么

用 LangGraph 的 `interrupt` 把"等农户回答"与"安全拦截后确认"两类暂停接入主图，并保证三个恢复场景（农户中途退出、模型超时、服务重启）都能从检查点继续。方案 7.3 明确 `interrupt` 有两个用法，且强调"本产品用 LangGraph 的持久执行能力覆盖多轮问诊的断点续问需求"。本项改动集中在 `app/agent/graph/main.py`，是 T2-25 的增量：主图节点序列不变，只在 `interview` 与 `handoff`/`gate` 两处引入中断点。

## 前置依赖

- T2-30 Postgres 检查点器替换与中断恢复：`interrupt` 依赖 checkpointer 持久化中断时的完整状态，SQLite 单连接实现的并发与跨循环问题会直接破坏中断恢复。
- T2-25 主图组装 main：`interview`、`gate`、`handoff` 节点已就位。
- T2-31 轮次与成本预算守卫：恢复时需要读 `budget` 判断是否仍可继续问诊。
- T2-20 受控并行会诊 Panel：panel 节点同样需要支持中断（茶/辣椒/杂草）。
- T2-09 至 T2-12 契约层：`interview` 产出的 `InterviewBatch`、`gate` 产出的 `GateResult` 字段名。
- 外部环境：PostgreSQL 可连（中断状态持久在此）；前端支持携带 `sessionId` 续问。

## 实现要点

### 两类 interrupt 用法

| 类别 | 触发位置 | 中断载荷（interrupt 值） | 恢复输入 | 用途 |
| --- | --- | --- | --- | --- |
| 等待农户回答 | `interview` 节点生成问题后 | 本轮问题列表 + `stage_hint` + 进度 | 农户的 `answers` / `message` / `imageUrl` | 最基础的 human-in-the-loop，多轮问诊的每一轮都靠它 |
| 安全拦截后的确认 | `gate` 判定 `degrade` 后 | 转人工引导文案 + 命中规则摘要 + 是否继续咨询的选项 | `continue` 或 `abort` | 高风险输出前先由农户知情确认，对应"高风险操作前必须经过人工审批" |

两类中断的差别在恢复语义：第一类恢复是"接着问"，第二类恢复是"是否继续"。因此第二类的恢复输入是一个枚举，不是农户的自然语言回答。

### interview 处的中断

```python
from langgraph.types import interrupt


async def interview(state: ConsultationState, runtime) -> dict:
    """问五情：生成问题后中断等待农户回答，下个 HTTP 请求携带回答恢复。"""
    batch = await run_interviewer(state)          # 候选池由代码筛选，模型只生成问法
    payload = {
        "questions": [q.model_dump() for q in batch.questions],
        "stage_hint": batch.stage_hint,
        "progress": progress_of(state),
    }
    # 中断点：此处暂停，检查点已保存完整状态；返回值即恢复时传入的答案
    answers = interrupt(payload)

    slots = apply_answers(state.get("slots", {}), answers)
    budget = ConsultBudget(**state.get("budget", {}))
    budget.note_interview_round()
    return {"slots": slots, "budget": budget.to_state(), "stage": ConsultStage.INTERVIEW}
```

关键点：`interrupt` 必须在节点函数内、在写入新状态之前调用，这样恢复时节点从头执行、重新生成同一批问题（确定性）、再套用答案。因为候选池筛选与问题是确定性生成，重复执行不会产生不同的问题。

### gate 处的中断（安全拦截后的确认）

```python
async def gate_with_confirm(state: ConsultationState, runtime) -> dict:
    """安全闸门：allow 直接过；degrade 时中断，等农户确认是否继续咨询。"""
    gate_result = await run_gate(state)
    if gate_result.decision == "allow":
        return {"gate_result": gate_result.model_dump(), "stage": ConsultStage.GATE}

    # degrade/block：不直接返回处方，先中断让农户知情
    decision = interrupt({
        "kind": "gate_confirm",
        "decision": gate_result.decision,
        "why": gate_result.degrade_output,
        "options": ["continue", "abort"],
    })
    return {
        "gate_result": gate_result.model_dump(),
        "gate_confirmed": decision == "continue",
        "stage": ConsultStage.GATE,
    }
```

`block` 与 `degrade` 在中点行为上相同（都要农户知情），但恢复后的走向不同：`degrade` 且农户选 `continue` 时进 `handoff` 输出转人工引导（不是放行处方）；`block` 无论选什么都不输出处方。这条由 `route_after_gate` 保证——它只认 `decision`，不认 `gate_confirmed` 是否放行。

### 恢复入口

```python
from langgraph.types import Command


async def resume_graph(session_id: str, resume_value: object) -> dict:
    """按 thread_id 恢复中断的图，传入农户的回答或确认选择。"""
    graph = await get_agent()
    config = {"configurable": {"thread_id": session_id}}
    return await graph.ainvoke(Command(resume=resume_value), config=config)
```

### 三个恢复场景

**场景一，农户中途退出，稍后继续。** 农户提问后图在 `interview` 中断，检查点已保存。农户关闭小程序、次日回来，前端带同一 `sessionId` 调 `/chat`。服务端不新建会话，而是用该 `sessionId` 作 `thread_id` 调 `resume_graph`，图从 `interview` 的断点继续，`stage` 停在 `interview`，`slots`、`messages`、`budget` 全部保留。可观察的验收点：次日续问时 `progress.current` 与上次一致，已答槽位不再被重复提问。

**场景二，模型服务超时。** 节点级重试由 tenacity 做（指数退避，最多 2 次），重试发生在节点内部，不涉及检查点。超过 2 次后走降级分支：`interview` 降级为固定模板问题（不问模型），`judge` 降级为 `confidence_level = "uncertain"` 并置 `degraded = True`。检查点的作用是保证重试不会重复执行已完成的节点——若中断发生在 `verify` 之后，恢复从 `verify` 之后开始。

**场景三，服务重启。** 检查点持久在 PostgreSQL 的 `checkpoint` schema，进程重启不丢状态。重启后第一个请求带 `sessionId` 进来，服务端用 `graph.aget_state(config)` 读取该 thread 的最新快照，若存在 `next` 节点则用 `resume_graph` 继续；若不存在（会话已结束）则按新会话或返回历史。这里有一个硬要求：**重启后不能把已有会话当成新会话处理**，否则农户会看到"从头再问一遍"。

### 判断"是否需要恢复"

服务端在 `/chat` 入口处要先判断这次请求是新会话还是续问：

| 条件 | 判定 | 处理 |
| --- | --- | --- |
| `req.sessionId is None` | 新会话 | 生成新 `session_id`，`graph.ainvoke(initial_state)` |
| `sessionId` 存在且 `graph.aget_state()` 有 `next` | 中断中 | `resume_graph(sessionId, resume_value)` |
| `sessionId` 存在且 `aget_state()` 无 `next` | 已结束 | 视为新会话或返回结束时的产出（由 T2-33 决定） |

`next` 为空表示图没有待执行节点，即已走到 `END`。中断中时 `next` 会包含被中断的节点名。

### 与预算守卫的协同

恢复时必须用检查点里的 `budget` 继续记账，不能在 `intake` 重新初始化。因此 `intake` 只在 `budget` 为空时初始化：

```python
budget = state.get("budget") or ConsultBudget.initial().to_state()
```

若恢复时把 `budget` 重置为零，轮次上限会被绕过，农户可以靠"退出再进来"无限追问——这是本项必须堵住的一个漏洞。

### 中断载荷的展示约束

首类中断的载荷（问题列表）会被接口层渲染成 `questions` 字段，第二类中断的载荷会被渲染成 `handoff` 字段加确认选项。这两类载荷都必须走口语化映射，不能把内部术语（`slot_key`、规则 id）直接给农户看。中断载荷里携带内部字段（如 `matched_signals`）是允许的，用于前端调试面板，但展示文案必须经 `colloquial_map` 替换。

## 验收标准

- `pytest tests/graph/test_interrupt.py` 全部通过，包含：
  - 第一次 `ainvoke` 在 `interview` 处返回中断，断言返回值的 `__interrupt__` 载荷含 `questions`、`stage_hint`、`progress`，且节点数不超过 2。
  - 用 `Command(resume={"answers": [...]})` 再次 `ainvoke`，断言图继续执行且 `slots` 中出现对应槽位、`budget.interview_rounds == 1`。
  - 构造 `gate_result.decision="degrade"`，断言在 `gate` 处中断，恢复输入 `continue` 后路径为 `handoff` 而非 `followup`；恢复输入 `abort` 后同样到 `handoff` 且 `reply` 为中止提示。
  - 场景一侧试：中断后丢弃图实例，重新 `build_graph()` 用同一 `thread_id` 恢复，断言已答槽位不重复出现在下一轮问题里。
  - 场景三侧试：中断后 `await close_checkpointer()` 再 `await get_checkpointer()`，用同一 `thread_id` 恢复成功，`progress.current` 与中断前一致。
- 恢复时不重置预算的回归测试：中断、恢复、再中断、再恢复两次后，断言 `budget.interview_rounds == 2` 而非 `1`；累计到 4 轮后断言走向 `handoff`。
- `graph.aget_state(config).next` 在中断中非空、在 `END` 后为空，用两条断言固定这一语义。
- `ruff check`、`ruff format --check`、`mypy app/agent/graph/main.py` 均返回 0。

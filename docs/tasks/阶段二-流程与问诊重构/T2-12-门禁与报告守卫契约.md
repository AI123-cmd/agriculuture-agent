# T2-12 门禁与报告守卫契约

## 这一项要做什么

在 `app/agent/contracts/gate.py` 与 `app/agent/contracts/report.py` 中定义安全闸门与报告守卫的输出契约 `GateResult`、`GateViolation`、`ReportDecision`、`ContactInfo`。这两个契约是仅有的两个守卫组件的输出形态，它们的失败行为都是 fail-closed。 契约要表达的三个关键点：`GateResult.decision` 有三个语义不同的取值且 `process_redlines_loaded` 为 False 时必须直接 block；`ReportDecision.trigger_source` 的 signal 分支判定条件极低；`ReportDecision.triggered` 为 True 时必须携带可执行的强制动作与联系电话。

## 前置依赖

- 依赖 T2-09：必须已提供 `ObservationResult`，报告守卫要读取现场识别信号；依赖 T2-08：必须已提供 `ConsultationState`，守卫从全量槽位读取；依赖 T2-01：必须已提供 `ViolationSeverity`、`GateDecision`、`TriggerSource`；依赖 T2-06：必须已提供 `LoadedRedlines`，`process_redlines_loaded` 的来源；依赖 T2-11：必须已提供 `Prescription`，闸门的被校验对象；与 T2-34 的关系：本项定义契约，规则引擎与规则实现在 T2-34 及其后各项

## 参考章节

- 技术方案 第5章 5.3.6 门禁契约 GateResult（三个 decision 语义与红线未加载的处理）；技术方案 第5章 5.3.7 报告守卫契约 ReportDecision（优先级与触发条件极低）；技术方案 第8章 8.1 闸门在链路中的位置（输入只有三类，不接收会话消息）；技术方案 第8章 8.2 规则清单（违规等级 block 与 warn 的划分）；技术方案 第8章 8.5 审计与复盘（`checked_rules` 反查漏配）；技术方案 第6章 6.7 转人工升级（法定报告义务的输出内容）；产品说明书 5.7 认识盲区（不是只有群死群伤才需报告）

## 实现要点

### GateViolation

```python
class GateViolation(BaseModel):
    """一条违规明细。"""
    model_config = ConfigDict(extra="forbid")
    rule_id: str
    severity: Literal["block", "warn"]
    message: str
    field: str
```

`field` 指向违规的具体字段路径（如 `pesticide_items[K-1023]`、`slots.next_pick_date`），使违规既能给人看也能被程序定位。审计表里的 `violations` 是这一对象的 JSON 数组。 `rule_id` 用字符串而非 T2-06 的 `GateRuleId` 枚举，是因为契约要能被审计表原样存储，且未来可能引入非枚举化的规则变体（如带参数的规则实例 `R-DOSAGE:unit=ml`）。枚举校验留在规则引擎侧，不在契约侧。

### GateResult

```python
class GateResult(BaseModel):
    """门禁输出。技术方案 5.3.6 原样定义。"""
    model_config = ConfigDict(extra="forbid")
    passed: bool
    violations: list[GateViolation]
    checked_rules: list[str]
    process_redlines_loaded: bool
    decision: Literal["allow", "degrade", "block"]
    degrade_output: str | None = None
    @model_validator(mode="after")
    def _redlines_missing_forces_block(self) -> "GateResult":
        if not self.process_redlines_loaded and self.decision != "block":
            raise ValueError("流程红线未加载时必须判定 block")
        return self
    @model_validator(mode="after")
    def _decision_consistency(self) -> "GateResult":
        has_block = any(v.severity == "block" for v in self.violations)
        if has_block and self.decision == "allow":
            raise ValueError("存在 block 级违规时不得 allow")
        if self.decision == "allow" and not self.passed:
            raise ValueError("decision=allow 时 passed 必须为 True")
        return self
    @model_validator(mode="after")
    def _degrade_needs_output(self) -> "GateResult":
        if self.decision == "degrade" and not self.degrade_output:
            raise ValueError("degrade 必须给出降级文案")
        return self
```

第一条校验器落实产品说明书 9.3 与 8.4 的"红线缺失即不可用"。它把这条规则从"实现者要记得判断"变成"构造不出违反它的对象"。 第二条防止出现"有 block 级违规但仍放行"这种显然错误。技术方案 8.2 中绝大多数规则的违规等级是 block，只有 `R-REGION` 与 `R-CAUTION` 是 degrade 与 warn。 第三条要求 degrade 必须带输出文案。技术方案 5.3.6 明确 degrade 的输出替换为 `degrade_output`（标准转人工引导文案），产品说明书 6.2 要求"校验不通过时，输出降级为建议联系当地农技站，而不是修改后输出"。没有文案的 degrade 等于没有输出。 三个 decision 的语义要写进 docstring：

```python
# decision 语义：
# allow   —— 放行，处方卡正常返回
# degrade —— 不通过但不属严重违规，输出整体替换为 degrade_output
# block   —— 命中硬红线，拒绝输出并记录审计事件，同时触发知识条目复核工单
```

### GateContext

```python
class GateContext(BaseModel):
    """闸门全部输入。刻意不含会话消息。"""
    model_config = ConfigDict(extra="forbid")
    process_id: ProcessId
    config_version: int
    prescription: Prescription
    redlines: LoadedRedlines
    slots: dict[str, SlotValue]
    knowledge: KnowledgeFacts          # 已核准条目的只读视图（协议类型）
    medication_history: list[dict]
    region_code: str | None
    today: date
    checked_rule_ids: list[str] = []
```

`GateContext` 不含 `messages`，这是物理隔离的实现：闸门拿不到会话文本，因此无法被对话中的表述影响。技术方案 8.1 明确"它不接收会话消息，因此无法被对话中的表述影响；不调用大模型，因此每次判定都可复现"。把这两条写进类型的字段集合，比写在文档里更可靠。 `knowledge` 是只读协议（`Protocol`）而非具体仓储类型，因为 L1 规则要求 `app/gate/` 不得导入 `app/services/`。闸门只声明它需要的方法（如 `get_registered_crops(knowledge_id)`），由调用方传入满足协议的实现。

### ReportDecision

```python
class ReportDecision(BaseModel):
    """报告守卫输出。技术方案 5.3.7 原样定义。"""
    model_config = ConfigDict(extra="forbid")
    triggered: bool
    matched_signals: list[str]
    trigger_source: Literal["signal", "group", "mass_death", "none"]
    mandatory_actions: list[str]
    contacts: list[ContactInfo]
    stop_consultation: bool
    @model_validator(mode="after")
    def _trigger_requires_content(self) -> "ReportDecision":
        if self.triggered:
            if not self.matched_signals:
                raise ValueError("triggered=True 时必须给出命中的识别信号")
            if not self.mandatory_actions:
                raise ValueError("triggered=True 时必须给出强制动作")
            if self.trigger_source == "none":
                raise ValueError("triggered=True 时 trigger_source 不得为 none")
        return self
    @model_validator(mode="after")
    def _stop_only_when_triggered(self) -> "ReportDecision":
        if self.stop_consultation and not self.triggered:
            raise ValueError("未触发报告时不得中止问诊")
        return self
    @model_validator(mode="after")
    def _non_trigger_defaults(self) -> "ReportDecision":
        if not self.triggered and self.trigger_source != "none":
            raise ValueError("未触发时 trigger_source 必须为 none")
        return self
```

第一条要求触发时必须带可执行内容。产品说明书 5.7 要求输出"立即隔离、消毒、报告 + 本地联系入口"，因此 `mandatory_actions` 与 `contacts` 都在触发时有意义。这里只强制 `mandatory_actions` 非空，`contacts` 允许为空（本地联系入口可能尚未配置），但为空时须由 T2-22 记录告警。 第二条与第三条构成完整的双向约束：`stop_consultation` 与 `triggered` 同真同假。

### 触发条件的极低门槛

`trigger_source = "signal"` 的判定条件极低这一点要写进 docstring 并配一条明确注释：

```python
# trigger_source 语义：
# signal     —— 单个识别信号命中即触发。不是只有群死群伤才需报告（产品说明书 5.7）
# group      —— 同栏舍或同批次多点出现
# mass_death —— 出现群体性死亡
# none       —— 未触发
#
# 注意：signal 的门槛必须低。守卫是 fail-closed 组件，宁可多报一次，
# 不可漏报一次。误报的代价是农户多打一个电话，漏报的代价是动物疫病扩散。
```

这段注释的作用是防止后续实现者"为了降低误报率而收紧 signal 判定"。收紧是产品决策而非工程决策，必须显式提出并经过确认。

### ContactInfo

```python
class ContactInfo(BaseModel):
    """本地联系入口。承载法定报告路径与农技站联系方式。"""
    model_config = ConfigDict(extra="forbid")
    kind: Literal["vet_station", "agri_station", "authority", "hotline"]
    name: str
    phone: str | None = None
    region_code: str | None = None
    note: str | None = None
```

`kind` 区分兽医站、农技站、主管机构与热线。养猪流程的法定报告对象与种植流程的农技站不是同一类，用枚举区分让前端能按类别分组展示。`phone` 允许为空但 `kind` 必填，因为在地图与地址尚未接入时，至少能告诉农户"该联系哪个机构"。

### ReportSignal

```python
class ReportSignal(BaseModel):
    """识别信号定义。从流程配置的槽位与关键词推导。"""
    model_config = ConfigDict(extra="forbid")
    signal_id: str
    keywords: list[str]
    slot_key: str | None = None
    severity: Literal["signal", "group", "mass_death"]
    description: str
```

`ReportSignal` 列表由 T2-22 从流程配置（养猪流程的 `required_slots` 与 `banned_topics` 之外的识别信号槽位）与内置关键词表组装。本项只定义结构，信号的取值内容属于农技确认范围。

### 两个守卫的失败行为对比

| 组件 | 失败行为 | 契约体现 |
| --- | --- | --- |
| 报告守卫 ReportGuard | fail-closed，有疑即报 | `triggered=True` 时字段必须齐备，`stop_consultation=True` |
| 安全闸门 SafetyGate | fail-closed，拒绝放行 | `process_redlines_loaded=False` 强制 block |

其余智能体的失败行为是降级但仍服务。这个区别来自产品说明书 6.1 的定义，要在两个契约模块的文件头 docstring 中各写一句，避免执行者按同一套模式处理。

# T2-60 提示词模板组织与版本管理

## 这一项要做什么

在 `app/agent/prompts/` 下建立提示词的模板组织与版本管理：按方案 9.4 的"结构化拼装"方式组织提示词，把角色定位、输出契约、硬规则、术语规范、禁用输出、易混淆项、候选问题池七个部分分开构造；每个模板带版本号并与 `process_config.version` 绑定，使评估服务能按版本分组统计"改了提示词之后效果变好了还是变差了"。

关键设计是候选追问方向由代码筛选后注入，模型只能在给定范围内选择问题方向。这让"跳过已知项"与"不漏必问项"由代码保证，模型只负责语言表达。

## 实现要点

### 结构化拼装的七步

按方案 9.4 的骨架，问诊提示词由七个部分组成：

```python
def build_interviewer_prompt(config: ProcessConfig, state: ConsultationState) -> list[dict]:
    """拼装问诊智能体的提示词：结构化字段注入，便于按流程差异化。"""
    system = [
        # 1. 角色定位（按流程）
        f"你是{config.role_definition}。",
        # 2. 输出契约（共用，强制 JSON）
        f"你必须输出符合以下 JSON Schema 的内容：{InterviewBatch.model_json_schema()}",
        # 3. 硬规则（共用）
        "每轮最多问 2 个问题。每个问题必须说明为什么问。",
        "不得询问已经知道答案的信息。",
        # 4. 术语规范（按流程）
        f"使用以下术语：{format_terms(config.terminology.display_metrics)}",
        f"面向农户的表述必须口语化：{format_colloquial(config.terminology.colloquial_map)}",
        # 5. 禁用输出（按流程红线）
        f"严禁输出：{format_redlines(config.redlines)}",
        # 6. 易混淆项（按流程）
        f"你必须主动追问下列鉴别点：{format_confusables(config.confusable_items)}",
    ]
    # 7. 候选问题池（代码筛选，非模型生成）
    candidates = select_candidate_slots(config, state, top_k=6)
    user = [
        f"已确认信息：{format_slots(state['slots'])}",
        f"当前环境事实：{format_observations(state.get('observations'))}",
        f"候选追问方向（从中选择，不得超出）：{format_candidates(candidates)}",
    ]
    return [{"role": "system", "content": "\n".join(system)},
            {"role": "user", "content": "\n".join(user)}]
```

七个部分的顺序固定：前三部分是"这个智能体是谁、输出什么、有什么硬约束"，中间三部分是"按流程差异化的术语、红线、鉴别点"，最后一部分是"本次的候选池"。把流程差异集中在第 4 到 6 部分，让"新增一条流程"只需新增 YAML，提示词自动包含新流程的术语与红线，不需要改提示词代码。

第 2 部分注入 `InterviewBatch.model_json_schema()` 是结构化输出的第二层（提示词约束），与网关把 schema 传适配器的第一层配合。两层中任一层成功即可。

### 候选问题池由代码筛选后注入

```python
def format_candidates(candidates: list[SlotSpec]) -> str:
    """候选追问方向。模型只能从这些方向选，不得超出。"""
    if not candidates:
        return "（本轮无候选问题，应进入下一环节）"
    return "\n".join(f"- {spec.display_label}（槽位 {spec.key}）" for spec in candidates)
```

方案 9.4 明确"候选追问方向由代码筛选后注入，模型只能在给定范围内选择问题方向。这使跳过已知项与不漏必问项两个要求由代码保证，模型只负责语言表达。"

因此提示词里给出的候选是**封闭集合**，且用"不得超出"显式约束。模型若生成了集合外的 `slot_key`，由 T2-13 基类的契约校验拦截（`slot_key` 必须来自流程配置，且本轮候选池可查）。这一层防护把"模型自由发挥问了个不在流程里的问题"这类错误挡住。

`formatters` 里的函数全是纯函数，输入配置对象、输出字符串，无副作用、无外部依赖。这保证提示词的构造可被完整单测：给一份配置，断言生成的文本含哪些片段。

### 术语两套分开

```python
def format_terms(display_metrics: list[str]) -> str:
    """内部术语口径。给模型与知识库用。"""
    return "、".join(display_metrics) or "无特殊口径"

def format_colloquial(colloquial_map: dict[str, str]) -> str:
    """面向农户的口语化对照。展示层据此替换。"""
    return "；".join(f"{k} 说成 {v}" for k, v in colloquial_map.items()) or "按日常说法"
```

`format_terms` 用 `display_metrics`（内部规范口径），`format_colloquial` 用 `colloquial_map`（农户能懂的说法）。方案 9.1 明确两套必须分开，展示层渲染时必须过 `colloquial_map`。提示词里同时给出两套，是为了让模型知道"生成问句时用口语、填充字段时用内部口径"。

### 其他智能体的模板差异

| 智能体 | 拼装差异 |
| --- | --- |
| 问诊 Interviewer | 七步全量，含候选问题池与易混淆鉴别点 |
| 判定 Diagnoser | 无候选问题池；增加"必须填充 `excluded` 字段"与易混淆项的判据全文 |
| 处方 Prescriber | 无候选问题池；增加"不得新增、修改或删除任何药剂条目"与"不得改动任何数字"两条硬规则 |
| 分诊 Triage | 用七条流程的识别词替代单个流程的术语；显式"不得生成任何问题" |

判定与处方的模板没有第 7 部分（候选问题池），因为这两个环节不生成问题。它们把易混淆项从"鉴别点提示"改为"判据全文注入"，因为判定需要据此做排除裁定。处方模板的两条硬规则是"模板出事实"原则在提示词层的表达，与 T2-21 的代码覆写形成双保险。

### 版本管理

```python
class PromptTemplate(BaseModel):
    """一个提示词模板。版本与流程配置版本绑定。"""
    name: str                             # 如 interviewer
    version: int
    process_id: ProcessId | None = None    # None 表示共用模板
    build: Callable[[ProcessConfig, ConsultationState], list[dict]]

PROMPT_VERSIONS: dict[str, int] = {
    "triage": 1,
    "interviewer": 1,
    "retriever": 1,
    "diagnoser": 1,
    "prescriber": 1,
    "report_guard": 1,
    "snapshot_writer": 1,
}
```

版本号是模块级常量，每次修改模板必须递增。方案 9.4 要求"每次提示词模板变更记录版本号，与 `process_config.version` 绑定"。绑定的实现方式是在计量与评估记录里同时写下 `prompt_version` 与 `config_version`，使评估服务能按这两个维度分组：只改提示词时按 `prompt_version` 分组，只改配置时按 `config_version` 分组。

版本号要能被写入 `llm_call` 或评测结果。本项提供 `current_prompt_version(name)` 供网关的调用上下文与评测记录读取。评估按版本分组是"改了提示词之后效果变好了还是变差了"可被量化回答的前提，没有这层绑定，提示词改动就是不可归因的。

### 不引入模板引擎

模板用 Python f-string 与 join 构造，不用 Jinja2 之类的外部模板引擎。原因是拼装逻辑本身就是代码（含条件、含从配置取值），用模板引擎反而要把这些逻辑塞进模板语言，更难测试与调试。方案 9.4 的骨架也是纯 Python 构造。

### 与配置分离的边界

提示词里**不写任何农技事实**（药剂名、剂量、阈值）。事实由知识库检索后注入到 user 消息的候选区，或由代码在处方里填充。提示词只含"如何组织语言"与"有哪些约束"。这条边界让"改了提示词就把药剂名改错"这类事故不可能发生。

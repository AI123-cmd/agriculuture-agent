# T2-34 闸门规则引擎与规则基类

## 这一项要做什么

在 `app/gate/` 下建立安全闸门的骨架：规则抽象基类 `Rule`、规则注册表、判定入口 `GateEngine.evaluate`、闸门全部输入类型 `GateContext`。闸门是本方案唯一拥有否决权的组件（产品说明书 6.2 要求它"必须独立于生成环节实现"，6.4 要求四条红线"任何迭代不得突破"），因此本项第一目标不是功能而是边界：让闸门成为不依赖智能体层、不调用模型、每次判定可复现的独立包。第二目标是让八类规则成为同构纯函数，每条都能脱离数据库与模型单独单测，这是 14.2"闸门即评测关卡"能落地的前提。

## 前置依赖

- 依赖 T2-12：已提供 `GateResult`、`GateViolation` 的字段语义与三条校验器（红线未加载强制 block、存在 block 违规不得 allow、degrade 必须带文案）。本项把这三类契约的定义位置迁到 `app/gate/contracts.py`，T2-12 改为从闸门包再导出（方向 agent → gate，合法）。
- 依赖 T2-11：已提供 `Prescription`、`PesticideItem` 的字段集合（`pesticide_items`、`safety_interval_days`、`max_uses_per_season`、`facts_provenance`），闸门侧建同结构只读镜像。
- 依赖 T2-06：已提供 `LoadedRedlines` 与 `GateRuleId`（含 `declared_rule_ids()` 与 `blocking_labels()`），闸门据此判断 `process_redlines_loaded`。
- 依赖 T2-01：已提供 `ProcessId` 与 `ViolationSeverity` 取值集合；闸门不直接导入，改用同值镜像枚举（理由见"包的边界"）。
- 外部环境：无。本项不碰数据库、缓存与模型服务，`pytest tests/gate/` 可纯内存运行。

## 实现要点

包的边界：L1 由 `scripts/check_layers.py` 以 import 前缀判定，`app.gate` 下出现 `app.agent` 或 `app.services` 开头的 import 即构建失败，这与 T2-12 把闸门契约放在 `app/agent/contracts/gate.py` 冲突，故做两处推断。其一，**闸门契约归闸门所有**：`app/gate/contracts.py` 是唯一定义处，agent 侧改为 `from app.gate.contracts import ...` 再导出（L1 只禁止 gate → agent，此方向合法）。其二，**枚举镜像**：闸门不能导入 `app/agent/state.py`，故在 `app/gate/enums.py` 定义同值枚举，靠 `tests/gate/test_contracts_mirror.py` 断言两侧取值集合相等来同步；宁可多一份枚举与一条测试，也不让闸门对生成链路产生编译期依赖。

### 规则基类 Rule 与规则注册表

```python
# app/gate/rules/base.py
class Rule(ABC):
    """一条闸门规则。实现为纯函数：只读 ctx，不做 IO，不调模型。"""
    rule_id: ClassVar[str]
    severity: ClassVar[GateSeverity]          # block / degrade / warn
    @abstractmethod
    def check(self, ctx: GateContext) -> list[GateViolation]:
        """返回本轮命中的全部违规。无命中返回空列表，不得返回 None。"""
    def violation(self, field: str, message: str, severity: GateSeverity | None = None) -> GateViolation:
        """按规则自身的 id 与等级构造违规，避免每条规则各写一遍 rule_id。"""
        return GateViolation(rule_id=self.rule_id, severity=severity or self.severity,
                             message=message, field=field)
_REGISTRY: dict[str, type[Rule]] = {}

def register(cls: type[Rule]) -> type[Rule]:
    """登记规则类。rule_id 必须是枚举值、不得重复、不得是抽象类。"""
    rid = getattr(cls, "rule_id", None)
    if rid not in {r.value for r in GateRuleId}:
        raise GateConfigError(f"{cls.__name__} 的 rule_id {rid!r} 不在 GateRuleId 内")
    if rid in _REGISTRY:
        raise GateConfigError(f"规则 id 重复登记: {rid}")
    if inspect.isabstract(cls):
        raise GateConfigError(f"{cls.__name__} 仍有未实现的抽象方法")
    _REGISTRY[rid] = cls
    return cls

def build_rules(rule_ids: Iterable[str] | None = None) -> list[Rule]:
    """实例化规则。None 表示全部；未登记 id 直接抛错，不静默跳过。"""
    ids = [r.value for r in GateRuleId] if rule_ids is None else list(rule_ids)
    missing = [i for i in ids if i not in _REGISTRY]
    if missing:
        raise GateConfigError(f"规则未登记: {missing}")
    return [_REGISTRY[i]() for i in ids]
```

`check` 返回列表而非 `GateResult`：规则只负责"我发现什么"，"整体怎么裁定"由引擎统一决定，新增规则无需理解 decision 聚合。`severity` 是类属性而非 `check` 参数，因为等级属于规则定义，不属于某次判定。注册表以 `GateRuleId` 为白名单：配置里写了不存在的 id 由 T2-06 拦，代码侧漏实现一条已声明规则由 `missing` 分支发现；规则无参数、无状态，可实例化后跨判定复用。

### GateContext 与知识事实协议

```python
# app/gate/contracts.py
class GateContext(BaseModel):
    """闸门全部输入。刻意不含会话消息与任何模型句柄。"""
    model_config = ConfigDict(extra="forbid", frozen=True)
    process_id: ProcessId
    config_version: int
    prescription: GatePrescription            # 处方只读镜像（字段与 T2-11 同名）
    payload: GatePayload                      # 展示文本，溯源扫描的输入
    redlines: LoadedRedlines
    slots: dict[str, str | date | None] = {}  # 槽位原始值，日期为 ISO 字符串
    knowledge: KnowledgeFacts                 # 只读事实源协议，非具体仓储
    medication_history: list[MedicationRecord] = []
    region_code: str | None = None
    today: date
    season_start: date | None = None          # 每季次数的统计起点
    rule_configs: dict[str, dict[str, object]] = {}   # rule_id -> 红线 data 载荷
    def slot_date(self, key: str) -> date | None:
        """取日期型槽位。空、unknown、解析失败一律返回 None（fail-closed）。"""
        raw = self.slots.get(key)
        if raw in (None, "", "unknown"):
            return None
        if isinstance(raw, date):
            return raw
        try:
            return date.fromisoformat(str(raw))
        except ValueError:
            return None

# app/gate/ports.py
class KnowledgeEntrySnapshot(Protocol):
    """知识条目只读快照，字段与 T2-47 的知识条目表同名同义。"""
    knowledge_id: str
    name: str                                 # 药剂名
    status: str                               # draft/approved/suspended/deprecated
    registered_crops: tuple[str, ...]
    region_scope: str | None
    dosage_min: float | None                  # 与 dosage_max、dosage_unit 同组
    dosage_max: float | None
    dosage_unit: str | None
    safety_interval_days: int | None
    max_uses_per_season: int | None
    forbidden_combinations: tuple[str, ...]

class KnowledgeFacts(Protocol):
    def get_entry(self, knowledge_id: str) -> KnowledgeEntrySnapshot | None: ...
    def is_approved(self, knowledge_id: str) -> bool: ...
    def get_registered_crops(self, knowledge_id: str) -> tuple[str, ...]: ...
```

`GateContext` 用 Pydantic 而非 `dict`：`extra="forbid"` 让"给闸门塞了一个会话消息字段"在构造时报错，把 8.1 的两条物理隔离从文档约定变成类型约束。`knowledge` 声明为 `Protocol` 而非具体类，是 L1 与可测性的共同要求：闸门只声明它需要的方法，测试可喂三行假实现。`get_entry` 返回 `None` 表示"该 knowledge_id 不在已核准库中"，与"条目存在但 `status != approved`"是两件事，规则要分别给出提示语。协议里不放 `search`：闸门不做检索——检索属生成侧，闸门只核对已被引用条目的字段，这是"独立仲裁"与"生成"在数据上的分界。

### GateEngine.evaluate 完整骨架

```python
# app/gate/engine.py
_PRECHECK_RULE_IDS = (GateRuleId.REDLINE_LOAD.value,)

class GateEngine:
    """规则执行与结果聚合。无状态，可跨请求复用。"""
    def __init__(self, rules: list[Rule] | None = None) -> None:
        self._rules = build_rules() if rules is None else rules
        order = {r: i for i, r in enumerate(_PRECHECK_RULE_IDS)}
        self._rules.sort(key=lambda r: (order.get(r.rule_id, len(order)), r.rule_id))
    def evaluate(self, ctx: GateContext) -> GateResult:
        """执行全部规则并裁定。任何异常一律 fail-closed。"""
        checked: list[str] = []
        violations: list[GateViolation] = []
        for rule in self._rules:
            if rule.rule_id in _PRECHECK_RULE_IDS or self._gate_open(ctx, violations):
                checked.append(rule.rule_id)
                violations.extend(self._run(rule, ctx))
            if not ctx.redlines.loaded:
                break                # 红线未加载：前置规则跑完即停，不再执行其余规则
        decision = self._decide(violations)
        return GateResult(passed=decision == "allow", violations=violations,
                          checked_rules=checked, process_redlines_loaded=ctx.redlines.loaded,
                          decision=decision,
                          degrade_output=DEGRADE_OUTPUT_TEXT if decision == "degrade" else None)
    def _run(self, rule: Rule, ctx: GateContext) -> list[GateViolation]:
        """单条规则执行。抛异常即视为判定失败，按最保守方向记一条 block。"""
        try:
            return rule.check(ctx)
        except Exception as exc:                  # noqa: BLE001 —— 闸门必须吞掉一切异常
            return [GateViolation(rule_id=rule.rule_id, severity="block", field="-",
                                  message=f"规则执行异常，按最保守判定拦截：{exc}")]
    @staticmethod
    def _gate_open(ctx: GateContext, violations: list[GateViolation]) -> bool:
        """红线未加载或已出现 block 级违规时，后续规则不再执行。"""
        return ctx.redlines.loaded and not any(v.severity == "block" for v in violations)
    @staticmethod
    def _decide(violations: list[GateViolation]) -> str:
        """聚合裁定：block 优先于 degrade，degrade 优先于 warn，其余放行。"""
        if any(v.severity == "block" for v in violations):
            return "block"
        if any(v.severity == "degrade" for v in violations):
            return "degrade"
        return "allow"
```

`_run` 的异常兜底是 fail-closed 在引擎层的执行点。生成链路遇异常可降级但仍服务（全局约定第六节），闸门不可以：规则抛异常意味着"没能完成校验"，唯一安全结论是不放行；用 `Exception` 粒度而非窄类型捕获，是因为规则里任何一处 `KeyError`、`TypeError` 都会让校验半途而废，而半途而废的校验看起来像通过。`_gate_open` 短路是"红线缺失即不可用"的工程落地：`R-REDLINE-LOAD` 排序第一，一旦 block 后续规则整体跳过，代价是 `checked_rules` 变短，正好被 8.5 第三条复盘用途当作信号。

严重度取值与一处分歧：技术方案 8.2 的"违规等级"列有三个取值（`block`、`degrade`、`warn`），而 5.3.6 的 `GateViolation.severity` 只声明 `Literal["block", "warn"]`。本项按 8.2 取三值全集 `GateSeverity = Literal["block", "degrade", "warn"]`：T2-04 的 `tea.yaml` 里 `TEA-05` 明确写 `severity: degrade`，契约收不下就只能偷偷降级；`decision` 的三值与等级三值一一对应（block→block、degrade→degrade、warn→allow 但留痕），收成两值会让"不通过但不属严重违规"这一档无处安放。`ViolationSeverity` 仍保持 T2-01 的两值枚举，它给配置层用，与规则判定档位不冲突。

十二条规则 id 分布在八个实现文件里（对应关系见 README 闸门层表格，`R-DOSAGE`/`R-MAX-USE` 与 `R-PROVENANCE`/`R-NO-DATA` 各同文件）。八条实现文件共同遵守三条约定：`check` 内不出现 `await`、任何网络调用与 `ctx` 之外的状态；每条规则输入全部来自 `ctx` 字段，不读全局配置；每条规则各自有独立测试文件，互不依赖。

## 实现要点

### 一、先把 42 处调用点分类

按"是否已带归属条件"分三类，处理方式不同。

**第一类，完全没带归属条件（必须修，属高危）。** 只有两处：

```python
# ai_service.py:43 —— 按 sessionId 查会话，未校验归属
conv = db.query(AIConversation).filter(AIConversation.id == req.sessionId).first()
```

危害是：攻击者只要猜到或枚举到他人的 `sessionId`（现状由小程序生成，形如 `sess-001`，可预测），调 `/api/ai/chat` 带上该 `sessionId`，就会把新消息写进他人会话，同时 `_persist` 里 `conv.crop_tag = req.cropTag` 会改写他人会话字段。修复后：

```python
conv = await self.conv_repo.get(db, user_id, req.sessionId)
if conv is None and req.sessionId and req.sessionId not in (None, ""):
    # 指定了 sessionId 但不存在或不属于当前用户：新建而非接管
    conv = None
```

关键决策：**归属不符时不报错，而是当作新会话处理**。理由是产品说明书 4.2 里 `sessionId` 由前端生成，农户换手机或清缓存后会拿到同一个本地 `sessionId`，如果报 403 会让正常用户卡死。但"当作新会话"必须保证新会话用不同主键，不能覆盖他人数据。这是对技术方案的一处推断，方案未讨论该分支。

```python
# user_service.py:25 —— 按 id 取 User，此处 id 就是当前用户，无越权
user = db.query(User).filter(User.id == user_id).first()
```

这处虽无归属风险，但 `User` 表本身不继承 `OwnedMixin`，需要保留一个专用的 `UserRepository`（不带归属过滤，因为 `id` 即归属），并在白名单里登记。

**第二类，带了归属条件但归属条件可被绕过（必须修，属中危）。** 典型是"先按父对象过滤、再按子表外键删除"：

```python
# ai_service.py:107-111 —— 删除历史
conv = db.query(AIConversation).filter(
    AIConversation.id == session_id, AIConversation.user_id == user_id
).first()
if conv:
    db.query(AIMessage).filter(AIMessage.conversation_id == session_id).delete(...)
    db.delete(conv)
```

父查询带了 `user_id`，但子表删除只按 `conversation_id`。如果 `conv` 为 None（不属于你），`if conv:` 会跳过，看似安全；但 `user_service.cancel_account` 第 33-35 行是反过来的：

```python
conv_ids = [c.id for c in db.query(AIConversation).filter(AIConversation.user_id == user_id).all()]
if conv_ids:
    db.query(AIMessage).filter(AIMessage.conversation_id.in_(conv_ids)).delete(...)
```

这里 `in_(conv_ids)` 是安全的。但 `cancel_account` 第 36-45 行有一处真缺陷：它按 `user_id` 删除 9 张表，唯独第 35 行的 `AIMessage` 删除依赖 `conv_ids` 列表；若并发下 `conv_ids` 为空而消息已存在（另一进程刚插入消息但会话行已被前一次调用删除），消息会残留成为孤儿数据。修复方式是用 `ConversationScopedRepository` 统一"先校验父归属、再级联子表"。

**第三类，带了归属条件且写法正确（只做替换，不改语义）。** 其余 28 处属于此类，如 `farmer_service.py:20` 的 `db.query(Crop).filter(Crop.user_id == user_id)`。这些替换为仓储方法即可，风险在"替换时把 `filter` 条件漏掉"，所以每处替换都要求对应一条断言。

### 二、替换的机械化规则

为降低 42 处替换的出错率，定四条机械规则：

规则一，`db.query(X).filter(X.user_id == user_id)...` → `await repo_<x>.list(db, user_id, ...)` 或 `get`/`count`。原 `filter` 里的其它条件作为仓储方法的可选参数传入。

规则二，`db.query(X).filter(X.user_id == user_id).delete()` → `await repo_<x>.delete_all(db, user_id, **conditions)`。基类已由 T1-05 提供 `delete_all`：

```python
async def delete_all(self, db: AsyncSession, user_id: str, **conditions: Any) -> int:
    stmt = delete(self.model).where(self.model.user_id == self._require_user(user_id))
    for field, value in conditions.items():
        stmt = stmt.where(getattr(self.model, field) == value)
    return (await db.execute(stmt)).rowcount
```

规则三，`db.add(obj)` → `await repo.add(db, user_id, obj)`，由仓储覆写 `user_id`。规则四，`db.delete(obj)` → `await repo.delete(db, user_id, obj.id)`，用归属条件删除。四条规则要在提交说明里逐条列出对应文件行号，且每条替换都标注属于第一/二/三类中的哪一类。

### 三、tools/ 与 broadcast/ 的处理

`app/tools/profile.py`、`sensors.py`、`app/broadcast/snapshot.py` 也用了 `db.query`。这三处不能简单换仓储，因为它们接收的是 `Session | None`：

```python
# tools/profile.py:9
profile = db.query(FarmerProfile).filter(FarmerProfile.user_id == user_id).first() if db else None
```

`db` 可能为 None（工具层被无库上下文调用，用于离线兜底）。处理方式：把工具层改为接收仓储对象而非 `Session`，调用方在 `fetch_environment` 节点里注入仓储。这同时满足 L2 规则（`app/agent/` 不得直接导入 ORM）——现有 `agent/nodes/fetch_environment.py` 通过 `_db_from_config` 拿 `db` 再传给 `tools`，是把 ORM 泄漏进了 agent 层。本项把这一处的调用形态改为"传入 repository"，与 T2-13 的 Agent 基类对齐。这是本项与技术方案边界的一处接缝：技术方案 15.2 第 2 条说"`agent/` 不得直接 import `db.models`"，本项顺手把 `tools` 的形态改掉，但 `agent/nodes/` 的重构留给第二步 T2-13；本项只保证 `tools/` 与 `broadcast/` 不再出现裸 `db.query`。

### 四、`cancel_account` 的重写

现状是 9 连删 + 1 次 `commit()`，且跨 9 张表顺序硬编码。重写为按依赖顺序调用各仓储：

```python
async def cancel_account(self, db: AsyncSession, user_id: str) -> None:
    """注销账号：按依赖逆序删除，全程同一事务。"""
    await self.message_repo.delete_by_user(db, user_id)      # ai_message（子表）
    await self.conv_repo.delete_all(db, user_id)             # ai_conversation
    await self.memory_repo.delete_all(db, user_id)
    await self.broadcast_repo.delete_all(db, user_id)
    await self.location_repo.delete_all(db, user_id)
    await self.device_repo.delete_all(db, user_id)
    await self.crop_repo.delete_all(db, user_id)
    await self.field_repo.delete_all(db, user_id)
    await self.profile_repo.delete_all(db, user_id)
    await self.tag_repo.delete_all(db, user_id)
    await self.user_repo.delete(db, user_id)
```

不在这里 `commit()`——事务边界由 T1-09 统一在服务层入口提交，避免"删了一半提交失败"的中间态。

### 五、跨用户测试矩阵

`tests/ownership/test_cross_user_access.py` 按资源类型逐条覆盖，每类至少两条（读、写）：

| 资源 | 读断言 | 写断言 |
| --- | --- | --- |
| 会话 | `GET /api/ai/history/{B的id}` 为 403 或列表不含 B 的项 | `POST /api/ai/chat` 带 B 的 sessionId 不改变 B 的会话行数 |
| 档案 | `GET /api/farmer/profile` 只返回 A 自己的 | `POST /api/farmer/profile` 不覆盖 B 的档案 |
| 设备 | `GET /api/environment/detail` 的 devices 不含 B 的设备 | 无写接口，仅读 |
| 播报 | `GET /api/broadcast/today` 不含 B 的条目 | `POST /api/broadcast/mark-done` 传 B 的 itemId 返回 0 行受影响 |
| 标签 | `GET /api/farmer/profile` 的 tags 为 A 的 | 同上 |

写断言必须校验"B 的数据未被修改"，而不只是"返回码正确"——这是验收项第 1 条的实质。

## 验收标准

- `grep -rn "db.query(" backend/app` 输出为 0 行（除 `app/repositories/base.py` 中作为注释出现的示例）；`grep -rn "\.query(" backend/app/services backend/app/tools backend/app/broadcast` 输出为 0 行。
- `pytest backend/tests/ownership/` 全部通过，跨用户矩阵中每类资源至少 2 条断言，合计不少于 10 条。
- 用用户 B 的 token 请求用户 A 的 `/api/ai/history/{A的sessionId}`，返回 HTTP 403 且响应体 `code=403`；A 的该会话在库中行数与内容不变（用前后快照比对断言）。
- 用用户 B 的 `sessionId` 调 `/api/ai/chat`，B 的 `ai_conversation` 与 `ai_message` 行数不变（断言 SQL 前后计数），A 名下新增一条会话。
- `pytest backend/tests/` 全量通过，原有 `test_ai.py` / `test_auth.py` / `test_farmer.py` 不因本次替换而失败。
- `ruff check backend/app`、`ruff format --check backend/app`、`mypy backend/app` 三条命令返回 0。
- 每个替换点在提交说明里标注类别（一/二/三），第一类 2 处、第二类修复点逐条列出。

# T1-11 历史列表查询性能优化

## 这一项要做什么

现有 `app/services/ai_service.history` 是典型的 N+1：先查一页会话（20 条），再对每条会话单独查一次消息列表，最后在 Python 里取 `msgs[-1].content[:30]` 作为预览。20 条会话会产生 21 次查询，且每次查询都把整段对话读进内存只为取 30 个字符。本项把它改为"一次分页查询 + 一次窗口函数查询"，查询数固定为 2。

对应产品说明书 9.2 第 7 条（历史列表存在逐条查询的性能问题，必须优化）。

## 前置依赖

- 依赖 T1-05 已提供：`ConversationRepository` 与 `ConversationScopedRepository`，本项在其上实现批量查询。
- 依赖 T1-04 已提供：`ai_message.conversation_id` 与 `ai_conversation.update_time` 的索引，本项的分页与排序依赖它们。
- 依赖 T1-02 已提供：异步引擎，使 `window function` 查询可 `await` 执行。
- 外部环境：PostgreSQL 16+（`row_number() OVER (PARTITION BY ...)` 与 `LATERAL` 均可用）。
- 需要人工确认：历史列表的实际规模（用于确定是否需要 `keyset` 分页而非 `offset` 分页）。本项按 `offset` 实现并留出 `keyset` 扩展点；若单用户会话数超过 1 万，应切换到 `keyset`。

## 实现要点

### 一、现状的查询数是多少

现有实现（`ai_service.py:81-105`）：

```python
q = db.query(AIConversation).filter(AIConversation.user_id == user_id).order_by(AIConversation.update_time.desc())
total = q.count()                       # 查询 1：COUNT
convs = q.offset((page - 1) * size).limit(size).all()   # 查询 2：分页
for conv in convs:                      # 查询 3..N+2：每条会话一次
    msgs = db.query(AIMessage).filter(AIMessage.conversation_id == conv.id).order_by(AIMessage.id).all()
```

`size=20` 时总查询数 = 1（COUNT）+ 1（分页）+ 20（消息）= 22 次。而且第 3..22 次查询把每条会话的**全部消息**取回，只为算 `preview = msgs[-1].content[:30]` 与构造 `messages` 列表。当单条会话有 50 轮对话时，这一页要传输 1000 条消息才能渲染 20 行摘要。产品说明书 9.2 第 7 条说的就是这个。

### 二、目标形态：固定 2 次查询

```python
async def history(self, db: AsyncSession, user_id: str, page: int = 1, size: int = 20) -> dict:
    size = min(size, 50)                       # 上限保护，避免一页拉过多
    total = await self.conv_repo.count(db, user_id)
    rows = await self.conv_repo.paginate_with_preview(db, user_id, page=page, size=size)
    return {
        "list": [
            {
                "id": conv.id,
                "title": conv.title or "新对话",
                "preview": preview or "",
                "messageCount": msg_count,
                "updatedAt": int(conv.update_time.timestamp() * 1000) if conv.update_time else 0,
            }
            for conv, msg_count, preview in rows
        ],
        "total": total,
    }
```

`messages` 字段从列表接口移除。理由：列表页只需要标题、预览、时间；完整会话通过 `GET /api/v1/ai/consult/{id}` 获取（技术方案 13.1 已定义该接口）。现状把 `messages` 塞进列表响应，是"一次请求返回全部数据"的常见反模式，既慢又让前端不得不处理大数据包。

如果小程序端确实需要首屏直接渲染几条消息，则改为 `?withMessages=true` 且只取最近 N 条（默认 6 条），由同一个窗口函数带出，查询数仍为 2。

### 三、窗口函数实现

```python
# app/repositories/conversation.py
from sqlalchemy import desc, func, select

from app.models import AIConversation, AIMessage


class ConversationRepository(OwnedRepository[AIConversation]):
    async def paginate_with_preview(
        self, db: AsyncSession, user_id: str, *, page: int, size: int
    ) -> list[tuple[AIConversation, int, str | None]]:
        """一次查询取会话 + 消息数 + 最后一条预览。

        用 LATERAL 子查询对每条会话取 1 行，避免把全部消息拉回应用层。
        """
        uid = self._require_user(user_id)

        latest = (
            select(
                AIMessage.conversation_id,
                AIMessage.content,
                func.count().over(partition_by=AIMessage.conversation_id).label("msg_count"),
                func.row_number()
                .over(partition_by=AIMessage.conversation_id, order_by=desc(AIMessage.id))
                .label("rn"),
            )
            .subquery("ranked")
        )
        agg = (
            select(latest.c.conversation_id, latest.c.msg_count, latest.c.content)
            .where(latest.c.rn == 1)
            .subquery("agg")
        )
        stmt = (
            select(AIConversation, func.coalesce(agg.c.msg_count, 0), agg.c.content)
            .outerjoin(agg, agg.c.conversation_id == AIConversation.id)
            .where(AIConversation.user_id == uid)
            .order_by(AIConversation.update_time.desc())
            .limit(size)
            .offset((page - 1) * size)
        )
        result = await db.execute(stmt)
        return [(row[0], row[1], row[2]) for row in result.all()]
```

这段 SQL 生成的形态：

```sql
SELECT c.*, COALESCE(agg.msg_count, 0), agg.content
FROM ai_conversation c
LEFT JOIN (
    SELECT conversation_id, msg_count, content
    FROM (
        SELECT conversation_id, content,
               COUNT(*) OVER (PARTITION BY conversation_id) AS msg_count,
               ROW_NUMBER() OVER (PARTITION BY conversation_id ORDER BY id DESC) AS rn
        FROM ai_message
    ) ranked
    WHERE rn = 1
) agg ON agg.conversation_id = c.id
WHERE c.user_id = $1
ORDER BY c.update_time DESC
LIMIT $2 OFFSET $3;
```

`ROW_NUMBER() ... WHERE rn = 1` 是"取每组最后一条"的标准解法；`COUNT(*) OVER (PARTITION BY ...)` 顺带在同一遍扫描里算出消息数，不需要第二条聚合查询。整个子查询只在 `ai_message` 上扫一遍，且有 `conversation_id` 索引。

### 四、如果消息表很大：改为 LATERAL

窗口函数会把 `ai_message` 全表参与分区与排序。若消息表达到千万级，外层 `LEFT JOIN` 的中间结果集会大于必要量。此时改用 `LATERAL`：

```sql
SELECT c.*, m.content, m.msg_count
FROM ai_conversation c
LEFT JOIN LATERAL (
    SELECT content,
           (SELECT count(*) FROM ai_message m2 WHERE m2.conversation_id = c.id) AS msg_count
    FROM ai_message m
    WHERE m.conversation_id = c.id
    ORDER BY m.id DESC
    LIMIT 1
) m ON true
WHERE c.user_id = $1
ORDER BY c.update_time DESC
LIMIT $2 OFFSET $3;
```

`LATERAL` 的代价是"只对被翻页选中的 20 条会话各取一次"，不扫全表。两种写法的选择标准是数据量：小于 500 万行用窗口函数（一次扫描，计划稳定），大于则用 `LATERAL`（按需取）。本项默认用窗口函数，并在 `ConversationRepository` 里保留 `paginate_with_preview_lateral` 方法，由配置 `HISTORY_QUERY_STRATEGY` 选择。

这是对技术方案的一处推断：方案只指出"逐条查询的性能问题"，未规定解法。给出双实现是为了避免上线后发现"窗口函数在大表上回表过多"时无路可退。

### 五、总数量查询的取舍

`count()` 单独一次查询是无法避免的，因为前端需要 `total` 来渲染分页。一次查询数固定为 2 是可接受的下限。若列表规模大到 `COUNT` 成为瓶颈（`COUNT` 在有大量行时也是全扫描），可用两个办法：

第一，改用 `keyset` 分页，用 `where update_time < :cursor` 替代 `OFFSET`，并去掉 `total`，前端改为无限滚动。这与产品说明书 4.5 的历史页交互形态相关，需产品确认。

第二，用 `pg_class.reltuples` 的估算值，代价是 `total` 不精确。产品说明书 4.5 未要求精确总数，本项保留精确 `COUNT`。

### 六、`build_context` 的顺带优化

`ai_service.build_context` 里有 4 次查询（`FarmerProfile`、`Crop`、`UserProfileTag` 各一次，加上外层调用）。其中 `Crop` 查询取全部再在 Python 里 `next(...)` 找主作物，可在 SQL 里 `ORDER BY is_main DESC, create_time LIMIT 1`。这 4 次查询是不同表，无法合并为 1 次，但可以并行：

```python
profile, crops, tag = await asyncio.gather(
    self.profile_repo.get(db, user_id, user_id),
    self.crop_repo.list(db, user_id, order_by=[desc(Crop.is_main), Crop.create_time]),
    self.tag_repo.get(db, user_id, user_id),
)
```

注意：同一个 `AsyncSession` 不能并发执行多条语句（SQLAlchemy 的 `AsyncSession` 不是并发安全的）。因此 `asyncio.gather` 必须换成"用独立会话"或"顺序执行但减少查询"。本项选择顺序执行 + SQL 侧裁剪，因为仅 4 次轻量查询，不值得引入连接分裂。这一处要在代码注释里写明原因，避免后来者误用 `gather`。

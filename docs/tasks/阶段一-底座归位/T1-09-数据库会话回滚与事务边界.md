# T1-09 数据库会话回滚与事务边界

## 这一项要做什么

现有 `app/db/session.py` 的 `get_db` 只有 `try/finally: db.close()`，异常时既不回滚也不记录；而各服务在方法内部自行 `commit()`（`auth_service`、`ai_service`、`farmer_service`、`user_service`、`broadcast_service` 各有一处），事务边界散落且不一致。本项把事务边界收敛到服务层的显式工作单元，请求级会话在异常时自动回滚，并让"提交成功"与"业务返回"成为一个原子事实。

对应产品说明书 9.2 第 8 条（数据库会话异常时缺少回滚，必须添加）。

## 前置依赖

- 依赖 T1-02 已提供：`AsyncSession`、`async_sessionmaker(expire_on_commit=False)`、`engine`。
- 依赖 T1-05 已提供：仓储层。事务边界统一后，仓储只负责构造语句，不再自行提交。
- 依赖 T1-06 已提供：42 处 `db.query` 已换仓储，替换过程中出现的提交点必须在本项一起收敛。
- 外部环境：PostgreSQL 16+（回滚断言依赖 `SAVEPOINT` 与错误恢复语义，SQLite 与 PG 在此不等价）。

## 实现要点

### 一、现有提交点盘点

`grep -rn "db.commit()" backend/app` 命中的是服务层内部提交。逐条看会发现边界不一致：

- `auth_service.login`：在 `create_token` 之后 `commit`。如果 `commit` 失败，令牌已签发但用户未落库，农户会拿到一个指向不存在用户的 token。
- `ai_service._persist`：在 `remember` 之后 `commit`。而 `chat` 方法在 `_persist` 之后返回——`_persist` 失败时 `chat` 抛异常，但此时 `graph.ainvoke` 已经跑了完整的智能体链路并可能已写检查点，产生"检查点有进度、业务表无记录"的分裂。
- `farmer_service.save_profile`：先 `delete` 全部 `Crop` 再逐条 `add`，中间 `commit`。若 `add` 时某条数据违反约束，删除已提交，农户的作物列表被清空。
- `user_service.cancel_account`：11 步删除后一次 `commit`，是唯一"单次提交"的写法，但它一次性删 11 张表，长事务持有时间过长。

四处里最危险的是 `save_profile`：删除与新增之间没有事务保护，是"数据被清空"这类事故的典型结构。

### 二、get_db 的回滚改造

```python
"""数据库引擎与会话管理（异步）。"""
from collections.abc import AsyncIterator

from sqlalchemy.ext.asyncio import AsyncSession

from app.core.logging import get_logger   # T6-08 建立，此前用标准 logging
from app.db.session import SessionLocal

logger = get_logger(__name__)


async def get_db() -> AsyncIterator[AsyncSession]:
    """请求级会话：正常结束提交、异常回滚、始终关闭。

    不在这里做业务提交判断——业务提交由服务层 UnitOfWork 显式完成；
    这里只兜底"服务层忘记提交但也没抛异常"的情况，避免脏读残留连接。
    """
    async with SessionLocal() as session:
        try:
            yield session
        except Exception:
            await session.rollback()
            logger.exception("请求级会话异常，已回滚")
            raise
        finally:
            if session.in_transaction():
                # 服务层未显式提交：按 fail-closed 处理，回滚而不是静默提交
                await session.rollback()
                logger.warning("会话结束仍处于事务中，已回滚（服务层可能漏了提交）")
```

关键取舍是 `finally` 分支：**不静默提交**。理由是"忘记提交"比"忘记回滚"更常见，若在这里替服务层提交，会把未经验证的写入落库；而回滚会让测试立刻暴露漏提交，属于 fail-closed。这个选择要在代码注释里写明，避免后来者改成自动提交。

`in_transaction()` 是 SQLAlchemy 2.0 的同步布尔属性（不是协程），可直接调用。

### 三、UnitOfWork

```python
# app/db/uow.py
"""显式工作单元：把事务边界从仓储内部上移到业务用例。"""
from contextlib import asynccontextmanager
from collections.abc import AsyncIterator

from sqlalchemy.ext.asyncio import AsyncSession

from app.core.exceptions import TransactionError


@asynccontextmanager
async def unit_of_work(db: AsyncSession, *, name: str) -> AsyncIterator[AsyncSession]:
    """一次业务用例一个事务。

    用法：
        async with unit_of_work(db, name="ai.chat"):
            ... 仓储读写 ...
    内层不调用 db.commit()，由本上下文统一提交或回滚。
    """
    if db.in_transaction():
        # 已有外层事务：嵌套进 SAVEPOINT，失败只回滚内层
        async with db.begin_nested():
            yield db
        return

    try:
        yield db
        await db.commit()
    except Exception as exc:
        await db.rollback()
        raise TransactionError(f"{name} 事务失败，已回滚：{exc}") from exc
```

三处设计说明：

**嵌套用 `begin_nested()`。** 现实场景里 `ai_service.chat` 内部会调用 `ProfileService.add_tags` 与 `MemoryService.remember`，后者又调用别的仓储。如果每层都开事务，会互相覆盖。`begin_nested` 生成 `SAVEPOINT`，内层失败只回滚内层，外层可决定继续或放弃。PG 对 `SAVEPOINT` 支持完整，这也是必须用 PG 跑这类测试的原因。

**异常包装为 `TransactionError`。** 技术方案与全局约定都要求"失败行为分两类"。`TransactionError` 属于服务层可识别的一类，其 `code` 取 500；后续 T2 阶段的降级判断可以按异常类型分流，而不必解析数据库原始错误。

**`name` 参数必填。** 用于日志与 trace，使"哪次业务操作回滚了"可检索。这为 T6-06 的 OpenTelemetry span 命名打基础。

### 四、服务层的改法

以 `ai_service.chat` 为例：

```python
async def chat(self, db: AsyncSession, user_id: str, req: ChatRequest) -> dict:
    context = await self.build_context(db, user_id, req.cropTag)
    graph = await get_agent()
    result = await graph.ainvoke(initial_state, config=config)
    reply = result.get("reply") or ""

    async with unit_of_work(db, name="ai.chat"):
        await self._persist(db, user_id, req, reply)

    return {...}
```

`_persist` 内部去掉 `db.commit()`，只做 `add` 与 `update`。注意 `graph.ainvoke` 放在事务之外——智能体链路耗时长（秒级），把它包进事务会长时间持锁，并且检查点写入本身由 `AsyncPostgresSaver` 的连接池管理，不应混进业务事务（技术方案 7.5 的连接池 `autocommit=True` 也印证两者是不同连接）。

这是对技术方案的一处推断：方案说"检查点与业务状态需事务一致性"（4.3 第二条），但 `AsyncPostgresSaver` 用独立连接池且 `autocommit=True`，实际无法与业务事务共享同一连接。因此本项按"同库不共享事务"实现，一致性靠"业务事务成功后写检查点"的顺序保证。若第二步要严格同事务，需在 T2-30 换用手工 `put` 方式，本项在注释里留出接口。

`farmer_service.save_profile` 的改法：

```python
async with unit_of_work(db, name="farmer.save_profile"):
    await self.crop_repo.delete_all(db, user_id)
    for i, item in enumerate(req.crops):
        await self.crop_repo.add(db, user_id, Crop(...))
    await ProfileService().update_tags(db, user_id, [...])
return await self.get_profile(db, user_id)
```

删除与新增进入同一事务后，"某条作物约束失败导致列表被清空"不再可能。

### 五、并发冲突的处理

`ConflictError` 用于乐观锁或唯一约束冲突：

```python
class ConflictError(AppException):
    def __init__(self, message: str = "数据已被并发修改，请重试"):
        super().__init__(409, message)
```

在 `unit_of_work` 捕获 SQLAlchemy 的 `IntegrityError` 并转换为 `ConflictError`：

```python
from sqlalchemy.exc import IntegrityError

    except IntegrityError as exc:
        await db.rollback()
        raise ConflictError() from exc
```

这样接口层不需要知道数据库错误码。注意 `IntegrityError` 有两种成因：唯一约束冲突（可重试）与外键违反（不可重试）。本项不做细分，统一 409，细分留给第二步的具体用例。

### 六、测试要求

`tests/test_transaction.py` 必须覆盖：

- 在 `unit_of_work` 内 `add` 一行后抛异常，断言该行未落库（用新会话查询）。
- 嵌套内层抛异常、外层捕获后继续，断言内层改动被回滚而外层改动可提交。
- 连续两次 `unit_of_work` 均成功，断言两次提交都生效（幂等性，不是"只剩最后一次"）。
- 唯一约束冲突触发 `ConflictError`（409）而非 500。
- 服务层漏提交时，`get_db` 的 finally 分支回滚，断言数据未落库且日志含 "已回滚"。

`tests/test_rollback_on_error.py` 覆盖端到端：调 `/api/ai/chat`，用 monkeypatch 让 `_persist` 的第二步抛异常，断言 `ai_conversation` 与 `ai_message` 行数均未变化（不是只断言返回码）。

# T5-02 厂商模板库与内置模板

## 这一项要做什么

建立 `vendor_template` 表与内置模板数据集，覆盖主流厂商与型号的报文结构。模板记录"这个型号的报文长什么样、每个字段对应什么标准指标、缩放与偏移是多少"，农户绑定时若命中模板，第二步的"粘贴样例报文"与第三步的"逐字段点选"可以一并省略，只需一次确认。产品说明书 7.3 明确"厂商模板的建设是本模块投入的重点，覆盖主流型号即可覆盖多数农户"，本项对应的就是这块投入。

没有模板时农户必须粘贴一条报文并逐字段点选；有模板时系统直接铺开映射。两种路径都要能走通，模板命中不是前置条件。

## 前置依赖

- T5-01 提供的 `field_mapping` 表与 `StandardMetric` 枚举（模板的 `field_spec` 取值必须落在同一枚举上）。
- T5-01 提供的 `device_config.vendor_template_id` 列（模板与设备的关联列）。
- 外部环境：PostgreSQL 16+（`field_spec` 用 `JSONB`）。
- 需要人工确认：内置模板的型号清单与字段对应关系。这部分属于农技与产品共同确认的内容（全局约定 八、需要人工确认的三处），执行者按给定数据录入，不自行决定"某型号的 `t1` 是不是土壤温度"。
- 现有改造起点：无。当前代码不存在模板概念，从零新增。

## 实现要点

### 一、表结构按方案 12.6 原样采用

```python
class VendorTemplate(Base, TimestampMixin):
    """厂商报文模板：覆盖主流型号，使第二步粘贴动作可省略。"""

    __tablename__ = "vendor_template"
    __table_args__ = (Index("ix_vendor_template_vendor", "vendor_name"),)

    id: Mapped[str] = mapped_column(String(36), primary_key=True)
    vendor_name: Mapped[str] = mapped_column(String(60), nullable=False)
    model_pattern: Mapped[str | None] = mapped_column(String(80))     # 型号匹配规则
    sample_payload: Mapped[str] = mapped_column(Text, nullable=False)  # 样例报文
    field_spec: Mapped[dict] = mapped_column(JSONB, nullable=False)    # 字段 → 指标预映射
```

`vendor_template` 不继承 `OwnedMixin`：模板是平台侧公共资产，不属于任何农户。这是全局约定中"所有业务表带 `user_id`"的一个合理例外——模板由运营维护，农户只能读不能写，平台管理员才能增删。`id` 用固定字符串而非随机 UUID，因为内置模板要能在多环境间稳定对应（T5-06 排查、T5-04 匹配都按 `id` 引用）。

方案 12.6 原文 `field_spec = mapped_column(JSON)`，本项改用 `JSONB`，与知识条目 `facts` 列的选型保持一致，理由是 `field_spec` 需要按键查询（按 `raw_field` 找映射）与去重比较，`JSONB` 有结构化的索引与等值比较能力。

### 二、field_spec 的数据格式

`field_spec` 是一个字段列表，每项包含原始字段名与其标准指标、单位、换算参数。格式与 `field_mapping` 的行结构一一对应，使"模板铺开映射"是纯粹的字段复制，不需要再做一层翻译：

```json
{
  "air_temp": {
    "standard_metric": "air_temp",
    "unit": "°C",
    "scale_factor": 0.1,
    "offset_value": 0,
    "data_type": "float",
    "sample_value": 265
  },
  "air_humi": {
    "standard_metric": "air_humidity",
    "unit": "%",
    "scale_factor": 1,
    "offset_value": 0,
    "data_type": "int",
    "sample_value": 78
  }
}
```

顶层键是报文里的 `raw_field`，值里的 `sample_value` 是该模板 `sample_payload` 中该字段的实际值。`sample_value` 存在的意义是：农户确认模板时界面要展示"这个字段（`air_temp`）读到的原始值是 `265`，换算后是 `26.5°C`"，让农户能对着设备说明书核对。只有 `standard_metric` 与 `scale_factor` 而没有原始值，农户无法判断模板是否选对。

换算公式统一为 `物理值 = scale_factor × raw + offset_value`，来自调研报告 9.2 与 9.4 的参考换算（"常见 scale 为 0.1（÷10）、0.01、0.001"）。`265 × 0.1 + 0 = 26.5` 是本格式的最小自洽样例。

### 三、内置模板数据集

`vendor_templates.json` 覆盖调研报告 9.4 给出的四类报文结构，对应四个典型场景：

| 模板 id | vendor_name | model_pattern | sample_payload 结构 |
| --- | --- | --- | --- |
| `tpl_generic_http` | 通用四合一 | `.*` | `{"sn":...,"ts":...,"data":{"air_temp":26.5,...}}` |
| `tpl_aliyun_alink` | 阿里云 Alink | `Ali.*` | `{"id":...,"method":"thing.event.property.post","params":{...}}` |
| `tpl_tencent_iot` | 腾讯云物模型 | `TC.*` | `{"method":"report","clientToken":...,"params":{...}}` |
| `tpl_onenet_dp` | OneNET | `ON.*` | `{"id":...,"dp":{"temperature":[{"v":25.3,"t":...}]}}` |

`tpl_generic_http` 的 `model_pattern` 写成 `.*`（匹配一切）是刻意的兜底项，排在匹配顺序末位。理由来自调研报告 8.2：推荐起点是 L1 HTTP 直报，自定义 JSON 是"推荐本项目 L1 采用，结构最简"的形态。多数自建固件会采用它，而这类设备没有可识别的厂商型号，只能靠"报文结构像不像"来匹配。

四种结构的差异决定了匹配不能只看型号字符串，还要看报文形态：

```python
class VendorTemplateRepository:
    async def match(self, db: AsyncSession, payload: dict,
                    model_hint: str | None = None) -> VendorTemplate | None:
        """两层匹配：先按型号字符串，再按报文结构特征，最后落通用模板。"""
        templates = (await db.execute(select(VendorTemplate))).scalars().all()
        if model_hint:
            for tpl in templates:
                if tpl.model_pattern and re.fullmatch(tpl.model_pattern, model_hint):
                    return tpl
        shape = _payload_shape(payload)          # method+params / dp / data
        for tpl in templates:
            if _template_shape(tpl.sample_payload) == shape:
                return tpl
        return _find_generic(templates)          # tpl_generic_http
```

`_payload_shape` 返回报文的结构签名（`{"method","params"}` 存在则为 `alink/tencent`，`{"dp"}` 存在则为 `onenet`，`{"data"}` 存在则为 `generic`）。按结构匹配比对字段名匹配稳健：底层平台不同但报文结构相同的设备会得到同一个模板，这正是模板能覆盖"多数农户"的实现方式。`model_hint` 为可选参数，仅在小程序侧能取到型号（如扫码带出）时传入。

### 四、内置模板的幂等导入

模板随代码发布，不靠人工插库。启动时从 `vendor_templates.json` 导入，以固定 `id` 为键做 upsert：

```python
async def seed_vendor_templates(db: AsyncSession) -> int:
    """幂等导入内置模板：按 id upsert，不删除运营手工新增的模板。"""
    data = json.loads(Path(__file__).with_name("vendor_templates.json").read_text("utf-8"))
    count = 0
    for item in data:
        existing = await db.get(VendorTemplate, item["id"])
        if existing is None:
            db.add(VendorTemplate(**item))
        else:
            for k, v in item.items():
                setattr(existing, k, v)
        count += 1
    await db.commit()
    return count
```

只 upsert 不删除，因为运营会在库里补充新采购型号的模板，启动清理会把这些手工数据抹掉。这也意味着 `vendor_templates.json` 是"内置基线"，数据库是"基线加运营增量"。幂等是必需的：容器滚动重启会多次执行，非幂等的插入会让第二次启动直接失败。

### 五、"粘贴样例报文"这一步如何被省略

三步接入的第二步（T5-04）分两条路径，模板命中与否决定走哪条：

| 路径 | 触发条件 | 农户操作 | 得到的结果 |
| --- | --- | --- | --- |
| 模板命中 | `BindResponse.vendorTemplateMatched=true` | 确认一次 | `field_mapping` 直接铺开，跳过粘贴 |
| 自由推断 | 未命中模板 | 粘贴一条样例报文 | 进入 T5-04 的两层启发式推断 |

`BindResponse.nextStep` 在两个分支下取值不同：命中模板时为 `"confirm_template"`，未命中时为 `"provide_sample"`（方案 13.4 的默认值）。前端据 `nextStep` 决定渲染确认页还是粘贴页，这个字段是两条路径的开关。

需要强调的是模板命中后仍要农户确认一次，而不是静默铺开：模板是"某型号通常这样"，但同一型号的不同固件版本可能改过字段名。让农户看一眼"你的设备读到 `air_temp=26.5`，我们认它为空气温度"再确认，成本是一次点击，收益是错配在数据落库前被发现。

- `alembic upgrade head` 与 `alembic downgrade -1` 均返回 0；`\d vendor_template` 显示 `field_spec jsonb` 且 `ix_vendor_template_vendor` 存在。

- 对每条内置模板，断言 `json.loads(sample_payload)` 的字段集合与 `field_spec` 顶层键的集合一致（样例报文里出现的字段都有映射，反之亦然）。

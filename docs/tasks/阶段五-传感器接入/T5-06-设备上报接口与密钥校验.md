# T5-06 设备上报接口与密钥校验

## 这一项要做什么

实现设备的 HTTP 直报入口。设备按周期 POST 报文到 `/api/v1/device/report/{device_sn}`，后端用设备密钥鉴权、按字段映射解析、校验数值范围后写入时序表，返回接收与标记的条数。这个接口不属于小程序，因此不走小程序令牌体系，改用绑定时下发的设备密钥。

接口的设计原则是"对设备宽容，对安全严格"：设备端通常是简单固件，收到 5xx 会触发重试风暴，因此业务失败用 200 加计数字段表达；但鉴权失败必须明确拒绝，防止数据串号或伪造。异常数据标记而不丢弃，保留原始值供排查。

## 实现要点

### 一、接口代码骨架按方案 13.3 原样保留

```python
@router.post("/device/report/{device_sn}")
async def device_report(
    device_sn: str,
    payload: dict,
    x_device_secret: str = Header(..., alias="X-Device-Secret"),
    db: AsyncSession = Depends(get_db),
):
    """设备 HTTP 直报入口。

    校验顺序：密钥 → 设备存在 → 归属 → 字段映射 → 数值范围。
    任何一步失败都记录但不抛 5xx（避免设备重试风暴）。
    """
    device = await device_repo.get_by_sn(db, device_sn)
    if device is None or not verify_secret(device, x_device_secret):
        raise DeviceAuthError()                        # 403

    mappings = await mapping_repo.list_by_device(db, device.id)
    readings = parse_payload(payload, mappings)        # 按映射解析

    accepted, rejected = [], []
    for r in readings:
        if not in_valid_range(r.metric, r.value):
            r.quality = "suspect"                      # 标记而非丢弃
            rejected.append(r)
        else:
            accepted.append(r)

    await env_repo.bulk_insert(db, accepted + rejected)
    await device_repo.touch_last_report(db, device.id, now())
    return {"accepted": len(accepted), "flagged": len(rejected)}
```

框架差异两点：方案写 `db: Session = Depends(get_db)`，本项按全局约定"全异步：数据库、HTTP、Redis 均用 async 驱动"改为 `AsyncSession`。函数体内 `raise DeviceAuthError()` 是唯一的非 200 返回，其余路径全部返回 200。

需要澄清一处与方案文字的差异：`get_by_sn` 已经过滤了 `unbound_at IS NULL`，因此"设备存在"与"设备未解绑"在此合并为一步。方案注释写"密钥 → 设备存在 → 归属 → 字段映射 → 数值范围"五步，本项保留这个顺序，只是把"设备存在"与"归属（解绑状态）"在实现上落到同一个查询里，行为与方案一致。

### 二、设计要点一：设备密钥而非小程序令牌

产品说明书 7.4 要求"设备上报需校验设备归属，防止数据串号或被伪造"。设备侧没有微信登录态，无法走小程序令牌，因此用绑定时下发的设备密钥。

```python
def verify_secret(device: DeviceConfig, presented: str) -> bool:
    """设备密钥比对；不解密、不查库二次请求，纯函数在内存完成。"""
    if not presented or not device.secret_digest:
        return False
    expected = hashlib.sha256(
        (get_settings().DEVICE_SECRET_SALT + presented).encode()
    ).hexdigest()
    return secrets.compare_digest(expected, device.secret_digest)
```

密钥比对用常量时间函数（`compare_digest`），不用 `==`。设备上报入口是对外暴露的匿名入口（只凭 SN 与密钥），`==` 的短路比较会泄露密钥前缀信息，足够多的请求可以逐字节猜出密钥。这个入口的调用方是设备而不是浏览器，没有 CSRF 顾虑，但时序侧信道顾虑存在。

密钥校验与"设备存在"合并返回同一个 403，不区分"SN 不存在"与"密钥错误"。区分会让攻击者能枚举合法 SN（虽然 SN 通常印在设备上，但枚举本身会带来无效查询压力）。

### 三、设计要点二：异常数据标记而非拒绝

产品说明书 4.4.3 功能点 2 明确"异常数据（明显超范围）应被标记并排除在阈值判断之外，而不是直接丢弃或直接使用"。落地方案是写库时带上 `quality` 标记，两类都入库：

| 情况 | `quality` | 是否参与阈值判断 | 是否落库 |
| --- | --- | --- | --- |
| 数值在量程内 | `ok` | 是 | 是 |
| 数值超量程 | `suspect` | 否（保留原始值供排查） | 是 |
| 时间戳超 24 小时 | `stale` | 否（仅看板参考） | 是 |

`accepted` 与 `rejected` 都进 `bulk_insert`，命名只是为返回计数：`accepted` 是 `ok`，`rejected` 是 `suspect`。仓储层不做过滤，确保"保留原始值供排查"成立。若在入口就把 `suspect` 丢掉，农户设备装反了也查不出原因。

标记发生在写库前，因此 `parse_payload` 产出的读数对象在入队前就被改了 `quality`，不存在"写进去是 ok、事后才发现超范围"的窗口。

### 四、设计要点三：不返回 5xx

设备端固件收到 5xx 会重试（多数 4G DTU 的重试策略是立即重试加退避）。若平台因某条报文的字段缺失而返回 500，设备会把同一条报文反复送来，把一次小错误放大成持续压力。因此：

| 失败情形 | 返回 | 说明 |
| --- | --- | --- |
| SN 不存在或密钥错误 | 403 | 唯一允许的非 200；设备固件通常不会对 403 重试 |
| 报文不是合法 JSON | 200 `{"accepted":0,"flagged":0,"note":"payload_unparsable"}` | 记录但不重试 |
| 报文无映射字段 | 200 `{"accepted":0,"flagged":0,"note":"no_mapping"}` | 同上 |
| 设备未配置映射 | 200 `{"accepted":0,"flagged":0,"note":"mapping_missing"}` | 设备先接入、映射后配置的窗口期 |
| 数值超范围 | 200，`flagged` 计数 | 已标记入库 |
| 数据库瞬时故障 | 200 `{"accepted":0,"flagged":0,"note":"deferred"}` | 记日志由运维处理，不让设备重试 |

不返回 5xx 不等于不记录失败。每一次异常路径都写结构化日志（含 SN、失败环节、报文摘要），运维按 `note` 分类排查。这就是方案注释"任何一步失败都记录但不抛 5xx"的完整含义：500 换成日志，设备侧感知不到失败，平台侧仍可追溯。

`deferred` 这一类是本项对方案的补充。方案未涉及落库失败，但数据库瞬时故障在分布式环境必然出现，若此时抛 5xx 会触发全量设备重试风暴，比丢一批读数严重得多。取舍是不让设备重试，接受少量数据缺口。

### 五、校验顺序与每一步的失败记录

顺序不可调换，原因各有不同：

| 步骤 | 校验内容 | 为什么必须在此位置 |
| --- | --- | --- |
| 1 | 密钥 | 最早，未鉴权的请求不应触达任何业务查询 |
| 2 | 设备存在 | 密钥比对需要设备行，两者合并 |
| 3 | 归属（未解绑） | 解绑的设备立即停止入数，防止旧设备继续写 |
| 4 | 字段映射 | 解析需要映射，映射缺失则无法继续 |
| 5 | 数值范围 | 最后，需要解析结果才能判断 |

若把数值范围提到映射之前，就没有"指标"可用于查区间（区间按指标定义）。若把映射查询提到密钥之前，未鉴权请求会消耗数据库连接。这个顺序是"先廉价后昂贵、先安全后业务"的体现。

### 六、parse_payload 的契约

`parse_payload` 是 T5-05 与 T5-06 共享的纯函数，签名与行为要稳定：

```python
def parse_payload(payload: dict, mappings: list[FieldMapping]) -> list[Reading]:
    """按映射把报文翻译成标准读数。

    - 只取 mappings 中出现的 raw_field，报文里多余的字段忽略
    - 数值换算 value = scale_factor * raw + offset_value
    - 无法数值化或字段缺失的映射项跳过，不产出行
    - observed_at 取报文中的时间戳，缺失或非法则用服务端当前时间
    """
```

三条边界约定要与 T5-05 一致：多余字段忽略（设备固件版本升级可能多发字段，不应导致解析失败）、缺字段跳过（不应让一个字段的缺失拖垮整批读数）、时间戳缺失回退服务端时间（本项取服务端 `now()` 并交给 T5-07 判 `stale`）。时间戳来源要记录在读数对象上，供 T5-07 区分"设备报的时间"与"平台收到的时间"。

## 验收标准

# T5-03 设备绑定接口

## 这一项要做什么

实现三步接入的第一步：农户提交设备编号（扫码或手填），后端校验编号可用性、建立设备与农户的归属关系、生成并下发设备密钥，返回下一步的引导信息。这个接口是整个接入流程的入口，它决定后面两步走模板确认还是粘贴推断，也决定设备后续上报能否通过鉴权。

现有代码没有任何设备绑定入口：`Device` 表虽有 `user_id`、`bind_time` 字段（注释写明"未绑定为null"），说明设计时预留了绑定流程，但没有实现，小程序侧也没有对应页面。本项把预留补齐。

## 前置依赖

- T5-01 提供的 `device_config` 表、`DeviceConfigRepository`、`get_by_sn()`。
- T5-02 提供的 `VendorTemplateRepository.match()`，用于在绑定时判断该设备是否有可命中模板。
- T1-05 提供的 `OwnedRepository` 与归属校验基类；T1-07 提供的令牌与安全工具（密钥哈希沿用同一套）。
- 外部环境：密钥哈希所需的盐值配置（`DEVICE_SECRET_SALT`）；Redis（可选，用于绑定过程的短时状态）。
- 现有改造起点：`app/api/v1/device.py` 不存在，需新建路由文件；`app/api/v1/__init__.py` 的路由注册需要挂载。现有 `app/core/response.py` 的 `ok()` 包装沿用。

## 实现要点

### 一、出入参按方案 13.4 原样采用

```python
class BindRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    deviceSn: str
    farmEntryId: str | None = None


class BindResponse(BaseModel):
    deviceId: str
    vendorTemplateMatched: bool
    templateId: str | None = None
    nextStep: str = "provide_sample"
```

字段名保持方案里的驼峰形式，因为这套出入参是给小程序前端消费的，与 T3、T2 阶段的接口风格一致（`ChatResponse` 的 `sessionId` / `stageLabel` 同为驼峰）。后端内部变量用蛇形，转换发生在 schema 边界。

`farmEntryId` 可为空：产品说明书 4.4 把"地块"作为可选维度，农户可以只绑设备不指定地块。为空时上报的读数 `farm_entry_id` 落 `NULL`，环境看板按用户维度展示（T5-08 处理）。

### 二、绑定流程与密钥下发

```python
async def bind_device(db: AsyncSession, user_id: str, req: BindRequest) -> BindResponse:
    """三步接入第一步：绑定设备编号并下发设备密钥。"""
    sn = req.deviceSn.strip()
    if not _valid_sn_format(sn):
        raise ValidationError("设备编号格式不正确，请核对后重新输入")

    existing = await device_repo.get_by_sn_any(db, sn)
    if existing and existing.unbound_at is None:
        if existing.user_id == user_id:
            # 已绑定在同一农户名下：幂等返回，不重复下发密钥
            return _to_bind_response(existing, matched=existing.vendor_template_id is not None)
        raise ConflictError("该设备已被绑定，请核对设备编号或联系客服")

    secret = generate_device_secret()              # 32 字节随机，base64url
    secret_ref, hashed = hash_device_secret(secret)

    if existing:
        # 曾被解绑：复用同一行，重置绑定关系与密钥
        device = await device_repo.rebind(db, user_id, existing.id,
                                          farm_entry_id=req.farmEntryId,
                                          secret_ref=secret_ref)
    else:
        device = await device_repo.create(db, user_id, device_sn=sn,
                                          farm_entry_id=req.farmEntryId,
                                          protocol_type="http_direct",
                                          secret_ref=secret_ref,
                                          bound_at=now())

    matched_tpl = await template_repo.match(db, payload={}, model_hint=_model_from_sn(sn))
    if matched_tpl:
        device.vendor_template_id = matched_tpl.id
        await db.commit()

    return BindResponse(
        deviceId=device.id,
        vendorTemplateMatched=matched_tpl is not None,
        templateId=matched_tpl.id if matched_tpl else None,
        nextStep="confirm_template" if matched_tpl else "provide_sample",
    )
```

`deviceSn` 必须在绑定时就做格式校验，不能等到上报（T5-06）才发现编号不合法。格式规则按 `String(60)` 上限与前缀约定（如 `HN` 开头加数字）在 `_valid_sn_format` 内定义，规则本身要放宽，避免把合法编号误判为非法（不同厂商编号规则差异大），因此只做"非空、长度不超过 60、不含空白与非法字符"三条，不做正则强约束。

### 三、密钥下发与存储

密钥不能明文落库。调研报告 11.1 指出"密钥管理的核心矛盾"是设备端是简单固件、无法安全保存密钥材料，而平台侧又不能因为设备弱而放松。本项的取舍是：

```python
def generate_device_secret() -> str:
    """生成 32 字节随机密钥，base64url 编码，无填充。"""
    return base64.urlsafe_b64encode(secrets.token_bytes(32)).rstrip(b"=").decode()


def hash_device_secret(secret: str) -> tuple[str, str]:
    """返回 (secret_ref, digest)。digest 用加盐 SHA-256，secret 不在任何表中留存。"""
    digest = hashlib.sha256((get_settings().DEVICE_SECRET_SALT + secret).encode()).hexdigest()
    ref = f"device_secret:{uuid4()}"          # 引用名，用于审计与轮换定位
    return ref, digest


def verify_device_secret(device: DeviceConfig, presented: str) -> bool:
    """常量时间比较，避免时序侧信道。"""
    expected = hashlib.sha256(
        (get_settings().DEVICE_SECRET_SALT + presented).encode()
    ).hexdigest()
    return secrets.compare_digest(expected, device.secret_digest)
```

`secret_ref` 与 `secret_digest` 分开：`secret_ref` 是可读的引用名，用于审计日志与轮换记录（"某设备在何时换了密钥"），`secret_digest` 是比对材料。这两个字段都落在 `device_config`，本项在 T5-01 的列基础上补 `secret_digest` 列（T5-01 只建了 `secret_ref`）。

密钥只在 `bind_device` 的响应里出现一次（在 T5-03 的响应体里补充下发字段），之后平台无法再取到明文。这是与 T1-07 令牌处理一致的取舍：可重复取回的秘密等于没有秘密。

### 四、下发方式与上报地址

响应中除了方案 13.4 的四个字段，还要附带上报地址：农户需要把地址与密钥抄进设备/网关的配置，调研报告 8.2 的农户操作是"小程序内填设备 SN + 平台生成的接入 Token，粘贴一条样例报文"。

| 下发项 | 取值来源 | 农户用途 |
| --- | --- | --- |
| 上报地址 | `DEVICE_REPORT_BASE_URL` + `/api/v1/device/report/{sn}` | 配置进设备或 DTU |
| 设备密钥 | 本次生成的明文 | 配置为 `X-Device-Secret` 请求头 |
| 上报周期建议 | 由设备侧决定，平台不强制 | 说明书参考值 |

上报地址的域名必须是已备案域名（产品说明书 7.4："请求域名必须预先在微信后台备案，仅支持 https，不接受 IP 地址与 localhost"）。因此地址来自配置项而不是请求 Host 头推导，防止在反向代理后生成内网地址。

### 五、幂等与重复绑定

重复绑定分三种情况，行为不同：

| 情况 | 行为 | 理由 |
| --- | --- | --- |
| 同一农户重复绑定同一 SN | 返回既有 `deviceId`，`nextStep` 按已有状态给出 | 农户重复点击不应产生第二台设备 |
| 设备已绑定到他人 | 409，提示"已被绑定" | 防止数据串号（产品说明书 7.4） |
| 设备曾被本人解绑 | 复用原行，重置密钥与绑定时间 | 重新接入不应重复占号 |

第一种情况不重新下发密钥：农户重复点击时若密钥被刷新，之前已配进设备的密钥会立即失效，表现为"设备突然不上报了"。这是幂等要覆盖的核心场景。

`get_by_sn_any` 与 T5-01 的 `get_by_sn` 区分：后者过滤 `unbound_at IS NULL`，服务上报入口（只认有效绑定）；前者不过滤，服务绑定时判断"这台设备历史上有没有被用过"。

## 验收标准

- `pytest backend/tests/api/test_device_bind.py` 全部通过，含五条用例：新 `deviceSn` 绑定返回 200 且 `deviceId` 非空、`nextStep` 为 `"provide_sample"` 或 `"confirm_template"`；同一农户重复绑定同一 SN 两次返回同一 `deviceId` 且不重复建行；他人已绑定的 SN 绑定返回 409；`deviceSn` 为空或超 60 字符返回 422；响应体不含任何明文密钥以外的设备他人信息。
- `POST /api/v1/device/bind` 请求头无令牌时返回 401（接口属于小程序域，走令牌体系）。
- 绑定后 `SELECT device_sn, secret_ref, secret_digest FROM device_config WHERE device_sn='...'` 显示 `secret_ref` 有值、`secret_digest` 为 64 位十六进制，且表中不存在明文密钥列。
- `verify_device_secret(device, secret)` 对正确密钥返回 `True`、对错误密钥返回 `False`；`grep -rn "== presented\|== secret" backend/app/core/device_secret.py` 无输出（用 `compare_digest`）。
- 构造 `model_hint` 命中 `tpl_generic_http` 的 SN，断言 `vendorTemplateMatched is True` 且 `templateId == "tpl_generic_http"`；构造无模板可匹配的报文形态，断言 `nextStep == "provide_sample"`。
- `ruff check backend/app`、`ruff format --check backend/app`、`mypy backend/app` 三条命令均返回 0。

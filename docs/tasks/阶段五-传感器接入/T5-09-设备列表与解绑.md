# T5-09 设备列表与解绑

## 这一项要做什么

实现设备的查看与管理：返回农户已绑定设备的列表（含在线状态与最近上报时间），支持解绑。列表要让农户能看出"哪台设备断了、断了多久"，解绑要真正停止该设备继续写入数据，同时保留历史读数与映射供追溯。

现有 `environment_service.detail()` 里已有一段设备列表装配（`devices` 字段，取 `Device` 表），但字段不完整、无在线状态判据、无解绑入口。本项补齐为独立接口，与 T5-03 的绑定构成完整生命周期。

## 前置依赖

- T5-03 提供的绑定关系与 `device_config` 表（列表与解绑都针对这张表，不是旧的 `device` 表）。
- T5-06 提供的 `last_report_at` 与 `online_status` 写入（列表的在线状态据此计算）。
- T5-01 提供的 `DeviceConfigRepository` 与归属校验基类。
- T5-07 提供的读数链路（解绑后设备上报返回 403 的回归验证）。
- 外部环境：Redis（可选，用于最近上报时间的快速读取，不强制）。
- 现有改造起点：`app/api/v1/device.py`（T5-03 新建，本项追加两个路由）；`app/services/environment_service.py::detail()` 的 `devices` 装配段需改为复用本项的服务方法。

## 实现要点

### 一、列表出入参

```python
class DeviceListItem(BaseModel):
    id: str
    deviceSn: str
    deviceName: str | None
    farmEntryId: str | None
    onlineState: str              # online / offline / fault
    lastReportAt: datetime | None
    silenceNote: str | None       # "你的设备已 3 天没有上报数据"
    mappedFields: int             # 已配置的映射条数，0 表示未完成接入
    boundAt: datetime


class DeviceListResponse(BaseModel):
    devices: list[DeviceListItem]
```

`mappedFields` 是让农户知道"这台设备接好了没有"：绑定成功但映射没保存的设备会持续 `mappedFields == 0`，上报时返回 `mapping_missing`（T5-06）。农户在列表里看到"已配置 0 个字段"就能意识到接入没走完，不必去翻接入记录。

`onlineState` 用字符串枚举而不是现有 `Device` 表的 `status`（0/1/2 整数）。全局约定要求"状态字段用字符串枚举值，不用整数编码"，且 `device_config.online_status` 列本身就是字符串。旧 `Device` 表的整数 `status` 保留不动（其他模块可能引用），新接口以 `device_config` 为准。

### 二、在线状态与静默提示

在线状态不用设备主动上报心跳，而是由最近上报时间反推，避免要求设备实现额外的保活协议（设备通常是简单固件）：

```python
OFFLINE_THRESHOLD_S = 3 * 600          # 3 倍采集周期；采集周期取 10 分钟


def _online_state(last_report_at: datetime | None, now: datetime) -> str:
    """按最近上报时间反推在线状态；从未上报视为 offline。"""
    if last_report_at is None:
        return "offline"
    delta = (now - last_report_at).total_seconds()
    if delta <= OFFLINE_THRESHOLD_S:
        return "online"
    if delta <= 7 * 86400:
        return "offline"
    return "fault"
```

阈值的取值逻辑来自调研报告 10.5："阈值建议取 3 倍采集周期"。采集周期取 10 分钟（技术方案第 4 章的估算口径"每户 1 台设备、10 分钟一次上报"），因此 `OFFLINE_THRESHOLD_S = 1800`。取 3 倍而不是 1 倍是给网络抖动留余量：设备晚 1 个周期上报是常态，晚 3 个周期才值得提示。

`fault` 与 `offline` 的区别是时长：短时间失联可能是断网（会自行恢复），长期失联更可能是设备断电或被拆（需要农户干预）。用状态区分让列表能给出不同的提示语气。

静默提示按产品说明书 4.4.3 功能点 5 的原文形态给出：

| 静默时长 | `silenceNote` |
| --- | --- |
| 少于 30 分钟 | 无 |
| 30 分钟至 24 小时 | 你的设备已 X 小时没有上报数据 |
| 1 至 7 天 | 你的设备已 X 天没有上报数据 |
| 超过 7 天 | 你的设备已长期没有上报数据，请检查设备通电与网络 |

`silenceNote` 只在 `onlineState != "online"` 时非空。天数取整并设下限 1，理由与 T5-08 的小时数下限一致：不足 1 天显示"1 天"比"0 天"更符合农户理解。

### 三、解绑

```python
async def unbind_device(db: AsyncSession, user_id: str, device_id: str) -> None:
    """解绑：软删除设备，保留历史读数与映射供追溯。"""
    device = await device_repo.get(db, user_id, device_id)
    if device is None:
        raise NotFoundError("设备不存在或无权访问")
    if device.unbound_at is not None:
        return                                        # 幂等：重复解绑不报错

    await device_repo.update_fields(db, user_id, device_id,
                                    unbound_at=now(), online_status="offline")
```

解绑的三个语义决定：

第一，**软删除而非物理删除**。写 `unbound_at` 而不删行，因为 `env_reading` 里的历史读数带 `device_id` 外键，物理删除设备会让历史读数的归属断链。产品说明书 4.4.3 功能点 5 只说"支持解绑与重新绑定"，未规定历史数据处置；本项选择保留全部历史（卷宗价值：农户回看"去年那块地的湿度"仍然可用）。这处是对方案的一处推断。

第二，**不删除字段映射**。解绑后映射保留，重新绑定同一 SN 时可以直接复用，不必重走三步接入。T5-01 的唯一约束 `(device_id, raw_field)` 与 T5-03 的 `rebind` 复用同一行，两者配合使"解绑再绑"是廉价的。

第三，**不删除设备密钥**。解绑后 T5-06 的 `get_by_sn` 因过滤 `unbound_at IS NULL` 返回 `None`，设备上报即返回 403。密钥留着是为了重新绑定时判断"这台设备历史上是否被用过"（T5-03 的 `get_by_sn_any`），以及审计追溯。密钥的作废由解绑本身的效果保证（查不到设备即无法鉴权），不需要额外吊销动作。

### 四、解绑后旧设备的即时失效

解绑要真正停止数据写入，这是产品说明书 4.5.2 功能点 4 的要求（"所有查询、更新、删除操作都必须校验数据归属"）。验证路径是：

| 时刻 | 设备上报 | 结果 |
| --- | --- | --- |
| 解绑前 | 带正确密钥 | 200，读数入库 |
| 解绑后立刻 | 带正确密钥 | 403，读数不入库 |
| 解绑后 | 重新绑定后带新密钥 | 200，读数入库 |
| 解绑后 | 带旧密钥 | 403 |

失效依赖的是 T5-06 的 `get_by_sn` 过滤条件，不依赖缓存过期或后台任务。这一点很重要：如果用缓存存"设备是否有效"，解绑后到缓存失效之间会有一个写入窗口，旧设备能继续写数。用数据库的 `unbound_at IS NULL` 条件判定，失效是即时的、无窗口的。

重新绑定时 T5-03 会生成新密钥（旧密钥随之失效），因为 `rebind` 覆写 `secret_ref` 与 `secret_digest`。因此"解绑后带旧密钥"返回 403 有两重保证：设备查不到，以及即便查到了密钥也已不匹配。

### 五、归属校验与越权

列表与解绑都要带 `user_id` 条件，走 `OwnedRepository`。越权访问的行为统一为 404 而不是 403：返回 403 会泄露"这个 `device_id` 存在但不属于你"，攻击者能据此枚举有效 ID。返回 404（"设备不存在或无权访问"）对越权和不存在给出同一个响应，不泄露存在性。这与 T5-03 的"他人已绑定返回 409"不同——那里必须告诉农户"该设备已被绑定"，因为这是农户需要采取行动的信息（换一台设备或联系客服）；而对自己名下不存在的 ID，农户不需要区分，只需知道操作没成功。

```python
@router.get("/device/list")
async def list_devices(db: AsyncSession = Depends(get_db),
                       user_id: str = Depends(get_current_user)):
    return ok(await device_service.list_devices(db, user_id))


@router.delete("/device/{device_id}")
async def unbind_device(device_id: str, db: AsyncSession = Depends(get_db),
                        user_id: str = Depends(get_current_user)):
    await device_service.unbind_device(db, user_id, device_id)
    return ok({"unbound": True})
```

两个接口都走小程序令牌体系（`get_current_user`），与 T5-06 的设备密钥体系分开。设备上报入口是设备调用，管理入口是农户在小程序里调用，两套凭据不混用。

### 六、与 detail() 设备段的收敛

现有 `environment_service.detail()` 直接查 `Device` 表装配 `devices`，字段只有 `id` / `name` / `type` / `status` / `lastOnline`。本项把它改为调用 `list_devices()`，使两个界面的设备信息一致：

| 界面 | 现状 | 改造后 |
| --- | --- | --- |
| 环境详情（`detail()`） | 查 `Device` 表，整数 `status` | 调 `list_devices()`，字符串 `onlineState` |
| 设备管理列表（本项） | 无 | 调 `list_devices()` |

两处都查 `device_config`、都用同一套在线判据，避免"环境页说在线、设备页说离线"这种矛盾。旧 `Device` 表在收敛后仅供历史数据引用，新功能一律以 `device_config` 为准（T5-01 已说明两表并存的原因）。

## 验收标准

- `pytest backend/tests/api/test_device_manage.py` 全部通过，含以下用例：`GET /api/v1/device/list` 返回该农户全部未解绑设备，不含他人设备；`lastReportAt` 为 10 分钟前的设备 `onlineState == "online"`；1 小时前的设备 `onlineState == "offline"` 且 `silenceNote` 含"小时"；10 天前的设备 `onlineState == "fault"`；从未上报的设备 `onlineState == "offline"` 且 `lastReportAt is None`。
- 解绑用例：`DELETE /api/v1/device/{id}` 返回 200；解绑后该设备不再出现在列表中；`SELECT unbound_at FROM device_config` 非空；重复解绑返回 200（幂等）。
- 失效用例：解绑后用原密钥与 SN 调用 `POST /api/v1/device/report/{sn}` 返回 403，且 `SELECT count(*) FROM env_reading` 在解绑前后差值为 0。
- 重新绑定用例：解绑后再次调用 `POST /api/v1/device/bind` 返回同一 `deviceId`，且 `SELECT count(*) FROM field_mapping WHERE device_id=...` 保持解绑前的条数（映射未被清除）。
- 越权用例：用 `u2` 的令牌 `DELETE u1` 的设备返回 404，且 `u1` 该设备的 `unbound_at` 仍为 `NULL`。
- `mappedFields` 用例：完成三步接入的设备返回大于 0，绑定但未保存映射的设备返回 0。
- `environment_service.detail()` 的 `devices` 返回项与 `GET /api/v1/device/list` 对同一农户的 `deviceSn` 集合一致。
- `ruff check backend/app`、`ruff format --check backend/app`、`mypy backend/app` 三条命令均返回 0。

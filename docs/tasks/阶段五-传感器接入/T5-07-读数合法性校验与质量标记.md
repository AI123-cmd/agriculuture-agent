# T5-07 读数合法性校验与质量标记

## 这一项要做什么

实现读数落库前的三条校验规则与 `quality` 三值判定，把"能用的数据"和"可疑数据"分开，供下游决策如何引用。校验分三类：数值范围合法性、时间戳有效性、设备归属。前两类标记而不阻断，第三类直接拒绝。判定结果写进 `env_reading.quality`，取值为 `ok` / `suspect` / `stale`。

这三条规则是产品说明书"异常数据应被标记并排除在阈值判断之外，而不是直接丢弃或直接使用"的落地形态。它们不只是数据清洗，还直接决定 T3-02 的环境事实采集能否引用某条读数、T5-08 的环境看板如何标注。

## 前置依赖

## 实现要点

### 一、quality 三值与三条规则表

`quality` 三值的含义与来源：

| 取值 | 含义 | 是否参与阈值判断 | 是否进看板 | 是否落库 |
| --- | --- | --- | --- | --- |
| `ok` | 正常读数 | 是 | 是 | 是 |
| `suspect` | 数值超范围，保留原始值供排查 | 否 | 是（带标记展示） | 是 |
| `stale` | 时间戳超时效 | 否（仅参考） | 是（标注"数据为 XX 小时前"） | 是 |

三条规则按方案 12.6 原样采用：

| 检查 | 处理 |
| --- | --- |
| 数值范围合法性 | 超范围标 `suspect`，保留原始值供排查，不参与阈值判断 |
| 时间戳有效性 | 超出 24 小时标 `stale`，仅用于看板参考展示 |
| 设备归属校验 | 不匹配直接拒绝（403），不落库 |

第三条规则与前两条性质不同：前两条是数据质量问题，可以标记后继续用；第三条是安全问题，必须阻断。这个差别决定了它们的实现位置不同——归属校验在 `ingest_report` 的入口（T5-06 校验顺序第三步），本项只负责前两条的判定，并保证归属校验失败时不会走到 `classify_quality`。

### 二、规则一：数值范围合法性

```python
def classify_quality(reading: Reading, *, now: datetime) -> str:
    """三值判定。范围与时效都不合格时，范围问题优先（suspect 优先于 stale）。"""
    if not in_valid_range(reading.metric, reading.value):
        return "suspect"
    if _stale(reading.observed_at, now):
        return "stale"
    return "ok"


def in_valid_range(metric: str, value: float) -> bool:
    """量程判定；区间取自 StandardMetric，与 T5-05 换算级校验同源。"""
    lo, hi = METRIC_RANGES[StandardMetric(metric)]
    return lo <= value <= hi
```

超范围标 `suspect` 而不是丢弃，是产品说明书 4.4.3 功能点 2 的硬要求。原始值必须保留：农户把探头的硅胶套没拆、探头插在空气里、装了光照但遮了膜，这些都表现为"数值明显不合理"，而原始值本身是排查依据。若在入口丢弃，农户报修时平台拿不出任何数据。

`suspect` 的读数不参与阈值判断这条要在读取侧落实，不能只在写入侧"标记一下"就算了。读取侧的统一入口是 `latest()` 与 `is_fresh()`，两者都过滤掉非 `ok` 读数（T3-02 的 `is_fresh` 内部叠加 `quality == "ok"`）。读取侧不过滤的话，写入侧的标记形同虚设。

判定用闭区间 `lo <= value <= hi`，区间端点边界值（如 `soil_moisture=0` 或 `air_humidity=100`）算合法。土壤水分 0% 在极端干旱时是实测可能值，不应被标 `suspect`；判定阈值与"合法物理范围"对齐而非与"常见值范围"对齐。

### 三、规则二：时间戳有效性

```python
STALE_HOURS = 24


def _stale(observed_at: datetime | None, now: datetime) -> bool:
    """超出 24 小时即 stale。observed_at 缺失视为 stale（无法证明新鲜）。"""
    if observed_at is None:
        return True
    if observed_at.tzinfo is None:
        observed_at = observed_at.replace(tzinfo=timezone.utc)
    return (now - observed_at) > timedelta(hours=STALE_HOURS)
```

24 小时的取值来自产品说明书 4.4.3 功能点 3，与 T3-02 环境事实采集的窗口完全一致：超 24 小时后，环境事实采集回退到天气服务，不再引用该读数。因此 `stale` 的读数只对看板有展示价值（让农户看到"设备 3 天没上报"），对判断链路无价值。

未来时间戳（设备时钟超前）的处理：`now - observed_at` 为负，`> timedelta(hours=24)` 为假，于是被判 `ok`。这在容忍范围之外——设备时钟错到超前数天时会污染"最新读数"。本项对超前超过 1 小时的时间戳标 `suspect` 而不是 `stale`（因为它不是"旧"，是"不可信"）：

```python
CLOCK_SKEW_TOLERANCE = timedelta(hours=1)

def _skewed(observed_at: datetime, now: datetime) -> bool:
    """设备时钟超前超过容忍度，时间戳不可信。"""
    return observed_at - now > CLOCK_SKEW_TOLERANCE
```

这处是对方案的一处推断：方案 12.6 只写"超出 24 小时标 `stale`"，未涉及时间戳超前。但基层设备的 RTC 电池耗尽后时间归零或跳到出厂时间很常见，不处理会让 `latest()` 取到一条未来时间戳的读数并当作最新。

时间戳来源要区分：T5-06 的 `parse_payload` 在报文无时间戳时用服务端 `now()` 填充，此时 `timestamp_source == "server"`。服务端填充的时间戳不会 `stale`（它就是当前时间），但要记录来源——否则"设备从不报时间、平台补当前时间"会让一组旧读数看起来始终新鲜。`stale` 判定只对 `timestamp_source == "device"` 的时间戳生效，`server` 来源的读数不做时效判定，但要在看板标注"时间由平台记录"。

### 四、规则三：归属校验不匹配直接拒绝

```python
device = await device_repo.get_by_sn(db, device_sn)
if device is None or not verify_secret(device, x_device_secret):
    raise DeviceAuthError()                        # 403，不落库
```

这一条的处理是"拒绝"而非"标记"，与另外两条不同，是全局约定"守卫类 fail-closed"的适用：归属不确定时选更保守的一方（拒绝写入）。产品说明书 4.5.2 功能点 4 把"未校验归属的访问路径"列为必须修复的既有缺陷，设备入口是其中最容易被绕过的一处——它不经过小程序令牌体系，若不在入口校验，任何人都能凭猜测的 SN 往库里写数。

拒绝的粒度是"整批拒绝"而不是"逐条拒绝"：设备一次性上报多个读数，SN 与密钥是该批次的整体属性，不存在"部分读数归属正确"的情况。403 一经返回，整批都不落库。

不落库的同时要记审计日志（SN、失败原因、来源 IP、时间）。审计写入失败不得阻断 403 返回，因此审计日志走日志系统而非业务表（若走业务表，审计表写入失败会让已鉴权失败的请求变成 5xx，与 T5-06"不返回 5xx"矛盾）。

### 五、与 T3-02 环境事实采集的口径统一

T5-07 产出的 `quality` 是 T3-02 `is_fresh()` 的输入。两处判据必须一致，否则会出现"看板显示 22°C 正常、提示系统认为无数据"这类矛盾：

| 判据 | 位置 | 取值 |
| --- | --- | --- |
| 实时新鲜窗口 | T5-07 `_stale` 与 T3-02 `is_fresh` | 30 分钟（实时） |
| 参考窗口 | T5-07 `STALE_HOURS` 与 T3-02 `is_within_hours` | 24 小时 |
| 参与判断的质量值 | T5-07 `classify_quality` 与 T3-02 `is_fresh` | 仅 `ok` |

三处判据中，30 分钟与 24 小时两个窗口的常量必须定义在一处（`app/domain/metrics.py`），由 T3-02 与 T5-07 共同导入。任何一处硬编码 30 或 24 都会在调整窗口时漏改，而这种漏改不会报错，只会让两处判断悄悄分叉。

`suspect` 与 `stale` 对 T3-02 的效果相同（都导致降级），但对看板不同：`stale` 可以展示并标注"XX 小时前"，`suspect` 应展示但标注"数值异常"。这个差别由 T5-08 的看板接口负责渲染，T5-07 只保证 `quality` 值准确。

### 六、静态兜底降为末级

现有 `sensors.py::query_sensors` 返回硬编码常量，`source` 写死 `"sensor_snapshot"`。真实链路建好后，这个兜底的定位要改变：

```python
async def query_sensors(db: AsyncSession | None, user_id: str) -> dict:
    """三级取数：真实读数 → 天气服务 → 静态兜底。

    静态兜底的 source 明确标为 "fallback"，不再伪装为传感器读数。
    """
```

关键改动是把 `source` 从 `"sensor_snapshot"` 改为 `"fallback"`，并在返回值中标注静态值不是实测。调研报告 10.5 建议"现有 `sensors.py` 的静态兜底逻辑应保留为最后一级兜底，保证零设备农户仍能看到合理的页面内容"，但保留兜底不等于让兜底值冒充实测——产品说明书 6.4 红线四禁止"无数据支撑的数字"，兜底值必须可识别为兜底值。

现有 `query_sensors` 用 `db.query(Device)` 直接查询，违反全局约定 L4"任何模块不得直接使用 `db.query(Model)`"。本项在改造该函数时一并改为走仓储层。

## 验收标准

- `pytest backend/tests/services/test_quality.py` 全部通过，含以下用例：`soil_temp=25.0` 且时间戳为 5 分钟前判为 `ok`；`air_temp=265.0` 判为 `suspect` 且 `value` 保持 265；`observed_at` 为 25 小时前判为 `stale`；`observed_at` 为 2 小时前判为 `ok`；`observed_at` 超前 3 小时判为 `suspect`；`observed_at is None` 判为 `stale`。

## 一、结论速览

本报告针对两个问题给出结论：智慧农场传感器的类型体系，以及如何让农户在小程序里自行填参数完成传感器接入。

**关于传感器类型。** 智慧农场传感器可分为六大类：土壤类、气象类、水质类、作物生理/表型类、图像/视频类、执行器。其中国产农业现场几乎以 **RS485 + Modbus-RTU 为事实标准**，4–20 mA / 0–10 V 主要出现在工业变送器与科研级采集系统，SDI-12 是国际科研土壤传感器的主流但国产化程度低。[cite:38][cite:40][cite:41][cite:46]

**关于小程序接入。** 最关键的约束是：**微信小程序只能与开发者事先配置、且已 ICP 备案的域名通信**，域名不支持配置父域名，https 域名一旦配置了端口就只能请求该端口。[cite:1] 这意味着**农户在小程序里填写的"任意第三方平台地址"无法被小程序前端直接访问**。因此，"填参数即接入"的正确形态不是"小程序直连设备"，而是：**农户在小程序填参数 → 参数提交到自家后端 → 后端代农户去连接设备或第三方平台 → 小程序只与自家后端通信**。

**最简可行路径。** 综合复杂度和本项目现状，建议以 **L1「HTTP 直报」** 作为起点：设备或 4G DTU 网关以 HTTP(S) POST 向自家后端上报数据，农户只需在小程序填 **设备 SN + 平台生成的接入 Token**，再粘贴一条设备上报报文样例、点选字段含义即可完成绑定。这条路径**不需要 MQTT Broker、不需要对接第三方 IoT 平台、不需要申请微信硬件设备类目**，是当前投入产出比最高的方案。[cite:1][cite:3]

**明确建议放弃的部分。** 不建议做"让农户手填 MQTT host / port / Topic / 字节序 / 缩放系数"的专业模式。小程序 WebSocket 全局并发上限只有 5 条，[cite:1][cite:2] 加上域名白名单限制，手填参数这条路在小程序侧既做不到也难维护。

### 核心判断对照表

| 问题 | 结论 | 关键依据 |
|---|---|---|
| 小程序能直接连设备吗 | 不能（域名白名单 + 端口规则 + 备案要求） | [cite:1] |
| 小程序能直连 MQTT 吗 | 官方无 MQTT API，需 mqtt.js 包在 wss 上，且有版本/端口坑 | [cite:2][cite:25][cite:26] |
| 小程序能同时连几个设备 | 最多 5 条 WebSocket，硬约束 | [cite:1][cite:2] |
| 需要微信"设备管理"类目吗 | 只有要用微信原生设备消息推送时才需要 | [cite:3][cite:4] |
| 农户要填协议细节吗 | 不要，改为"粘贴报文样例 + 点选字段" | 本报告 §9 |
| 485 老传感器能直接接吗 | 不能，必须经 DTU/边缘网关转换 | [cite:29][cite:39][cite:52] |
| 推荐起步方案 | L1 HTTP 直报 + 后端适配层 | 本报告 §8 |

## 三、智慧农场传感器类型全景

### 3.1 土壤类

土壤类是智慧农场最基础、国产化最成熟的一类。国产插针式多合一传感器已可在单支探头内集成温度、水分、EC、pH、氮磷钾（NPK）五项，采用电源/探头/信号三部分隔离设计，防护等级 IP68，默认配置 5 m 线缆。[cite:38]

| 子类 | 典型量程 | 精度 / 分辨率 | 输出接口 |
|---|---|---|---|
| 土壤水分（FDR/电容式） | 0～100% VWC | ±2%（0～50% VWC）；分辨率 0.1% | RS485 Modbus-RTU [cite:33] |
| 土壤温度 | −40～85℃ | ±0.5℃；分辨率 0.1℃ | RS485 Modbus-RTU [cite:33][cite:34] |
| 土壤 EC / 盐分 | 0～10000 μS/cm | ±10%；分辨率 1 μS/cm | RS485 Modbus-RTU [cite:38] |
| 土壤 pH | 3～9 | ±0.6 pH；分辨率 0.01 | RS485 Modbus-RTU [cite:38] |
| 土壤 NPK | 0～1999 mg/kg | ±2% FS；分辨率 0.1～1 mg/kg | RS485 Modbus-RTU [cite:37][cite:38] |

两点工程提示。第一，**"土壤墒情"不是传感器类型，而是业务概念**，通常指多深度土壤水分 + 温度的组合监测。管式/剖面式墒情仪监测深度最大可达 70 cm（超过 70 cm 可定制），土层最小间距 10 cm，采集间隔 5 min～12 h，支持远程设置。[cite:34] 第二，**土壤 NPK 的原位直读精度存在争议**：厂商普遍标注 ±2% FS，但本次调研未找到第三方与实验室化学法的比对数据，属 **【未证实】** 区间，若业务上要用 NPK 做施肥决策，建议在 UI 上标注"参考值"。

### 3.2 气象类

气象类传感器正从"分立式"向"一体式"演进。超声波风速风向已明显替代传统风杯方案，优势是无启动风速限制、可零风速工作、360° 无角度限制，且能同时输出风速与风向数值。[cite:35] 一体化六要素/多要素气象站把温湿度、气压、光学雨量、风速风向集成于一体，统一 RS485 输出。[cite:45]

| 子类 | 典型量程 | 精度 / 分辨率 |
|---|---|---|
| 空气温度 | −40～65℃ | ±0.3～0.5℃；0.1℃ [cite:42][cite:45] |
| 空气湿度 | 0～100% RH | ±3% RH；0.01～0.1% RH [cite:45][cite:46] |
| 风速 | 0～40 m/s（Davis 1～67 m/s） | 超声波 ±(0.3+0.03V) m/s [cite:42][cite:45] |
| 风向 | 0～360° | 分辨率 1°；精度 ±3°～±4° [cite:42] |
| 降雨量（翻斗式） | 0～9999 mm | ±4%；分辨率 0.2 mm [cite:42][cite:47] |
| 光学雨量（无机械） | 0～4 mm/min | — [cite:45] |
| 大气压力 | 880～1080 hPa | ±1.0 hPa；0.1 hPa [cite:42][cite:46] |
| 光合有效辐射 PAR | 0～2500 μmol/(m²·s) | ±5%；1 μmol；400–700 nm [cite:48] |
| 太阳辐射 | 0～1800 W/m² | ±5%；1 W/m²；300–1100 nm [cite:42] |
| CO₂ | 0～10000 ppm（农业大棚常用） | 分辨率 5 ppm（NDIR 红外原理） [cite:43] |

农业大棚的 CO₂ 传感器需注意选型：单通道红外模组（如 MH-Z19/MH-Z14 系列）偏家居新风场景，明确面向农业大棚的是双通道红外型号（如 MH-411D、MH-Z14B/Z16），后者能抑制温湿度与老化漂移。[cite:43]

### 3.3 水质类

水质类是水产养殖与灌溉水质监测的核心，特点是**功耗显著高于土壤/气象类**。这类传感器普遍 12–24 VDC 供电、RS485 Modbus 输出、IP68 可长期浸没，其中氨氮传感器功耗约 1.2 W，是太阳能供电方案的主要负载约束。[cite:50]

| 子类 | 原理 | 量程 | 精度 |
|---|---|---|---|
| 溶解氧 DO | 荧光法/荧光寿命法 | 0～20 mg/L | ±2%～±3%；0.01 mg/L [cite:49] |
| 浊度 | 散射光法 | 0～40 / 1000 / 3000 NTU 分档 | ±1%～<3% FS；0.1 NTU [cite:50] |
| pH / ORP | 电化学 / 铂金电极 | pH 0～14；ORP 0～±1999 mV | ORP 分辨率 1 mV [cite:50] |
| 氨氮 | 离子选择电极法 | 0～100 mg/L（可扩至 0～1000） | ±5% FS 或 ±1 mg；0.01～0.1 mg/L [cite:50] |

### 3.4 作物生理 / 表型类

这一类面向科研与高端种植，观测的是"作物自身状态"而非环境。国产厂商多以"植物生理生态监测系统"整机形态交付，而非单卖传感器。[cite:36]

| 子类 | 量程 | 精度 / 分辨率 |
|---|---|---|
| 茎流（液流） | −100～+100 cm/h | 0.01 cm/h；准确度 0.5 cm/h |
| 茎秆微变化（纵向/直径） | 0～5 mm（或 0～11 mm） | ±0.001 mm（国产） [cite:36] |
| 果实膨大（直径） | 15～90 mm | 0.001 mm [cite:36] |
| 叶面温度 | 0～50℃ | ±0.2℃；0.1℃ [cite:36] |
| 光合速率 Pn / 气孔导度 | — | 分辨率 0.001 μmol/(m²·s) [cite:36] |

此类传感器多为模拟电压（0～2 Vdc）或 4～20 mA 输出，**必须配数据采集器**（如 CR300/CR1000X 类），不能直接接网关的 RS485 口。柔性可穿戴茎秆膨胀传感器属科研前沿方向，尚未进入商用主流，标记为 **【未证实】**。

### 3.5 图像 / 视频类

| 设备 | 典型配置 | 联网方式 |
|---|---|---|
| 虫情测报灯 | 1200 万像素相机 + 20 W 紫外诱虫灯（365 nm）+ 光栅计数 + 远红外杀虫烘干 + GPS/北斗 | 4G / 有线 [cite:59] |
| 孢子捕捉分析仪 | 500～1200 万像素 + 光学放大 20X～千倍显微成像 + 自动换载玻片 | 4G / RJ45，支持 MQTT / FTP / TCP-IP |
| 农业物联网摄像机 | 支持接收光照、CO₂、土壤 EC、温湿度、土壤 pH 并叠加到视频 OSD，IP67，含 1 路 485 接口 | 以太网 / 4G [cite:44] |

孢子捕捉仪的上传协议已明确支持 **MQTT / FTP / TCP-IP** 三种模式，并遵循 GB/T 24689.3-2009 相关技术要求。[cite:55] 农业摄像机这类"视频 + 物联感知融合"的形态值得关注：它把 485 传感器数据聚合到视频流中，等于自带了一个轻量网关。[cite:44]

### 3.6 执行器

智慧农场不只是"感知"，反向控制同样属于物联网接入范围。

| 类型 | 规格 | 控制方式 |
|---|---|---|
| 灌溉电磁阀 | 先导式隔膜，EPDM 隔膜；脉冲阀 DC12–40V，直流阀 DC12V | RS485 Modbus 或 4–20 mA / 脉冲 |
| 开关类执行器 | 单路继电器可控制 220V、2 kW 以下负载（水泵/风机/补光灯/卷帘/CO₂ 补气） | 继电器干接点 |
| LoRaWAN 阀门控制器 | 空旷通信距离可达 15 km，支持 FUOTA | LoRaWAN，兼容第三方平台 [cite:51] |

LoRaWAN 阀门控制器值得注意：它兼容标准 LoRaWAN 网关与第三方平台，且在不便部署网关时可选用 4G 版本，这对大田场景很实用。[cite:51]

### 3.7 品类优先级建议

结合本项目"面向农户的农事播报"定位，传感器品类应按以下优先级接入：

| 优先级 | 品类 | 理由 |
|---|---|---|
| P0 | 土壤温度、土壤水分、空气温度、空气湿度 | 直接驱动播报规则（高温、低温、土壤偏旱、高湿） |
| P0 | 降雨量 | 直接驱动降雨预警规则 |
| P1 | 光照强度、风速 | 补充光照评估与大风预警 |
| P2 | 土壤 pH / EC | 辅助施肥建议，但精度争议大 |
| P3 | CO₂、水质、图像、生理表型 | 垂直场景（大棚/水产/科研），按需扩展 |

P0 品类恰好对应本项目 `backend/app/core/config.py` 中已定义的规则阈值（`BROADCAST_TEMP_HIGH`、`BROADCAST_TEMP_LOW`、`BROADCAST_SOIL_DRY`、`BROADCAST_HUMIDITY_HIGH`、`BROADCAST_RAINFALL_MM`），落地时无需改动播报逻辑。

## 四、传感器接口、供电与组网

### 4.1 输出信号与现场总线

| 接口类型 | 农业中的实际使用 | 备注 |
|---|---|---|
| **RS485 / Modbus-RTU** | 土壤多参数、气象站、水质、雨量、执行器控制 | **事实标准**；波特率 9600、8N1、默认地址 01 [cite:38][cite:45][cite:46] |
| 4–20 mA | 翻斗式雨量计、温湿度变送器、果实生长传感器 | 工业型变送器主流 [cite:46][cite:47] |
| 0–10 V（及 0–5V/1–5V/0–2V） | 温湿度变送器、果实生长传感器 | 科研级采集系统 [cite:46] |
| 脉冲 | 翻斗式雨量计：1 脉冲 = 0.2 mm 降雨 | [cite:47] |
| SDI-12 | METER TEROS 12、Sentek Drill & Drop | 国际科研土壤剖面主流，国产化低 [cite:40][cite:41] |
| RS232 | Sentek Drill & Drop（可与 RS485 固件切换） | [cite:41] |
| I2C / UART / PWM | 传感器模组级（如 CO₂ 模组） | **非**农业现场总线主流 [cite:43] |
| 干接点 / 继电器 | 水浸传感器、单路继电器控制器 | [cite:38] |

**选型结论**：对接国产农业传感器，**只需优先支持 RS485 Modbus-RTU**，即可覆盖绝大多数品类。SDI-12 出现在 METER、Sentek 这类国际科研品牌上，精度更高但价格与生态门槛也高。[cite:40][cite:41]

### 4.2 供电与组网方式

| 方式 | 典型形态 | 特点 |
|---|---|---|
| **NB-IoT** | 免布线温湿度变送器，定时上报 | 低功耗、穿透好，但下行控制能力弱 [cite:53] |
| **LoRa / LoRaWAN** | 气象站主机兼容 RS485 与 LoRa 双接口 | 距离远（开阔 10～15 km）、需自建网关 [cite:35][cite:51] |
| **4G（Cat.1 / Cat.M）** | 4G DTU、边缘采集网关 | 无需自建网络，工程最省事 |
| **太阳能 + 电池** | 墒情监测点、孢子捕捉仪 | 政府项目标准配置，需关注负载功耗 [cite:57] |
| **WiFi / 蓝牙** | RS485↔WiFi 透传模块（802.11b/g/n + BLE 5.0） | 适合大棚近距离场景 [cite:54] |
| **RS485 总线** | 现场有线组网主干 | 抗干扰好，但布线成本高 |

**一个可复用的落地范式**：政府墒情监测点建设项目明确要求"**太阳能供电 + 3.7V 锂电池 + 北斗定位 + 4G 模组 + MQTT 接入云平台 + IP65**"，并要求平台侧提供基本信息页、原始数据页、告警页、设备日志页。[cite:57] 这套要求可以直接作为本项目设备侧的最低对接标准，既符合行业惯例，也便于后续参与政府项目。

## 五、通信协议栈与行业标准

### 5.1 协议层

| 协议 | 定位 | 在农业中的实证 |
|---|---|---|
| **Modbus RTU** | 现场总线（RS485 串口），主从轮询 | 国产土壤/气象/水质/执行器的默认协议 [cite:38][cite:45][cite:46] |
| **Modbus TCP** | 以太网/网关侧透传 | 平台支持"Modbus + DTU"采集模式 [cite:22] |
| **MQTT** | 设备→云上行，发布/订阅 | 墒情监测点要求 MQTT 接入；孢子捕捉仪支持 [cite:57] |
| **CoAP** | UDP，超低功耗窄带 | NB-IoT 场景常用（端口 5683） [cite:22] |
| **LwM2M** | 设备管理（基于 CoAP） | NB-IoT 套件标准实现，含 Object3/Object5 远程升级 [cite:22] |
| **HTTP / HTTPS** | 简单上行上报 | 最简单的接入方式，适合起步阶段 [cite:22] |

**重要澄清**：JT/T 808-2019 是《道路运输车辆卫星定位系统 终端通信协议及数据格式》，属**交通运输行业标准**，不是农业标准。[cite:58] 它在智慧农业中的相关性仅在于农机（拖拉机、收割机）车载终端沿用了该协议族，属跨行业借用。本次调研未找到"农业专用 JT/T 808 扩展规范"的权威文件，此项为 **【未证实】**。

### 5.2 国内农业行业标准

| 标准号 | 名称 | 状态 | 关键内容 |
|---|---|---|---|
| **NY/T 4062-2021** | 农业物联网硬件接口要求 第1部分：总则 | 2022-06-01 实施 | 规定通信参考体系结构、接口描述与要求；感知控制域硬件接口按连接对象分 **9 类**；从物理接口、信号接口、数据接口三维度提要求 [cite:55] |
| **NY/T 4063-2021** | 农业信息系统接口要求 | 同期发布 | 规定系统参考体系结构（数据采集、分析等模块）与安全机制，解决"信息孤岛" [cite:55] |
| **NY/T 4375-2023** | 一体化土壤水分自动监测仪技术要求 | 2023-04-11 发布 | 要求出厂前完成一体化设计调试，田间"**即插即用**"，农户**扫码查数据**；明确内置数字终端的物联网属性 [cite:55][cite:56] |
| GB/T 24689.3-2009 | 植物保护机械 孢子捕捉仪（器） | 现行 | 固定式孢子捕捉仪安全与技术要求 [cite:55] |

**NY/T 4375-2023 的两个提法值得本项目直接借用**：一是"田间即插即用"，二是"**农户扫码查数据**"。这说明"扫码绑定"是国内农业物联网标准已经认可的用户交互范式，也印证了本报告 §9 推荐的自助绑定设计方向。[cite:55][cite:56]

NY/T 4062-2021 的落地效果有公开数据支撑：该标准已助力头部企业生产万余台新型设备、覆盖 10 多个省市。[cite:55] 这意味着在设备选型时优先要求厂商声明符合 NY/T 4062，能显著降低后续对接成本。

## 六、小程序接入物联网的硬约束

这一节是整个方案的地基。以下约束均来自微信官方文档原文，是**不可绕过的**。

### 6.1 网络白名单与协议限制

| 约束项 | 具体规则 |
|---|---|
| 通信对象 | 小程序**只可以跟指定的域名进行网络通信**，须在小程序后台「开发-开发设置-服务器域名」配置 [cite:1] |
| 协议 | 只支持 `https`（`wx.request`/`uploadFile`/`downloadFile`）与 `wss`（`wx.connectSocket`） [cite:1] |
| IP 限制 | 域名不能使用 IP 地址或 localhost（局域网 IP 除外，且不允许与本机 IP 通信） [cite:1] |
| **备案要求** | **域名必须经过 ICP 备案** [cite:1] |
| 父域名 | **不支持配置父域名**，使用子域名，须逐个配置 [cite:1] |
| **端口规则** | https 域名若配置了端口，就只能请求该端口（连默认 443 也需显式，否则失败）；**wss 域名无需配置端口，默认允许该域名下所有端口** [cite:1] |
| 并发上限 | `wx.request` 最大并发 **10**；`wx.connectSocket` 最大并发 **5** [cite:1] |

**端口规则的实战含义**：如果选 wss 通道，可以省掉端口配置的坑；如果选 https，端口必须与配置完全一致，多一个少一个都会失败。这是排障时最容易踩的坑。[cite:1]

### 6.2 WebSocket 与 MQTT

- 微信**官方未提供 MQTT API**，通行做法是把 MQTT 跑在 WebSocket（wss）之上，用 mqtt.js 浏览器版实现。[cite:25][cite:26]
- `wx.connectSocket` 并发上限 5 条（1.7.0 及以上；1.7.0 以下全局仅 1 条且会自动踢掉旧连接）。[cite:1][cite:2]
- 社区反馈的具体坑（**【未证实】**，需自行验证）：mqtt.js v4.2.8 在小程序报 `net.createConnection is not defined`，需回退到 4.0.1 或 4.1.0；连接串需写 `wxs://`；EMQX Cloud 专业版 MQTT over WebSocket 的 wss 端口为 8084、路径带 `/mqtt`；有社区文章称安卓真机必须用 TLS/443 且地址不带端口。[cite:25][cite:26][cite:27]

**对多设备场景的直接影响**：5 条 WebSocket 上限意味着"每台设备一条连接"的架构不可行。正确做法是**单连接多主题订阅**，或干脆由后端汇聚数据、小程序只轮询自家后端 API。[cite:1][cite:2]

### 6.3 微信原生设备能力（可选，非必需）

微信确实有官方硬件设备能力，但门槛较高：

- **硬件设备接入指引**：面向"智能硬件生产企业或开发者"，要求**经过微信认证的非个人主体**小程序；步骤为申请服务类目「工具——设备管理」→ 后台「功能-硬件设备」开通能力 → 添加设备类型 → 获得平台分配的 `model_id`。[cite:3]
- **设备消息**：属"长期订阅类型的订阅消息"，**必须先完成设备接入**才可用，用途是设备异常/故障/耗材不足等事件触达用户。[cite:4]
- **硬件设备 OpenAPI**：包括发送设备消息、获取设备票据（5 分钟有效）、创建设备组。[cite:5]
- **审核实践**：主体营业执照经营范围须含"智能硬件销售及服务"或"物联网设备销售及服务"，否则需提供生产厂商营业执照 + 采购合同。[cite:9]
- **Wi-Fi 接口现状**：`framework/device/wifi` 系列接口**已下架**，"小程序直接连指定 Wi-Fi"这条路已不可用，配网需走 AP/蓝牙协议或设备侧自建配网协议。[cite:6][cite:7]
- **蓝牙 BLE**：主机模式基础库 1.1.0 起支持，从机模式 2.10.3 起；经典蓝牙 iOS 因系统限制暂不支持。[cite:8]

**关键判断**：微信原生设备能力的价值在于"设备消息推送"（把设备告警通过微信长期订阅消息触达用户）。但本项目已有自己的播报体系（`backend/app/broadcast/`），完全可以走小程序站内消息或公众号模板消息，**不必为了接入传感器而申请设备管理类目**。这能省掉主体资质与类目审核两道门槛。[cite:3][cite:9]

### 6.4 为什么"农户在小程序里填任意平台地址"不可行

综合 §6.1 的约束，可以推导出一个决定性结论：

1. 小程序的服务器域名白名单由**开发者**在后台维护，**农户无法自行添加**。[cite:1]
2. 域名必须 ICP 备案，农户自有的第三方平台域名无法被小程序访问。[cite:1]
3. https 端口必须与配置严格一致，农户填的 port 大概率不匹配。[cite:1]

因此，**农户填写的 host / port / Topic 这类参数，只能作为"后端连接设备"的配置，不能作为"小程序连接设备"的配置**。这既是限制，也是简化方案设计的钥匙——因为一旦把连接动作收到后端，小程序前端就只剩下"表单 + 展示"两件事，复杂度大幅下降。

## 七、四种接入通道对比

| 通道 | 设备侧要求 | 小程序侧 | 农户操作 | 复杂度 | 适用性 |
|---|---|---|---|---|---|
| **A. HTTP 直报（推荐起点）** | 支持 HTTP(S) POST 上报 | 只调自家后端 API | 填 SN + Token + 粘贴报文样例 | **低** | ★★★★★ |
| **B. MQTT + 自建 Broker** | 支持 MQTT 接入 | 仍只调自家后端 API | 填 MQTT 连接参数 | 中 | ★★★★ |
| **C. 对接第三方 IoT 平台** | 使用平台 SDK 或模组 | 调自家后端，后端调平台 OpenAPI | 填 ProductKey/DeviceName/Secret 或扫码 | 高 | ★★★ |
| **D. 小程序直连 MQTT** | 支持 MQTT over WebSocket | mqtt.js + wss 白名单 | 填连接参数 | 中高 | ★（不推荐） |

### 7.1 通道 C 的平台细化对比

| 平台 | 设备认证方式 | 小程序侧友好度 | 时效性提示 |
|---|---|---|---|
| **涂鸦智能** | DP 点模型；支持 Wi-Fi/蓝牙/Zigbee/扫码配网 | **最友好**：唯一有专门"IoT 微信小程序 SDK"的厂商，提供配网插件、设备列表插件、场景插件 [cite:14][cite:15] | 活跃；免费体验版限 10 人 |
| **腾讯云 IoT Explorer** | MQTT/CoAP/HTTPS，对称与非对称认证 | **较友好**：提供"设备状态推送"，小程序监听 WebSocket OnMessage 实时获取设备上下线、属性与事件 [cite:11] | 活跃 |
| **华为云 IoTDA** | 设备密钥认证（DeviceId + DeviceSecret 生成 MQTT 三元组） | 无小程序专用 SDK，需自建后端 | 活跃；**基础版不含 MQTT 推送消息队列**，需标准版及以上 [cite:21] |
| **阿里云 IoT 平台** | 一机一密 / 一型一密 | 需自建后端调 OpenAPI | ⚠️ **已停止新购**：自 2025-02-01 起不再支持公共实例与企业版实例新购，仅维护存量 [cite:18] |
| **阿里云生活物联网平台（飞燕）** | 网关+子设备，配网成功后仍需调绑定接口 | 面向消费级设备，一站式配置 | 仍在运营，但与 IoT 平台新版公共实例互斥 [cite:19] |
| **EMQX / 自建 Broker** | 标准 MQTT | 有官方"使用微信小程序连接到部署"文档（wss 8084 + `/mqtt`）[cite:25] | 活跃，可控性最高 |
| **ThingsBoard** | MQTT access_token 或 X.509 | 无小程序 SDK，走自建后端 | 开源，含 IoT Gateway 可转 Modbus/BLE [cite:28][cite:29] |

**平台选型的两个重要提醒**：
1. **阿里云 IoT 平台已进入停止维护阶段**，自 2025-02-01 起不再支持新购，规则引擎跨区域流转将于 2026-11-30 下线。[cite:18] 新项目不应再选。
2. **物联网卡本身是微信小程序的禁发商品**（禁售"物联网终端使用的物联网卡"），且阿里云 IoTMCP 自 2024-09-30 起停止新购卡。[cite:10][cite:60] 涉及资费采购时需提前确认路径。

### 7.2 通道 D 为何不推荐

小程序直连 MQTT 看似省掉后端，实际代价很高：设备密钥会下发到客户端（安全风险）、broker 需公网域名 + TLS + ICP 备案、要接受 5 条连接上限、还有安卓端口兼容性风险。[cite:1][cite:25][cite:27] 对面向农户的产品，这条路的体验与安全都不可控。

## 八、推荐方案：三级"填参数即接入"

### 8.1 总体架构

核心原则一句话：**连接动作全部收在后端，小程序只负责"填参数"和"看数据"**。

```
[设备/网关] ──HTTP/MQTT──> [自家后端 适配层] ──> [时序库/快照缓存]
                                    ↑                      ↑
                                    │                      │
                          [小程序 绑定表单]        [小程序 环境页]
                                    │                      │
                                    └─── 自家已备案域名 ────┘
```

架构成立的依据是 §6.4 的推导：小程序只能访问自家备案域名，所以农户填的参数必然经后端中转。[cite:1]

### 8.2 L1：HTTP 直报（推荐起点）

**适用**：设备或 4G DTU 网关支持 HTTP(S) POST 上报。绝大多数 4G DTU、边缘采集网关（如有人 USR-M300 系列支持自定义 JSON 上报模板、分组主动上报）都支持。[cite:39][cite:52]

**农户操作**：小程序内填设备 SN + 平台生成的接入 Token（或扫码自动带入），粘贴一条设备上报报文样例，点选字段含义。

**数据流**：
1. 农户在小程序提交绑定 → 后端生成 `ingest_token`，返回上报地址。
2. 农户（或安装工）把上报地址与 token 配进设备/网关。
3. 设备按周期 POST JSON 到 `POST /api/v1/device/report`。
4. 后端校验 token → 按映射规则解析 → 写时序 + 更新快照。
5. 小程序 `GET /api/environment/summary|detail` 读快照，接口签名保持不变。

**复杂度评估**：后端约需新增 1 个上报入口 + 1 个适配器 + 1 张映射表；小程序新增 1 个绑定页。**不需要** MQTT Broker、**不需要**第三方平台账号、**不需要**微信硬件类目。[cite:1][cite:3]

### 8.3 L2：MQTT + 自建 Broker

**适用**：设备已支持 MQTT 接入，或农户设备数量多、希望实时性更好。

**做法**：后端跑单个 EMQX 实例，用通配订阅（`+/devices/+/telemetry`）统一收数，按 Topic 路由到驱动解析器。[cite:25][cite:28] 小程序仍只调自家后端。

**农户操作**：填 MQTT 地址（平台固定，自动带出）、客户端 ID、用户名/密码或设备密钥、上报 Topic。

**注意**：MQTT 报文常带 `clientToken`/`id` 用于上下行配对，需处理 QoS1 确认、断线重连与遗嘱消息。[cite:12][cite:28]

### 8.4 L3：对接第三方平台

**适用**：需要兼容涂鸦等生态内的大量消费级/白牌设备。

**做法**：后端调平台 OpenAPI 拉数据（轮询式），订阅平台推送（实时式）。腾讯云的路径最顺——后端订阅或轮询，小程序侧可用其"设备状态推送"WebSocket 监听。[cite:11][cite:12] 涂鸦路径最成熟——但其价值主要在"配网+控制"，本项目只需"读数据上报"，收益有限，建议后置。[cite:14][cite:15]

**平台侧数据获取的两种方式**：

| 方式 | 机制 | 优缺点 |
|---|---|---|
| 订阅式 | AMQP / MQTT 消息队列 / Webhook 推送 | 实时、推荐；注意华为云需标准版及以上 [cite:21] |
| 轮询式 | 定时调平台"查询设备最新数据/历史数据" API | 实现简单；有延迟与配额成本 |

### 8.5 老式 485 传感器怎么办

**必须经网关**，不存在"485 直接接小程序"的路径。[cite:29][cite:39]

三条可选路径：
1. **4G DTU 透传**：485 → DTU → MQTT/HTTP 上云。农户只需绑定 DTU 的 SN，子传感器由网关侧映射。这是农业最常见形态。
2. **边缘采集网关**：如 USR-M300 支持 Modbus 采集 + 自定义 JSON 上报模板 + 分组主动上报。[cite:39] 亿佰特 E870 系列明确支持阿里云 IoT JSON 协议、变化上报/周期上报、边缘计算。[cite:52]
3. **软件网关**：ThingsBoard IoT Gateway 的 Modbus Connector（支持 TCP/UDP/Serial、byteOrder/wordOrder、poll period 默认 5000 ms）或 Telegraf `inputs.modbus`（支持 `data_type`、`byte_order`、`scale` 等完整字段）。[cite:29][cite:30]

**对农户的产品化建议**：把"网关 + 多路 485 传感"打包成一个 SKU 交付，农户只绑网关一个设备，UI 上展示为多个测点。这能避免让农户理解"子设备"概念。

## 九、自助绑定表单设计

这是"太复杂就不要了"这条需求的直接回应。核心策略：**不给农户填协议细节，改为"粘贴样例 + 点选含义"**。

### 9.1 极简模式（推荐给所有农户）

| 步骤 | 农户看到什么 | 农户要做什么 |
|---|---|---|
| 1 | 设备二维码 | **扫码**（自动带入 SN 与绑定码），或手动填 SN |
| 2 | 平台自动带出的上报地址 | **复制**到设备/网关配置 |
| 3 | "粘贴一条设备上报的数据" 输入框 | **粘贴**一条 JSON 样例 |
| 4 | 系统解析出的字段列表 | **点选**每个字段的物理量（下拉：土壤湿度/气温/…） |
| 5 | 预览换算后的读数 | **确认** |

**关键设计**：第 3–4 步是"傻瓜化"的核心。后端用样例报文解析出字段名（如 `t1`、`humi`、`soil`），前端把字段名与真实值并列展示，农户只需下拉选择"这是什么"。所有字节序、缩放系数、单位换算由**预置模板**承担，农户不可见。

### 9.2 预置模板机制

针对主流厂商型号预置映射模板，农户选型号即可零配置：

| 模板字段 | 示例 |
|---|---|
| 厂商 / 型号 | 有人 USR-SSO10 / 托普墒情站 / 通用四合一 |
| 字段映射 | `t → 土壤温度`、`h → 土壤水分`、`ec → EC`、`ph → pH` |
| 缩放 / 偏移 | `value = scale × raw + offset`（如温度 ÷10） |
| 字节序 | Modbus 场景使用：ABCD / CDAB / BADC / DCBA [cite:31] |
| 单位 / 精度 | ℃、%、μS/cm；保留 1 位小数 |

Modbus 场景的换算规则是集成第二大错误源。典型错误是读到 0、负数或 1.73e-38 之类的值，多半是字节序错，**先试 CDAB**。[cite:31] 参考换算：`物理值 = raw × scale + offset`，常见 scale 为 0.1（÷10）、0.01、0.001。[cite:31][cite:32]

### 9.3 完整字段清单（后端内部配置，不全部暴露给农户）

**A. 设备标识**

| 字段 | 说明 |
|---|---|
| 平台类型 | 阿里云 / 腾讯云 / OneNET / 涂鸦 / EMQX 自定义 / Modbus 网关 |
| 设备标识类型 | SN / IMEI / DevEUI / ProductKey+DeviceName / ClientID |
| ProductKey / ProductID / pid | 云平台产品标识 [cite:16][cite:12][cite:23] |
| DeviceName / SN / ClientID | 设备名或唯一序列号 |
| 网关标识 | 上下级从属关系 |
| Modbus Slave ID | 从站地址（0～255，0 = 广播） [cite:29][cite:30] |

**B. 接入地址与鉴权**

| 字段 | 说明 |
|---|---|
| 域名 + 端口 | MQTT 常用 1883/8883；Modbus TCP 502；HTTP 80/443 |
| 协议类型 | MQTT / MQTT-TLS / HTTP(S) / Modbus TCP / Modbus RTU / CoAP |
| 鉴权方式 | 一机一密 DeviceSecret / Token / 用户名密码 / X.509 证书 |
| 签名算法 | hmacmd5 / hmacsha1 / hmacsha256 [cite:17] |
| QoS | 0 / 1 |

**C. Topic / 路径**

| 字段 | 示例 |
|---|---|
| 上行 Topic | `/sys/{pk}/{dn}/thing/event/property/post` [cite:16]；`$thing/up/property/{PID}/{DN}` [cite:12]；`$sys/{pid}/{dn}/dp/post/json` [cite:23] |
| 下行/订阅 Topic | 属性设置下发、RPC |
| HTTP 路径 + 方法 | POST /api/v1/device/report |

**D. 采集方式与周期**

| 字段 | 说明 |
|---|---|
| 采集模式 | 订阅（MQTT push）/ 轮询（HTTP pull、Modbus poll） |
| 采集周期 | 如 300 s；ThingsBoard Modbus 默认 5000 ms [cite:29] |
| 上报策略 | 定时 / 变化上报 / 变化或定时 / 收到即报 [cite:29] |
| 超时与重试 | 连接超时、重试次数、失败等待 |
| 死区 deadband | 变化小于阈值不上报 [cite:29] |

**E. 字段映射（核心）**

| 字段 | 说明 |
|---|---|
| 原始字段名 / 寄存器地址 | `temperature` / `holding:40001` / DP ID `6` [cite:23][cite:31] |
| 数据类型 | INT16 / UINT16 / INT32 / UINT32 / FLOAT32 / FLOAT64 / BOOL / STRING |
| 寄存器功能码 | 保持寄存器 / 输入寄存器 / 线圈 / 离散输入 |
| 寄存器数量 | FLOAT32 = 2，FLOAT64 = 4 |
| 字节序 / 字序 | ABCD / CDAB / BADC / DCBA [cite:31] |
| 缩放系数 scale | 如 0.1、0.01 [cite:31] |
| 偏移量 offset | `输出 = scale × raw + offset` [cite:32] |
| 精度 precision | 有效小数位 [cite:32] |
| 物理量名称 + 单位 | ℃ / %RH / lux / kPa |
| 量程 / 合法区间 | 用于异常值过滤，如温度 0～60℃ |

**F. 离线与告警**

| 字段 | 说明 |
|---|---|
| 离线判定阈值 | 超过 N 个周期无数据判离线（常见做法 ≥ 3 × 采集周期） |
| MQTT KeepAlive | 心跳间隔 |
| 异常值过滤 | 越界丢弃 / 变化率阈值 |

### 10.1 现状盘点

本项目已有较完整的设备与环境基础，改造量可控：

| 现有资产 | 位置 | 说明 |

| 传感器工具 | `backend/app/tools/sensors.py` | 当前返回**静态兜底值**（气温 26.5、土壤含水率 23 等），注释明确写"无设备/无平台接入时返回静态兜底" |

| 规则阈值 | `backend/app/core/config.py` | `BROADCAST_TEMP_HIGH/LOW`、`BROADCAST_SOIL_DRY`、`BROADCAST_HUMIDITY_HIGH`、`BROADCAST_RAINFALL_MM` 等 |

**三个关键观察**：

1. `device` 表已有 `user_id` 与 `bind_time` 字段，且 `user_id` 注释为"未绑定为null"——**说明绑定流程在设计时已预留**，自助绑定无需改动表结构主干。
2. `sensors.py` 目前返回硬编码常量，`source` 字段为 `"sensor_snapshot"`。**真实接入的第一步就是把这个函数改为"查快照，查不到再兜底"**。
3. 小程序端**完全没有设备/绑定相关页面**，这是本次改造的前端主体工作量。

### 10.2 建议新增的表结构

在保留 `device` 表主干的前提下，新增三张表：

| 表名 | 用途 | 关键字段 |
|---|---|---|
| `device_config` | 存接入参数与鉴权 | `device_id`、`platform_type`、`protocol`、`host`、`port`、`client_id`、`secret_ref`、`up_topic`、`poll_period_s`、`offline_threshold_s` |
| `metric_mapping` | 字段映射规则 | `device_id`、`raw_key`、`metric_key`、`data_type`、`byte_order`、`scale`、`offset`、`unit`、`precision`、`min`、`max` |
| `telemetry` | 时序数据 | `device_id`、`metric_key`、`value`、`ts` |

**关键设计点**：`device_config.secret_ref` **存引用而非明文**，指向密钥托管（KMS/Vault 或加密列），避免密钥进入业务表。快照则复用现有 Redis 能力（`backend/app/db/redis_client.py`）存"最新值"，供 `environment_service` 直接读取。

### 10.3 适配层设计（驱动注册表模式）

参考 ThingsBoard 的协议连接器与 Telegraf 的输入插件设计思路，采用"驱动注册表 + 统一数据模型"。**以下为设计方案，非官方规范。**

```
DeviceAdapter (抽象接口)
  ├─ connect()
  ├─ subscribe() / poll()
  ├─ parse(raw) -> UnifiedSample[]
  └─ decode(commands)

注册表：{ "http_ingest": HttpIngestAdapter,
          "mqtt": MqttAdapter,
          "modbus_tcp": ModbusTcpAdapter,
          "aliyun": AliyunAdapter,
          "tencent": TencentAdapter,
          "tuya": TuyaAdapter }
```

新增厂商只需新增一个驱动并注册，不动主干代码。

### 10.4 数据链路的四个环节

| 环节 | 做法 |
|---|---|
| **接收** | L1 用 FastAPI 新增 `POST /api/v1/device/report`，带 `ingest_token` 鉴权；L2 用 MQTT 订阅服务通配订阅后按 Topic 路由 |
| **解析** | 按 `metric_mapping` 做字段名映射 → 类型转换 → 字节序处理 → `scale × raw + offset` → 单位归一 |
| **存储** | 写 `telemetry` 时序表；同时更新 Redis 最新值快照 |
| **对外** | `environment_service.summary()` / `detail()` 改为优先读快照，接口签名与返回结构**保持不变**，小程序侧 `environment.ts` 无需改动 |

**这个"接口签名不变"的设计很重要**：它让传感器接入成为一个纯后端增量改造，前端环境页可以立即受益，无需等待绑定页开发完成。

### 10.5 离线判定与异常值过滤

- **离线判定**：`now - last_seen > offline_threshold_s` 则置 `device.status = 0`。阈值建议取 3 倍采集周期。现有 `status` 字段已支持 0/1/2 三态，无需扩展。
- **异常值过滤**：先用 `metric_mapping.min/max` 做量程校验（越界丢弃或置 NaN），再做变化率/死区判断。参考边缘网关的通用做法：本地清洗后再上报，报包含设备 ID、时间戳、数据值、质量标志。[cite:52]
- **多源兜底**：现有 `sensors.py` 的静态兜底逻辑应保留为最后一级兜底（真实快照 → 天气 API → 静态值），保证"零设备农户"仍能看到合理的页面内容。

## 十一、安全、合规与资质

### 11.1 密钥管理的核心矛盾

"让农户自己填参数"与"密钥安全"存在天然冲突：农户手填/截图密钥易泄露，弱口令复用会导致假冒设备接入甚至越权控制其他设备。**缓解措施按优先级排列**：

| 措施 | 做法 | 优先级 |
|---|---|---|
| **密钥托管** | 服务端安全存储（KMS/Vault 或加密列），前端永不回显明文，只做"掩码 + 重新生成" | P0 |
| **扫码绑定** | 设备二维码内含一次性绑定 token，扫码后由平台代持设备密钥，用户不接触密钥 | P0 |
| **一机一密** | 优先一机一密，避免产品级密钥外泄导致全系列沦陷 [cite:17] | P0 |
| **强制 TLS** | 8883/443，禁用明文 1883 传输敏感数据 [cite:28] | P1 |
| **最小权限** | MQTT ACL 限制每设备只能 publish/subscribe 自己的 Topic（`/sys/{pk}/{dn}/#`） | P1 |
| **Token 轮换** | 短期 token + refresh；签名加 `timestamp` 防重放 [cite:17] | P1 |
| **服务端签名校验** | HTTP 接入校验 HMAC，校验 timestamp 时间窗与 nonce | P1 |

**与本项目的结合点**：本项目已有微信登录体系（`backend/app/services/auth_service.py`、`miniprogram/api/auth.ts`），农户身份是可靠的。因此"扫码绑定"完全可行——微信扫码天然带身份，是替代"手填密钥"的最佳载体，也符合 NY/T 4375-2023 中"农户扫码查数据"的标准范式。[cite:55][cite:56]

### 11.2 网络侧合规清单

| 要求 | 具体规则 | 依据 |
|---|---|---|
| ICP 备案 | 小程序通信域名**必须** ICP 备案 | [cite:1] |
| TLS 版本 | **TLS 必须 ≥ 1.2**；同时需向下兼容 TLS 1.2 以下的旧安卓机型 | [cite:1] |
| 证书要求 | 证书有效、根证书系统内置、域名与证书一致、信任链完整；**iOS 不支持自签名证书** | [cite:1] |
| 域名配置 | 不支持父域名，子域名须逐个配置 | [cite:1] |
| 端口规则 | https 配了端口就只能该端口；**wss 无需配端口** | [cite:1] |
| 联调注意 | 开发者工具可临时"不校验域名/TLS/证书"，但**上线前必须关闭该选项做真机验证** | [cite:1] |

### 11.3 主体与类目资质

| 场景 | 是否必需 | 说明 |
|---|---|---|
| 接入传感器读数据（本方案 L1/L2） | **不需要**微信硬件类目 | 走自家后端，不触达微信设备能力 [cite:1] |
| 使用微信原生设备消息推送 | **需要** | 需微信认证非个人主体 + 「工具——设备管理」类目 + 营业执照经营范围含智能硬件/物联网设备销售及服务 [cite:3][cite:9] |
| 物联网卡采购 | 受限 | 小程序禁售物联网卡；阿里云 IoTMCP 自 2024-09-30 停止新购卡 [cite:10][cite:60] |

**结论**：本报告推荐的 L1/L2 方案**完全规避了微信硬件类目与主体资质门槛**，这是它相对"通道 C/D"的显著优势。若未来需要把设备告警通过微信长期订阅消息触达农户，再单独评估类目申请。

## 十二、复杂度取舍建议

用户的原始约束是"太复杂的我就不要了"。以下按"要不要做"给出明确取舍。

### 12.1 建议做的

| 项目 | 理由 |
|---|---|
| L1 HTTP 直报 + 后端适配层 | 复杂度最低、无需第三方平台、无需微信类目 |
| 扫码绑定（替代手填密钥） | 微信扫码天然带身份，安全且符合 NY/T 4375 范式 |
| 预置厂商型号模板 | 让绝大多数农户零配置，是"傻瓜化"的关键 |
| 粘贴报文样例 + 点选字段 | 把协议细节翻译成农户能理解的动作 |
| 网关打包交付（多 485 传感 → 一个绑定） | 避免让农户理解"子设备"概念 |
| Redis 最新值快照 | 复用现有 Redis，让环境接口零改动即可用真实数据 |

### 12.2 建议暂缓或放弃的

| 项目 | 原因 |
|---|---|
| **让农户手填 MQTT host/port/Topic** | 小程序域名白名单使前端无法直连，填了也只能后端用，体验收益低 |
| **小程序 mqtt.js 直连 Broker** | 5 条连接上限 + 密钥下发客户端 + 安卓端口兼容风险 [cite:1][cite:25] |
| **对接阿里云 IoT 平台** | 已停止新购、文档停止维护 [cite:18] |
| **Modbus 字节序让农户选** | 集成第二大错误源，必须由预置模板承担 [cite:31] |
| **申请微信设备管理类目** | 本项目已有播报体系，无需微信原生设备消息即可触达农户 |
| **全品类传感器一次接完** | 按 §3.7 的 P0→P3 优先级分批，P0 四要素 + 降雨即可覆盖核心播报规则 |

### 12.3 复杂度分级速查

| 方案 | 后端工作量 | 前端工作量 | 农户操作步骤 | 建议 |
|---|---|---|---|---|
| L1 HTTP 直报 | 低（1 上报口 + 1 适配器 + 1 映射表） | 低（1 绑定页） | 3 步（扫码/填 SN → 粘样例 → 点字段） | ★ 立即做 |
| L2 MQTT 自建 | 中（+ Broker + 订阅服务） | 低（复用绑定页） | 3～4 步 | 设备量大时做 |
| L3 第三方平台 | 高（+ 平台账号 + OpenAPI + 协议适配） | 低 | 4～5 步（含平台侧注册） | 后置 |
| D 小程序直连 | 中 | 高（连接管理 + 重连 + 多设备） | 5+ 步 | 不建议 |

## 十三、落地路线图

### 阶段一：打通数据链路（核心，建议优先）

1. **数据库迁移**：新增 `device_config`、`metric_mapping`、`telemetry` 三张表（现有 `device` 表主干不改）。

4. 引入 Modbus TCP 轮询驱动，打通 485 网关路径。

### 阶段四：扩展与优化

1. 按需引入 MQTT 订阅（L2），提升实时性。

3. 评估是否需要微信原生设备消息推送（涉及类目申请）。

7. **汉枫（Hi-Flying）官方透传配置文档**：未取得，其常规做法为 RS485↔MQTT/HTTP 透传网关。
8. **JT/T 808 农业专用扩展标准**：未找到权威文件，其本体属交通运输行业标准。

### 14.3 关于"太复杂就不要了"的最终回应

用户的核心诉求是**低门槛**。本报告的取舍原则可以概括为一句话：

> **凡是需要农户理解通信协议的地方，都必须由系统承担；农户只需要回答"这是什么传感器"和"这是哪个数据"。**

具体地，农户需要做的只有三件事：**扫码（或填 SN）→ 粘贴一条报文明 → 点选字段含义**。其余的鉴权、协议、端口、字节序、缩放系数、Topic、离线上报策略，全部由后端与预置模板承担。这样既满足了小程序端的合规约束（只访问自家备案域名），也把复杂度控制在了后端一次性投入的范围内。[cite:1][cite:31][cite:55]

# 话农点金 · 前后端接口对接技术设计方案

> 文档版本：v1.1　撰写日期：2026-08-30　适用代码：`d:\CSECL\wx-mini`　后端统一技术栈：Python / FastAPI

## 1. 背景与目标

「话农点金」小程序的 7 个页面在前端侧已全部完成，页面交互、路由守卫、定位权限状态机、AI 对话滚动与本地历史存储均已跑通。当前所有业务数据来自两类假实现：本地缓存（`wx.setStorageSync`）和硬编码 mock（`mock_token_`、`mockAIResponse`、`mockReverseGeocode`），尚未连接任何真实后端。本文档在 v1.0 的基础上，补充完整的代码目录结构、逐文件归属、精确的分层文件数量，以及支撑「可维护、可扩展」的具体架构手段。

要落地的目标是打通 `docs/前后端对接文档.md` 定义的 15 个接口，把前端从本地假数据切换到后端真实数据（Python 服务），同时保留本地缓存作为离线兜底。验收标准：登录用真实 `code` 换取 token；档案、地点、播报、环境、AI 对话、历史数据均能从服务端读写；头像上传走 `wx.uploadFile` 拿到永久 URL；注销账号能真正删除服务端数据；新增一个作物垂类模型或一个外部集成时，不改动核心代码。

## 2. 后端技术选型（Python）

后端整体采用 Python 3.11+，框架与库的取舍围绕「类型可校验、接口自文档化、依赖可替换」展开。

| 能力 | 选型 | 理由 |
|---|---|---|
| Web 框架 | FastAPI | 基于 Pydantic 的请求/响应校验，自动生成 OpenAPI 文档，异步原生支持 |
| 数据校验 | Pydantic v2 | 与 FastAPI 天然集成，schema 即契约 |
| ORM | SQLAlchemy 2.0 | 成熟的表结构与关系建模，配合 Alembic 做数据库版本管理 |
| 数据库 | MySQL 8.0 | 沿用对接文档已给出的建表语法 |
| 会话 / Token | Redis（`redis` 库） | 支持注销即失效、主动踢人 |
| 外部 HTTP | httpx | 异步调用微信 `jscode2session`、地图逆地理、天气接口 |
| 对象存储 | 抽象接口 + 可插拔实现 | 本地磁盘 / MinIO / 阿里云 OSS / 腾讯云 COS 均可替换 |
| 配置 | pydantic-settings + `.env` | 密钥、域名、鉴权信息环境变量隔离 |
| 依赖管理 | `requirements.txt` + `pyproject.toml` | 直接可复现，也可迁 Poetry |

## 5. 可维护与可扩展性设计

结构本身并不等于可维护，以下机制是支撑「改得动、扩得开」的关键设计。

### 5.1 前端：页面与接口分离

页面不再直接拼 `wx.request`，而是通过 `api/*.ts` 调用，每个业务域一个文件。页面只关心「拿数据、渲染数据」，接口地址、header、参数、响应解析全部收敛在 `api/` 层；`utils/request.ts` 负责 token 注入与 401 拦截。这样的依赖方向是单向的——页面依赖 `api`，`api` 依赖 `request`，`request` 依赖 `config`，任何一层都可独立测试与替换。新增一个接口 = 在对应 `api/*.ts` 加一个函数 + 在 `types/api.d.ts` 加类型，页面不变。

### 5.2 后端：分层约束与依赖方向

后端严格按 `api → services → models/integrations` 单向依赖。路由层只做协议转换（收 Pydantic、调 service、返回统一响应），业务判断全部落在 `services`，数据访问落在 `models`，外部调用落在 `integrations`。好处是：换一个地图厂商、换一个对象存储，只动 `integrations` 下对应文件并注入新的实现，service 与路由零改动。

### 5.3 后端：AI 垂类大模型路由（策略 + 注册表）

这是本项目扩展性最敏感的点。核心机制是「装饰器注册」：`ai_router/base.py` 定义抽象基类 `CropModel`，`ai_router/registry.py` 维护 `{作物名: 模型}` 的注册表并提供 `register("水稻")` 装饰器；`ai_router/crops/*.py` 每个作物一个文件，用装饰器自注册。

```python
# ai_router/registry.py（示意）
_registry: dict[str, CropModel] = {}

def register(name: str):
    def deco(cls):
        _registry[name] = cls()
        return cls
    return deco

def resolve(crop_name: str) -> CropModel:
    return _registry.get(crop_name) or _registry.get("通用农业")
```

```python
# ai_router/crops/rice.py（示意）
from ..base import CropModel
from ..registry import register

@register("水稻")
class RiceModel(CropModel):
    async def chat(self, message: str, context: dict) -> str:
        # 对接水稻垂类大模型
        ...
```

新增一个作物专家模型 = 在 `crops/` 下加一个文件、写一个 `@register("作物名")` 的类，核心路由、对话流程、历史记录逻辑都不动。作物名无法精确命中时，`resolve` 自动回落到 `general.py` 的通用农业模型，满足对接文档「模糊匹配或归入通用农业模型」的要求。

### 5.4 档案内容注入 AI（Prompt 组织）

档案怎么交给模型，此前只留了 `context` 参数，这里把它补全。整体策略是「结构化拼接 + 裁剪」，而不是把整份档案无差别塞进请求——既省 token，也避免无关字段（手机号、完整姓名）泄露给第三方模型。

**注入什么**：`ai_service.py` 在调用模型前组装一个 `ProfileContext`，只打包与本次问答相关的字段：

```python
# app/services/ai_service.py 组装的 context 结构
{
  "farmer":  { "name": "李**", "location": "江西省抚州市XX县" },
  "crop":    { "name": "水稻", "plantMu": 12.5, "growthStage": "分蘖期" },
  "profile_tags": ["病虫害防治", "水肥管理"],
  "recent_context": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ],
  "environment": { "temperature": 28, "humidity": 65, "soilStatus": "偏干" }
}
```

**谁负责组装**：`ai_service.py` 的 `build_context()` 查三处——`farmer_profile`（档案主体 + 当前 `cropTag` 对应作物）、`user_profile_tag`（历史画像）、`ai_message`（最近若干轮对话）；`environment` 为可选字段，只在环境页语境下附带。

```python
# app/services/ai_service.py（示意）
async def build_context(user_id: int, crop_tag: str, history: list) -> dict:
    profile = await get_farmer_profile(user_id)
    crop = next((c for c in profile.crops if c.crop_name == crop_tag), None)
    tags = await get_profile_tags(user_id)
    return {
        "farmer": {"name": mask(profile.real_name), "location": profile.location_name},
        "crop": crop or {"name": crop_tag or "通用农业"},
        "profile_tags": tags,
        "recent_context": history[-6:],
    }
```

**模型怎么消费**：垂类模型把 `context` 序列化拼进系统提示词，用户问题作为正文，历史对话作为多轮上下文：

```python
# ai_router/crops/rice.py（示意）
async def chat(self, message: str, context: dict) -> str:
    system = (
        "你是水稻种植专家，请结合农户档案与近期对话，用通俗中文回答。\n"
        f"农户档案：{json.dumps(context, ensure_ascii=False)}"
    )
    return await call_llm(
        system=system,
        user=message,
        history=context["recent_context"],
    )
```

**裁剪与隐私约束**：只带当前询问作物、最近 6 轮对话、画像标签，不返回整表；`real_name` 脱敏为姓氏、手机号一律不进 context。字段规模涨到需要检索历史知识时，再把这层升级成向量检索（RAG），当前纯 prompt 注入足够。

### 5.5 记忆功能设计

记忆分三层，从「这一轮记得住」到「以后再问也记得住」：

| 层级 | 存什么 | 生命周期 | 存放位置 |
|---|---|---|---|
| 短期 | 当前会话最近 6 轮对话 | 会话内 | `ai_message` 表（已存在） |
| 中期 | 每个会话的摘要 | 跨会话可读 | 新增 `memory_summary` 表 |
| 长期 | 画像标签 + 抽取的关键事实 | 永久 | `user_profile_tag` + `memory_summary` |

由 `app/services/memory_service.py` 统一管两条主链路：

```python
# app/services/memory_service.py（示意）
def recall(user_id: int, query: str) -> dict:
    """回答前组装记忆上下文"""
    return {
        "profile_tags": [...],              # 长期画像
        "session_summary": "...",           # 中期摘要（上一次会话）
        "relevant_facts": ["上次说地块偏干"],  # 长期关键事实
    }

async def remember(user_id: int, session_id: str, messages: list):
    """回答后增量写入：更新画像、生成/更新摘要、抽取关键事实"""
    ...
```

`ai_service.py` 在调用模型前把记忆合并进上下文，与 5.4 节的档案上下文合流：

```python
context = {**profile, **memory.recall(user_id, message)}
reply = model.chat(message, context)
```

关键事实抽取用一次轻量 LLM 调用（或关键词规则）从对话里抽出「地块偏干、种植了水稻」这类可复用事实，存进 `memory_summary`；后续提问时按相关性拉取，实现跨会话记忆。全量历史做向量化检索属于可选升级（pgvector / Milvus），初期用 SQL 按会话摘要 + 事实表检索即可，量不大不需要向量库。

### 5.6 框架选型结论（LangChain / LangGraph 还是纯自研）

结论：**AI 部分继续纯自研，不统一切到 LangChain 或 LangGraph**；仅在将来出现「多步 Agent」需求时，对那一个 agent 模块局部引入 LangGraph。

| 需求 | 纯自研方案 | LangChain | LangGraph |
|---|---|---|---|
| 记忆读写 | `memory_service` + SQL | 有 Memory 抽象但版本动荡 | 不直接管记忆 |
| 多步 Agent / 工具调用 | 手写状态机 | 可用 | 强项 |
| 本项目当前需求 | 刚好够用 | 过度抽象 | 用不上 |

判断依据有三：记忆的本质是「存 + 取」，`memory_service` 用 SQLAlchemy 十几行就能实现，套 LangChain 反而把「对话、摘要、检索」绑进一套不稳定的抽象；LangGraph 解决的是多步、带工具、有分支的复杂 agent，本项目问答是单步直连，用不上；继续纯自研还守住了前文「换模型厂商只改一个文件」的可插拔原则。

引入 LangGraph 的触发条件：出现「查询天气 → 判断是否预警 → 调用播报接口 → 追问用户」这类 3 步以上、含工具调用的编排时，再对 `ai_service` 内部改造，不改变对外接口与其它层。

### 5.7 后端：外部集成抽象接口

`integrations/` 里每个外部系统都先定义抽象基类，再用依赖注入替换实现，避免业务代码与具体 SDK 耦合：

```python
# integrations/storage.py（示意）
class Storage(ABC):
    @abstractmethod
    async def upload(self, key: str, data: bytes) -> str:
        """上传并返回可公网访问的 HTTPS URL"""
    @abstractmethod
    def public_url(self, key: str) -> str: ...
```

本地磁盘实现先满足联调，上线时新增 `oss_storage.py` / `cos_storage.py` 实现同一个接口，通过 `config` 选择注入，`user_service` 不感知底层差异。

## 9. 本地数据迁移与离线兜底

本地缓存不废弃，降级为「秒开 + 离线兜底」：进页面先读本地缓存立即渲染，再发请求用服务端数据覆盖；网络类错误（`errMsg` 含 `timeout` / `network` / `fail`）时保留本地数据并轻提示离线，不打断用户；仅对 `401` 强制重登，其余错误不重登。历史、环境、档案数据统一遵循「本地优先渲染 + 服务端覆盖」，服务端为权威来源，关键字段以 `updatedAt` 较新者为准。

## 10. 错误处理与鉴权失效

| 类型 | 判断依据 | 处理 |
|---|---|---|
| 业务失败 | `code` 为 400/500 | toast 展示 `message`，不重登 |
| 鉴权失效 | `code === 401` | 清 token，`reLaunch` 登录页 |
| 网络异常 | `errMsg` 含 `timeout/network/fail` | 保留本地数据，提示离线 |

前端 `handle401()` 加防抖标记，多个并发过期请求只触发一次登录页跳转。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 临时路径直接入库 | 头像 7 天过期变灰 | 强制 `wx.uploadFile` 拿永久 URL，评审时检查 `chooseAvatar` 返回值不落库 |
| 域名未配置 HTTPS | 请求被微信拦截 | 后台配 `request` / `uploadFile` 合法域名，且必须 HTTPS |
| `getLocation` 权限 | 自动定位不可用 | 后台声明 `scope.userLocation`，前端保留手动输入兜底 |
| 多请求并发触发 401 | 登录页重复跳转 | `handle401()` 加防抖标记 |
| 作物名无法匹配垂类模型 | 通用作物无法路由 | `ai_router.resolve()` 模糊匹配 + 回落到通用农业模型 |
| 本地缓存与后端不一致 | 历史/档案显示错误 | 服务端为权威，接口成功即覆盖本地，以 `updatedAt` 较新者为准 |
| 对象存储厂商锁定 | 迁移成本高 | `integrations/storage.py` 抽象接口，本地/MinIO/OSS/COS 可插拔 |

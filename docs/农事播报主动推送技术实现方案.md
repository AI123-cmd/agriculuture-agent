# 农事播报主动推送技术实现方案

> 在「话农点金」现有后端架构上，把"硬编码模板播报"改造为「传感器 + 气象 + 物候期 + 画像 → 规则优先 + AI 兜底 → 主动提醒」，本文档给出播报内容的调研结论、目录结构、文件新增/修改清单与核心模块设计。

---

## 一、调研结论：农业播报「播什么、依据什么生成」

依据中国气象局《涉农网站信息分类》(QX/T 203—2013) 及多地气象为农服务实践，农业播报/农事服务的核心内容分四类 [1][2][3]：

| 播报类别 | 播什么 | 生成依据 |
|---|---|---|
| 气象风险预警 | 高温热害、低温冻害、干旱、渍涝、连阴雨、霜冻、干热风、大风 | 天气实况 + 预报 + 阈值（分灾种、分作物、分区域） |
| 病虫害气象风险 | "高湿/适温是否利于某病害发生流行" | 温湿组合阈值（如玉米大斑病 20~25℃ + 湿度≥90%） |
| 土壤墒情 | 是否需要灌溉/排水 | 土壤含水率/相对湿度阈值 |
| 关键农事提醒 | 追肥、打药、灌溉、排水、收获 | 作物生育期/物候期 + 农事历 |

### 1.1 关键阈值依据（可直接落地到规则引擎）

| 风险 | 触发指标 | 来源 |
|---|---|---|
| 水稻高温热害 | 日平均气温≥30℃ 或日最高气温≥35℃，持续 3~8 天 | QX/T 820-2026 [5] |
| 冬小麦干热风 | 日最高气温≥32℃、14 时湿度≤30%、14 时风速≥3 m/s | QX/T 820-2026 [5] |
| 玉米大斑病 | 日均温 20~25℃ 且 湿度≥90% | QX/T 718-2024 [6] |
| 马铃薯晚疫病 | 日均温 10~30℃（最适 16~20℃）且 湿度≥80% | QX/T 718-2024 [6] |
| 越冬期冻害 | 低温降幅>8℃，或最低温过低 | 泰州为农服务方案 [4] |
| 土壤受旱 | 土壤相对湿度<40%（含水率阈值可配置） | 泰州为农服务方案 [4] |

### 1.2 物候期农事提醒（播报的"日历"维度）

农事操作严格跟着生育期走，例如水稻"返青后追分蘖肥（占总氮肥 30%）、倒二叶露尖施穗肥"、葡萄"落叶后 30 天至萌芽前 15 天冬季修剪" [7][8]。因此播报必须结合作物当前生育期给出**阶段对应的农事提醒**，而不是同一套模板。

**结论**：一次合格的"农事播报"= **环境快照（传感器+天气）× 风险阈值规则 ∪ 物候期农事历 → 结构化提醒卡片（结论/要点/来源/下一步）**。规则能命中就直出（稳定、可验证），规则覆盖不了的就交给 AI 生成简报兜底。

## 二、设计目标与原则

1. **规则优先、AI 兜底**：阈值明确的用规则（可测、稳定），开放的用 AI 简报。
2. **可插拔规则**：新增一种环境风险 = 新增一个规则文件，注册即生效（沿用 `ai_router` 的装饰器注册模式）。
3. **向后兼容**：播报响应在现有 `{date, items:[{id,time,title,content,done,type}]}` 基础上**只加字段**，前端零改动可跑。
4. **数据源统一**：环境数据统一收敛到 `EnvSnapshot`，屏蔽"设备/天气/mock"差异。

## 三、总体架构（播报生成流水线）

```
传感器(Device) ─┐
天气(weather)  ─┼─► snapshot.py 组装 EnvSnapshot ─► rules/ 规则引擎 ─命中─► 提醒列表
农户档案/画像 ──┘                                     │
                                          ┌──────────┴──────────┐
                                     未命中/不足             命中
                                          │                    │
                                  农事历(calendar)         组装卡片
                                  按物候期补充提醒              │
                                          │                    │
                                          ▼                    ▼
                               skill.py AI 简报 ──► generator.py 统一输出 BroadcastCard
```

生成器 `generator.py` 是唯一对外出口，`broadcast_service.get_today` 只负责调它并落库。

## 六、核心模块详细设计

### 6.1 环境快照（`snapshot.py`）

```python
@dataclass
class EnvSnapshot:
    temp: float | None            # 空气温度 ℃
    humidity: float | None        # 空气湿度 %
    soil_moisture: float | None   # 土壤含水率 %
    soil_temp: float | None
    light: float | None           # 光照 lux
    rainfall: float | None        # 降雨 mm（实况/预报）
    wind_speed: float | None
    crop_name: str
    growth_stage: str
    location: str
    forecast: dict                # 未来天气（高温/降温/降雨趋势）
    source: str                   # device / weather / mock

async def build_snapshot(db, user_id, location) -> EnvSnapshot
```

**数据优先级**：真实 `Device` 读数 → `weather.query_weather` 兜底 → mock 常量兜底。这样规则引擎的输入永远有值，只影响"来源"标签和置信度。

### 6.2 规则引擎（`rules/`，可插拔）

沿用 `ai_router` 的装饰器注册模式：

```python
# rules/base.py
@dataclass
class RuleResult:
    type: str       # high_temp / low_temp / soil_dry / ...
    level: str      # danger / warning / normal
    title: str
    content: str
    source: str     # sensor / weather / calendar
    action: str     # 下一步建议

class BaseRule(ABC):
    name: str = ""
    @abstractmethod
    def match(self, s: EnvSnapshot, cfg: Settings) -> RuleResult | None: ...

_registry: dict[str, BaseRule] = {}
def register(cls): _registry[cls.name] = cls(); return cls
def all_rules() -> list[BaseRule]: return list(_registry.values())
```

`threshold.py` 用**数据驱动**的方式定义 6 条阈值规则（一条规则一个阈值来源），命中即产出 `RuleResult`：

| 规则 | 条件（读 config） | 播报内容 |
|---|---|---|
| `high_temp` | `temp >= BROADCAST_TEMP_HIGH` | 高温热害风险，减少高温时段作业、关注胁迫 |
| `low_temp` | `temp <= BROADCAST_TEMP_LOW` | 低温/冻害，做好防寒 |
| `soil_dry` | `soil_moisture < BROADCAST_SOIL_DRY` | 土壤偏干，检查墒情补水 |
| `high_humidity` | `humidity >= BROADCAST_HUMIDITY_HIGH` | 高湿易发病，通风排湿 |
| `rainfall` | `forecast.rainfall > 阈值` | 降雨，提前清沟排水 |
| `strong_wind` | `wind_speed >= 阈值` | 大风，注意倒伏/飞防安全 |

`pest_risk.py` 做**温湿组合**判断（比单阈值更准），例如"湿度≥90% 且 20≤温≤25℃ → 高湿适温，叶部病害发生风险升高"，阈值按作物可配置 [6]。

### 6.4 生成器（`generator.py`）

```python
async def generate_broadcast(db, user_id) -> list[dict]:
    snap = await build_snapshot(...)
    hits = [r.match(snap, cfg) for r in all_rules() if r.match(...)]
    hits += calendar.phase_tasks(...)
    if not hits:
        hits = [await BroadcastSkill().brief(snap, profile)]   # AI 兜底
    return [card(r) for r in hits]   # 组装 {type,level,title,content,source,action}
```

`skill.py` 的 `BroadcastSkill` 复用一个通用模型（`ai_router.resolve("通用农业")`）生成当日简报，逻辑与诊断 Skill 隔离。

## 八、主动推送（分阶段落地）

"主动"的完整闭环需要三步叠加：

1. **拉取时实时生成**（阶段一即可用）：用户打开首页实时算播报，取代硬编码。
2. **定时预生成**（阶段二）：后台定时任务每天早 8 点对所有用户预生成当日播报落库，减少首页等待（可用 `APScheduler` 或简单 `asyncio` 循环）。
3. **微信订阅消息推送**（阶段三）：前端 `wx.requestSubscribeMessage` 引导订阅 → 后端温度/降雨阈值触发或定时触达时，调微信订阅消息接口推送。依赖微信订阅消息模板审批，故放最后。

## 九、可维护性与扩展性

| 扩展诉求 | 做法 | 涉及文件 |
|---|---|---|
| 新增一种环境风险 | `rules/` 加一个 `@register("name")` 文件 | 新增 1 文件 |
| 调整阈值 | 改 `.env` 的 `BROADCAST_*` | 改配置 |
| 新增作物农事历 | 改 `CropCalendar` 表数据 | 改数据 |
| 换天气/传感器源 | 改 `snapshot.py` 的取数来源 | 改 1 处 |
| AI 简报换风格 | 改 `skill.py` 的 prompt/模型 | 改 1 文件 |

**单一职责**：`snapshot` 管"取数"、`rules` 管"判断"、`calendar` 管"物候"、`generator` 管"编排"、`skill` 管"AI 兜底"，互不越界，便于分别单测。

## 十、分阶段实施计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| 阶段一 | 落地 `broadcast/` 包 + 阈值规则 + `snapshot` + 改造 `get_today`；`mark_done` 不动 | 首页播报由传感器/阈值实时生成，而非硬编码 |
| 阶段二 | 物候期农事历 + `pest_risk` + `BroadcastSkill` AI 兜底 + `environment_service` 换真实数据 | 复杂环境风险能判断、无设备时 AI 能生成简报 |
| 阶段三 | 定时预生成 + 微信订阅消息推送 + `/broadcast/preview` | 不打开小程序也能收到提醒（订阅用户） |

## 十一、风险与对策

| 风险 | 对策 |
|---|---|
| 传感器一直无数据 | `snapshot` 保留天气/mock 双兜底，规则照跑、仅降低"来源"可信度 |
| 阈值拍板不准 | 阈值全部走 `.env` 可配；首批值对齐 QX/T 标准，后续按地区作物校正 |
| 误报打扰用户 | 播报默认"拉取时展示"，推送需用户显式订阅，且支持取消 |
| AI 简报长耗时 | `skill` 走通用模型 + 超时兜底到"规则结果"，不阻塞首页 |

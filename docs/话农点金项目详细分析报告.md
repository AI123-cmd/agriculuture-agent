# 话农点金项目详细分析报告

话农点金（HNDJ）是一套面向农户与农技人员的微信小程序系统，围绕三件事展开：农事播报、环境监测、AI 农技问答。后端是 FastAPI + LangGraph 的 AI 编排服务，前端是原生小程序 + TypeScript。整体判断是：分层骨架完整、模块边界干净，但业务数据几乎全是占位值，且鉴权边界存在数处实质漏洞 —— 属于"架构已立、真实数据与安全加固尚未开始"的早期阶段。

## 项目定位与代码规模

`README.md` 把产品能力归纳为「农事播报 / 环境监测 / AI 农技诊断问答」，技术栈标注为 Python 3.11+、FastAPI、SQLAlchemy 2.0、Alembic、MySQL 8.0、Redis（可选）、LangGraph、MCP 工具层、DeepSeek-v4-flash。这些依赖在 `backend/requirements.txt` 与 `backend/pyproject.toml` 里都能对应上，配置项也齐备（`app/core/config.py` 共 30 余项，含播报阈值、置信度阈值、MCP 开关、存储类型等）。

仓库的提交历史只有 3 次，最近一次是删除文档，工作区里还有一份被删除但未提交的 `docs/农事播报主动推送技术实现方案.md`，以及三份未纳管的新调研文档。这说明项目由单人一次性导入，尚未进入多人协作与版本治理阶段。

| 维度 | 数量 |
| --- | --- |
| 后端业务代码 `backend/app` | 约 2 226 行 Python |
| 小程序逻辑代码（`.ts`） | 约 1 701 行 |
| 后端接口 | 15 个（7 个 router 模块） |
| 数据表模型 | 10 张，无外键、无 relationship |
| 测试用例 | 9 个（test_ai 3 / test_auth 4 / test_farmer 2） |
| 文档体量 | 4 份 Markdown 约 280 KB，另有 3 张 SVG 架构图与 4 张界面截图 |

文档量显著大于代码量，其中 `docs/智慧农场语音播报流程调研报告.md` 单份就有 123 KB。这本身反映了一个事实：项目的产品侧想得比工程侧远，落地的代码还停在可用性验证层面。

## 架构分层

后端是标准的四层结构，自上而下依次为路由层、服务层、能力层与集成层，职责切分是这份代码最扎实的部分。

```
backend/app/
├── api/v1/         路由 + 鉴权依赖（deps.py 统一解析 Bearer token）
├── services/       业务编排（auth / farmer / location / broadcast / environment / ai / memory / profile / user）
├── agent/          LangGraph 诊断状态机（nodes / graph / state / confidence / checkpointer）
├── broadcast/      播报生成（rules / calendar / snapshot / skill / generator）
├── ai_router/      作物垂类模型注册与路由（crops/rice · tobacco · general）
├── tools/          MCP 工具层（sensors / weather / profile / knowledge / catalog）
├── integrations/   外部依赖（wechat / weather / geocoding / storage）
├── models/         SQLAlchemy 模型
├── schemas/        Pydantic 请求响应模型
└── core/           配置 / 异常 / 统一响应 / 安全
```

服务层统一用 `@lru_cache` 暴露单例（`services/__init__.py`），路由层只做参数接收与依赖注入，业务逻辑一律下沉。响应结构统一信封化为 `{code, message, data}`（`core/response.py`），异常由 `main.py` 里两个 handler 收敛，前后端契约清晰。

模型层采用 SQLAlchemy 2.0 的 `Mapped` 声明式风格，主键统一由 `new_id(prefix)` 生成 `前缀_24位hex` 形式的业务键，时间字段通过 `TimestampMixin` 复用。这套约定在 10 张表里执行得很一致。

架构的短板同样明显：`ai_router`、`broadcast.rules` 都用了装饰器注册表模式（`@register`），这个模式本身很好，但注册依赖导入副作用，`app/models/__init__.py` 与 `app/ai_router/crops/__init__.py` 必须被导入才会生效，缺少显式的注册入口，后续加作物容易漏。而 `tools/catalog.py` 提供的 `build_tools()` 在全仓库没有任何调用点 —— 需求文档里反复强调的"MCP 工具层"目前只是目录结构，实际取证走的是 `agent/nodes/fetch_environment.py` 里对 `tools/*.py` 函数的直接调用。

## 后端接口与数据模型

15 个接口集中在 7 个模块，全部挂在 `/api` 前缀下，除登录外都要求 `Authorization: Bearer <token>`。

| 方法与路径 | 归属模块 | 说明 |
| --- | --- | --- |
| POST `/api/login` | `auth.py` | code 换 openid，签发 token |
| GET/POST `/api/farmer/profile` | `farmer.py` | 读取 / 保存农户档案（含作物列表） |
| GET `/api/location/reverse-geocode` | `location.py` | 逆地理编码，**未要求鉴权** |
| POST `/api/location/set` | `location.py` | 保存地点 |
| GET `/api/broadcast/today` | `broadcast.py` | 今日播报，空则懒生成 |
| POST `/api/broadcast/mark-done` | `broadcast.py` | 标记完成 |
| POST `/api/broadcast/preview` | `broadcast.py` | 实时生成不落库，**调试用接口保留在生产路由** |
| GET `/api/environment/summary` | `environment.py` | 环境摘要 |
| GET `/api/environment/detail` | `environment.py` | 环境详情 |
| POST `/api/ai/chat` | `ai.py` | AI 诊断对话 |
| GET `/api/ai/history` | `ai.py` | 对话历史，page/size **无上限** |
| DELETE `/api/ai/history/{session_id}` | `ai.py` | 删除会话，已按 user_id 过滤（正确） |
| POST `/api/user/avatar/upload` | `user.py` | 头像上传 |
| DELETE `/api/user/cancel` | `user.py` | 注销账号 |

数据模型共 10 张表：`user`、`farmer_profile`、`field`、`crop`、`device`、`location`、`broadcast_log`、`ai_conversation`、`ai_message`、`memory_summary`、`user_profile_tag`。设计上有几处值得注意：

`broadcast_log.date` 用 `String(16)` 存 `YYYY-MM-DD`，且没有 `(user_id, date)` 唯一约束，这是后面播报重复写入的直接原因。`ai_conversation.id` 直接复用前端传来的 `sessionId`，使会话主键由客户端控制。`device` 表只有设备元信息（序列号、类型、状态、绑定时间），没有任何实时读数字段，意味着"设备数据"在当前模型里无处安放。

最值得注意的是：全仓库 grep `ForeignKey` 与 `relationship` 零命中。十张表之间的关联完全靠应用层手工维护，`user_service.cancel_account` 就不得不按依赖顺序手工 delete 十张表。任何一处遗漏都会留下孤儿数据，而数据库层不会报错。

## AI 诊断链路

诊断链路的实现质量是整个项目里最高的部分，它是一个真正跑通的 LangGraph 状态机。

`agent/graph.py` 装配了 6 个节点与 3 条条件边：

```
START → intake → collect_symptoms ─┬→ collect_management ─┬→ fetch_environment → diagnose ─┬→ prescribe → END
                          │        └→ END                 └→ END                            └→ collect_symptoms（低置信度回环）
```

`collect_symptoms` 没有症状也没有图片就直接结束并追问，`collect_management` 未收齐"施肥/打药/浇水/天气"四个键就结束并抛出待补问题（`_PROMPTS`），`diagnose` 判定为 low 且轮次未超 `MAX_COLLECT_ROUNDS`（默认 3）时回到 `collect_symptoms` 重新取证。这套"证据不足就追问、追问三次为止"的控制流是明确的工程决策，`state.AgentState` 里 `round` 字段的注释也点明了防死循环意图。

置信度分级（`agent/confidence.py`）完全规则化、可单测：图片、症状、管理信息完整、环境无冲突各记 1 分；≥3 分且有图片为 high，≥2 分为 medium，否则 low。这个函数是纯函数，没有副作用，写测试成本极低 —— 但仓库里恰恰没有它的测试。

记忆分两层。短期记忆用 `agent/checkpointer.py` 的 `AsyncSqliteSaver` 单例，绑事件循环并支持跨循环重建（`agent/__init__.py` 的 `get_agent()` 同理），设计上考虑到了测试隔离。长期记忆由 `services/memory_service.py` 维护，`remember()` 按 `(user_id, session_id)` 做 upsert 存摘要与关键事实，`_extract_facts()` 用标点切分取长度 ≥4 的前 5 段。

模型路由（`ai_router/registry.py`）支持精确命中、名称互含的模糊命中、最后回落"通用农业"三级策略。`base.CropModel` 统一封装 mock 与真实调用：真实分支向 OpenAI 兼容端点 POST，兼容 `answer` 与 `choices[0].message.content` 两种返回结构，带 2 次重试，失败后返回 `_fallback_reply` 的安全提示。这一层防御性写得好。

但这条链路有一个致命的输入缺口：图片。`miniprogram/pages/ai/chat.ts` 的 `requestAIResponse` 恒传 `imageUrl: null`，首页 `index.ts` 的拍照入口选完图后只写入 `PENDING_CHAT_MODE='camera'` 就 `switchTab`，把 `filePath` 丢掉了；而 `chat.ts` 从头到尾没有读取这个 storage key。结果是图片证据整条链路不通，置信度评分里的"有图片得 1 分"永远拿不到，high 档位在当前前端下不可能触达。

## 农事播报链路

播报生成走"规则优先、逐级兜底"（`broadcast/generator.py`）：先把环境收敛成 `EnvSnapshot`，跑全部注册规则，再叠加物候期农事历，两者都空时调用 `BroadcastSkill().brief()` 生成 150 字 AI 简报。生成结果会把环境快照 `asdict` 后塞进每条结果的 `meta`，便于追溯触发依据 —— 这个设计对排障很友好。

规则集有两组。阈值组（`rules/threshold.py`）6 条：高温 35℃、低温 5℃、土壤含水率 <20%、湿度 ≥85%、降雨 >25 mm、风速 ≥8 m/s。组合组（`rules/pest_risk.py`）用"湿度 ≥90% 且气温 20~25℃"判断叶部病害风险，比单阈值更接近真实植保逻辑。农事历（`broadcast/calendar.py`）内置水稻/小麦/玉米三个作物的生育期关键词映射，命中即产出阶段提醒。

问题出在快照的完整性上。`build_snapshot` 构造 `EnvSnapshot` 时完全没有给 `wind_speed` 赋值，`forecast` 里的 `rainfall` 也恒为 `None`。而 `StrongWindRule` 与 `RainfallRule` 恰恰读的就是这两个字段，判断条件都是"为 None 就返回 None" —— 这两条规则在当前实现下永远不会触发，属于装饰性代码。

传感器数据（`tools/sensors.py`）返回的是硬编码常量：气温 26.5、湿度 78、土温 25.0、含水率 23、pH 6.6、EC 1.2、光照 58 000。函数确实查询了 `Device` 表，但只用来拼设备列表，读数字段一个都没读（表里也没有）。返回值的 `source` 却标着 `sensor_snapshot`，前端据此展示为"实时监测"。环境详情（`environment_service.detail`）里还有一批更明显的写死值：风速 2.3 m/s、东南风、日照 7.2 h、紫外线"中等 (UV 4)"、降雨 0 mm。

天气与逆地理集成（`integrations/weather.py`、`geocoding.py`）都只实现了兜底分支 —— 未配置时返回固定"多云 26°C"和经纬度字符串；即便配置了 URL，也没有针对真实厂商返回结构的验证。微信登录（`integrations/wechat.py`）同样：`WECHAT_APP_SECRET` 为空时直接返回 `mock_openid_<code 前 8 位>`。

这意味着当前系统在默认配置下的行为是：任意人构造一个 code 就能拿到有效 token 并登录，看到的天气是"多云 26°C"，看到的环境数据是永远不变的 26.5/78/23，收到的播报来自这批固定值。这个"演示态"用于汇报很完整，用于生产则完全不可信。

## 小程序端

小程序共 7 个页面：`login`（首屏）、`profile/farmer-profile`、`index`、`ai/chat`、`history/list`、`mine`、`env`。采用 glass-easel 组件框架、自定义 tabBar（4 项）、`lazyCodeLoading: requiredComponents`，但未启用分包。

请求层（`utils/request.ts`）做了两件对的事：统一注入 Bearer token、统一解析 `{code,message,data}` 信封、401 走防抖后的单次 `reLaunch` 登录页。`upload` 分支单独解析响应体文本也是必要的（`uploadFile` 不自动 JSON 化）。鉴权守卫（`utils/guard.ts`）把"未登录跳登录页、已登录无档案跳建档页"收敛成一个函数，调用点统一。

缺陷集中在三处。第一是请求层没有设 `timeout`、没有重试、没有取消机制，而 `sendMessage` 又缺少在途保护，连点发送会并发调用模型并各写一条消息。第二是 `saveConversationToStorage` 里的运算符优先级 Bug：`(lastAiText || last ? last.content : '')` 中条件运算符优先级低于 `||`，实际等价于 `(lastAiText || last) ? last.content : ''`；由于 `last` 恒为真，`lastAiText` 分支永远不会生效，预览始终取最后一条消息内容 —— 恰好在 AI 回复后写入时最后一条就是 AI 消息，所以功能看似正常，属于"结果对但写法错"的隐藏坑。第三是 `scrollToBottom` 用 `99999999 + random` 强制滚动并配一个从不清理的 `setTimeout`，频繁刷新下会堆积定时器。

页面交互上，首页的 `onLoad` 与 `onShow` 重复调用同样 4 个加载函数（用户信息、地点、播报、环境），每次进出都翻倍请求；`markDone` 用乐观更新但 `catch` 为空，标记失败时界面与后端不一致且无提示；`index.ts` 默认数据里写着 `farmerName:'张叔'`、`currentCrop:'水稻（分蘖期）'`；`env.ts` 内置了整套 26.5/78/23/58k 指标和 3 台虚构设备（土壤传感器 #01、气象站 #01、摄像头 #01）作为默认兜底。

登录流程（`login.ts`）有一个顺序问题：`wx.getUserProfile` 成功后先写入 `USER_INFO` 和 `HAS_LOGIN`，再调后端 `login`。后端失败时本地已处于"已登录"状态，`guard.ts` 会放行进入首页，随后所有请求因无 token 而 401。另外 `wx.getUserProfile` 自 2022 年起对小程序的返回已改为匿名数据（"微信用户"+ 灰色头像），把它作为登录前置条件在当前微信环境下拿不到有效资料。

配置层面，`utils/config.ts` 指向 `http://172.16.60.90:8000`，是内网 IP 加明文 HTTP。微信正式版要求 HTTPS 且需在白名单内配置请求域名，这一项上线前必须替换。`project.config.json` 的 `libVersion` 是 `"trial"`，`skylineRenderEnable` 为 `true`。

## 文档与实现的偏差

`docs/` 下的四份文档质量不低，`农技人员指导农民全流程调研报告.md` 引用了 80 余个来源并给出了可量化的机构指标，`智慧农场语音播报流程调研报告.md` 与 `智慧农场传感器类型与小程序自助接入方案调研报告.md` 覆盖了传感器选型与接入通道。这些是真实的前期调研，不是空话。

但产品方案书与代码之间存在系统性偏差。方案书名为「新域农力」，代码与界面统一叫「话农点金」；方案书第 13.2 节写了 Docker 启动方式，仓库里却没有 Dockerfile；方案书第 14 章描述"自动化质量评估"与 90% 通过率目标，`HARNESS_PASS_RATE_THRESHOLD=0.90` 这个配置项也存在于 `core/config.py` 与 `.env.example`，但全仓库没有任何代码引用它 —— 质量评估机制尚未实现。

架构图也有类似落差。`docs/photo/architecture.svg` 标注"环境快照：设备 → 天气 → mock 三级兜底"，实际实现里 `build_snapshot` 只调了 `sensors`（自身即静态兜底）和 `weather`（未配置即静态），所谓三级是概念上的，代码里是两级且两级都是常量。`docs/photo/ai-diagnosis-flow.svg` 标注"MCP 工具层取传感器 / 天气"，实际是节点内直接函数调用。

此外，`README.md` 的目录结构写的是 `wx-mini/`（实际仓库根目录就是项目根），把 `docs/` 描述为"设计与对接文档"，而一份对接技术设计文档已被删除。

## 问题清单

下面按严重程度分三档列出。每条都附了定位位置与判断依据。

### 高优先级：安全与鉴权

**AI 会话存在越权写入（IDOR）**。`services/ai_service.py` 的 `_persist` 用 `AIConversation.id == req.sessionId` 查已有会话，没有带 `user_id` 条件。由于主键由客户端指定，攻击者只要猜到或复用一个已存在的 `sessionId`，就能把自己的消息写进他人的会话，并覆盖其 `crop_tag`。对照之下，同文件的 `delete_history` 与 `history` 都正确带了 `user_id` 过滤 —— 说明这不是有意的设计，而是遗漏。

**注销账号不吊销 token**。`core/security.py` 定义了 `revoke_token`，但全仓库 grep 只有这一个定义点，没有任何调用。`user_service.cancel_account` 删完十张表后用户注销完成，而该 token 在其 7 天有效期内（`TOKEN_EXPIRE_SECONDS`）依然可用。此时 `get_current_user` 能正常解析出 user_id，各接口的查询会因数据已删而返回空，但**已登录态本身没有失效** —— 配合 `ai_service._persist` 的越权，注销用户仍可向旧会话写入数据。

**无凭证即可登录**。`integrations/wechat.py` 在 `WECHAT_APP_SECRET` 为空时返回 `mock_openid_<code[:8]>`。默认配置（`.env.example` 里该项留空）下，任何人提交任意 8 位以上字符串为 code 即可获得合法 token。这意味着在未配置密钥的部署中，整套"需鉴权"接口实际上是无鉴权的。

**CORS 组合配置危险**。`main.py` 同时设置 `allow_origins=["*"]` 与 `allow_credentials=True`。这套组合在带凭证的跨域场景下会被浏览器拒绝或产生意料外的放行行为，同时 `DEBUG=True` 默认开启会让 `/docs`、`/redoc`、`/openapi.json` 在公网可达。

**头像上传无任何校验**。`user_service.upload_avatar` 直接 `file.file.read()` 全量读入内存，不限制大小、不校验 MIME 类型；`integrations/storage.py` 的 `LocalStorage.save` 直接用用户传入的 `filename` 扩展名拼路径，保存为 `/static/{uuid}{ext}`。而 `/static` 通过 `StaticFiles` 公开挂载。攻击者可上传超大文件耗尽内存，或上传 `.html`/`.svg` 并诱导访问，构成存储型 XSS。

**调试接口留在生产路由**。`POST /api/broadcast/preview` 会真实执行一遍生成链路（含可能的 LLM 调用），虽不落库，但它对外可调用且消耗算力。`GET /api/location/reverse-geocode` 未加 `get_current_user` 依赖，是唯一一个无鉴权的业务接口。

### 中优先级：一致性与数据完整性

**播报生成非幂等且会重复写入**。`broadcast_service.get_today` 在当天无记录时调用 `_generate` 生成并落库。两个并发请求会各自查到空、各自生成、各自插入，`broadcast_log` 没有 `(user_id, date)` 唯一约束能拦住，结果是同一天出现两套播报。另外 `_generate` 的时间字段是算出来的（`f"{9 + idx * 2:02d}:00"`），不是真实生成时刻。

**两条规则永远不会触发**。`StrongWindRule` 读 `snapshot.wind_speed`，`RainfallRule` 读 `snapshot.forecast["rainfall"]`，而 `build_snapshot` 对这两个字段从未赋值（保持 `None`），规则的第一个判断就是"为 None 则返回 None"。

**历史列表 N+1 查询**。`ai_service.history` 先分页取会话，再在循环里逐个查消息，20 条会话就是 21 次查询。同时 `GET /api/ai/history` 的 `size` 参数没有上限，前端 `history/list.ts` 直接传 `size=100`，可被放大为上万次查询。

**接口无外键约束**。十张表零 `ForeignKey`、零 `relationship`，关联完整性全靠应用层。`cancel_account` 手工按序删除十张表就是被迫的产物，任何新增表若忘记加入这个序列，就会产生孤儿数据。

**数据库会话不回收事务**。`db/session.py` 的 `get_db` 只 `close()` 不 `rollback()`。请求中途抛异常时，未提交的事务依赖连接归还时的隐式回滚，配合 `pool_recycle=3600` 存在脏连接风险。

**Redis 降级不可恢复**。`db/redis_client.py` 把 `_initialized = True` 写在 `ping()` 之前，一旦首次连接失败就永久返回 `None`，即使 Redis 随后恢复也不会重连。此时 token 退回进程内内存字典，多 worker 部署下登录态不共享 —— 而 `_memory` 字典本身也没有清理机制，过期项只在被访问时才剔除。

**迁移脚本不是真实 DDL**。`alembic/versions/0001_initial.py` 的 `upgrade()` 调用 `Base.metadata.create_all(bind)`，`downgrade()` 调用 `drop_all`。这使迁移失去了版本化演进能力：模型一改，0001 的行为就跟着变，无法在旧库上重现当时的表结构。0002 是真实 `add_column`，风格与 0001 不一致。

**前端多处状态不一致**。首页 `onLoad`/`onShow` 双份加载；`markDone` 乐观更新但忽略失败；`sendMessage` 无在途保护；`scrollToBottom` 的定时器不清理；`saveConversationToStorage` 存在运算符优先级隐患。这些单看都是小问题，叠加起来会让用户看到"操作成功但服务端未生效"的困惑状态。

**测试覆盖极薄**。9 个用例集中在登录、建档、AI 对话三条主流程，`agent/confidence.py`（纯函数、规则明确）、`broadcast/rules/*`（阈值可穷举）、`broadcast/snapshot.py`、`ai_router/registry.py` 全部没有测试。`requirements.txt` 里没有 `pytest-cov`，`pyproject.toml` 也没有覆盖率配置，没有量化基线的机制。

### 低优先级：工程规范

`.env` 不存在（仅 `.env.example`），`.venv` 与 `node_modules` 都不存在，本地环境 Python 3.10.11 低于项目要求的 3.11+，全局也未安装 `fastapi` —— 项目当前在本地无法直接运行，需要先完成环境搭建。小程序 `tsconfig.json` 的 `include` 为 `./**/*.ts` 且 `typeRoots` 指向 `./typings`，两者存在重叠；`request.ts` 里的 `ApiResponse<T>` 与 `types/api.d.ts` 的定义重复。`LocalStorage` 之外的对象存储实现直接抛 `NotImplementedError`（预留位），`get_storage()` 没有 `@lru_cache`，每次都重新 `makedirs`。`wx.getUserProfile` 已是微信不推荐的接口。用户协议与隐私政策在登录页与"我的"页都只弹 Toast 提示"开发中"，而实际收集了头像、昵称、位置与农户档案 —— 这在提交微信审核时会被要求整改。

## 改进建议

围绕"让演示态变成可信态"这个目标，建议按下面四步推进，每一步都独立可验证。

### 第一步：堵住鉴权与上传漏洞

改 `ai_service._persist` 的查询条件为 `.filter(AIConversation.id == req.sessionId, AIConversation.user_id == user_id)`，会话已存在但归属他人时直接抛 `Unauthorized`。在 `cancel_account` 里调用 `revoke_token`，并把当前 token 从请求上下文传进来。把 `code2session` 的 mock 分支改为"仅在 DEBUG 且显式开关打开时生效"，非 DEBUG 下密钥缺失直接启动失败，避免误部署。`upload_avatar` 增加体积上限（如 5 MB）、MIME 白名单（jpg/png/webp）与扩展名规范化，`LocalStorage.save` 不再信任用户文件名。CORS 收敛到具体来源列表，`DEBUG` 默认改为 `False`，`preview` 接口加管理员校验或直接移出生产路由。

### 第二步：给数据层补上约束

为 `broadcast_log` 加 `(user_id, date)` 唯一约束，在 `_generate` 外层用 `INSERT ... ON DUPLICATE KEY` 或捕获唯一键冲突后重查，保证幂等。为十张表补齐外键与 `ON DELETE CASCADE`，之后 `cancel_account` 可以简化，孤儿数据由数据库兜底。把 `0001` 迁移改为真实 `create_table` 语句，新增长按真实 DDL 风格编写。`get_db` 加 `except: db.rollback(); raise`。`history` 改为一次 `IN` 查询批量取消息，`size` 加 `le=100` 校验。`redis_client` 把 `_initialized` 赋值移到 ping 成功之后，失败时允许重试。

### 第三步：接通真实数据源

`tools/sensors.py` 是唯一需要动的接入点 —— 只要它的返回结构不变，`snapshot`、规则集、环境详情都无需改动。建议在 `Device` 表旁新增读数表（`device_reading`：`device_id`/`metric`/`value`/`collected_at`），`query_sensors` 改为按设备查最新读数，无读数时才回落到当前常量，并把 `source` 改成 `device` / `fallback` 以区分。同时给 `build_snapshot` 补上 `wind_speed` 与 `forecast["rainfall"]` 的赋值，让那两条沉睡的规则生效。天气与逆地理接入真实厂商时，需要按实际返回结构重写字段映射并去掉"未配置即返回固定值"的静默兜底 —— 静默兜底在演示阶段有价值，在生产阶段会把故障伪装成正常。

### 第四步：补齐前端断点与质量基线

把首页拍照流程接回来：`index.ts` 的 `chooseMedia` 成功回调里保存 `tempFilePath` 到 storage，`chat.ts` 的 `onShow` 读取该路径并作为 `imageUrl`（先调头像上传那类接口换成永久 URL）传入 `chat`，这样置信度里的图片信号才能生效，high 档位才有意义。`sendMessage` 加在途标志位，请求期间禁用发送按钮。首页去掉 `onShow` 里的重复加载或合并为一次。修正预览计算的括号。`scrollToBottom` 改用 `scroll-into-view` 或清理定时器。替换 `wx.getUserProfile` 为 `wx.login` + 头像昵称填写能力（`button open-type="chooseAvatar"`，头像上传流程已有）。补上用户协议与隐私政策的真实页面。`config.ts` 改为按环境区分的基础地址配置。

测试方面，优先给 `agent/confidence.py` 与 `broadcast/rules/*` 写穷举式单测 —— 这两处是纯函数或纯规则，投入产出比最高；再给 `ai_service` 的越权场景补一个回归用例；引入 `pytest-cov` 建立覆盖率基线。产品方案书里的 `HARNESS_PASS_RATE_THRESHOLD=0.90` 若要兑现，需要一个独立的评估脚本，用固定用例集跑诊断链路并统计通过率。

## 总体评价

这份代码的优点集中在"骨架"上。分层干净，职责边界清楚，统一响应信封、统一鉴权依赖、装饰器注册表、单例服务、业务键生成这些约定都执行到位，LangGraph 状态机的控制流设计（证据不足追问、置信度回环、轮次上限）是有想法的工程决策而非模板套用，真实模型调用分支的重试与兜底也写得克制。

问题集中在"血肉"上。数据层几乎全是占位：环境读数是常量、天气是常量、设备读数字段不存在、图片证据整条链路断在前端。安全边界有数处实质缺口：无凭证可登录、会话越权写入、注销不吊销 token、上传无校验。这些问题在演示阶段不会暴露，一旦接触真实用户与真实数据就会集中爆发。

从 3 次提交、280 KB 文档对 2 226 行后端代码的比例、以及方案书里 Docker 与质量评估机制的缺失来看，项目当前处于"方案已完成、骨架已搭、真实化未开始"的位置。好消息是所有缺口都有明确的、局部的修法 —— 传感器只需换一个函数的实现，鉴权只需补几处过滤条件，前端拍照只需把丢掉的路径接回来。坏消息是这些必须在上线前完成，且第二、三步之间没有捷径可走。
